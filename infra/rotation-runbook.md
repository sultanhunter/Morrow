# Credential rotation and operational signals

The local lab proves SCRAM authentication on PostgreSQL17.11, candidate rejection, new-login verification, abrupt client-worker death and committed SQL durability. Its AES-GCM credential fixture is process-local, not AWS secret storage. `npm run lab:operations` requires Docker; no network, ports, host mounts or persistent data. It removes only its newly created container. Reports exclude passwords/ciphertext/SQL/errors.

For an actual environment: bind account, region, role, secret identity and deployment revision. An owner-qualified rotation principal, separate from model/task/execution profiles, must have the exact provider update privileges. Current broker is retrieval-only; no such write principal or schedule is activated. Define provider-specific create/set/test/finish steps and retry IDs before enabling rotation. Require an authenticated new connection before promoting a candidate. Never log a secret, SQL statement, arbitrary error or raw provider response. Events use fixed codes/opaque correlation IDs; metric dimensions contain only environment/service/code.

Changing a database password affects new connections; existing sessions must be deliberately recycled. Observe each service reconnecting to the verified revision, drain old pools and terminate stale sessions only within owner-approved scope. IAM DB authentication and external OAuth refresh have different lifecycles; do not reuse this password lab as qualification for them. On uncertainty, keep the candidate unpromoted and hold consequential work; investigate authoritative credential/provider state before retry or rollback. A local invalid-readiness check is not a failed AWS deployment exercise.

Bind dashboards and alert routes from operations.json only after actual service signals, justified thresholds and eligible recipients exist. Exercise alert delivery with redacted evidence before declaring paging functional. Presently there is no dashboard deployment, alert recipient, scheduled rotation, live ECS service, AWS Secrets Manager rotation or Temporal worker. P04.A02 real integration remains pending.

Sources: [PostgreSQL17 password authentication](https://www.postgresql.org/docs/17/auth-password.html), [AWS secret rotation](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html).

## Workers secrets and login keyring

P04.T02a binds credentials by class under ADR-0007 (development and staging only; production custody needs a superseding ADR). The committed `wrangler.jsonc` files hold no identifier or secret; the owner places every value, never through chat, the repository, logs or process arguments.

- **Broker** (`morrow-<env>-broker`): `secrets.required` is exactly `WORKOS_API_KEY` plus `MORROW_DB_PASSWORD_<ROLE>` for the seven leased runtime roles (`brokerNeonRoles` in `packages/identity/src/broker-protocol.ts`). A development or staging broker accepts only an `sk_test_` key, production only `sk_live_`. Owner, migration, lifecycle and maintenance passwords, the Neon API key and Cloudflare tokens are bound to no Worker.
- **api** (`morrow-<env>-api`): its only secret is its own `LOGIN_CAPSULE_KEYRING`. It declares `secrets.required: []`, so neither `wrangler types` nor `wrangler dev` infers or loads api secrets, and its environment mapper refuses any provider or credential-like binding.
- **First deploy:** `wrangler deploy --env <env> --secrets-file <owner-only file>` ships the vars and secrets as one version; a deploy with a missing required secret fails closed. Never run a bare `wrangler secret put` for the keyring: it would create a version whose digest-bound keyring mismatches its vars.
- **Rotation of a single secret:** `wrangler secret put <NAME> --env <env>` reads the value from stdin (pipe it from an owner-only file); never pass it as an argument. Rotate every leased role password every 90 days and immediately on suspected exposure: `ALTER ROLE … PASSWORD` through the owner's migration path, then put the new broker secret. Only the broker changes; the api picks up the new password on its next lease (P04.T02a AC20 is the local precursor to P04.A02).
- **Login keyring (K1):** a single version, generated by the owner with `node scripts/login-keyring.mjs --config <login-config.json> --out <absolute path outside the checkout>`, which writes one 0600 `{"LOGIN_CAPSULE_KEYRING":"…"}` file and prints only the key id, windows and configuration digest. The window is `encryptFromMs = t0 − 300 s`, `encryptUntilMs = t0 + 90 d`, `decryptUntilMs = encryptUntilMs + 300 s`. Rotate every 60 days, on any login-configuration change (the keyring is bound to its digest) and on suspected exposure, always together with the vars through `--secrets-file`. A rotation may drop logins in progress (at most 300 s, plus isolates still on the old version); they see "Sign-in could not be completed" and restart. Outside the window, login start returns 503 `login_unavailable` and `/healthz` is not ready; the api logs `KEYRING_EXPIRING` once per isolate when fewer than 14 days remain. Delete the secrets file after the deploy.
- **Never** run `wrangler tail` during real sign-ins: invocation logs would record `/auth/workos/callback?code=…&state=…` until P04.T03a decides redaction. Observability, logpush and source-map upload stay off.
