# Credential rotation and operational signals

The local lab proves SCRAM authentication on PostgreSQL17.11, candidate rejection, new-login verification, abrupt client-worker death and committed SQL durability. Its AES-GCM credential fixture is process-local, not AWS secret storage. `npm run lab:operations` requires Docker; no network, ports, host mounts or persistent data. It removes only its newly created container. Reports exclude passwords/ciphertext/SQL/errors.

For an actual environment: bind account, region, role, secret identity and deployment revision. An owner-qualified rotation principal, separate from model/task/execution profiles, must have the exact provider update privileges. Current broker is retrieval-only; no such write principal or schedule is activated. Define provider-specific create/set/test/finish steps and retry IDs before enabling rotation. Require an authenticated new connection before promoting a candidate. Never log a secret, SQL statement, arbitrary error or raw provider response. Events use fixed codes/opaque correlation IDs; metric dimensions contain only environment/service/code.

Changing a database password affects new connections; existing sessions must be deliberately recycled. Observe each service reconnecting to the verified revision, drain old pools and terminate stale sessions only within owner-approved scope. IAM DB authentication and external OAuth refresh have different lifecycles; do not reuse this password lab as qualification for them. On uncertainty, keep the candidate unpromoted and hold consequential work; investigate authoritative credential/provider state before retry or rollback. A local invalid-readiness check is not a failed AWS deployment exercise.

Bind dashboards and alert routes from operations.json only after actual service signals, justified thresholds and eligible recipients exist. Exercise alert delivery with redacted evidence before declaring paging functional. Presently there is no dashboard deployment, alert recipient, scheduled rotation, live ECS service, AWS Secrets Manager rotation or Temporal worker. P04.A02 real integration remains pending.

Sources: [PostgreSQL17 password authentication](https://www.postgresql.org/docs/17/auth-password.html), [AWS secret rotation](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html).

## Workers secrets and login keyring

P04.T02a binds credentials by class under ADR-0007 (development and staging only; production custody needs a superseding ADR). The committed `wrangler.jsonc` files hold no identifier or secret; the owner places every value, never through chat, the repository, logs or process arguments.

- **Broker** (`morrow-<env>-broker`): `secrets.required` is exactly fourteen names in development and staging while the M5 Stripe switch is off, the committed state (`brokerRequiredSecretsFor`; sixteen in staging only while it is on, below): `WORKOS_API_KEY`, `TURNSTILE_SECRET_KEY` (P05.T01ab, ADR-0019 item 6; it verifies Turnstile tokens and cannot mint them; a staging or production broker without a valid one reports `health()` false), `MORROW_DB_PASSWORD_<ROLE>` for the ten leased runtime roles (`brokerNeonRoles` in `packages/identity/src/broker-protocol.ts`): the seven identity and workspace roles, `morrow_api_worker`, the api Worker's work login (P06.T01a, purpose `work_request_transaction`, one lease per request), and M2 PR-1's `morrow_connector_ingress` and `morrow_runtime_executor` (ADR-0022 item 8), plus M2 PR-1's vault secrets (ADR-0022 item 7): `MORROW_DB_PASSWORD_MORROW_VAULT_BROKER`, the broker's own login, never leased, and `MORROW_VAULT_KEK_V1`, the owner's KEK; and, only while the Stripe switch is on, M5 PR-1's Stripe secrets (ADR-0022 items 7 and 12): `STRIPE_RESTRICTED_KEY` (a restricted test key, `rk_test_` only: a secret `sk_` key or any live key is refused) and `STRIPE_WEBHOOK_SECRET` (the endpoint's `whsec_` signing secret). Production requires the twelve without the vault and Stripe secrets (`brokerRequiredSecretsFor("production")`), has no Stripe switch, and holds both until the ADR-0007 item 9 custody ADR. The broker requires `MORROW_DB_PASSWORD_MORROW_API_WORKER` like every other role password, so broker health stays false until it is placed; the connector's and the orchestrator's entrypoints are healthy only with their own role password and the vault. A development or staging broker accepts only an `sk_test_` key, production only `sk_live_`. Owner, migration, lifecycle and maintenance passwords, the Neon API key and Cloudflare tokens are bound to no Worker.
- **api** (`morrow-<env>-api`): its only secret is its own `LOGIN_CAPSULE_KEYRING`. It declares `secrets.required: []`, so neither `wrangler types` nor `wrangler dev` infers or loads api secrets, and its environment mapper refuses any provider or credential-like binding.
- **First deploy:** `wrangler deploy --env <env> --secrets-file <owner-only file>` ships the vars and secrets as one version; a deploy with a missing required secret fails closed. Never run a bare `wrangler secret put` for the keyring: it would create a version whose digest-bound keyring mismatches its vars.
- **Rotation of a single secret:** `wrangler secret put <NAME> --env <env>` reads the value from stdin (pipe it from an owner-only file); never pass it as an argument. Rotate every leased role password every 90 days and immediately on suspected exposure: `ALTER ROLE … PASSWORD` through the owner's migration path, then put the new broker secret. Only the broker changes; the api picks up the new password on its next lease (P04.T02a AC20 is the local precursor to P04.A02).
- **Login keyring (K1):** a single version, generated by the owner with `node scripts/login-keyring.mjs --config <login-config.json> --out <absolute path outside the checkout>`, which writes one 0600 `{"LOGIN_CAPSULE_KEYRING":"…"}` file and prints only the key id, windows and configuration digest. The window is `encryptFromMs = t0 − 300 s`, `encryptUntilMs = t0 + 90 d`, `decryptUntilMs = encryptUntilMs + 300 s`. Rotate every 60 days, on any login-configuration change (the keyring is bound to its digest) and on suspected exposure, always together with the vars through `--secrets-file`. A rotation may drop logins in progress (at most 300 s, plus isolates still on the old version); they see "Sign-in could not be completed" and restart. Outside the window, login start returns 503 `login_unavailable` and `/healthz` is not ready; the api logs `KEYRING_EXPIRING` once per isolate when fewer than 14 days remain. Delete the secrets file after the deploy.
- **Never** run `wrangler tail` during real sign-ins: invocation logs would record `/auth/workos/callback?code=…&state=…` until P04.T03a decides redaction. Observability, logpush and source-map upload stay off.

The owner places them with `morrow_put` (packet D9) in a terminal and browser profile Claude is not attached to. The tools read them in-process and print metadata only; Claude never reads them into its context. - **First provisioning.** After `npm run staging:migrate`, `npm run staging:provision-roles -- --first` gives each of the eleven broker logins (the ten leased roles and `morrow_vault_broker`) LOGIN with a password generated in-process (32 random bytes, base64url), sent once as the literal of its own `ALTER ROLE` over the TLS connection (P04.T01i M-N3 as amended 2026-10-20). Neon accepts only plaintexts; measured, `pg_authid` then holds the SCRAM-SHA-256 verifier, and what Neon's control plane keeps is not measured. Before any password statement it refuses: `STAGING_STATEMENT_STATS_PRESENT` for an unreadable statistics check or the `pg_stat_statements` extension in `morrow`; `STAGING_PASSWORD_ENCRYPTION` unless `password_encryption` is `scram-sha-256`; `STAGING_STATEMENT_LOGGING` unless `log_statement` is `none`, both duration thresholds are `-1` (or the sample rate is 0), `log_min_error_statement` is `panic`, and `debug_print_parse`, `debug_print_rewritten` and `debug_print_plan` are `off`, in the `morrow` session and in the `neondb` session. Neon preloads the module with utility tracking on (measured 2026-10-20), so the tool first opens a checked session on `neondb` (`STAGING_STATEMENT_STATS_PRESENT` with `reason` `module` when it is absent, unreachable or, `scratch` `other_instance`, not on the same PostgreSQL instance as the `morrow` session) and, right after the password statements, fully resets the statistics from there, verifies that the reset was full, that the instance has not changed and that no entry holds any of the new passwords (it sends only their SHA-256 digests, so each password is sent once, in its own `ALTER ROLE`), and drops the extension if it created it there; `morrow` never gets the extension. The report says `statementStats` (`wiped: true, entriesRemaining: 0`). It also sets `CONNECTION LIMIT 10`, `statement_timeout='5s'` and `idle_in_transaction_session_timeout='10s'`, revokes `TEMP` on `morrow` from PUBLIC, checks every control from the catalog and, where `pg_authid` is readable, that every stored password is SCRAM-SHA-256 (`passwordStorage` in its report), and writes the plaintexts with the WorkOS and Turnstile values, the owner's KEK (read from `vault-kek-v1`, never generated) and the owner's two Stripe files (`stripe-restricted-key`, `stripe-webhook-secret`; a missing or malformed file stops it before any role is touched) to one new 0600 `tmp/broker-secrets.json` for `staging:deploy -- --first`, which unlinks it.
- **Rotation.** `--rotate` first checks that the broker exists and holds the names, runs the same checks, changes the passwords and re-asserts the controls in one transaction, wipes and verifies the statistics as above, then pipes the new values as JSON on stdin to `wrangler secret bulk --env staging` (one broker version). Expect seconds of 503 between the two (P04.T02a AC20). If the bulk step fails the command exits with `STAGING_ROTATION_PARTIAL`: rotate again; the database already holds the new passwords.
- **Statistics residue.** `STAGING_STATEMENT_STATS_RESIDUE` (`stage` `extension`, `reset`, `verify` or `drop`, with `entriesRemaining`, `fullReset` and `sameInstance` when the verification read them) means the wipe could not be verified. Nothing was delivered: `--first` removed its file and `--rotate` ran no `secret bulk`. But the database may already hold the new passwords, and a statistics entry may still hold them in plaintext: until a rerun replaces them they are live LOGIN credentials that nobody keeps. Fix the cause, then promptly run the same command again (`--first` before the first deploy, `--rotate all` after); its full reset also clears the earlier entries, and its new passwords replace the old. **After a `drop` residue** the extension stays in `neondb`, and the rerun finds it there and leaves it. Once the rerun has succeeded, the owner runs `DROP EXTENSION pg_stat_statements;` in the Neon console's SQL Editor, on the `staging` branch and the `neondb` database (never `morrow`).
- **Interrupted runs.** A `provision-roles` run stopped after its first password statement (Ctrl-C, a closed terminal, a crash, a lost connection) never reaches the wipe and prints no residue code, so its passwords may still be in the statistics, and the roles may hold passwords nobody keeps. After any interrupted run or non-zero exit, fix the cause and rerun the same command. A refusal that stops before the first password statement (for example `STAGING_STATEMENT_STATS_PRESENT`, `STAGING_STATEMENT_LOGGING`, `STAGING_PASSWORD_ENCRYPTION` or `STAGING_ROLES_MISSING`) changed no password, so for it the rerun is simply the retry. An interrupted `--first` leaves its reserved `tmp/broker-secrets.json`, and the rerun refuses with `STAGING_FILE_EXISTS`. The owner deletes that file with `rm`, without opening it; the rerun generates new passwords, so whatever the file holds is useless.
- **Rotation record.** Each delivery writes `rotation-record.json` (non-secret: name, time, Worker, version id). `npm run staging:secrets-status` reads it for ages (warning at 80 days, 50 for the keyring; failure after 90, 60; a vault KEK's age is reported without a limit). The rollback refusal that will read it is deferred past launch (ADR-0021), so card effect E11 stays suspended and staging rolls forward: a new green `main` commit, with `npm run staging:kill` as the stop.
- **Status.** `npm run staging:secrets-status` reports each file's presence, mode, owner and format result; each Worker's deployed secret names against exact sets (broker 14 while the Stripe switch is off, 16 while it is on; api 1; others 0); the GitHub `staging` environment's secret and variable names and dates; and each role's LOGIN, limit, timeouts and the TEMP revoke. It exits non-zero on any mismatch.
- **Deploy.** `npm run staging:deploy -- --first` (D9 step 10) runs with `STAGING_DEPLOY_ENABLED=0` before the api exists. It publishes `STAGING_LOGIN_CONFIGURATION_DIGEST` before any upload (harmless while the flag is 0; if that fails, nothing is deployed and the command can run again), hands `tmp/broker-secrets.json` and `tmp/api-secrets.json` to wrangler by path, and unlinks both. After that every green push to `main` deploys through `.github/workflows/deploy-staging.yml`; `npm run staging:deploy` is the local equivalent from `origin/main` with a green `foundation`. Every deploy runs the account census before any upload (a finding stops it) and again on every path that started an upload, re-reads the flag before every upload, and writes its report before and after each upload. On `ready:false` the run fails and records both api version ids; nothing is rolled back.
- **Kill.** `npm run staging:kill` (anyone, any time): the flag to 0, the workflow disabled, queued and running deploys cancelled, the api's workers.dev off, and the hostname checked now, after 2 and after 10 minutes. `npm run staging:unkill` needs the active card.
- **Database recovery is not a Worker rollback.** Migrations are forward-only. **First run `npm run staging:kill`**: `STAGING_SCHEMA_HEAD` still names main's head after a reset, so without the kill a green push to `main` would pass gate 3 and deploy against the empty database. The owner then resets the `staging` branch from its root (`npx --no-install neonctl branches reset staging --project-id <id> --parent`); Claude reruns `staging:migrate` (it withdraws `STAGING_SCHEMA_HEAD` to `0` before its first statement and publishes the head only when the whole chain is applied), `staging:provision-roles -- --rotate all` and `staging:seed-platform`, then `npm run staging:unkill` under the card.
- **The Stripe switch (owner decision (c), 2026-10-21: "Merge with Stripe off").** `switch` in `docs/decisions/stripe-staging.json` is committed `"off"`: the staging api and broker carry no Stripe var, the broker requires neither Stripe secret, the tools neither require nor read the two Stripe owner files, `staging:put-secret` refuses both names (`STAGING_STRIPE_OFF`), and checkout, the portal and the webhook answer `unavailable`. `edge:check` (`EDGE_STRIPE_SWITCH_MIXED`) and gate 4 (`STAGING_STRIPE_SWITCH_MIXED`) refuse any Stripe var or secret while it is off, and anything less than the full set while it is on. **Turning it on:** (1) the owner's Stripe steps below, each under per-action approval with a `docs/evidence/live/` record, and both owner files placed with `morrow_put`; (2) one reviewed PR that sets `switch` to `"on"` with the portal configuration id and `observed_on`, adds `MORROW_STRIPE_MODE: "test"` to the staging api's and broker's `env.staging.vars`, the byte-equal `STRIPE_CONFIGURATION_JSON` to the broker's, and both Stripe names to the broker's `env.staging` `secrets.required`; (3) after it merges, `npm run staging:put-secret -- STRIPE_RESTRICTED_KEY` and `npm run staging:put-secret -- STRIPE_WEBHOOK_SECRET` (until both are placed gate 6 stops every deploy with `STAGING_BROKER_SECRETS_MISMATCH`, uploading nothing); (4) a deploy, then the owner-approved test-mode smoke. **Turning it off again**, in the order gate 6 requires: it holds the deployed broker's secret names exactly to the committed switch, so the off commit's deploy can pass only once the broker holds the fourteen, and no deploy of the on state can pass once it does. (0) A quiet point: no checkout open (the billing view's `checkout` is `null`) and no Stripe operation unsettled, because while off no purchase operation is reconciled and no webhook is read. (1) One reviewed PR, the reverse of the turning-on commit: `switch` `"off"` (the recorded portal configuration id and `observed_on` may stay), `MORROW_STRIPE_MODE` removed from the staging api's and broker's `env.staging.vars`, `STRIPE_CONFIGURATION_JSON` from the broker's, and both Stripe names from the broker's `env.staging` `secrets.required` (fourteen; `edge:check` refuses anything partial). (2) It merges, and its deploy stops at gate 6 with `STAGING_BROKER_SECRETS_MISMATCH`, uploading nothing: staging keeps running the on version, Stripe included. (3) Straight after, the owner removes both secrets from the broker, each a live effect under per-action approval (no card effect covers deleting a secret) with a `docs/evidence/live/` record: `npx --no-install wrangler secret delete STRIPE_RESTRICTED_KEY --config apps/broker/wrangler.jsonc --env staging`, then the same for `STRIPE_WEBHOOK_SECRET` (it asks for confirmation; `staging:put-secret` refuses both names once the switch is off, and no staging command deletes a secret). Each delete takes effect on the running broker at once: its Stripe methods hold (`BROKER_HELD`) and its health, which does not depend on Stripe, stays true. (4) Rerun the stopped deploy (`gh run rerun <run id>`, or `npm run staging:deploy` from `origin/main`): gate 6 passes and the deploy carries the switch, broker first, then the api. `npm run staging:secrets-status` then reports the broker's fourteen with nothing extra, and the smoke passes. Between (3) and the api's upload in (4), checkout and the portal answer `503 uncertain` after recording their operation, which stays open for the same key's retry once the switch is on again (list any such operation in STATUS as an open unknown outcome), and the webhook answers `503` (webhooks are answered 503 unread while off, and test mode retries a failed delivery only about three times over a few hours, so events sent while off are lost: before turning off, cancel any active test-mode subscription under per-action approval, and after turning on again reconcile each workspace's plan against Stripe before relying on it), so run (3) and (4) back to back.
