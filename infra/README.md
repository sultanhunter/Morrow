## Active local tooling

`npm run infra:synth`, `infra:permissions` and `infra:readiness` compile the selected environment inventories into `.artifacts/infra` (or `$MORROW_ARTIFACTS_DIR/infra`); in CI they are uploaded with the run's artifact, not committed. They make no provider calls and cannot deploy, grant permissions or authorize expenditure. Owned provider selectors, image digests, compute limits and receipts remain unbound. Unreviewed JSON changes are rejected; a JSON approval cannot activate resources. This exact-design checker is not production configuration or provider authorization.

`npm run cost:estimate` calculates a published-rate,100-merchant illustrative workload at a known-component subtotal of $548.19/month, excluding models/tools,35-day daily recovery bytes, added environments, observability/email, enterprise identity/contracts and other stated terms. The subtotal covers published E2B CPU/RAM and existing Cloudflare/Neon components; it omits unqualified E2B subscription/paused-resource meters and is not a full quote. Real workload measurements and a complete provider/environment-bound quote precede paid activation. Installed agents and concurrency alone do not determine runtime cost.

## Responsibility and authority

Separate API, connector, orchestrator and credential-broker Workers use environment-scoped bindings. Only the broker can access raw merchant/model credentials; it performs approved calls after current tenant, scope, operation and budget checks. Worker bindings do not establish tenant authorization. Secrets Store is beta and not automatically production-qualified. Session/private responses must not be cached.

Neon PostgreSQL owns business truth; Cloudflare Workflows owns resumable execution checkpoints; Queues carries opaque notifications from durable outbox/inbox records. Actual workflow versions, waits/events, duplicate delivery and uncertain effects must be qualified. No Temporal replay assumptions or retained-workflow behavior is claimed by local manifests.

Neon runtime, issuer, migration and recovery roles remain separate. Every interactive transaction sets tenant context using SET LOCAL and validates current identity. Qualify the actual Workers-compatible driver, pool lifecycle and reused-connection cross-tenant denial before hosted login. Local pinned PostgreSQL17 laboratories remain engineering evidence, not Neon provider acceptance.

Work roles (P06.T01a, ADR-0010): `infra/work-role-prerequisites.sql` creates `morrow_work_owner`, `morrow_work_command` and `morrow_work_api` (NOLOGIN NOINHERIT) and the `morrow_api_worker` login, with exactly two SET-only memberships, and grants `morrow_work_owner` CREATE on the database. Run it once through an owned database administrator before migrations 0014 and 0015, which refuse to apply on any attribute or membership drift. It has no PASSWORD clause: the `morrow_api_worker` password is set out of band and reaches only the broker, as `MORROW_DB_PASSWORD_MORROW_API_WORKER` (`rotation-runbook.md`). Applying 0014 and 0015 to a hosted database is a separate owner-approved action.

Spine executor logins (M2 PR-1, ADR-0022 item 8): `infra/spine-executor-role-prerequisites.sql` creates `morrow_connector_ingress`, `morrow_runtime_executor` and `morrow_vault_broker` as LOGIN roles with every other attribute off and no role membership in either direction. Run it once through the owned database administrator (with `createrole_self_grant` empty) before migration 0019, which refuses to apply on any attribute or membership drift. It has no PASSWORD clause: the connector and runtime passwords are set out of band and reach their Workers only through broker leases (`neonLease`); the vault broker's password is the broker's own secret and is never leased. Each login executes only its own definers (0020): the runtime executor `enter_lease`, `pending_starts`, `lease_mark_started` and `lease_release`; the vault broker `morrow_vault.app_secret_get`; the connector none until M2 PR-2. The identity owner executes one work definer, `morrow_work.revoke_member_leases` (0023), from the membership triggers of 0024. Applying 0019-0024 to a hosted database is a separate owner-approved action.

Broker secrets for M2 PR-1 (ADR-0022 item 7): the broker now requires `MORROW_DB_PASSWORD_MORROW_CONNECTOR_INGRESS`, `MORROW_DB_PASSWORD_MORROW_RUNTIME_EXECUTOR`, `MORROW_DB_PASSWORD_MORROW_VAULT_BROKER` and `MORROW_VAULT_KEK_V1` beside the earlier ten, P05.T01ab's `TURNSTILE_SECRET_KEY` included, and M5 PR-1 adds `STRIPE_RESTRICTED_KEY` and `STRIPE_WEBHOOK_SECRET` (`brokerRequiredSecrets`, 16 in all) in development and staging; their placement, the restricted key's exact permissions and the webhook endpoint settings are in `rotation-runbook.md`. Production requires neither vault secret nor a Stripe secret and holds both (`brokerRequiredSecretsFor("production")`, 12), and the vault script refuses `--environment production`, until the production custody ADR (ADR-0007 item 9). The role passwords are generated with the other role passwords (`staging:provision-roles`, which now covers the eleven broker logins). The KEK is the owner's: `npm run vault -- kek --out ~/.config/morrow/<env>/vault-kek-v1` writes 32 random bytes as 64 hex characters to a new 0600 file and prints only a fingerprint; keep an offline copy of that file. In staging that path is the tools' required owner file `vault-kek-v1`: `provision-roles --first` reads it into the first-deploy file and `staging:put-secret -- MORROW_VAULT_KEK_V1` re-places it, and neither ever generates a KEK. A Shopify app's client secret is sealed with `npm run vault -- seal-app-secret …` (stdin, never echoed) into a 0600 envelope file, and the administrator's runner applies it with `appSecretPutStatement` as `morrow_work_owner`, committing only when `app_secret_put` stores the envelope's version. The script refuses any path inside the repository (its real path: links into the checkout count as inside), any KEK file readable by others and any secret with a control character. Claude never runs it against the owner's files.

Private R2 artifacts use unique revision keys, checksum/manifests and conditional creation. Do not substitute S3 version identifiers or assume bucket locks solve authorization/deletion. Current policy must gate reads, previews and transfers, and erasure applies to derived copies and recovery replay.

The selected E2B merchant runtime requires a qualified hardware-isolated Linux microVM profile behind the provider port. Working files are tenant/agent-owned with one writer generation and isolated scratch for overlapping runs. No database, platform/model/Shopify keys or unrestricted direct internet enters a sandbox. Enforce broker/proxy leases and test actual effective network behavior, including redirects, rebinding, private/metadata addresses, alternative protocols and quota-tier exceptions. Keep execution disabled until P12 qualifies this profile. Native E2B timeout bounds running time only; paused resources have no automatic TTL. Preserve the original wall deadline and verified cleanup controller; paused-resource billing and entitlement are not assumed. Native memory/snapshots are not cross-provider migration formats. Merchant artifacts and durable agent memory belong in governed Neon/R2 records, not only working disks.

Account onboarding (P05.T01x Part B, ADR-0009): `infra/identity-onboarding-role-prerequisites.sql` creates `morrow_identity_onboarding` NOLOGIN NOINHERIT with no memberships; run it through an owned database administrator before migration 0013, which refuses to apply if that role has LOGIN or any membership, or if the database is not UTF8.
