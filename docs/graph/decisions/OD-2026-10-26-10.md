> yes to your prvious question regarding the foudnation work

The owner's message in chat on 2026-10-26, quoted in full. It answers the lead's earlier question
in chat about the foundation work: how to close the customer-names gap that ADR-0041 item 31 left
to the owner before ADR-0040's `async-conversations` switch goes on. The identifier screen that
OD-2026-10-26-7 approved (its question 23) catches emails, phone numbers, street addresses and
customer ids, but not a customer's name typed as free text, and before P09.T05 Morrow holds no list
of customer names to match against. The composer's standing line and redaction only narrow the
gap. The lead reads the "yes" as option (a) of that question.

Effect:

- **The P09.T05 customer-data deletion path is built first, as foundation.** It is the path by
  which messages, run turns, summaries, checkpoints and memory that may hold customer data are
  registered `content: customer` and found by `customers/redact`. It is built ahead of the
  features that need it, to production grade, under the owner's rule of the same day
  (OD-2026-10-26-6). The row that builds it first is SD4, the customer-data deletion base, of the
  store-data foundation plan (`docs/plan/store-data-foundation-implementation.md`, pull request
  88), after SD3; `v1-build-order.md` still places the first customer classes in its PR 25 until
  that plan's notes change it.
- **How a typed name is found is still to be decided, and tested.** Option (a), as the lead put it
  in chat, builds the path and keeps the switch off; it does not say how a name typed as free text
  is matched. Shopify's `customers/redact` request carries the customer's id, email and phone and
  the ids of their orders, not the name. The P09.T05 work's brief decides how a name is matched
  (for example, a lookup while the customer is still readable, or an index of names, which would
  itself be customer data), and what registering these tables `content: customer` means for their
  clocks under ADR-0031 item 2. A `lab:shopify-privacy` case shows the chosen matching deletes a
  name typed into a message before the `async-conversations` switch goes on. (Note of
  2026-10-27, from the review of pull request 86: one row owns this decision and this case, H9d
  of `docs/plan/harness-foundations-implementation.md`, a P09.T05 child. SD4 builds the base, the
  matcher over keyed digests and listed orders; H9d decides the name matching in its brief,
  registers messages, run turns, contexts, checkpoints, summaries and memory `content: customer`
  on that base, and carries the case.)
- **The `async-conversations` switch stays off until that path exists** and passes its tests (G9),
  the name-matching case included, on top of the evals and gates the harness plan already names
  for it.
- ADR-0041 item 31 carries a dated note, and the H20 row of
  `docs/plan/harness-foundations-implementation.md` names this decision as the one item 31 waited
  for.
- Nothing else in ADR-0040 or ADR-0041 changes. The CLAUDE.md invariant that customer data never
  enters before its P09.T05 deletion and privacy path exists stays as it is; this decision orders
  the work so that path comes first. COD Confirmation's contact data relies on the same path
  (ADR-0042, OD-2026-10-26-9).
