# Continuous integration

`.github/workflows/ci.yml` (workflow "Morrow foundation") runs on every pull request, on every push to `main` and by hand (`workflow_dispatch`, on any branch). It is a set of parallel jobs behind one aggregator, `foundation`, the single required check. How much of it runs depends on the event (P03.T04f):

| Event | Jobs that run | Why |
| --- | --- | --- |
| Pull request that changes anything other than Markdown | all of them (a *full* run) | the merge gate (ADR-0014) |
| Pull request that changes only Markdown (`*.md`, anywhere) | `scope`, `checks`, `foundation` (a *light* run) | `checks` holds every check that reads Markdown: `plan:check` and the rest of `verify`, and the unit tests. No lab reads Markdown (guarded, see Changing CI) |
| Push to `main` of a merge commit whose tree is exactly its second parent's | `scope`, `checks`, `foundation` (light) | the second parent is the merged pull request head, and ADR-0014 item 1 required a green `foundation` on that exact head, so the merged tree is the tree that run checked; `scope` verifies the tree equality |
| Any other push to `main` (a squash merge, a head that lacked the latest `main`, a direct push) | all of them (full) | the merged tree was never checked as a whole |
| `workflow_dispatch` | all of them (full) | a manual full run, on `main` or any branch |

Changing what the required gate accepts is Material under ADR-0002. The owner approved both light paths on 2026-10-19 (P03.T04f OQ-1, option (a)), and ADR-0014 records the amended item 4.

There are no workflow-level `paths` filters: a workflow skipped by a path filter never reports its checks, so `foundation` would stay pending (see Required check). `scope` narrows the run inside the workflow instead.

## Steps every job shares

Every job except `scope` and `foundation`, which write no report, runs these steps, in this order:

1. Check out the pull request head (or the pushed commit) with `persist-credentials: false`.
2. Set up Node from `.nvmrc` (exactly 24.13.0) with the npm download cache keyed on `package-lock.json`.
3. Set `MORROW_ARTIFACTS_DIR=$RUNNER_TEMP/morrow-artifacts` through `$GITHUB_ENV`. Reports go there, outside the checkout.
4. Run `npm ci --ignore-scripts --no-audit --no-fund`.
5. Run the job's own commands. The PostgreSQL jobs first pull the image pinned in `infra/local-engine.json`.
6. Always secret-scan the artifact directory with `scripts/scan-artifacts.mjs`.
7. Upload the artifact directory, but only if the scan passed.
8. Always require an unchanged checkout: `git status --porcelain --untracked-files=all` must print nothing.

Actions are pinned by full commit SHA: checkout `3d3c42e5…` (v7), setup-node `24997072…` (v6) and upload-artifact `b7c566a7…` (v6.0.0). Reuse these pins. Do not add an action without pinning it the same way.

## Artifacts

Each report-writing job, and each matrix leg, uploads one artifact named `morrow-<job>[-<leg>]-<run id>-<attempt>`, for example `morrow-postgres-core-<run id>-1`. Artifacts are kept for 90 days. [ADR-0012 (CI artifacts are the evidence)](../decisions/adr/ADR-0012-ci-artifacts-are-evidence.md) still holds; the only difference is that its single `morrow-ci-<run id>-<attempt>` artifact is now one artifact per job. Every upload step fails if no reports were written; `checks` always writes the static reports.

## Required check

`foundation` is the one status check to require in branch protection. It keeps the name of the old single job, so a rule that already names it keeps working. It runs with `if: always()` on every event, so it always reports, and it fails unless:

- there are exactly four lab job results (`workers`, `postgres`, `pgwire`, `ui`; it counts them, because blank results still leave the separating spaces);
- `scope` and `checks` succeeded; and
- on a full run (`full=true`: a pull request that changes more than Markdown, a push that is not a merge of an unchanged head, or a manual run), every lab job succeeded; or
- on a light run (`full=false`, on a pull request or a push only), every lab job was skipped.

Anything else fails it: a failed, cancelled or skipped `checks` or `scope`; a missing or unknown `scope` decision; `full=false` on any other event; a lab job that failed, was cancelled or was skipped on a full run, or ran on a light run; a missing lab result. `tests/ci-workflow.test.mjs` runs the aggregator script with bash over these combinations, and runs the `scope` script against a temporary git repository.

This changes ADR-0014 item 4, whose original text said the aggregator treats a skipped job as a failure. The owner approved the amendment on 2026-10-19 (P03.T04f OQ-1, option (a)); its text is in ADR-0014, section Amendments.

**When the workflow does not run at all.** GitHub reports nothing for a workflow it did not start (for example one skipped by a `paths` or `paths-ignore` filter). With branch protection that requires `foundation`, the check then stays "Expected — waiting for status to be reported" and the pull request cannot merge; it is not treated as skipped or passed. Without branch protection (today, ADR-0014 item 5), nothing blocks the merge button, but ADR-0014 item 1 still needs a green `foundation` on the exact head, so such a pull request could not be merged under the rules. That is why this workflow has no path filters and a Markdown-only pull request runs the light path instead: it costs about 6–7 billed minutes rather than nothing, and `foundation` reports green or red on every pull request.

**Push runs on `main`.** No written rule requires a pull request head to contain the latest `main` before it merges, and pull request runs check out the head, not GitHub's merge ref. So `scope` checks it on every push instead of assuming it: a merge commit whose tree equals its second parent's runs light, because that tree is exactly the head ADR-0014 item 1 required to be green; any other push (a squash merge, a head that lacked the latest `main`, a direct push) runs the full matrix. A manual full run stays available: Actions, "Morrow foundation", "Run workflow". STATUS.md records the last green commit with the run that verified it: the push run, and for a light push also the pull request run on the merged head.

## Changing CI

- Unit test files run concurrently (see Unit tests below). A file that cannot share the machine goes in `tests/serial-tests.json` with its reason; do not lower the concurrency for every file.
- Run labs one at a time within a job. The PostgreSQL labs use real lock waits and expiry windows, so a busy host can fail them. If one fails locally on a loaded machine, rerun it on an idle one before suspecting the code.
- A lab that waits on background sessions, locks or connections prints one log-safe stage line per stage on stderr and puts a deadline on every wait, so a stalled job names its stage instead of printing nothing until the job cap (`CONTROLLED_PG_PHASE:`, `LOGIN_HTTPS_PHASE:`, and `lab:spine-foundation`'s `SPINE_LAB_PHASE:<stage> t=<seconds>s`, which fails with `SPINE_LAB_STALLED:<stage>:<wait>` past a deadline). Why: on PR #30 (run 39364176106) `lab:spine-foundation` printed nothing for 10 minutes until `work` hit its cap. Its two stop races each awaited an async gate that returned its session's promise, so each waited out that session's 300 s kill timer: about 10 idle minutes per run, on macOS too.
- `tests/ci-workflow.test.mjs` (part of `npm test`) checks the workflows: actions pinned by commit SHA, checkouts without persisted credentials of the one ref each workflow file may use (`ci.yml` the pull request head, `heavy-faults.yml` `${{ github.sha }}`, `frozen-regressions.yml` the archive tag; any other workflow file fails), no `continue-on-error`, every upload gated on a passing secret scan, the shared step order and clean-tree gate in every report-writing job, `foundation` needing every `ci.yml` job and naming every lab job in its `LABS` list, and the triggers (no path filters). It requires full history in `checks` and the default depth in the lab jobs. It runs the `foundation` script over every combination of event and job results (including blank, missing and extra lab results), and the `scope` script against a temporary git repository (Markdown only, code, JSON under `docs/`, mixed, renames both ways, deletions, an empty diff, a manual run, an unreadable diff; and for pushes, a merge of an up-to-date head, a merge of a head that lacked `main`'s latest commit, a single-parent commit and an unknown commit). It also requires CI to run every `lab:*` script exactly once, all of them in jobs gated on a full run, except `lab:engine`, the `lab:e2b-*` operator commands and the local-only `lab:edge-postgresql-local` and `lab:workspace-ui-journey-local`; a light run to reach `format:check`, `typecheck`, `verify`, `plan:check`, `graph:check`, the build and `npm test` but no `lab:*` or `ui:*` script; each `lab:*` group to be a plain `&&` chain; `npm test` to run once, in `checks`, over every top-level test file; and every `heavy:*` script to run exactly once from `heavy-faults.yml` and never from `ci.yml`. It pins every job's `runs-on` (the `MORROW_CI_RUNS_ON` expression in `ci.yml`, `ubuntu-24.04` in every other workflow) and the Mac runner stack: named volumes only, pinned images, a socket-only daemon and a token that never reaches argv. `tests/ci-runner.test.mjs` runs `scripts/ci-runner.mjs` against a simulated GitHub and Docker Desktop.
- A new lab gets its own `lab:*` npm script and joins the matching group script in `package.json` (the test above fails until it does):
  - Workers labs join `lab:group:workers`;
  - network-none PostgreSQL labs join one of the `pg-*` groups;
  - PG-wire labs join `lab:group:pgwire`;
  - browser labs join `lab:group:ui` (the `ui` job, which alone installs Chromium).
- A light run skips the labs because no lab reads Markdown. `tests/ci-workflow.test.mjs` fails if any repository source file a gated job can load names a `.md` file: it starts from the files the gated npm scripts name, every Worker `main` in `apps/*/wrangler.jsonc` and the workspace SPA entries, and follows relative and `@morrow/*` imports and string literals that name repository source files (paths built at run time are not followed). A lab that must read one makes `scope` treat that file as code instead; the checks that read Markdown today (`plan:check`, `verify:foundation`, `verify:billing`, `verify:design` and several unit tests) all run in `checks`.
- Merge jobs only when the combined job stays under about 8 minutes, and keep a flaky or long group on its own runner: a rerun repeats the whole job. Each job pays about 20 s of setup (30 s with the image pull) and GitHub rounds each job up to a whole minute.
- The `pgwire` labs need Linux, `GITHUB_ACTIONS=true`, a rootful Docker daemon at `/var/run/docker.sock` and a bridge gateway in 172.16.0.0/12. That is why the job runs on Linux: `ubuntu-24.04`, or the Linux runner container of the Mac runner, whose daemon socket is at that path (see Self-hosted runner on the owner's Mac). Elsewhere, including Docker Desktop on macOS outside that runner, they refuse to run; they never pass by accident. Do not try to make them run on macOS itself. The one exception is deliberate and separate: `npm run lab:edge-postgresql-local` runs the `lab:edge-postgresql` journeys on a developer machine (pinned image already pulled, port published on 127.0.0.1 only, the synthetic loopback bridge). It refuses to run in GitHub Actions, never runs in CI, and is supporting evidence only; the `pgwire` job stays the authority.
- `npm run ci` stays as the full serial local pipeline (static checks and all tests, without the scaffold smoke and the Docker/Workers labs). It also runs `typecheck:edge`, `edge:check` and `edge:dry-run` after `build`; CI runs the dry-run in the `workers` job's network-none container instead, and `tests/ci-workflow.test.mjs` follows the npm scripts that container step runs through `sh -c`.
- Wrangler always runs through `scripts/edge.mjs`, with a scrubbed environment, a throwaway `HOME`, `--env-file=<an empty file>` (so no `.env` or `.dev.vars` is loaded), metrics, `cf.json` and the npm update check off, and never with an account or token. It refuses to run with a `.env*` or `.dev.vars*` at the repository root, under `apps/` or in its working directory.
- Timing to watch on the first hosted runs of P03.T04f: `postgres (core-http)` (estimated 7.5 to 8.2 minutes from the pg-core and pg-http job times below; cap 14), `workers` (about 5.8 minutes; cap 15) and `checks` (about 3.5 to 4 minutes; cap 15). If `core-http` stays above about 8 minutes, pair `pg-core` with `pgwire` instead (about 7 minutes by the same measurements) or split the leg again; do not raise the cap. Done on 2026-10-20: the leg reached 11 to 15 minutes once pg-core held the approval-records and createrole labs, so it is now split into `core` and `http`. Running `npm test && npm run ci:static` covers the same ground as CI's `checks` job.

## Formatting

`npm run format:check` is `prettier --check .` and `npm run format` is `prettier --write .`. Prettier reads `.gitignore` and `.prettierignore`. The ignore file states what is out of scope: untracked and generated outputs, the generated contracts (`packages/contracts/src/generated/`) and `apps/*/worker-configuration.d.ts` (their generators compare them byte for byte), `docs/` and Markdown, and the byte-locked `tests/fixtures/e2b-*` fixtures. A new code file is formatted by default. `tests/format-scope.test.mjs` fails if the ignore files hide any other tracked or new code or configuration file outside `docs/`, so widening `.prettierignore` cannot hide code. Commits that only reformat are listed in `.git-blame-ignore-revs` (`git config blame.ignoreRevsFile .git-blame-ignore-revs`).

## Unit tests

`npm test` runs `node scripts/run-tests.mjs`. It lists the top-level `tests/*.test.mjs` files and runs the parallel-safe ones with `--test-concurrency=k`, where k is `min(4, available CPUs)` (2 on the hosted runners). Then it runs the files named in `tests/serial-tests.json` one at a time. It exits 1 if either run failed. Each run prints its own `ℹ tests` total, so the job's total is the sum of its runs. CI's `checks` job runs plain `npm test`, unsharded (P03.T04f).

- `--shard=i/n` gives file j of each set, sorted, to shard (j mod n) + 1; CI no longer passes it, and the `test:shard` npm script was removed in P03.T04f. `--concurrency=k` (1–16), `--repeat=r` (1–10, a fresh child per repetition) and `--junit=<dir>` (one JUnit report per run under the artifacts directory) serve the heavy job. `--list` prints the plan as JSON and runs nothing.
- Every spawn passes an explicit file list. An empty set or shard is never spawned, because `node --test` without files falls back to default discovery.
- A file goes in `tests/serial-tests.json` (`{"file", "reason"}`, with a reason of 20–300 characters that names its wall-clock dependency) only when it fails under parallel files and passes 5 of 5 runs alone. The runner rejects an entry that is missing, duplicated or not a top-level test file.
- Test servers listen with `.listen(0, "127.0.0.1"` only, and temporary roots come from `mkdtemp` or a random UUID. `tests/run-tests.test.mjs` enforces the listen form, which also stops a test from starting the fixed-port 4110 operator listeners.

## Heavy faults

`.github/workflows/heavy-faults.yml` (workflow "Morrow heavy faults") holds the heavy fault matrices. It runs by hand (`workflow_dispatch`) and weekly (Mondays 03:23 UTC), never on pull requests or pushes. It is not a required check: `foundation` does not need it.

- The `gate` job checks out `${{ github.sha }}` and sets `run=true` for a manual run, or when the head commit is under 8 days old. A scheduled run on an unchanged repository therefore skips the heavy job. `gate` writes no report, so it has no scan, upload or clean-tree steps.
- The `heavy` job (40 min, `fail-fast: false`) runs `npm run "heavy:$HEAVY_SUITE"` for each `matrix.suite`, with the same hardened steps as `ci.yml`. Today its only leg is `unit-stress`: `heavy:unit-stress` runs the unit set 5 times at concurrency 8 and uploads the JUnit reports, which name any file that flakes under load.
- Later packets add legs and `heavy:<slug>` scripts: the PostgreSQL harness stress (P03.T04e PR-B), and the P06.T01a soak and race matrices. Each `heavy:*` script must be reached exactly once from this workflow.
- A failing scheduled run is not a required check, so the next session records it under Blockers in `docs/progress/STATUS.md` until it is fixed.
- One run costs about 18 billed minutes of the private repository's included Actions quota (P03.T04e OQ-1). Moving to a nightly cadence is a one-line cron change, made only after the owner confirms the GitHub plan and quota.

## Staging deploy

`.github/workflows/deploy-staging.yml` (workflow "Deploy staging", P04.T01i D2, trimmed by ADR-0021) deploys the four staging Workers. It is not a required check.

- **Trigger.** It runs on `workflow_run` of "Morrow foundation" (`completed`, `main`). The job runs only for a successful `push` run on `main` from this repository. It uses the `staging` environment and `concurrency: deploy-staging` without cancelling a running deploy.
- **Steps without the token.** `node scripts/staging.mjs ci-gates` checks the card, gate 1 (the sha is still the `main` tip) and gate 2 (`STAGING_DEPLOY_ENABLED` is `1` and the workflow is enabled). A stop is a successful no-op. Gate 5 runs `npm run build && npm run edge:check && npm run edge:dry-run`.
- **The token step.** Only this step's env holds `CLOUDFLARE_API_TOKEN`. It runs `node scripts/staging.mjs deploy --ci`, which:
  - checks gates 3, 4 (the login configuration digest and the P05.T01ab challenge configuration) and 6, and runs the account census, which stops the run on any finding before an upload;
  - deploys broker, orchestrator, connector and api, re-reading the flag just before every upload and just after the api deploy;
  - checks `/healthz`, then runs the unattended smoke;
  - runs the census again on every path that started an upload, including a failed, unknown or killed one.
- **Permissions.** `contents: read` and `actions: read`. The workflow's token cannot read variables, so its live flag re-read is the workflow's own state, which `npm run staging:kill` disables. The token (`GH_TOKEN`) is moved out of the process environment at startup and reaches only `gh` children.
- **Reports and checkout.** The report (`staging/deploy-report.json`) is written before and after every upload, so a cancelled or timed-out run still uploads one that names the upload in flight. It is secret-scanned before upload, and the checkout must be left clean.
- **No rollback.** Card effect E11 is suspended, so staging rolls forward from a new green `main` commit, with the kill switch as the stop.

## Self-hosted runner on the owner's Mac

GitHub-hosted Actions minutes ran out in October and reset on 1 November. On 2026-10-22 the owner decided "for CI lets use our mac" (ADR-0014, amendment of 2026-10-22).

**How it works.** Every `ci.yml` job has `runs-on: ${{ fromJSON(vars.MORROW_CI_RUNS_ON || '"ubuntu-24.04"') }}`:
- With the repository variable `MORROW_CI_RUNS_ON` unset, every job runs on `ubuntu-24.04`, as before.
- With it set to `["self-hosted","linux","arm64","morrow-mac"]`, every job queues for the Mac runner. Job names do not change, so the required `foundation` check is the same.
- No other workflow on `main` reads the variable. `deploy-staging.yml`, `heavy-faults.yml` and `frozen-regressions.yml` stay on GitHub-hosted runners.
- The variable is configuration, not a control. GitHub cannot restrict a repository runner to one workflow. While the runner is online, any workflow in any branch can name its labels and run on it, with or without the variable. `pause` and `down` therefore also take the runner offline.
- `ci.yml` names no secret, so GitHub sends no secret to the Mac. The Mac's own files are another matter: see File sharing below and the residual risks.
- Until 1 November, staging deploys run locally with the staging CLI under `staging-card-1`.
- Self-hosted jobs use no Actions minutes.

The stack is `infra/ci-runner/compose.yaml`: two containers in Docker Desktop, both images pinned by digest.
- `dind` is a privileged Docker daemon (`docker:29.8.2-dind`), the only daemon a job can reach. It has no TCP listener; its socket is in a named volume.
- `runner` is the GitHub runner `morrow-mac-1` (`ghcr.io/actions/actions-runner:2.338.0`, Ubuntu 24.04 arm64, passwordless `sudo` for `playwright install --with-deps`). It shares `dind`'s network namespace, so `127.0.0.1`, published ports and job containers' bridge addresses behave as on a hosted runner. It reaches the daemon at `/var/run/docker.sock`, the endpoint the `pgwire` and `ui` labs require.
- Both mount one named volume at `/home/runner/_work` (checkouts, `_tool`, `_temp`). A `docker run --volume <path under _work>` therefore resolves inside `dind`. There is no host bind mount and no host Docker socket.
- Before each job, a job-started hook (`ACTIONS_RUNNER_HOOK_JOB_STARTED`) removes every container and network left in the runner's own daemon, for example by a cancelled job, so each job starts as on a fresh hosted runner. Images stay as a cache. The checkout is cleaned by `actions/checkout` and `_temp` by the runner.
- The runner's registration (`.runner`, `.credentials`, `.credentials_rsaparams`) is kept in a named volume, so a container restart needs no new token. After a Mac reboot, the runner comes back once Docker Desktop runs again. Its key pair is a credential that any job can read (see the residual risks), and only `down` revokes it. The runner updates itself.
- Jobs queue on the one runner, so a full run takes the sum of its job times. On GitHub-hosted runners that sum was about 50 minutes (push run 39498651638); on the Mac it depends on the Mac's load.

**Before the first `up`: narrow Docker Desktop's File sharing.** Any job can reach every host folder that Docker Desktop shares, and can read and write it with your permissions (residual risk (b)). Docker Desktop's default list (`/Users`, `/Volumes`, `/private`, `/tmp`, `/var/folders`) includes `~/.config/morrow`, `~/.ssh`, your shell files, `~/Library/LaunchAgents` and every checkout.
- In Docker Desktop, open Settings, Resources, File sharing.
- Remove every entry that Morrow does not need. Morrow's local labs bind-mount no host folder (they pass SQL on stdin), so Morrow needs none. Keep only folders that your other Docker work needs and whose contents you never run or keep secret.
- Apply. Docker Desktop restarts, so do this while nothing runs in Docker.
- `up` reads Docker Desktop's settings file (`~/Library/Group Containers/group.com.docker/settings-store.json`). It refuses with `CI_RUNNER_HOST_SHARE_TOO_BROAD` while any shared folder is or contains your home folder or `/Volumes`. It also refuses when a shared folder is, contains or lies inside the checkout, `/tmp` (where agents keep their worktrees) or `/var/folders`, or lies inside `~/Library` or a dot entry of your home folder. That includes Docker Desktop's defaults. `status` reports the same check.
- Workflows from fork pull requests must stay disabled for this repository (today they are). `up` refuses with `CI_RUNNER_FORK_PR_WORKFLOWS_ON` otherwise.
- The repository must be private. A self-hosted runner never serves a public repository, where any fork pull request could name the runner's labels in its own workflow. `up` refuses with `CI_RUNNER_REPOSITORY_PUBLIC` otherwise. On 2026-10-22 the owner made the repository public, and the runner was taken `down` first (registration deleted, volumes removed). CI runs on GitHub-hosted runners.

**Commands.** The owner runs these, or an agent with the owner's per-action go-ahead in chat (ADR-0014 item 1).

```sh
npm run ci:runner -- up       # pull, register if needed, start, wait until online, set MORROW_CI_RUNS_ON
npm run ci:runner -- status   # the variable, the runners on GitHub, File sharing, the containers
npm run ci:runner -- pause    # delete MORROW_CI_RUNS_ON, stop both stacks: runners offline, still registered
npm run ci:runner -- down     # delete the variable, stop, deregister (revokes the key), remove containers and volumes
```

- `up` asks GitHub for a registration token only when the runner is not registered yet. The token stays in memory and reaches `config.sh` only on the stdin of a one-off `docker compose run --rm`: never argv, a file, a stored container configuration or output.
- `up` sets the variable only after GitHub lists the runner online with exactly those labels.
- `up` is safe to rerun. Rerun it when `status` reports a stale runner network (Docker restarted `dind` alone), or after `pause`. Run it while the runner is idle: a changed image pin recreates the containers.
- `pause` and `down` delete the variable before they check Docker, because the variable needs only `gh`. If Docker Desktop is not running, they still delete it, then stop with the Docker error; run them again once Docker Desktop runs.
- `pause` keeps the registration and the volumes. GitHub deletes a runner that has been offline for 14 days; `up` then registers it again.

**Adding a second runner.** `npm run ci:runner -- up --instance=2` starts a second, separate stack (`morrow-ci-runner-2`, runner `morrow-mac-2`) with its own daemon and volumes and the same labels, so two jobs run at once. `status --instance=2` and `down --instance=2` act on it. `down` keeps the variable while the other runner is online.

**Mac resources.**
- Idle: about 250 MB of memory and no CPU.
- During a job: up to what Docker Desktop allows (today 10 CPUs and 8 GB, shared with everything else in Docker Desktop).
- Disk inside Docker Desktop: about 2.3 GB of images, plus 2–4 GB of volumes (job images, the checkout and `node_modules`, Node in `_tool`, and Playwright's Chromium).
- `down` removes everything except the two images.

**Open pull requests** switch on their next `pull_request` event (push a commit, or close and reopen), because GitHub reads `ci.yml` from the pull request's merge commit with `main`. Re-running a run created before this change keeps `ubuntu-24.04` and gets no runner until the hosted minutes reset; push or reopen instead. A pull request with a merge conflict runs nothing until the conflict is resolved.

**Back to GitHub-hosted runners on 1 November.** Run `npm run ci:runner -- down`. `pause` deletes the variable and stops the runners, but it keeps the registration key and the volumes until `down`, so use it only for a short break. With the variable deleted, every job runs on `ubuntu-24.04` again and nothing in the repository changes. A job that was queued for the Mac before the variable was deleted keeps its labels. If no Mac runner is online, it waits until GitHub cancels it after 24 hours; rerun it.

**Residual risks** (ADR-0014, amendment of 2026-10-22):
- (a) Anyone, and any GitHub App, with write access can run code on the Mac, inside the container, by pushing a branch. This includes a branch that adds its own workflow naming the runner's labels, as long as the runner is online.
- (b) Through the privileged `dind`, any job can take root in Docker Desktop's Linux VM. It can then read and write every host folder that Docker Desktop shares, with your permissions, which is why `up` requires a narrowed File sharing list. It also reaches whatever else Docker Desktop exposes to its VM, the Mac's network services and the local network. A dedicated Linux VM with no host mounts (Lima or colima with mounts disabled) would remove the shared-folder path. It is not adopted, because it needs new software on the Mac.
- (c) CI results depend on the Mac's integrity. A job can tamper with the long-lived runner, its daemon and its `docker`, `work` and `registration` volumes. It can also copy the runner's registration key and run a listener as `morrow-mac-1` elsewhere, even after its author loses write access. That listener receives later `ci.yml` jobs and can report `foundation` results. Restarts, `up` and `pause` keep the key and the volumes. Only `down` revokes the key and clears the volumes. After removing anyone's write access, or on any suspicion, run `npm run ci:runner -- down` and then `up`. A just-in-time ephemeral runner, with a new key for every job, is the stronger alternative. It is not adopted, because a process holding a GitHub credential would have to create a registration for every job.
- (d) Timing checks may flake when the Mac is loaded; rerun once.

## Running it locally

With Node 24.13.0 and Docker Desktop running, every job except `pgwire` runs on macOS:

```sh
npm ci --ignore-scripts
npm test && npm run ci:static                                            # the checks job
npm run lab:workspace-api-workers && npm run lab:group:workers           # the workers job, without the container step
npm run lab:group:pg-core                                                # postgres core
npm run lab:group:pg-http                                                # postgres http
npm run lab:group:pg-linking && npm run lab:group:pg-work                # postgres linking and work
npx playwright install chromium && npm run ui:check && npm run ui:edge   # the ui job, without the journey
npm run lab:workspace-ui-journey-local                                   # supporting evidence only
git status --porcelain --untracked-files=all   # should print nothing
```

Reports go to the git-ignored `.artifacts/` directory unless `MORROW_ARTIFACTS_DIR` is set.

## Frozen regression replay

`.github/workflows/frozen-regressions.yml` is optional and can only be started by hand (`workflow_dispatch`). It is not a required check. It checks out the archive tag `codex-archive-f89ad75`, never the current tree. There it replays the frozen 71/74/75/80/82 WorkOS operator regressions retired by ADR-0013, together with their unit tests. The uploaded `frozen*.json` paths are tracked at the tag, so a report that a failed replay never rewrote would still be there. The upload therefore runs only when every replay and unit test succeeded and the archived tree's own secret scan (`verify:delivery`) passed. The replays rewrite tracked reports inside that archived tree, so this job has no clean-tree gate.
