## Goal

Until this PR, a change to the app's Shopify permissions or an uninstall ended the app for good. After it: a permission change keeps the connection and its token, stops only the agents that need a permission no longer granted, and puts one "Reconnect" item in front of the connection steward and the Owner; reinstalling the same app works; and the approved clean-up jobs run (leftover tokens destroyed, missed deliveries reconciled, the 48-hour self-deletion when `shop/redact` never comes, stuck deliveries closed).

## Scope

- **Scope changes keep the connection (ADR-0025 item 10).** `store_installations.granted_scopes` may record a narrower set (`{}` included) without a new token; two columns record what the broker observed with the installation's own token (`scopes_observed_at`, `token_refused_at`). The replaced Shopify record guard admits only: a delivery's scopes narrowing the record; a fresh broker observation (strictly later) recording the scopes and the refusal; a re-authorisation (the next credential version) recording the new token's scopes and clearing a refusal. A delivery never widens (deliveries arrive out of order). The connector's applier is `connector_inbox_apply_v2`: `app/scopes_update` records the delivery's current scopes, then `connection_health_reconcile` sets a system installation stop (`StopRecord@1`, actor `system`, `shopify_scope_missing`, or `shopify_token_refused` after a refused read-back) on each agent installation of the store whose release needs a missing scope (`release_shopify_scopes`; `read_products` is the connection's own and stops every agent; an unknown release needs every requested scope), unless a stop already stands on it, and raises or revises one `connection_notices` row per connection (`kind reconnect`; missing scopes, stopped agents, recipients steward and Owner; content-free). Every other topic is 0037's applier, unchanged, followed by the reconcile that clears an ended connection's item. 0037's `work_shopify_installation_end` refuses `scopes_changed` (0047), so the M2 PR-3 suspension can no longer run. Nothing resumes by itself: the stops stay until a person lifts them; a lift while a scope is still missing is stopped again by the cron's reconcile.
- **Reconnect.** `work_shopify_launch` reports `reconnect` for a live installation that lacks a requested scope or whose token Shopify refused; the connector then starts OAuth (the install link), and the re-authorisation records the new token's scopes; the next reconcile clears the item (`scopes_restored`). The connector's status page shows "Reconnect". The Inbox reads the items through `connection_notices_open()` (session only, recipients only) and `packages/work/src/connection-health/notices.ts` (statement, strict decoder, fixtures): the narrow seam until PR 10b adds a `reconnect` Inbox kind and PR 15 renders it.
- **Reinstall (ADR-0025 item 2's link rule kept).** One installation that is not uninstalled per app and shop (was one ever), one active candidate per shop. An uninstalled latest installation launches OAuth; the install is a new installation (new store, connection and credential ids) born unlinked, so only a person links it again. `shopify_install_prepare_v2` destroys every earlier installation's leftover token in the same install transaction, and the identity record refuses a reinstall while one is undestroyed. `workspace_connections` offers an uninstalled app's install link (a suspended one still blocks it). A reinstalled store is a new store: its agents are enabled again on it, and the earlier store's data is deleted on its own clock.
- **Clean-up jobs** (the connector's five-minute cron; ids only; each step in the tenant of the row it names, never a caller's):
  - always: the open Reconnect items, and every live connection that needs reconnecting without one (a recorded narrowing or refusal whose reconcile was lost), reconciled again; M2 PR-3's re-drives (received deliveries; tokens of ended installations destroyed);
  - behind the connection clean-up switch (`docs/decisions/connection-cleanup-staging.json`, committed **off**; `MORROW_CONNECTION_CLEANUP` exactly `on` on the staging connector; `edge:check` refuses a mixed state): the daily read-back of each live installation's granted scopes (`ConnectorBroker.shopifyConnectionCheck`: one fixed `AccessScopes` document with its own token, resolved and recorded in two vault transactions for the token version read; a 401 records a refusal, never an uninstall; anything unclear records nothing); the 48-hour deletion (`connector_deletion_apply`: every store-content handler through 0038's `store_content_redact`, the identity pseudonymised, the install link cleared unless a reinstall is live, the item cleared, and `store_data_deletions` completed once with content-free evidence only when nothing is outstanding, the token's destruction included); stuck deliveries (a scope change still received after 24 hours closed `stuck_closed`; every other topic counted and logged `INBOX_STUCK`).
- **Uninstall** destroys the token (unchanged path, now also clearing the item).

## Security notes

- Tenancy: both new tables are FORCE RLS with no PUBLIC grant; the connector reaches notices, agent installations, its stops and leases only through policies keyed to `morrow.connector_health` / `morrow.connector_agent_stop` / `morrow.connector_sweep`, which only the reconcile writes from the installation row itself and every connector definer clears on entry (P10 probes a forged context). The cron lists carry installation ids only; every step takes its tenant from the row it names.
- Authority: the system stop is set by code, never by a model; its policy admits only `set_by_kind system`, scope `installation`, the two codes, no lift and no update. An agent cannot lift a stop. Connector scopes stay in the intersection: the gateway's claim (0045) already refuses `scope_missing` once `write_products` is not recorded, before any stop.
- Credentials: the token is opened only in the broker, for one fixed document, and dropped; the connector passes an id and a budget. A reinstall stores its new token only after the old one is erased in the same transaction. No token, secret or shop value reaches a log (`lab:connection-health` O1).
- Unknown outcomes: an unclear Shopify answer or a lost COMMIT acknowledgement records nothing and is asked again; a refused token is a Reconnect, never an assumed uninstall; a deletion completes only when nothing is outstanding.
- Retention: the deletion record is content-free (ids, codes, counts, times; 365 days). Customer data still never enters. The 48-hour deletion runs anyway after a reinstall (ADR-0031 owner question 2); a reinstall's own data is a new store.
- Default off: the read-back, the self-deletion and the stuck close need the reviewed switch; the scope-change, reinstall and re-drive paths do not.
