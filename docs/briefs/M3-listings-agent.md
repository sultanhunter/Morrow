# M3 Listings agent

- Status: brief, 2026-10-19 (revised after critique). Spine: [mvp-architecture.md](mvp-architecture.md) §2 steps 6–9, §4, §5, §7, §9, §10. Material choices: ADR-0022 items 1–3, 10, 11, 15 and 16 (accepted 2026-10-19, including the model catalogue values listed under its "Owner confirmation of the catalogue values (2026-10-19)").
- Plan IDs: P13.T01a–T03a, P05.T04b (minimum), P11.T04a (minimum), P11.T05a (stops). Branch `claude/m3-listings-agent`, from M2 PR-1; two PRs.

## Goal

The owner enables the Listings agent for a linked store. A merchant asks for better listings on selected products and picks the Claude model and thinking effort, or keeps the workspace default. The Coordinator (code) scopes the request, the Listings specialist drafts exact changes one product at a time through the model gateway, and Morrow stores them as Proposal@2 records. Each run reserves credits and vendor cost first and settles at the end. Stops exist before the first model call. No store write happens in M3.

## Scope

- **PR-1, authority, stops and credits:**
  - forward migrations: `morrow_identity.grants` admits agent principals (`membership_id` null only for kind `agent`, with a kind-dependent check and foreign keys only for humans); `proposals.proposer_membership_id` null only for an agent proposer with an installation;
  - `agent_releases` (one seeded release `morrow.listings` v1), `agent_installations`, `work_envelopes`, `delegation_hops`, and SQL readers behind `AgentAuthorityReader.readDelegationCurrent`;
  - `POST /workspace/:ws/stores/:storeId/agents/listings` ("Enable Listings agent"; owner, `agents.installation.activate`): creates the installation and the workspace's Coordinator principal on first use, issues the installation's grants with the owner as issuer, and gives the owner `agents.installation.disable`;
  - stops: "Stop AI work" (`agents.installation.disable`), the owner-run platform stop script, and the stop checks in `resolve_call`;
  - `credit_wallets`, `credit_reservations`, `vendor_cost_reservations`;
  - the unrecovered-cost ledger per workspace and billing period (ADR-0022 item 11);
  - **the catalogue part (no longer gated: the owner confirmed ADR-0022's "Owner confirmation of the catalogue values (2026-10-19)" list, and catalogue version 1 is published with its pinned digest):** the model catalogue generated from `docs/decisions/model-policy.json` (rates, caps, multipliers and keys for the broker and the api's checks; `ModelSelection@1` keys stay pattern-checked strings, never enums), `workspace_model_defaults` with the member ceiling, `GET /workspace/:ws/models` and `PUT /workspace/:ws/settings/model-default` (`governance.model_default.revise`, signup template v2).
- **PR-2, runs and drafting:** `runs`, `run_manifests`, `product_snapshots`, `run_drafts`; `POST /workspace/:ws/work/tasks/:taskId/runs`, `GET /workspace/:ws/work/runs/:runId`; `ListingsRunWorkflow`; broker `modelRespond` with the `ModelProvider` port, the broker-internal `AdapterResult` and its Claude adapter (official SDK, retries off), reading the selection and catalogue version from the lease's run; the agent submit definer (`morrow_work.submit_agent_proposal`, executable by `morrow_runtime_executor` under a run lease) and the `catalog.content.publish` producer; the Ask and task screens.

## Non-goals

Store writes (M4); a model-based Coordinator; other model providers, `xhigh` and `max` effort, escalation, images, tools, streaming, prompt caching and fallback; questions back to the merchant; agent creation or the Agent Store; prompt-quality evaluation beyond a fixed fixture set.

## Flow

1. **Admit (api, one transaction):** human kernel on the store resource (`execute` on `catalog.content.propose`, `view` on `catalog.products.read`, plus `delegate` on both and `propose` + `delegate` on `catalog.content.publish`); entitlement through `entitlementFor`; stops, link and installation current; the selection's keys in the active catalogue version and within the requester's member ceiling (unless the requester holds `governance.model_default.revise`); the product count within the selection's run limit; and the workspace's unrecovered cost this billing period below its cap. The code Coordinator writes `CoordinatorRoute@1` from the picked products and fields. Then: the envelope on task T (requester and authorizer the merchant; the three capabilities; verbs `view`, `execute`, `propose`; the store resource; 24 h; depth 1, one child); child task T′ for the installation; the Coordinator's `workspace.task.delegate` {delegate} grant on T, expiring with the envelope; the hop T → T′; credit and vendor reservations; the run (with catalogue version, model, effort and multiplier), its lease and an outbox row.
2. **Start:** after commit the api sends the run id on the dispatch Queue; the orchestrator starts `ListingsRunWorkflow` with `id = runId` (an existing id means it already started), and its cron starts any run that `pending_starts()` still lists.
3. **Per product (one step each):** `decideDelegation`; the failed-product checks (the run stops after three consecutive failed products, or when the workspace's unrecovered cost this period plus this product's worst case would pass the cap); `shopifyRead(productContent)`; a content-addressed `product_snapshots` row; one `modelRespond` with the brief, the fields and that product only (the broker applies the run's selection; the call names none); validate. The draft's `productId` must equal the requested product. Fields are restricted to the brief's, length-capped (title 255 characters, `descriptionHtml` 10,000 bytes, SEO title 70, SEO description 320, at most 50 tags of 64 characters), stripped of no-op changes, and the HTML sanitised to an allowlist (`p`, `br`, `strong`, `em`, `ul`, `ol`, `li`, `h2`–`h4`; no attributes, links or images). URLs, email addresses and phone numbers absent from the source are flagged for the reviewer. One retry on a validation failure, `incomplete`, `refusal` or `uncertain`; then the product is marked failed and its booked cost is added to the workspace's unrecovered cost. Outcomes follow ADR-0022 item 10's table. The step writes `run_drafts` and returns ids only.
4. **Propose:** `decideDelegation` with `propose` on `catalog.content.publish`; the producer packs drafts into proposals by bytes (spine §7) and submits through the agent definer, with `proposedBy` the agent and `requestedBy` the task initiator.
5. **Settle:** credits for the products drafted times the multiplier, the rest released (failed products are not charged), vendor cost from usage, run `succeeded` or `failed`, lease released.

## Security notes

- **Stops before spend (invariants 14–15):** "Stop AI work", the platform stop and the `resolve_call` checks land in PR-1, and `ListingsRunWorkflow` stays disabled until they pass. A model call is metered spend, not a store effect (ADR-0022 item 10).
- **Checks outside prompts (invariant 13):** the model has no tools and returns one product's JSON. Authority, fields, sizes, budgets, stops and the model selection are code checks; the client sends only catalogue keys, never a provider model string, and model output never selects a model.
- **Agent authority is an intersection (invariant 5):** `decideDelegation` rereads facts at every step; the installation cannot exceed the requester or its owner; a disabled installation stops the run at its next step. Only the owner's explicit command creates an installation.
- **Approval binding (invariant 7):** M3 only creates pending approvals; the digest covers targets, fields, expected source revisions and the parameters digest.
- **Paid work:** no inference without a reservation; the broker refuses a call whose worst case exceeds the run's remaining vendor reservation and books cost at the run's catalogue version; a spend-limit refusal ends the run. Product text can make failure deliberate, so failed products are bounded by the run breaker and the workspace's unrecovered-cost cap (ADR-0022 item 11). A member without `governance.model_default.revise` cannot pick an entry above the workspace's ceiling.
- **Injection:** product text may carry instructions. One product per call stops cross-product steering. Model text cannot name a capability, store or price. Every proposal is `untrusted_external`, and its exact digest needs human approval. The review screen shows tag changes as functional (tags drive collections and automations) and shows contact and URL flags. There is no model-written note.
- **Model data (ADR-0022 item 10):** the request text and the product's catalogue fields only; Anthropic does not train on API data by default and deletes it within 30 days (if flagged, the content up to 2 years and its classification scores up to 7 years); Morrow does not persist prompts or raw outputs, and Workflow state holds ids only. The Anthropic key is in the broker only.
- **Rendering:** the review screen shows escaped HTML source; any preview renders in a sandboxed `iframe` with `srcdoc`, no scripts and `default-src 'none'`.

While off, admission answers 503 before any database access, `modelRespond` holds every call with `MODEL_UNAVAILABLE` before any input, database or provider access, and the orchestrator keeps dispatch disabled. Production refuses the switch.
- **Dispatch and admission stay closed even with the switch on** until M2 PR-3 lands `RuntimeBroker.shopifyRead(productContent)` (`runtimeProductReadAvailable` in `broker-protocol.ts`, a reviewed constant: an RPC stub answers any method name). The orchestrator dispatches and the api admits runs only with both (review finding, 2026-10-22: admission on the switch alone would reserve credits and open leases no Workflow ever started), so `GET /models` reports drafting unavailable until then. The product read's JSON shape is the integration point (`{schemaVersion: 1, outcome: "read", product: ListingSnapshot}` or `{outcome: "not_found"}`).
- **Start.** Flow step 2's api Queue producer is not built: the orchestrator's cron starts every run `pending_starts()` lists (ids only), so a run starts within a minute of admission. The Queue consumer still never acks.
- **Claude adapter by hand-written fetch, not the official SDK** (owner question 1): the SDK does not fit the broker's 256 KiB bundle cap (457,561 bytes with the full SDK, 315,143 with only its Messages resource; the broker is 249,874 bytes with the fetch adapter). The request fields and the outcome table are item 10's. Recorded deviations: every fetch exception is `uncertain` (fetch cannot tell a refused connection from a lost reply); on the send, every status of 500 or above but 529 (not only item 10's 500 and 504) and any non-200 status below 400 is `uncertain`, because a gateway or edge failure after the request was sent (502, 503, Cloudflare's 520-524) does not prove nothing was generated (item 10's "transport loss after the request was sent" row, never a free `provider_error`); the free count runs on the identical body without `max_tokens`, and a count failure is `not_sent`.
- **Call budgets follow the effort** (review finding, 2026-10-22). The send is non-streaming (streaming stays a non-goal), so one fixed 90 s budget could not hold a medium (12,000) or high (16,000) `max_tokens` reply, and an aborted send is `uncertain` at its worst case. Each run's `modelRespond` budget is now `modelCallBudgetMs` of its effort's `max_tokens` (`broker-protocol.ts`): the fence's 10 s, the count's 15 s, a 30 s first-token allowance and the whole reply at a floor of 128,000 output tokens an hour (the rate the official SDK assumes for its 10-minute non-streaming default), plus 1 s for the close: about 197 s at low, 394 s at medium and 506 s at high, within the protocol's new 600 s ceiling (and the fence's `budget_ms` bound). The broker holds a call whose budget cannot hold its entry's whole call, and never sends with less than the send window left. `run_start` returns the run's catalogue version and selection keys so the Workflow sizes the budget; a product step's lease margin is two calls plus a minute of throttle waits, the open-fence waits outlast budget plus a minute, and the Workflow step timeout is 30 minutes (the run lease). The floor is an assumption until the staging smoke measures it (owner question 6); a run of slow high-effort products drafts fewer products before its 30-minute lease ends (`time_budget`).
- **Drafted work is proposed after a run-ending outcome** (owner question 3): a spend limit, the breaker or a provider error still proposes the products already drafted and checked, and charges one credit each; the propose step reruns `decideDelegation`, so a run that lost its authority proposes nothing.
- **One lock order** (review finding, 2026-10-22): the workspace stream, then the run's advisory lock, then the rest, as every API command's prelude takes it. `run_start`, `submit_agent_proposal` and `run_finish` take the stream right after the lease and before the run; `run_end` takes it before any credit or cost row; the stale close never waits on a run's lock under the caller's stream (a busy run is skipped and closed next time) and rechecks a run it holds. `lab:listings-runs` D1-D2 drive a run finishing and a run starting against a session holding the stream as an admission and a stop do; `tests/listings-runs-sql.test.mjs` pins the order.
- **Pending approvals cap** (review finding, 2026-10-22): admission refuses (`approvals_limit`, 409) while the workspace's live pending approvals plus one per product would pass the agent submit's 1,000 cap, before any spend. The propose step retries only `stale_authority`; any other refusal rolls the step back and ends the run as `proposal_refused` (a new end reason), so a run never retries until its Workflow fails. `lab:listings-runs` P1-P2.
- **Stale runs** (a stop or a 30-minute lease end leaves no lease context) are closed in the workspace's own session: every stale run before each admission, and the actor's own by `POST /work/runs-reconcile` (the task screen offers it for an interrupted run; it needs `view` on `task.read`). There is no cross-tenant definer.
- **Run reads are gated** (review finding, 2026-10-22): `view` on `task.read` (404 for a run, 403 for a task's runs) and `view` on `catalog.products.read` on the run's store with its fields (404, or left out of the list); `lab:listings-runs` B8-B9 and `tests/workspace-web-runs.test.mjs`.
- **Ask** takes products by product number until M2 PR-3 brings the catalog picker; the task screen has a Runs tab.
