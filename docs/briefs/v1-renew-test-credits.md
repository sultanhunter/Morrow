## Goal

Today `staging:test-entitlement` gives the owner's workspace 300 test credits for 30 days, once. This PR lets the lead renew them with one command, once per 30-day period, until Shopify billing exists. No money changes hands, and the Anthropic monthly limit stays the outside cap (the credits-only decision of pull request 75, item 6).

```
npm run staging:test-credits -- renew --operator <id>
```

## Scope

- **Migration 0053:**
  - `morrow_billing.operator_test_entitlement_renewals`: one row per renewed period of a grant, with the terms revision its credits came from. It is append-only, owner only, FORCE RLS, and holds one row per grant and period.
  - `renewal_guard`, a BEFORE INSERT trigger on that table (review R1): a renewal record, even one the owner writes by hand, must be the one the renewal would write at that moment. Its grant is of its own account; the route, account, wallet and latest snapshot are that grant's (the function's `route_conflict` rules); its period number and start are recomputed from the grant's grid at the database's clock and start no earlier than the latest snapshot's period ended; its snapshot revision is the next one; its credits and terms revision are the current terms' one operator entry; and the units it adds are exactly the room the wallet's unspent credits leave below those credits, funding the wallet's next revision. Its recorded time is set to the database's clock. Anything else is `BILLING_RENEWAL_INVALID`.
  - `wallet_guard` and `snapshot_guard` are replaced, and only when they still have 0035's exact bodies (md5 pins). The owner may fund the wallet revision a renewal names with exactly the units it added, and only when those units are the room below the renewal's credits and those credits are the current terms revision's operator entry (review R1, so the wallet's rule bounds a funding even without the record's guard). An operator snapshot's successor must be the same grant's renewal for that revision, from the owner, for an active account (review R3), and must start no earlier than the previous period ended. Everything 0035 refused is still refused.
  - `morrow_billing.operator_test_entitlement_renew(operator, workspace, grant approval, standing approval, evidence)`: five closed text values, none an amount. INVOKER, owned by the owner, granted to nobody. It returns `renewed`, `current` (the period that contains the clock is already written, so nothing is written), `grant_missing`, `route_conflict`, `terms_missing`, `not_staging`, `invalid` or `denied`.
- **Periods:** the grant's period is period 0. Period k starts (k − 1) × 720 hours after the grant's period ended and lasts 720 hours. A renewal writes only the period that contains the database's clock, so a lapsed period is never back-filled.
- **Credits** come only from the versioned terms (R10): the current `BillingTerms` revision's one `operator_test_entitlement` entry (300 in staging revision 1), read exactly as 0035's grant reads it, so the source is the one the grant's own credits came from. No argument, record or CLI flag names an amount. A renewal tops the unspent credits (available plus reserved) up to that entry and never above it, so unused credits do not pile up beyond one period's credits. Raising them is a new staging `BillingTerms` revision (ADR-0035 item 4: only with the owner's yes for that use); the next renewal reads it, and the current period keeps the credits it was written with. Since review R2 that yes is checked in code: a revision whose operator entry carries credits other than 300 must name its committed owner record (`ownerRecord`, `docs/evidence/live/<date>-test-credits-raise[-slug].md`, naming the revision, the credits and quoting the owner's words, which name the amount), and `verify:billing` and `seed-platform` refuse it otherwise. The record gates the revision and never supplies an amount. Terms without the one operator entry refuse a due period (`terms_missing`).
- **Committed record** `docs/decisions/test-credits-staging.json`, read at verified `main` as a git blob: the owner's workspace id and the grant's approval reference (`adr-0035.e13.<date>.<n>`, from the grant's printed result), and nothing else (no amount). It is committed unset (`null`), so `renew` refuses (`STAGING_TEST_CREDITS_UNSET`) until a routine commit fills it in. The workspace is never a command-line value.
- **Runner** `renewTestCredits`: one administrator transaction under the D4 SET-row protocol.
  - As `morrow_identity_owner`, it checks that the environment's active live-store app invites this workspace. This check is shared with `grantTestEntitlement`.
  - Then, as `morrow_work_owner`, it runs the function.
  - Only `renewed` or `current` commits. A failed COMMIT after `renewed` is `STAGING_TEST_CREDITS_OUTCOME_UNKNOWN`: rerun `renew`, which reads it back as `current` if it committed.
- **CLI** `test-credits renew`:
  - It is refused in CI, without the standing approval (and its E13), off a clean `main` at `origin/main` with `foundation` green, and on any binding other than staging's.
  - It reads the owner database URL in-process and never prints it.
  - It prints one closed JSON line on stdout. A notice on stderr gives the exact activity-log line to append. That line carries no workspace id, shop domain, store data or secret.

Non-goals: ADR-0026 item 7's `TestEntitlementSeed`, Shopify billing, any change to the grant or checkout, any money cap.

## Security notes

- **Only the owner's workspace.** It must be named in the committed record and invited by the active live-store app (read as the identity owner in the same transaction). Its grant must be the one under the recorded approval reference, and the route, account, wallet and latest snapshot must all be that grant's.
- **Staging only.** The binding must be staging's, the owner URL must name the bound host and database, and the database's mark must say `staging`. Labs and unit tests use fakes or a local engine. CI never runs it.
- **Never a payment.** No receipt, payment event or `credit_grants` row is written. The route, account and grant record are unchanged.
- **Credits from the terms only (R10).** No caller value can change a period's credits; each renewal records the terms revision they came from, in its row, its digest and its result.
- **No new authority.** No runtime login, role or definer gains anything. The function is INVOKER, granted to nobody, and refuses any session, lease or receipt context and any Morrow login. `renewal_guard` is an INVOKER trigger, granted to nobody.
- **The owner role is held to the function's own rules (review R1).** A renewal record or a wallet funding written by hand as `morrow_work_owner` cannot name other credits, another period, a later snapshot or a larger top-up than the renewal would write now, so the wallet never holds more unspent credits than the current terms' operator entry.
- **A raise needs the owner's committed yes (review R2).** Operator credits other than 300 pass `verify:billing` and `seed-platform` only with the revision's committed owner record. Code cannot prove the owner said it; the record makes the yes a reviewed, committed artefact that the tools check, instead of a convention.
- **No money cap is added** (the credits-only decision of pull request 75). The 720-hour period and the top-up rule bound test credits, not spend.

## Lead steps after merge

1. Run `staging:migrate` to apply 0053.
2. Run the grant (`staging:test-entitlement`) if it has not run yet.
3. Commit the record with the workspace id and the grant's approval reference.
4. After the grant's period ends, run `staging:test-credits -- renew --operator <id>`.
5. Append the printed line to `docs/evidence/activity-log.md`.
6. To raise the credits (ADR-0035 item 4), only after the owner's yes in chat for that amount: commit `docs/evidence/live/<date>-test-credits-raise.md` with three labelled lines, each once: `Terms revision:` with `staging.<n>` in backticks, `Credits per period:` with the units in backticks, and `Owner's words:` with the owner's words in double quotes, naming the amount; add staging revision n to `docs/decisions/billing-terms.json` with `ownerRecord` naming that file; merge; run `staging:seed-platform`. The next renewal reads the new credits.

## Review findings

- **F1 (high, AI review, separate context, same model family).** The first draft let the caller name the period's credits (`p_credit_units` with `p_raise_evidence_ref`, from a `raise` member of the committed record), so credits could be funded from a value outside `BillingTerms`. That broke R10, ADR-0022's "the terms stay the only source of credit units" and this PR's own safety test, and it was a material billing change with no accepted ADR. **Fixed:** the two parameters, the `raise_evidence_ref` column, the record's `raise` member, `requireTestCreditsRaiseRecord` and the CLI wiring are gone. Each period's credits are the current terms' operator entry, read as 0035's grant reads it, and the renewal records `terms_revision`. The runner's input is closed to five values, and the psql lab fixture's null binding (added only for the raise) is reverted. Tests: the migration test pins the terms read to 0035's text and the five-value signature; the input, record and CLI tests refuse any amount; lab N cases show that no caller value names the credits, that a new terms revision changes the next renewal's credits but not the current period's, and that terms without the operator entry refuse.
- **F2 (medium, AI review; refuted by a skeptic pass).** The claim: the period grid is anchored at the end of the grant's period, not at the last renewal, so a renewal run late in one period and another early in the next can top the wallet up twice within minutes, more than 300 credits in a rolling 30 days. **Refuted, not changed:** the periods are fixed back-to-back 720-hour windows, exactly like the grant's own period; each window's credits are at most the terms' one operator entry, and a renewal only tops the unspent credits up to it, never above, so the wallet never holds more than one period's credits. That is this brief's reading of ADR-0035 item 3 ("300 credits for 30 days", per period). A rolling-window reading is listed below for the owner.
- **Second review (AI review, separate context, same model family, security lens; 2026-10-26).** F1's fix confirmed. Three low findings, all fixed before 0053 is applied anywhere (the migration is edited in place and its manifest `sha256` updated; it stays 0053, which `main` has not taken):
  - **R1 (low, defence in depth).** The renewal record had no INSERT guard, so as `morrow_work_owner` a forged record (any `credit_units` and `added_units` up to 10^18, an unused period, `funded_wallet_revision` = the wallet's revision + 1) and a matching wallet UPDATE passed `wallet_guard`, repeatably, where 0035's anchor was once per workspace. **Fixed:** `renewal_guard` (BEFORE INSERT) holds a hand-written record to what the renewal would write now (the grant's account, the route and account rules, the period recomputed from the grant's grid, `recorded_at` set to the database's clock, the next snapshot revision, the current terms' credits and revision, and units added equal to the room below them); `wallet_guard`'s renewal funding also needs `v_delta` = the renewal's credits minus the unspent credits (equality, which implies the review's bound), the renewal's terms revision to be the latest, and its credits to be that revision's one operator entry (two entries match nothing, so the funding is refused with `BILLING_WALLET_INVALID`, as the record guard and the renewal refuse them). Lab: the reviewer's forged record and its funding, and eight other forged records, are refused (`BILLING_RENEWAL_INVALID`), while the record the renewal would write is accepted with the clock as its recorded time; with the record guard switched off inside a rolled-back transaction, the reviewer's forgery, a top-up above the room and a stale terms revision's credits are each refused by the wallet (`BILLING_WALLET_INVALID`), and the exact funding is accepted. Unit: the trigger's rules and the wallet's new conditions are pinned in the migration test.
  - **R2 (low, a process gate not in code).** Raising the operator test credits above 300 needed only a merged change to `docs/decisions/billing-terms.json` and to `verify:billing`'s "300" pin, then `seed-platform`; no record of the owner's yes was checked, although ADR-0035 item 4 requires it for every raise. **Fixed:** an operator entry with credits other than 300 is accepted by `verify:billing` and by `seed-platform` only when its revision names `ownerRecord`, a committed `docs/evidence/live/<date>-test-credits-raise[-slug].md` read the way the standing approval's record is read: one `Terms revision` line (`<environment>.<n>`), one `Credits per period` line (the units) and one `Owner's words` line quoting the owner, whose words name the amount. `seed-platform` reads `billing-terms.json` and the record as committed at verified `main` (the same terms, offers and digest as the rows it seeds) before any database statement, and refuses with `STAGING_TERMS_RAISE_UNRECORDED`, `STAGING_EVIDENCE_MISSING` or `STAGING_EVIDENCE_MISMATCH`; a seed with no raise reads nothing more. `renew` never reads the record, and no amount comes from it. Tests: `verify:billing`'s synthetic raise check (refused without a record, with a record of another revision or amount, with words that do not name the amount, with a duplicated line, and a record on a revision that raises nothing; accepted with the owner's record); unit tests of the record reader, the seed rows and `requireTermsRaiseRecords`; and `seed-platform` refusing before any SQL without the record and reaching the database with it. Checked once by hand: a real staging revision 2 of 1,000 credits fails `verify:billing` without `ownerRecord` and passes with a record (reverted).
  - **R3 (low, test gaps).** (a) No renewal test reached `route_conflict`, so dropping the route's `shopify_bound_at` rule or the account's `active` rule went unnoticed, and `snapshot_guard` did not check the account's status. **Fixed:** lab cases, while a period is due (the control renews it in a rolled-back transaction): a suspended, cancelled or pending account and a Shopify-bound route (the superuser drops 0035's variant CHECK inside a rolled-back transaction, since no route row can otherwise hold it) are each `route_conflict`; `snapshot_guard` now refuses an operator snapshot's successor for an account that is not active, with a lab case (refused after the account is suspended; the control without the suspension is accepted). (b) The Stripe-successor check also accepted `entitlement_snapshots_source`, which a NULL `receipt_id` trips anyway: it now requires `BILLING_SNAPSHOT_INVALID` (the guard runs before the CHECK). (c) Only `morrow.work_workspace` of the four context settings was exercised: the session digest, lease and receipt settings are each denied alone. (d) An SQL-level case: each of the five values malformed or absent, called directly, is `invalid` and writes nothing.

## Open questions

- F2's reading: this PR treats "300 credits in 30 days" as at most 300 per fixed 30-day period. If the owner reads it as a rolling 30-day window, the renewal needs a minimum gap since the last top-up (a non-money stop condition, not a money cap); that would be a routine follow-up.

- Raising the owner's test credits is a staging `BillingTerms` revision. ADR-0039 (pull request 75, accepted 2026-10-25 and on `main` since this branch was cut) names that mechanism under its Consequences. Under ADR-0035 item 4, each raise needs the owner's yes in chat before the revision is published; since review R2 the revision must name the committed record of that yes, which `verify:billing` and `seed-platform` check. If the owner wants another raise mechanism, it needs its own decision; this PR builds none.
