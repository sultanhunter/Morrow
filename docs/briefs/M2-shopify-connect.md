# M2 Shopify connect

- Status: brief, 2026-10-19 (revised after critique). Spine: [mvp-architecture.md](mvp-architecture.md) §3–§6, §10–§11. Material choices: ADR-0022 items 2–9, 13–15 (accepted 2026-10-19).
- Plan IDs: P08.T01a, P08.T02a, P09.T01a, P09.T02a, P09.T05a, closing the P05.T03 linking path. Branch `claude/m2-shopify-connect`; three PRs.

## Goal

A paid beta workspace connects one Shopify development store through its private install link. Morrow holds the offline token in the broker vault, links the store through the existing P05.T03 handoff, grants the owner store-level catalogue permissions, reads products, and handles uninstall and the compliance topics before any real store connects.

## Flows

1. **App registration (owner-run).** Claude prepares `shopify.app.<appKey>.toml` per beta store: `embedded = false`; `[access_scopes] scopes = "read_products,write_products"` with an explicit install-flow setting; `[auth] redirect_urls = ["https://<connector>/shopify/a/<appKey>/callback"]`; `application_url` the launch path; `[[webhooks.subscriptions]]` for the five topics, with `compliance_topics`. The owner deploys it with the Shopify CLI, picks custom distribution and generates the link in the Dev Dashboard, stores the client secret with the vault script, and runs an audited script that inserts the `shopify_apps` row. The first install from the custom link is proven on the development store before PR-2 closes.
2. **Launch.** Shopify opens `/shopify/a/:appKey/launch`. `shopifyLaunchVerify` checks the query HMAC and the shop against `*.myshopify.com` and the registry. With an active installation, the connector shows status and links to Morrow; there is no new OAuth. Otherwise it stores a state digest (10 min, single use), sets a `__Host-` state cookie on its own host and redirects to Shopify's authorize URL.
3. **Callback.** The cookie must match the state row. `shopifyInstallComplete` checks the HMAC and timestamp before it claims the state (an unverified callback consumes nothing; PR-2 review), exchanges the code (non-expiring offline token), compares expanded scopes, writes the vault and reads `shopIdentity`. A first install writes the candidate (`proof_kind: shopify_oauth`), the `store_installations` row and a continuation for the invited workspace, then redirects to the api origin with the token in the fragment. A callback for an existing installation re-authorises that row (a new credential version, the old one destroyed) and creates no candidate.
4. **Link.** The signed-in owner's SPA posts `{handoffToken}` to preview. The issuer checks the continuation, that the app's invited workspace equals `:ws`, that the actor is the organization's owner (its founding principal, to whom ADR-0022 item 3 gives the store-link grants; PR-2 review), a current `governance.connection.connect` `administer` grant, and that the route is `morrow_direct`. Apply is `link_workspace_store`, which rechecks the owner and the app's status, refuses unless the route is `morrow_direct`, and issues the store-link grants. Only the owner is offered the install link. It never sets `shopify_bound_at` (ADR-0022 item 5 and the 0020 variant check; recorded at PR-2).
5. **Uninstall.** The `app/uninstalled` webhook marks the installation `uninstalled`, calls `shopifyCredentialDestroy`, writes a connection stop (`StopRecord@1`, actor `system`) and revokes leases. Unsent operations become `conflict` at their dispatch check.
6. **Redaction.** `shop/redact` runs every registered handler for the store. `customers/*` record "no customer data held". Each completes with evidence in `privacy_requests`.

## Security notes

- **Broker-only credentials (invariant 11):** the connector binds no Shopify secret (ADR-0008 item 2). App secrets and tokens are decrypted only inside the broker, one vault row each, so one rotation touches one row.
- **Connector context is not a session:** the connector has its own host, so `__Host-morrow_session` never reaches it; linking still needs the human session and grant on the api.
- **Server-resolved tenancy (invariant 1):** the workspace comes from the app registry and the session, never from `shop`, `host` or a query value.
- **Webhooks:** raw-body HMAC before any parse; 401 with no state change on failure; `customers/*` bodies minimised before the insert; durable insert before the 200, within a 3-second budget (otherwise a 5xx, and Shopify's retry is de-duplicated by webhook id); never assume ordering.
- **Deletion before data (invariant 16):** PR-3 and its labs pass before any non-development store links.
- **Default deny (invariant 3):** an unknown app key, an unregistered shop or a missing configuration returns the existing fail-closed response; `npm run smoke:scaffold` keeps the "unconfigured connector fails closed" guard.
- **Database:** every new table is in the tenant-conformance registry, with the two lease probes of spine §5. Tenant-keyed references are composite foreign keys, and one shop has at most one installation that is not uninstalled, under any app (PR-2 review).
- **Connector ingress (PR-2 review; holds before the connector hostname is enabled).** The threat: launch, status, callback and webhook requests are anonymous, and each opened a transaction on the broker's vault login (`CONNECTION LIMIT 10`) before any signature check, so a flood could hold every connection and fail install stores, the PR-3 compliance webhooks and M5's Stripe receipts (availability only; no tenant data crosses and nothing is authorised). The layers, outermost first:
  1. The connector counts every broker-bound request per hashed client address (`CF-Connecting-IP`, the P05.T01ab key) before any broker call: `INSTALL_LIMITER` (launch, status and callback) 20 a minute, `WEBHOOK_LIMITER` 300 a minute. Webhooks are keyed by address, not app key: an unknown app key would be a fresh budget, and a public one would let anyone starve that store's deliveries; the higher limit leaves headroom for Shopify's delivery addresses, which carry every store's webhooks. Over the limit is 429; a missing address or a failed limiter is 503 with one fixed-code `morrow_connector_guard` line. The bindings are pinned per environment by `verify-config` (`EDGE_CONNECTOR_RATELIMITS`; namespaces 7004-7005, 7104-7105, 7204-7205) and required outside development. Workers rate limits count per Cloudflare location.
  2. In the broker, before any vault transaction, a request must be shaped like Shopify's: an `hmac` of 64 lowercase hex, a timestamp within 90 s and no `signature` parameter, or a webhook's headers with a base64 HMAC of 32 bytes. An isolate that read the app's secret from the vault within the last 60 s verifies Shopify's HMAC first, so a forged request for a known app reaches no database; the callback verifies inside the claim transaction before the claim, so an unverified callback consumes no state. A rotated app secret is honoured within those 60 s. An older held secret (up to an hour) still lets a request it verifies count as verified for the slots below, so Shopify's own traffic is not starved by anonymous traffic; a request it does not verify reads the vault.
  3. Per broker isolate, at most one ingress transaction whose signature could not be checked first (an app whose secret the isolate does not hold, or an unknown app key) and three ingress transactions in all run at once; one more is held (`INGRESS_BUSY`: the connector answers 503 and Shopify retries webhooks). The install store, which follows a successful code exchange, is not ingress and is never counted.

  **Global bound and residual risk.** Anonymous ingress holds at most one vault connection per broker isolate, and all ingress at most three; one address at one location sends at most 320 broker-bound requests a minute and holds at most one connection per broker isolate it reaches. The number of broker isolates is Cloudflare's, so the bound is not global: an attacker with many addresses reaching many locations at once, using unknown app keys (never cached), can still hold the login's ten connections. Installs, webhook verification and, after M5, Stripe receipt recording then fail closed for the attack's duration (Shopify and Stripe retry; an install relaunches). A hard global bound needs a coordination point the stack lacks: a separate ingress database login with its own connection limit (an ADR-0022 item 8 amendment, credential custody) or a Durable Object semaphore (a provider selection). Accepted for staging with development stores only; revisit before production (ADR-0007 item 9) or when staging logs show `INGRESS_BUSY`. Owner decision, 2026-10-21, in chat. The question was: "The Shopify connector is public, so a flood of fake requests could tie up the broker's 10 vault database connections. Three layers now protect it: per-address rate limits, Shopify signature checks before any database work, and a per-instance cap. A hard global cap would need a separate database login just for Shopify traffic. What should we do?" The owner answered: "Accept for staging (Recommended)". The option read: "The three layers are enough for staging with development stores only. We revisit the separate login before production, or sooner if staging logs show 'busy' errors. Recorded in the M2 brief."

- **Catalogue reads (M2 PR-3 review).** The catalogue routes are signed-in but not rate limited, and each read resolves its lease in one transaction on the broker's vault login (`CONNECTION LIMIT 10`), which ingress, install stores, credential destructions and Stripe receipts also need. Per broker isolate at most two read resolutions run at once (`shopifyReadSlots`); one more is held (`READ_BUSY`, the api answers 503 `unavailable`) before any transaction, and ingress keeps its own three slots. The Shopify call itself holds no connection. Like the ingress cap, the bound is per isolate, not global (the residual risk above); a per-session Workers rate limit on the catalogue routes is a later option.
