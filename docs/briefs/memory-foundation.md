## Goal

The data model every later memory layer builds on, before any notebook entry exists: notebooks keyed by agent principal with the fields ADR-0041 item 27 names; the lineage, repair and settings tables; and the server side of `memory.search` and `memory.read` with every layer's predicates (read tags, source subjects, audience) applied in SQL before ranking, so nothing a run may not read is ever ranked, counted or returned.

## Scope

- **Migration 0057** (executes as `morrow_work_owner`):
  - `pg_trgm` 1.6 in its own schema `extensions` (owned by the work owner; `USAGE` for the command role only, never an executor login or the api role), for the trigram half of hybrid lexical search (item 30).
  - **Notebooks re-keyed by agent principal**, guarded on empty tables (`MEMORY_FOUNDATION_NOTEBOOKS_NOT_EMPTY` otherwise) and on 0052's exact columns, constraints and guard (md5-pinned). An entry gains `kind` (`lesson`, `correction`, `procedure`, `shop_fact`, `open_question`), `title`, `taint` (kinds and up to 256 sources, the rest counted), `derived_from` (at most 64 notebook entries and knowledge pages, closed over pages), `audience` (workspace, subject or principal; never a principal for a notebook), `source_subjects` (at most 32 goals, tasks and conversations), the requester (principal and membership), renewal (count and time) and use counts, and the 90-day clock from its last write or re-affirmation. Its text is indexed in the same row (`simple` tsvector and trigram text, both expressions of title and text), so erasing the text erases its index in the same UPDATE. Live entries per notebook: at most 1,000 (a safety range; consolidation, H12d, tends it long before).
  - `agent_notebook_renewals` (content-free, append-only: one row per tool call that re-affirmed an entry, so the call's replay finds the entry it renewed however many calls renew it after), `memory_derivations` (content-free lineage: one row per derived row and source), `memory_repairs` (content-free flags: an entry erased because its source was, an entry whose page changed, a clean entry a tainted run tried to replace or retire), `memory_settings` (one row per person: personal memory on or off and its default scope; H12b writes it).
  - **Definers**: `run_notebook_write_v2` (add, replace, retire under the run lease), `run_memory_search` (up to five queries over the notebook and knowledge layers, at most 20 hits), `run_memory_read` (one item in full; counts a use), `cmd_notebook_clear_v2` (a person, at the revision their check read). 0052's `run_notebook_write` and `cmd_notebook_clear` stay registered and fail closed on the re-keyed tables (their statements name a dropped column).
  - **The deletion path**: triggers make every erasure path follow the source. A deleted knowledge page erases every live entry derived from it (directly or through lineage), a cleared or source-erased entry erases the entries derived from it, each in the same transaction and recorded as a repair; a page's new version flags them (stale, never expired). `memory_erase_expired` is the 90-day clock's handler for the daily sweep (bounded batches; its schedule comes with the sweep).
- **Code**: `@morrow/policy/memory` (closed shapes, the read predicates and lineage unions as SQL's oracle, the identifier backstop, `notebookTitleFrom`, the bounds); `decideNotebookWrite` (the v1.1 `{text}` input: an add of a lesson titled from its first line) and `decideNotebookOperation` (add, replace or retire with sources: tool catalogue version 4's seam); `KnowledgeRunFacts.memory` (the loop's memory facts); `notebookWriteStep` and `notebookOperationStep` on the v2 definer, with typed effects (`applied`, `renewed`, `flagged`) and replays; `packages/work/src/memory/run-steps.ts` (`memorySearchForRun`, `memoryReadForRun`, closed decoders); the notebook routes on the re-keyed notebook (the clear on v2; the read shows the newest 100 entries the viewer may see of up to 1,000); `redaction.ts`'s handlers for the clear, source erasure and the clock.

## Security notes

- **Tenant isolation**: composite tenant keys, ENABLE and FORCE RLS on the four new tables with the owner's maintenance policy, the session template and its lease twin; the api role reads repairs and settings column by column in its tenant, never the lineage or the renewals; no runtime role holds DELETE or TRUNCATE. Tenant, run, agent and requester come only from the entered lease (`memory_lease_agent`: a run lease of an active installation and that installation's agent principal); no definer takes a tenant or principal argument.
- **Predicates before ranking** (ADR-0041 items 25 and 30): the search's candidate sets apply, in SQL, the owning agent (a run reads only its own agent's notebook), liveness and the clock, read tags within the run's viewable set, every source subject within its subject view, and the audience readable by its output's audience; ranking (reciprocal-rank fusion of full text and trigram word similarity, k = 60, with small trust, recency and use priors) and the limit apply after. The read applies the same predicates; out of reach is the same as absent. Private-Ask content (a principal audience) reaches only that principal's private runs; a notebook never holds it.
- **Writes name only what the run could read**: a replace or retire target and every source must pass the same predicates as a read by the run, so a write cannot touch or launder memory outside its view. Never from a private Ask (`not_offered` in code, `ask_bound` in SQL), never after customer data (the `support.case.read` tag, `customer_data`), never after person memory (`authority_denied` in code, `person_memory_loaded` in SQL); email addresses and Shopify customer ids are refused by a SQL backstop the code mirrors (H9a's screen comes first and covers more). Taint, tags and subjects union over every source and the narrowest audience wins; taint is sticky.
- **A tainted run only flags a clean entry** (item 27): its retire leaves the target live and writes a repair naming the run and the call; its replace adds its own tainted entry derived from the target. A tainted run never re-affirms a clean entry, and its reads (and any read of a tainted entry) raise no use count. Nor does it supersede one: at the 1,000-entry cap the write supersedes the least recently renewed entry, never the call's own target and, for a tainted run, only a tainted one; with none, the call is refused (`notebook_full`) before it flags or writes anything (lab M13).
- **Bounds the code cannot see** are refusals, never a held step the loop would retry forever: what the unions over the run and its sources carry past an entry's bounds (`too_many_subjects` past 32, `lineage_too_large` past 64 references with the pages closed over and a replace's target, `tags_overflow` past 24 with the store's artifact tag) answers `invalid_input`; a full notebook a tainted run may not make room in, or a notebook whose million sequences are used (`notebook_exhausted`), answers `pending_limit`. The definer's `invalid` is kept for inputs the code validates first.
- **Idempotent per tool call**: a replay returns what the call did (the entry it wrote or renewed, its retire, its flag), before any check that depends on state the first call may have changed; the same call id with other content is a defect, never a result the model sees. A renewal's replay reads the call's own row in `agent_notebook_renewals` (append-only), so a later call's renewal of the same entry never makes it renew again, and after the entry is erased it still returns that entry, never a new one (lab M3).
- **Lock order**: knowledge pages, then notebooks, then entries, everywhere. The write locks the pages it names (directly or through its sources' lineage, `FOR SHARE`, in id order), then its notebook, then entries; the clear, its notebook, then entries; the deletion path (`memory_erase_derived`, `memory_erase_expired`) locks the notebooks of the entries it erases (`FOR UPDATE`, in agent principal order) before any entry. A page deleted under a write waits for it and then erases the new entry with the page (lab M6); a clear racing a page deletion makes the deletion wait at the notebook, never deadlock (lab M12).
- **People's view** (until H9c): a person sees an entry only when they may view every tag and its audience is the workspace with no source subject; a project-scoped entry is hidden from everyone on the agent page and blocks a clear (403) until that project's run retires it. Hidden, never shown by default.
- **Owner's environment**: the deployed notebooks are empty (`agent_tools` is committed off, so nothing writes them), so the guard passes there. `pg_trgm` is a trusted extension (PostgreSQL 13+): the work owner holds `CREATE` on the database (`infra/work-role-prerequisites.sql`), which the lab's Neon-shaped createrole administrator reproduces; whether Neon lets that role create it is not yet measured (below).

## Open questions and what is not built here

- **Neon and `pg_trgm`**: the lab proves a non-superuser work owner with database `CREATE` installs it; whether Neon's compute allows a role that is not `neon_superuser` to create a trusted extension is not measured. If it refuses, 0057 fails whole at the staging runner (one transaction) and a reviewed prerequisite (`CREATE SCHEMA extensions` and `CREATE EXTENSION pg_trgm` by the administrator) replaces those two statements before the apply.
- **Refusal codes**: v1.1's `ToolRefusalCode` has no `ask_bound`, `person_memory_loaded`, `notebook_full`, `notebook_exhausted` or overflow codes; the code answers `not_offered`, `authority_denied`, `pending_limit` (a full or exhausted notebook) and `invalid_input` (`too_many_subjects`, `lineage_too_large`, `tags_overflow`) until H5's contract edit adds precise codes. A run whose own 24 read tags lack the store's artifact tag gets `tags_overflow` for any write, which no input change cures; H5 or the loop's tag budget should name it.
- **People's subject view** is H9c's: until then project-scoped entries are hidden on the agent page and block a clear.
- Not built here, each with its row: `memory.read`'s other kinds (result items, teammate results, message ranges and the context's labels), which come with their tables (H7a, H7d, H10, H12c); the agent loop's calls (H7, H10, H11), tool catalogue version 4's inputs (H5), NotebookEntry@2 and MemorySearchHit@1 (H6), person memory and Settings › Memory (H12b, which first writes `memory_settings`), summaries (H12c), read-back, consolidation and Morrow's notebook (H12d), pins and descriptions (H12e), the recall eval and the embedding record (H12f), the sweep's schedule, and notebook erasure at agent uninstall.
