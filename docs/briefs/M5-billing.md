## Goal

A website workspace picks the beta plan, pays through Stripe Checkout in test mode, and becomes billable only when Morrow has verified the payment server-side. Morrow then fixes its route to `morrow_direct`, grants the plan's credits to its wallet, and shows plan, credits and usage. Live mode waits for M6.

Owner decision (c), 2026-10-21: M5 merges with Stripe switched off on staging. The reviewed Stripe switch (below) is off, so checkout, the portal and the webhook answer `unavailable`, no Stripe secret is required and deploys keep working, while credits, the wallet, entitlements and the receipt definers work as built. Until the switch is turned on, a staging workspace gets its beta plan from the staging test entitlement of decision (b), a separate small PR that amends ADR-0022 item 5, not from this path.

## Scope

- **PR-1, server:** `governance.billing.manage` and the signup template v2 backfill; the M5 `morrow_billing` tables (spine §6); the route-row writer in the signup transaction; the purchase guard and routes; Stripe operations (kind `stripe_write`, `taskId` null) on the M2 `operations` table; the webhook route; broker `stripeCustomerEnsure`, `stripeCheckoutCreate`, `stripePortalCreate`, `stripeWebhookVerify` on one pinned API version; payment classification, entitlement fold and credit grants.
- **PR-2, screens:** `/w/:ws/settings/billing` (plan, status, "Choose plan", "Manage billing") and `/w/:ws/settings/usage` (credits available, reserved and used; runs and their charges). Every purchase link and wording comes from `billingCallToAction`.

## Non-goals

Shopify App Pricing; top-ups, coupons, trials, proration and plan changes; dunning email; automated conflict remediation (P18.T01c); invoices inside Morrow (the portal shows them). Moved to M6, before live money: refunds, disputes, held-payment handling and `payment_reversals`, and Stripe Tax registrations (or Managed Payments).

## The Stripe switch (owner decision (c), 2026-10-21)

- **One committed field.** `switch` in `docs/decisions/stripe-staging.json`: `"off"` (committed) or `"on"`, checked by one rule (`reviewedStripeRecord` in `scripts/edge.mjs`) that `edge:check` and the staging tools share. It governs staging only: development's committed config may name no reviewed identifier (PR-D), so it is always off there (local Stripe runs are the labs', with bound fakes), and production holds Stripe until the ADR-0007 item 9 custody ADR (12 names; `brokerRequiredSecretsFor("production", "on")` throws).
- **Runtime image.** The api's and the broker's var `MORROW_STRIPE_MODE`, exactly `"test"` while on and absent while off. The api maps it in step 11 of `mapApiEnvironment` (absent is off; any other value keeps the api on its deny-all instance) and composes no broker Stripe port while off. The broker reads no Stripe secret or configuration while off (`stripeMode: "off"` on its init line).
- **Off (now).** `brokerRequiredSecretsFor("staging")` and the broker's wrangler `secrets.required` in development and staging are the 14 names the deployed broker holds; gate 6, `secrets-status`, `provision-roles --first` (no Stripe file read) and the first-deploy file agree, and `staging:put-secret` refuses both Stripe names (`STAGING_STRIPE_OFF`) before any effect. Each ApiBroker Stripe method is `BROKER_HELD` with the fixed code `STRIPE_UNAVAILABLE` before its inputs, with no vault transaction and no Stripe request. `POST .../checkout` and `POST .../portal` answer the fixed `503 unavailable` envelope after the request guard and before any database access or broker call (log outcome `stripe_off`); `GET .../morrow/plans` offers neither action, so the billing view's call to action is none wherever it would be the Morrow plans link ("Choose a plan" or "Manage plan"; `billingViewCallToAction`); `POST /api/billing/stripe/webhook` answers `503 {"code":"unavailable"}` before reading its body. The billing view's plan, credits and period, the wallet, entitlements, the receipt definers, the terms seed and `staging:billing-customer-resolve` are unchanged.
- **Mixed states are refused.** `edge:check` (`EDGE_STRIPE_SWITCH_MIXED`, with `EDGE_VARS` or `EDGE_BROKER_SECRETS`): off, any Worker carrying `MORROW_STRIPE_MODE`, `STRIPE_CONFIGURATION_JSON` or a Stripe secret; on, the staging api without its mode, or the staging broker without its mode, its configuration (byte-equal to the record) or either secret; on without a recorded portal configuration (`EDGE_STAGING_STRIPE_RECORD`); an unreadable or invalid record counts as off. Gate 4 holds the deployed vars to the switch (`STAGING_STRIPE_SWITCH_MIXED`) and gate 6 the broker's secret names.
- **Turning it on** is one reviewed commit plus the two secrets: (1) the owner's Stripe test-mode steps below, each under per-action approval with a `docs/evidence/live/` record, and the two owner files placed with `morrow_put`; (2) one reviewed PR that sets `switch` to `"on"` with the portal configuration id and `observed_on`, adds `MORROW_STRIPE_MODE: "test"` to the staging api's and broker's `env.staging.vars` and the byte-equal `STRIPE_CONFIGURATION_JSON` to the broker's, and adds `STRIPE_RESTRICTED_KEY` and `STRIPE_WEBHOOK_SECRET` to the broker's `env.staging` `secrets.required` (`edge:check` names anything missing); (3) after the merge, `npm run staging:put-secret -- STRIPE_RESTRICTED_KEY` and `-- STRIPE_WEBHOOK_SECRET` (gate 6 stops every deploy, uploading nothing, until both are placed); (4) a deploy, then the owner-approved test-mode smoke.
- **Turning it off again** follows gate 6, which holds the deployed broker's secret names exactly to the committed switch, so the off commit's deploy can pass only after both Stripe secrets are gone, and no deploy of the on state can pass once they are: (0) a quiet point (no checkout open, no Stripe operation unsettled; while off none is reconciled and no webhook is read); (1) one reviewed PR, the reverse of the turning-on commit (`switch` `"off"`, both vars and both `secrets.required` names removed; `edge:check` refuses anything partial); (2) it merges and its deploy stops at gate 6 (`STAGING_BROKER_SECRETS_MISMATCH`), uploading nothing, so staging keeps running the on version; (3) straight after, the owner removes both secrets with `npx --no-install wrangler secret delete <NAME> --config apps/broker/wrangler.jsonc --env staging` (`staging:put-secret` refuses the names while off and no staging command deletes a secret), each under per-action approval with a `docs/evidence/live/` record; (4) the stopped deploy is rerun, gate 6 passes, and `staging:secrets-status` shows the broker's 14. Between (3) and the api's upload in (4), checkout and the portal answer `503 uncertain` (their operation waits for the same key's retry once the switch is on again, and goes into STATUS as an open unknown outcome) and the webhook `503`, so (3) and (4) run back to back. `infra/rotation-runbook.md` has the full procedure.

## Flow

1. **Signup:** the creating transaction writes the route row with origin `website` (persistence item 1). Existing workspaces are backfilled `website`.
2. **Checkout:** `purchaseDecision` must allow `morrow` in phase `open` with no `shopify_bound_at`; `execute` on `governance.billing.manage`. Under the route-row lock, close any open intent past its `expires_at`, then record a checkout intent (one open per workspace) and its operation. The broker loads the operation, ensures the mapped customer (idempotency key bound to its operation), and creates a subscription-mode session with `customer` (never `customer_email`), the price from `BillingTerms`, `expires_at` one hour ahead, and the operation and workspace ids in both `metadata` and `subscription_data.metadata`. Billing address collection and `automatic_tax` follow configuration (off in test mode). The success return proves nothing.
3. **Webhook:** the api passes the raw body and `Stripe-Signature` unparsed to `stripeWebhookVerify`. The broker verifies over the raw bytes (5-minute tolerance), checks `livemode` and the account, de-duplicates by event id, reads the object back, and records a `stripe_event_receipts` row with the object digest.
4. **Apply:** the api applies only a receipt the broker recorded with a matching digest. `classifyPayment` decides, with the operation id read from the invoice's subscription metadata. On the first paid invoice (`billing_reason` `subscription_create`) of a `subscription_period` in phase `open`, Morrow fixes the route to `morrow_direct`, creates the account, writes the `VerifiedPaymentEvent`, and grants credits once per `(route, mode, paymentKey)` to the wallet in the same commit. A held, unattributed or mismatch outcome is recorded on the receipt and logged for the owner. Subscription updates fold through `foldEntitlementEvidence`. `checkout.session.expired` closes its intent. The handler returns 200 after commit; an unknown commit is read back before any acknowledgement.
5. **Portal:** a session on the mapped customer, through the saved portal configuration (its id in configuration). Cancellation folds to `active` until the period ends, then `cancelled`.

## Security notes

- **Broker-only credentials (invariant 11):** the restricted key and webhook secret bind only to the broker; `mapApiEnvironment` rejects `STRIPE_` bindings on the api.
- **Ids only across RPC:** every Stripe method takes an operation id; the broker loads the customer mapping, price and metadata from the database.
- **Server-held route:** clients, return URLs, metadata and price keys never set the route; a workspace with `shopify_bound_at` never reaches checkout.
- **Reconcile before retry (invariant 10):** every Stripe write carries an idempotency key bound to its operation; on an unknown outcome the broker reads back first and replays with the same key only after proving absence, within 23 hours (persistence item 6).
- **Credits only from confirmed payment:** grants come from `BillingTerms` and a read-back paid invoice, never from Checkout success or a client.
- **Tenant from mapping:** the event's workspace comes only from the customer mapping, cross-checked with the operation in the subscription metadata.
