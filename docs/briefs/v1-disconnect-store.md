# v1 PR 2: Disconnect store

- Status: brief, 2026-10-23. Branch `claude/v1-disconnect-store`. The v1 build order's PR 2, its "Disconnect store" part only: the Claude switch stays off and is not part of this PR. Change class: material (authority, a v1.1 contract and credential destruction), already owner-approved: owner decision 8 of 2026-10-22 (ADR-0022 items 2 and 3 amendments, recorded in ADR-0022's Amendments), with ADR-0022 items 13 and 15, ADR-0005, ADR-0025 and ADR-0031 item 3. No new decision is taken here.

## Goal

A person who holds `governance.connection.disconnect` on a store can end that store's connection inside Morrow, at once and for good in this release: no agent run, read or gateway apply can touch the store afterwards, the offline token is erased from the broker vault, and the installation is marked disconnected. Spine §10 and owner decision 14 require this before the first Claude call.

## Scope

- **Grant (store-link template v2, ADR-0022 item 3 as amended).** Migration `disconnect-store-identity`: `morrow_identity.store_link_grants_v2()` is version 1's four rows plus `governance.connection.disconnect {execute}` (fields `connectionId`, `control`); `link_workspace_store` is v1 PR 1's text (0039: 0026's, with the owner's live store linkable) with exactly the template version changed (pinned by md5 in the prerequisites and by `tests/listings-authority.test.mjs`). The one forward backfill gives that grant, once, to the linking owner of every store still linked (the holder of version 1's `agents.installation.activate` row issued by `morrow.linking` on that store resource), at the organization's current policy revision. Nothing else is issued, revoked or revised. `packages/policy/src/store-link-template.ts` is the TypeScript twin (`storeLinkGrantTemplate` v2, `storeLinkGrantTemplateV1`, `disconnectFields`).
- **Record (core v1.1, ADR-0022 item 2 as amended).** `KillSwitchConnectionTarget` `{kind: connection, id: connectionId, storeId, connectionId}` is a `KillSwitchRecord` target beside the v1 `ResourceRef`s; `validateCurrentDefinition("KillSwitchRecord")` adds the code rule `id === connectionId`. It is a record target only, never a grant or scope resource.
- **Command.** Migration `disconnect-store-work`: `kill_switch_records` accepts the pair `governance.connection.disconnect`/`connection` (target id = connection id), `kill_switch_record_matches` checks it, `commands` accepts `connection.disconnect`. Definers (api login only, tenant from `current_tenant()`): `begin_connection_command` (replay first), `connection_target` (ids and status of a connection ever linked here) and `cmd_store_disconnect`: in one transaction, the prelude's locked authority recheck, the installation's end through 0036's `work_shopify_installation_end` (`suspended`, `disconnected`; open handoffs and continuations end), then under the store's stop interlock the `KillSwitchRecord` and, unless a connection stop already stands, the person's connection stop (`human_disconnect`), whose `stop_guard` revokes every read, run and operation lease on the connection; `kill_switch.executed`; the recorded result.
- **Routes** (`packages/work/src/connections/`; `docs/contracts/work-api.md`, "Connection routes"): `GET` and `POST /workspace/:ws/connections/:connectionId/disconnect`, a new row of the api Worker's dispatch table (every other `/connections` path stays the managed handler's). The Worker runs the human kernel (`execute` on the store resource, `kill_switch_record` obligation, no entitlement) and `checkKillSwitchTarget` (`planDisconnect`) before the definer. After COMMIT, one `ApiBroker.shopifyCredentialDestroy(installationId)` (new; the broker fixes the reason `disconnected`, so the api can destroy only a token whose installation records a person's disconnect); anything but a confirmed destruction is reported `pending` and the connector's cron re-drive finishes it. A replay asks the broker again (idempotent).
- **Screen.** The connection page's "Disconnect store" card: the button only when the server says this person may, a dialog that says what happens, a required reason, and the reconnect note (a new install is needed; a disconnect cannot be undone here). The Listings card remounts and shows the store blocked.

## Security notes

- Person only: an agent never holds the grant (only `morrow.linking` issues it, to the linking owner), `planDisconnect` refuses any non-human actor, and the definer takes the actor from the session. Agents may only propose stops (ADR-0005); there is no proposal path in the MVP (`sourceProposalRef` must be null).
- Authority is decided in code, before the definer: the human kernel on the exact store resource with its connection, then the kill-switch target check over the actor's current execute grants; the definer's prelude rechecks under lock that the authority the kernel read is still current (`stale_authority` otherwise), as for "Stop AI work". The definer itself does not re-evaluate the grant (the existing kill-switch pattern); the Tier 2 review should keep this in view.
- Tenant isolation: no tenant, store, installation or actor value comes from the client; the connection id is resolved against the session tenant's installations only (another tenant's or a never-linked connection is 404 and writes nothing).
- Fail closed and idempotent: refusals roll back everything; a lost reply is `uncertain`, never success; the same key replays the recorded result; a new key on a stopped connection records `already_stopped` and changes nothing else.
- Credentials: the token is destroyed only by the broker's vault definer, never read; the api passes an installation id alone; no token, secret or reason text reaches a log or a response (`lab:disconnect-store` O1).
- Retention: a disconnect deletes no store content and starts no deletion clock (ADR-0031 item 3); `shop/redact` and the uninstall's path still do.
- Lock order: the per-shop install lock, then the store's stop interlock, the same order as the connector's applier, so a concurrent uninstall cannot deadlock with a disconnect.
- The gateway apply (v1 PR 3) does not exist yet: its claim and dispatch must check the same connection stop (`stop_active(..., 'operation', ...)`), which this PR proves already refuses an operation lease on a disconnected connection.
