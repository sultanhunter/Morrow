## Goal

One durable job runner for every agent (`AgentRunWorkflow`, `agent-run@1`), in which the model calls Morrow's tools, each call is checked in code at call time and recorded, and a run can wait for a person's answer. Everything ships behind the agent-loop switch, committed off; nothing here can start a run on staging.

## Scope

- **Records** (migration 0047, `morrow_work`): `agent_runs` (the pinned AgentRunManifest@1, caps, hold, counters; ids, digests, codes and amounts), `run_turns` (the only place loop content lives: each turn's input, the reply, the tool results; 90 days after the run ends; reasoning stripped at the end), `run_tool_calls` (RunToolCall@1, ids and digests; 365 days), `agent_model_calls` (the broker's turn fence), `agent_run_questions`; the loop catalogue v2 (`loop_catalogue_versions`, `loop_catalogue_entries`, committed `proposed`) and ToolCatalogue v2 (`tool_catalogue_entries`), drift-tested against the generated data. FORCE RLS on all eight; no DELETE or TRUNCATE.
- **Admission** (`packages/work/src/loop/admission.ts`, `cmd_agent_run_admit`): a person's routed run of one installed agent on one store. The switch first (`switch_off` before any statement), the manifest in code, then one definer that re-checks the task, store, stops, installation and release, takes only an `active` catalogue version, derives the caps and the hold (the turn limit lowered so it times the worst-case turn fits US$7), requires the operator test entitlement (ADR-0027 item 6), closes the workspace's stale runs, counts the daily backstop and the period's unrecovered cost, and writes the lease, child task, envelope, Coordinator grant, hop and run. Its manifest CHECK proves the canonical text is exactly the run's columns. The answer (`cmd_agent_run_answer`) is the requester's only and opens the resume lease.
- **The runner** (`packages/work/src/loop/runner.ts`, steps in `steps.ts`): durable steps carry ids and codes only; every step re-enters the run lease. Before each turn, in code: the turn limit, the hold left against the entry's worst-case turn (a final turn, `tool_choice: none`, when it cannot also cover one after), the wall time (waits excluded) and the lease's time against the call's whole budget. An uncertain turn is booked at its worst case and sent again at most once; a throttle resends with the next sequence; a lost reply is read back from SQL, never resent; a broker hold that left nothing in SQL (no fence, so no request: a transient database or binding failure) is tried again at most twice, after 5 and 10 seconds, before the run ends `provider_error`. Each tool call: lease re-entry, replay of a recorded call, the full ToolInput validation, ids in scope, the authority decision in code, the handler. The end reason is derived in code.
- **Authority per call** (`authority.ts`): `decideDelegation` over facts read again in the call's own step (`delegation_facts`, `run_billing_facts`): the requester's live grants with delegate, the envelope and the Coordinator's hop, the installation's grants and scope, the installation owner's authority, the policy revision, the store association and stops, the entitlement. Any one failing refuses the call (`authority_denied`, or `stopped`); missing facts refuse it.
- **Untrusted content** (ADR-0027 item 5): the request is the one text block; tool results enter only as tool results whose content names their `source`; a result carrying store, email or upload text taints the run; data blocks are wrapped by the adapter so they cannot close their wrapper. Tools, recipients and caps come from the manifest and SQL, never from text. The requester's answer enters the next turn as a text block (their own words, as the request is).
- **The broker** (`apps/broker/src/agent-turn-gateway.ts`, `claude-turn-adapter.ts`): `RuntimeBroker.modelTurn` holds every call (`MODEL_UNAVAILABLE`) unless both the model-provider and the agent-loop switches are on, checks ModelCall@2 by hand (no model, effort, tool list, limit or provider), refuses `prefix_mismatch` before any request, fences the turn in SQL (`morrow_vault.agent_turn_begin`/`agent_turn_end`), reads the selection, offered tools and system text from the run, counts, sends once, checks the reply against the run, and books the cost at the entry's rates (overflow never dropped). Strict tools, adaptive thinking, the effort, the system text cached for five minutes.
- **The orchestrator** (`apps/workers/src/orchestrator.ts`, `agent-run.ts`, `environment.ts`, `wrangler.jsonc`): `AgentRunWorkflow` beside `ListingsRunWorkflow`; it throws `dispatch_disabled` before any step unless the agent-loop var is exactly `on` with `modelTurn` and the `AGENT_RUN` binding. The cron starts queued runs, wakes a waiting run's Workflow on its answer, and keeps agent-run leases out of the Listings starts. **Deploy order:** the cron reads `agent_run_pending_starts` on every tick, switch on or off, and skips the tick's starts when that read fails, so migration 0047 must be applied before the orchestrator carrying this code deploys (otherwise Listings starts pause until it is).
- **The plan start's seam**: `PlanStepAdmitter` (`planStepAdmitterOff`); #58's plan start now reads its loop switch from it and still reports every agent and specialist step `not_started` with `agent_loop_off`.
- **Tools composed in this build**: `inbox.ask` only. A tool without a handler is never offered.
- **The switch** (`docs/decisions/agent-loop-staging.json`, committed `off`): it names five prerequisites, each `null`; `edge:check` refuses it on before every one is recorded with an evidence file, refuses it on without the model-provider switch, and refuses any Worker carrying `MORROW_AGENT_LOOP` while it is off. The plan-drafts check now reads it.

Follow-ups (not in this PR): **Listings on the runner** (`products.read`, `proposal.listing` with taint carried to the proposal and approval of the exact digest only, and `run_turns`' store-content cleanup handler before any store text enters a turn); listings' `run_reserve` counting loop spend against the shared daily backstop; the Ask route (PR 12) composing `admitRoutedRun`, and the Inbox's answer route (PR 15) composing `answerRunQuestion`; a reconcile path that runs the stale close outside admission; mandate, Coordinator and specialist runs (later forward migrations widen `kind`); catalogue v2's publication migration.

## Security notes

- **Tenancy**: every new tenant table is FORCE RLS with the session and lease templates; the runtime login reaches records only through its step definers under the entered run lease (`agent_run_entered`, which also takes the run's lock); the broker's two definers reach only the run and call their own transaction-local settings name, as the broker's login; the cron's list and the lease lookup are ids only. The api role reads `agent_runs` column by column (no manifest text, lease, envelope, digest or tool list) and nothing else.
- **The intersection, in code**: every tool call is decided at call time over facts read in that step; a profile never changes a tool, capability or cap; no tool takes SQL, a URL, a store, a recipient, a credential or a model.
- **Unknown outcomes**: the fence commits before any request; an open fence past its budget is booked as uncertain at its worst case by the next step, finish or stale close; a late close is `already_closed`; an uncertain turn is resent at most once.
- **Money**: the hold and caps are derived in SQL and code and compared; every counted turn is booked against the hold; what it cannot hold is overflow, never dropped; admission counts open holds against the daily backstop and the period's unrecovered cost. Before the rate card a loop run earns no credit and runs only under the operator test entitlement.
- **Content**: conversation text lives only in `run_turns` and the questions; Workflow results, events, commands and logs carry ids and codes (checked by the unit tests and the lab).
- **Default deny**: the switch is committed off and refused on by `edge:check` until its prerequisites are recorded; catalogue v2 is committed `proposed`, so SQL admits nothing even with the switch on; production has no switch.

## Open questions

1. **Owner: catalogue version 2's values** (ADR-0027 items 6 and 12, ADR-0026 item 4; committed `proposed`, awaiting the owner's yes). Models Haiku 5.5, Sonnet 5.5 and Opus 5.5 (provider ids `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`), each at `low`, `medium` and `high` with adaptive thinking. Prices per million tokens (input / output / cache write / cache read): Haiku US$0.10 / 0.50 / 0.125 / 0.01; Sonnet US$2 / 10 / 2.50 / 0.20; Opus US$4 / 20 / 5 / 0.20. `max_tokens` 5,000 / 12,000 / 16,000 (call budgets about 197 s, 394 s, 506 s). Limits: 64,000 input tokens per turn; 16 turns per run (6 for the Coordinator); 4 tool calls per turn and 40 per run; 2 questions per run, each open 72 hours; 30 minutes of wall time (waits excluded); specialists 60 minutes by default, at most 480; tool results 8 KiB. Money: US$7 per run, US$25 per workspace per day, US$4.50 unrecovered cost per period. Defaults: Coordinator Opus 5.5 high, specialists Opus 5.5 medium, installed agents Sonnet 5.5 low. Worst-case turn, turn limit and hold per entry: Haiku low US$0.0105 (16 turns, US$0.168), medium 0.014 (16, 0.224), high 0.016 (16, 0.256); Sonnet low 0.21 (16, 3.36), medium 0.28 (16, 4.48), high 0.32 (16, 5.12); Opus low 0.42 (16, 6.72), medium 0.56 (12, 6.72), high 0.64 (10, 6.40).
2. **Owner: the US$4.50 unrecovered-cost cap against loop holds.** Before the rate card every loop run counts toward the period's unrecovered cost, and admission counts an open run at its hold (fail closed). With the cap at US$4.50, every entry whose hold is above it is always refused `unrecovered_cost_cap`: Sonnet high and all three Opus entries, which include the Coordinator's and the specialists' defaults; a Sonnet low run (US$3.36) is admitted only while no other run is open. Raise the cap for loop runs, count only booked cost, or keep it (only routed runs of installed agents are admitted in this PR).
3. **Lead: deploy order.** Apply migration 0047 before deploying the orchestrator with this code (see the orchestrator bullet).
4. **Lead: the pg-http leg's time.** `lab:agent-loop` took about 17 minutes locally at load 300 to 1,000 (about 3.5 of them applying the chain). If the hosted `pg-http` leg nears its 20 minutes, move the lab to a leg of its own.
