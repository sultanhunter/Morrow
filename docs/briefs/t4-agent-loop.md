## Goal

One durable job runner for every agent (`AgentRunWorkflow`, `agent-run@1`), in which the model calls Morrow's tools, each call is checked in code at call time and recorded, and a run can wait for a person's answer. Everything ships behind the agent-loop switch, committed off; nothing here can start a run on staging.

## Scope

- **Records** (migration 0047, `morrow_work`): `agent_runs` (the pinned AgentRunManifest@1, caps, hold, counters; ids, digests, codes and amounts), `run_turns` (the only place loop content lives: each turn's input, the reply, the tool results; 90 days after the run ends; reasoning stripped at the end; each attempt's caps, `final` and `budget_ms`, fixed when it opens), `run_tool_calls` (RunToolCall@1, ids and digests; 365 days; born `counted` or not: a call over a cap or not offered is recorded uncounted and can only finish refused with that code), `agent_model_calls` (the broker's turn fence), `agent_run_questions` (at most one open per run; on `run_turns`' clock: 90 days after the ask, then 90 days after the run ends); the loop catalogue v2 (`loop_catalogue_versions`, `loop_catalogue_entries`, committed `proposed`) and ToolCatalogue v2 (`tool_catalogue_entries`), drift-tested against the generated data. FORCE RLS on all eight; no DELETE or TRUNCATE.
- **Admission** (`packages/work/src/loop/admission.ts`, `cmd_agent_run_admit`): a person's routed run of one installed agent on one store. The switch first (`switch_off` before any statement), the manifest in code, then one definer that re-checks the task, store, stops, installation and release, takes only an `active` catalogue version, derives the caps and the hold (the turn limit lowered so it times the worst-case turn fits US$7), requires the operator test entitlement (ADR-0027 item 6), closes the workspace's stale runs, counts the daily backstop and the period's unrecovered cost, and writes the lease, child task, envelope, Coordinator grant, hop and run. The envelope and the hop carry exactly the offered tools' capability pairs and a scope of the run's store with exactly the tools' fields (`loop_tool_fields`, drift-tested against `authority.ts`'s `toolFieldScopes`). Its manifest CHECK proves the canonical text is exactly the run's columns. The answer (`cmd_agent_run_answer`) is the requester's only and opens the resume lease.
- **The runner** (`packages/work/src/loop/runner.ts`, steps in `steps.ts`): durable steps carry ids and codes only; every step re-enters the run lease. Before each turn, in code: the turn limit, the hold left against the entry's worst-case turn (a final turn, `tool_choice: none`, when it cannot also cover one after), the wall time (waits excluded) and the lease's time against the call's whole budget. `agent_turn_open` checks them again and fixes the attempt's caps (SQL derives `final` itself and compares); a replayed turn step takes the recorded caps, never ones worked out again from the run's state after its own booking, and every new send (a replay's first, a throttle's resend) goes only while the wall time and the lease's time still cover its budget. An uncertain turn is booked at its worst case and sent again at most once, and only when SQL recorded it uncertain: a broker hold or the broker's own `uncertain` (its close failed, or found the fence already closed) is never taken as SQL's verdict, so the step settles against SQL first (a live fence is waited for, an expired one booked as uncertain, a committed reply read back); `agent_turn_open` also books an expired fence of attempt 1 before it opens attempt 2; a throttle resends with the next sequence; a lost reply is read back from SQL, never resent; a broker hold that left nothing in SQL (no fence, so no request: a transient database or binding failure) is tried again at most twice, after 5 and 10 seconds, before the run ends `provider_error`. Each tool call: lease re-entry, replay of a recorded call (an unfinished uncounted call is refused again, never resumed), the full ToolInput validation, ids in scope, the authority decision in code, the handler. The wait step is safe to replay: when it cannot enter the lease its first attempt released, the run's status (`agent_run_resume_lease`, now with the status, waiting runs included) says whether the wait committed. The end reason is derived in code.
- **Authority per call** (`authority.ts`): `decideDelegation` over facts read again in the call's own step (`delegation_facts`, `run_billing_facts`): the requester's live grants with delegate, the envelope and the Coordinator's hop, the installation's grants and scope, the installation owner's authority, the policy revision, the store association and stops, the entitlement. Any one failing refuses the call (`authority_denied`, or `stopped`); missing facts refuse it.
- **Untrusted content** (ADR-0027 item 5): the request is the one text block; tool results enter only as tool results whose content names their `source`; a result carrying store, email or upload text taints the run; data blocks are wrapped by the adapter so they cannot close their wrapper. Tools, recipients and caps come from the manifest and SQL, never from text. The requester's answer enters the next turn as a text block (their own words, as the request is).
- **The broker** (`apps/broker/src/agent-turn-gateway.ts`, `claude-turn-adapter.ts`): `RuntimeBroker.modelTurn` holds every call (`MODEL_UNAVAILABLE`) unless both the model-provider and the agent-loop switches are on, checks ModelCall@2 by hand (no model, effort, tool list, limit or provider), refuses `prefix_mismatch` before any request, fences the turn in SQL (`morrow_vault.agent_turn_begin`/`agent_turn_end`), reads the selection, offered tools and system text from the run, counts, sends once, checks the reply against the run, and books the cost at the entry's rates (overflow never dropped). Strict tools, adaptive thinking, the effort, the system text cached for five minutes.
- **The orchestrator** (`apps/workers/src/orchestrator.ts`, `agent-run.ts`, `environment.ts`, `wrangler.jsonc`): `AgentRunWorkflow` beside `ListingsRunWorkflow`; it throws `dispatch_disabled` before any step unless the agent-loop var is exactly `on` with `modelTurn` and the `AGENT_RUN` binding. The cron starts queued runs, wakes a waiting run's Workflow on its answer, and keeps agent-run leases out of the Listings starts. **Deploy order:** the cron reads `agent_run_pending_starts` on every tick, switch on or off, and skips the tick's starts when that read fails, so migration 0047 must be applied before the orchestrator carrying this code deploys (otherwise Listings starts pause until it is).
- **The plan start's seam**: `PlanStepAdmitter` (`planStepAdmitterOff`); #58's plan start now reads its loop switch from it and still reports every agent and specialist step `not_started` with `agent_loop_off`.
- **Tools composed in this build**: `inbox.ask` only. A tool without a handler is never offered.
- **The switch** (`docs/decisions/agent-loop-staging.json`, committed `off`): it names five prerequisites, each `null`; `edge:check` refuses it on before every one is recorded with an evidence file, refuses it on without the model-provider switch, and refuses any Worker carrying `MORROW_AGENT_LOOP` while it is off. The plan-drafts check now reads it.

Follow-ups (not in this PR): **Listings on the runner** (`products.read`, `proposal.listing` with taint carried to the proposal and approval of the exact digest only, and `run_turns`' store-content cleanup handler before any store text enters a turn); the run-content deletion handlers of ADR-0031 item 3 (the agent uninstall's run-turns deletion and the retention sweep), which must cover `agent_run_questions` with `run_turns` (one clock, `expires_at`); listings' `run_reserve` counting loop spend against the shared daily backstop; the Ask route (PR 12) composing `admitRoutedRun`, and the Inbox's answer route (PR 15) composing `answerRunQuestion`; a reconcile path that runs the stale close outside admission; mandate, Coordinator and specialist runs (later forward migrations widen `kind`); catalogue v2's publication migration.

## Security notes

- **Tenancy**: every new tenant table is FORCE RLS with the session and lease templates; the runtime login reaches records only through its step definers under the entered run lease (`agent_run_entered`, which also takes the run's lock); the broker's two definers reach only the run and call their own transaction-local settings name, as the broker's login; the cron's list and the lease lookup are ids only. The api role reads `agent_runs` column by column (no manifest text, lease, envelope, digest or tool list) and nothing else.
- **The intersection, in code**: every tool call is decided at call time over facts read in that step; a profile never changes a tool, capability or cap; no tool takes SQL, a URL, a store, a recipient, a credential or a model. The envelope and the hop are never wider than the offered tools (their pairs and fields); the per-turn and per-run tool-call caps hold across retried steps (an uncounted call is never resumed).
- **Unknown outcomes**: the fence commits before any request; an open fence past its budget is booked as uncertain at its worst case by the next step, finish, stale close or attempt 2's open; a late close is `already_closed`; the broker's answer is never SQL's verdict (a hold or its own uncertain is settled against SQL first); an uncertain turn is resent at most once, only after SQL recorded it; a replayed turn step keeps the reply SQL recorded (and booked) under the caps the attempt was opened with.
- **Money**: the hold and caps are derived in SQL and code and compared (a turn attempt's `final` too, at its open); the broker's fence refuses a call whose `final` or budget is not the attempt's (`turn_state`); every counted turn is booked against the hold; what it cannot hold is overflow, never dropped; admission counts open holds against the daily backstop and the period's unrecovered cost. Before the rate card a loop run earns no credit and runs only under the operator test entitlement.
- **Content**: conversation text lives only in `run_turns` and the questions, both on one clock (90 days after the run ends, ADR-0031 item 1; the questions' copy is open question 6); Workflow results, events, commands and logs carry ids and codes (checked by the unit tests and the lab).
- **Default deny**: the switch is committed off and refused on by `edge:check` until its prerequisites are recorded; catalogue v2 is committed `proposed`, so SQL admits nothing even with the switch on; production has no switch.

## Review findings and fixes (Tier 2: AI review, separate context, same model family; 2026-10-24)

Five confirmed findings, each fixed with a test that fails without the fix (checked by reverting the fix):

- **F1 (medium), the broker's own `uncertain` taken as SQL's verdict.** The gateway answers `uncertain` when its close throws or finds the fence `already_closed`; the runner went straight to attempt 2, which SQL refuses (attempt 1 not recorded uncertain), so the Workflow spent its retries, the run stayed `running` with its hold counted, and a paid reply the close did commit was thrown away. Fix: `runTurn` settles a broker `uncertain` exactly as a hold (waits for a live fence, books an expired one as uncertain, reads a committed reply back) and resends only when SQL recorded attempt 1 uncertain; defence in depth, `agent_turn_open` books an expired open call of attempt 1 before it opens attempt 2. Tests: `agent-loop.test.mjs` "the broker's own uncertain is settled against SQL" (an open fence, a committed reply, a recorded uncertain); the migration test's review block; lab U3 (attempt 2 books an aged fence itself) and U4 (the real gateway's committed reply masked as uncertain is read back, one send).
- **F2 (medium), a lost `wait-q` result.** `agent_run_wait` releases the lease in its own transaction, so a retried wait step could not enter it and the Workflow ended `interrupted` with the run `waiting`; the person's answer then woke a finished instance and was lost. Fix: on a refused entry the wait step reads the run's status through `agent_run_resume_lease`, widened to return the status and to include waiting runs (the runtime policy `runtime_agent_open` now reads queued, running and waiting runs, ids and a code only); waiting, or queued or running under a newer lease, is this step's wait. `startRun` and `tryResume` treat a waiting run as before. Tests: "a wait step whose result was lost after it committed goes on waiting" (lost before and after the answer, and a stop that is still a refusal); the decoder; lab Q3 (wait-1's result lost once against PostgreSQL).
- **F3 (medium), the per-run tool-call cap bypassed on a retried step.** A call `agent_tool_call_begin` refused `tool_call_limit` was recorded uncounted, but a retried begin before the refusal's finish returned `resumed`, and the runner dispatched it. Fix (0047 is not applied): `run_tool_calls.counted boolean NOT NULL`, set at insert; an unfinished uncounted call is refused again with the same code, never resumed; `run_tool_calls_counted` lets an uncounted call finish only refused `not_offered` or `tool_call_limit`. Tests: "a call refused at the run's tool-call cap stays refused when its finish fails"; the migration test; lab C2 (the cap reached, the finish's transaction failed once, never decided or dispatched).
- **F4 (low), admission's listings-only scope blocks the composed tool.** The envelope and the hop were scoped to the five listing fields, so the real kernel could never allow `inbox.ask` (fail closed). Fix: `cmd_agent_run_admit` scopes both to the run's store and exactly the offered tools' fields (`loop_tool_fields(text[])`, a pure function drift-tested against `toolFieldScopes`, which `toolOperation` now also enforces). Tests: the real kernel allows `inbox.ask` under the tools' field scope and refuses it `origin_denied` under listings' (agent-loop.test.mjs, over the kernel's own delegation fixture); the drift test; lab A3 (the stored envelope and hop fields). Not done: the lab's question phase still stubs the authority for `inbox.ask`, because no installation can hold `workspace.question.request` yet (open question 5).
- **F6 (low), two asks in one turn.** Both questions opened, the run waited on the newest only, and the other could never be answered. Fix: at most one open question per run: `agent_question_ask` refuses `question_limit` while one is open, backed by the unique index `agent_run_questions_one_open`. Tests: "one open question at a time"; the question limit across turns; the migration test; lab Q1 and Q3 (the second ask refused, one question row, the refusal and the answer in turn 2).

### Second review (R1, R3; AI review, separate context, same model family; 2026-10-25)

Two confirmed findings, each fixed with a test that fails without the fix (checked by reverting the fix, or against the pre-fix migration):

- **R1 (medium), the turn step not safe to replay.** `runTurn` worked out `turnCaps` again from the run's state after its own booking before it read back what SQL recorded, so a turn step run again after the broker's close committed (a lost result, a failed settle or read-back transaction, a Workflow re-run) could end a recorded, paid reply as `invalid_output` (a `tool_use` turn that became final), `cost_budget` or `wall_time`: a completed run recorded failed, a `tool_use` reply's calls never run. Fix (0047 is not applied): `run_turns.final` and `run_turns.budget_ms`, set by `agent_turn_open` with the input and never changed (SQL derives `final` with nextTurn's rule and refuses a different one `invalid`; the same input with other caps is a `conflict`); `agent_run_conversation` returns them; the runner checks the caps only for an attempt SQL has not opened and otherwise takes the recorded ones; each new send checks the wall time and the lease's time against its budget (so a replayed attempt that sent nothing still sends only in time); the broker's `agent_turn_begin` refuses a call whose `final` or budget is not the attempt's (`turn_state`). Tests: `agent-loop.test.mjs` "a turn step replayed after its close committed keeps its recorded reply and sends nothing" (the finding's two holds, the wall time and lease passed after the close, a whole run with turn 1's result lost, and an attempt whose step failed before any send: sent once under its recorded caps, or ended `wall_time` with nothing sent; with the caps worked out again on replay it ends `invalid_output`), the decoders; `agent-loop-migrations.test.mjs` "review R1"; lab U2 (a reopen with other caps is a conflict, a fence with other caps `turn_state`), U3 (a `final` SQL does not derive is `invalid`) and U5 (turn 1's result lost and the run moved past its wall time in between: the recorded reply, one send, completed).
- **R3 (low), questions outside `run_turns` with no clock.** `agent_run_questions` held the question and the answer with no `expires_at`, so the run's end never moved it and the copy outlived the run's turns (ADR-0027 item 7, ADR-0031 item 1). Fix (0047 is not applied): `expires_at timestamptz NOT NULL`, born 90 days after the ask (the guard requires it), at least 90 days after `created_at` (`agent_run_questions_times`, the same floor as `run_turns`), moved by `agent_run_end` for every question of the run, answered ones too, to 90 days after the end, with the run's turns, and only ever later (the guard). Not a cap at 90 days plus the 72-hour window after the ask, as the finding suggested: a run can end long after that (a second question, or a stale close that runs later), and the run's end would then fail that CHECK and could never close; the run-end clock is the bound. The deletion handlers that would cover it do not exist yet (Follow-ups); open question 6 asks whether the copy should stay. Tests: `agent-loop-migrations.test.mjs` "review R3" (every loop table holding content is on `run_turns`' clock); lab Q5 (born on the clock, then the same expiry as every turn of the run after its end).

## Open questions

1. **Owner: catalogue version 2's values** (ADR-0027 items 6 and 12, ADR-0026 item 4; committed `proposed`, awaiting the owner's yes). Models Haiku 5.5, Sonnet 5.5 and Opus 5.5 (provider ids `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`), each at `low`, `medium` and `high` with adaptive thinking. Prices per million tokens (input / output / cache write / cache read): Haiku US$0.10 / 0.50 / 0.125 / 0.01; Sonnet US$2 / 10 / 2.50 / 0.20; Opus US$4 / 20 / 5 / 0.20. `max_tokens` 5,000 / 12,000 / 16,000 (call budgets about 197 s, 394 s, 506 s). Limits: 64,000 input tokens per turn; 16 turns per run (6 for the Coordinator); 4 tool calls per turn and 40 per run; 2 questions per run, each open 72 hours; 30 minutes of wall time (waits excluded); specialists 60 minutes by default, at most 480; tool results 8 KiB. Money: US$7 per run, US$25 per workspace per day, US$4.50 unrecovered cost per period. Defaults: Coordinator Opus 5.5 high, specialists Opus 5.5 medium, installed agents Sonnet 5.5 low. Worst-case turn, turn limit and hold per entry: Haiku low US$0.0105 (16 turns, US$0.168), medium 0.014 (16, 0.224), high 0.016 (16, 0.256); Sonnet low 0.21 (16, 3.36), medium 0.28 (16, 4.48), high 0.32 (16, 5.12); Opus low 0.42 (16, 6.72), medium 0.56 (12, 6.72), high 0.64 (10, 6.40).
2. **Owner: the US$4.50 unrecovered-cost cap against loop holds.** Before the rate card every loop run counts toward the period's unrecovered cost, and admission counts an open run at its hold (fail closed). With the cap at US$4.50, every entry whose hold is above it is always refused `unrecovered_cost_cap`: Sonnet high and all three Opus entries, which include the Coordinator's and the specialists' defaults; a Sonnet low run (US$3.36) is admitted only while no other run is open. Raise the cap for loop runs, count only booked cost, or keep it (only routed runs of installed agents are admitted in this PR).
3. **Lead: deploy order.** Apply migration 0047 before deploying the orchestrator with this code (see the orchestrator bullet).
4. **Lead: the pg-http leg's time.** `lab:agent-loop` took about 17 minutes locally at load 300 to 1,000 (about 3.5 of them applying the chain). If the hosted `pg-http` leg nears its 20 minutes, move the lab to a leg of its own.
5. **Lead (authority, material): an installation that can hold `workspace.question.request`.** After F4 the envelope and the hop no longer block `inbox.ask`, but the real kernel still refuses it on every installation this build can make: `agent_installations.grant_refs` must be exactly the three Listings grants (`valid_grant_refs`, migration 0031), `delegation_facts` reads an agent principal's grants for those three capabilities only, and the Listings installation's scope carries the listing fields only. So `inbox.ask` is offered but always refused `authority_denied` (fail closed), and the lab's question phase stubs that one decision. Letting a released package declare and an installation hold `workspace.question.request` (and the requester's grant with `delegate` for it) changes the installation's grant model, which is an authority change for its own PR and ADR (PR 12's packages, per the lab's note).

6. **Lead (retention, material): the question's copy outside `run_turns`.** ADR-0027 item 7 puts loop content only in `run_turns`; `agent_run_questions` keeps the question and the answer too, because the answer command and the Inbox (PR 15) read them by the question's id. After R3 the copy has `run_turns`' clock and never outlives the run's turns. If the Inbox needs the question text kept longer than 90 days after the run ends, or the copy should be emptied at the run's end instead, that is an ADR-0031 amendment; this PR assumes neither.
