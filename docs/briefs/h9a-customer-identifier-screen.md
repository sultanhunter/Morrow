# H9a: The customer identifier screen

- Status: brief, 2026-10-26. Branch `claude/h9a-customer-identifier-screen`. Plan row H9a of `docs/plan/harness-foundations-implementation.md` (size M, after H6; parallel with H5, H6, H12a and H14). Change class: material (customer data and retention), already owner-approved: ADR-0041 item 31 and ADR-0040 item 2, owner question 23 of OD-2026-10-26-7 ("customer details typed into messages are refused until P09.T05; order numbers pass"). No new decision is taken here. No migration: the screen is code, the refusal is a closed contract, and no table changes.

## Goal

Until P09.T05's deletion and privacy path exists, Morrow keeps no customer details (CLAUDE.md). This PR builds the one screen in code, outside any prompt, that keeps them out of what Morrow stores: a person's post (ADR-0040's post command, H11b) and every text a model writes that Morrow commits (ADR-0041 items 13 and 31). It wires the screen into the three model-written write paths that exist on `main` today, gives the refusal its closed contract and the records' exact words, and puts the standing line under every composer that writes to an agent.

## Scope

- **The screen** (`packages/policy/src/customer-screen.ts`, exported as `@morrow/policy/customer-screen`; pure, synchronous apart from one port, no I/O, no `node:` import, so it runs in the api, runtime and broker Workers). It reads a scan copy that is never stored: NFKC-folded, format characters (zero-width, bidi, soft hyphen, variation selectors, fillers) dropped, HTML references and percent escapes of the characters an address or id needs decoded up to three times, every script's decimal digits made ASCII, every dash "-", bracketed "(at)" and "(dot)" closed up. It finds, by kind (`CustomerDataKind@v1.1`):
  - `email`: an address (not a file name such as `logo@2x.png`), also obfuscated; a spaced ("jane @ shop.com") or written-out ("jane.doe at shop dot com") form when its local part is address-like (a dot, underscore or plus, or letters with digits) or its domain is a personal mail provider; and `jane@gmail` without its top-level domain;
  - `phone`: a run of digits classified by its shape and the words before it (a phone word makes 7 to 15 digits a phone; an id or money word makes it not one; otherwise an international number, a grouped one, or a bare national one with its trunk 0 or a valid North American number), and `tel:`, `wa.me` and WhatsApp's send links;
  - `street_address`: shapes, never a gazetteer: a house number with up to four name words and a street word (words that are also ordinary nouns, such as Drive, Court, Place and Way, only in title case and never after the words that make them ordinary), a number, street type and name ("10 rue de Rivoli"), a street type, name and number ("Calle Mayor 5"), compound streets ("Hauptstraße 12"), unit and street pairs ("House 12, Street 5"), PO boxes, and postcodes or ZIPs in their place (UK, Canadian, "IL 62704" after a comma, "zip 90210");
  - `customer_gid`: a Customer, CustomerAddress, MailingAddress, CustomerPaymentMethod, CustomerSegmentMember or CompanyContact GID, plain, percent-encoded or base64; a customer link in the Shopify admin or the Admin API; `customer:<id>`; a numeric customer id of seven digits or more after the word "customer" (`customer_id`, `customerId`, "Customer ID:");
  - `listed_email`: a looser email form (a plain-word local part, spaced or written out) whose keyed digest is on the customer email list.
  Links, GIDs, addresses, Morrow record ids, ISO dates, times and IPv4 addresses are masked before the phone and address scans, so order GIDs, order numbers (`#1042`), product and variant ids, SKUs, tracking and barcode numbers, prices, counts, dates and times pass. Every pattern is bounded and linear; a text is at most 1 MiB and a call at most 4 MiB and 4,096 strings (a longer one is a caller defect that throws).
- **The verdict and the refusal.** The verdict names kinds only, sorted in the contract's order and frozen, never the text or what matched. `CustomerScreenRefusal@1` (`{schemaVersion 1, code customer_data, kinds}`, v1.1 core, release baseline updated) is the same for a post and for a model-written text. `ToolRefusalCode`'s `customer_data` now also covers a text the model wrote; plan.draft's refusal union gains `customer_data`.
- **The keyed customer email list** (`CustomerEmailDigestList`). ADR-0041 item 31 calls it "the keyed email-digest list that `customers/redact` already uses"; precisely, `customers/redact` today keeps a keyed digest of the customer **id** only (`apps/broker/src/shopify.ts`, `morrow.shopify.customer.v1|<id>` under the app secret), and no customer email is kept anywhere. The screen therefore holds the list as a port: it hands the broker the digest inputs of the looser forms (`customerEmailDigestInput`: NFKC, lower case, `+tag` dropped, `morrow.customer-email.v1|` prefix) and the broker answers one boolean; it is asked only when no pattern matched and a looser form exists; "unavailable", a throw or any non-boolean answer fails closed as `screen_unavailable` (nothing stored; retryable); more than 32 looser forms in one call are refused as `email` without asking. Until P09.T05 the list is empty (`noListedCustomerEmails`), so the synchronous screen is complete; P09.T05 binds the broker's list and moves each caller to the listed entry point.
- **Where it runs.**
  - The post command (ADR-0040 item 2; built in H11b): `screenPost(texts, list)` is its first check inside the command's transaction, before the message, inbox row or any run sees the text. A match answers `delivery not_started`, `code customer_data`, the refusal and the safe message, and stores nothing.
  - Every model-written stored text: `modelWrittenTexts` lists each kind ADR-0041 names (conversation summaries, the fallback checkpoint, compaction summaries, run plans and their notes, plan cards, `understood`, ledger titles, result items, findings, teammate results, agent messages, notebook entries, knowledge proposals, memory suggestions), with the decision that screens it today; a flagged compaction summary is `fallback_reset` (dropped for the reset on code facts), every other kind `refuse`. Wired here, in the decision before the command, refusal `customer_data`, nothing sent to SQL: `decideKnowledgePropose` (title, text and source values), `decideNotebookWrite` (text), `decidePlanDraft` (every string and key of the mapped card). The other kinds' writers have not landed; the PR that first writes each one calls `screenModelWritten` in the same step and records its decision in the registry (H5, H7b, H7d, H7e, H10, H11a, H11b, H12b, H12c).
- **The copy, exactly as the records give it.** The safe message is "Morrow can't keep customer details yet. Remove them and send again." (ADR-0040 item 2, ADR-0041 item 31). The standing line "Don't include customers' names or contact details." sits under every composer that writes to an agent: the project conversation, the private Ask and its free answer, a new project's request to Morrow, an answer to an agent's question in the Inbox, and the Listings request. `TextArea` and `TextField` gain a `standing` line read with the field (`aria-describedby`). The post route's safe message reaches the person through `CommandFeedback`'s `invalid` message when H11b lands; no UI mapping is needed.
- **What it cannot catch: customer names.** A name typed as free text ("Jane Smith asked for a refund") matches no pattern, and before P09.T05 Morrow holds no list of names to compare with. Such a name would reach messages, run turns, summaries and memory, where `customers/redact` cannot find it. The two controls that narrow it are the standing line (this PR) and message redaction that deletes every copy (ADR-0041 item 14). The owner chose option (a) on that question, as relayed with this task: P09.T05's deletion path comes first, and ADR-0040's `async-conversations` switch stays off until then. So this PR builds no redaction: the tables that hold a message's copies (`messages`, `run_turns`, epochs, checkpoints, derived memory) do not exist yet, and message redaction lands with P09.T05 and the PR that first writes each copy. H11b's switch record must refuse `async-conversations` on before P09.T05 and message redaction exist.
- **What it also refuses: the shop's own contact details.** No pattern can tell the shop's support address, phone or street from a customer's; owner question 23 approved the screen for every email, phone and street address. A post or a knowledge proposal naming the shop's own support address is refused until P09.T05 (open question 2).
- **Not screened here:** Listings drafts (`run_drafts`) are product copy from a run that reads only the catalogue, never customer data, and the review screen already counts the URLs, emails and phones a draft adds; person-typed fields outside a post (task objectives, question answers, knowledge pages a person writes, plan edits) are not in item 31's list (open question 1).

## Security notes

- Customer data: the screen is the code half of CLAUDE.md's rule that customer data never enters before P09.T05; the read-tag rule (a run that read customer data proposes and notes nothing) is unchanged and runs first. Nothing of a refused text is stored, logged or returned: the refusal names kinds only, and the lab searches every table for the planted values.
- Fail closed: an unanswerable keyed list is `screen_unavailable`; an input outside the bounds throws; a structured value that is not plain JSON throws.
- Authority and tenancy: unchanged. The screen grants nothing and reads no tenant; it runs in code before the definer, so no SQL changes and no migration.
- Model untrusted: the screen runs on what the model wrote, keys included, never on what the model says about it; obfuscations a model could produce (escapes, full-width and zero-width characters, other scripts' digits, base64 and percent-encoded GIDs) are decoded first.
- Denial of service: every pattern is linear; a mebibyte of adversarial text takes about a second on the loaded Mac (the unit test bounds it at 20 seconds per input).
