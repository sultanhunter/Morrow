# Collaboration and human takeover

Version: 1.0.0 candidate. Owner: Morrow platform owner. Review: Codex semantic self-review plus schema/fixture checks; integration qualification remains required. Canonical plan sequence: 13. Consumer: P07/P14.

## Shape and ownership

Schemas: ArtifactAnchor, ArtifactRevision, Task. Exact field types, nullability, required properties and closed object validation are in schemas/v1/core.schema.json; capability bodies are in capabilities.schema.json. State actors and guards are in state-transitions.json. Representative valid/invalid fixtures are in fixtures/P01.A02.json. Payload references are immutable scope/revision/digest bindings, not storage URLs or bearer credentials.

## Command and query semantics

Comments name artifact ID and exact revision. Text ranges, stable row/column IDs and normalized image regions are validated per anchor kind. Presence is transient and does not confer access. Human takeover atomically changes owner/lease generation before dispatch. Notifications are derived from authoritative events and permission-filtered at read time. Offline drafts retain their base revision and cannot silently overwrite current content.

## Failure invariant

An agent with an older generation cannot continue edits after takeover; invalid anchors become repairable conflicts. Failures use ErrorEnvelope and must not leak inaccessible content. Current policy and resource checks apply to all reads, mutations and derived artifacts.

## Compatibility and evidence

Every command/read declares schema version 1. Unknown fields and invalid enum values fail validation; no implicit coercion/default authority. Breaking fields/states/meaning require a new version and explicit migration with retained workflow histories. Additions remain opt-in via negotiated schema versions, not silently accepted fields. Consumers pin reviewed contract revisions. Run npm run verify:contracts and npm run test:contracts for contract fixture evidence; these do not prove production authorization or provider access. Open provider/region/retention/billing targets remain in the decision register and block consumers that need them.

## Contract v1.1: conversations, mentions, inbox, projects and access requests (P01.T02c, ADR-0016)

The definitions are in `schemas/v1.1/core.schema.json`, the eight capability bodies in `schemas/v1.1/capabilities.schema.json`, the fixed tables (trust rank, kind-to-machine map, open states, limits) in `collaboration-defaults.json`, and the cases in `fixtures/P01.T02c.json`. The comment, anchor and takeover text above is unchanged. Persistence, routes, sealing and delivery belong to P07.T03, P05.T02b, P06.T02a and P14; the pure library that decides the rules below is P01.T02c PR-B (`@morrow/policy/collaboration`).

- **Conversations.** One conversation per project and per task, lazily ensured by the first post; an Ask is created by `workspace.conversation.create` and is private to its creating owner. A Conversation has no status and revision 1: posts never change its revision or timestamps. `lastPosition`, `Message.position` and `InboxItem.position` are opaque, sealed per viewer and never compared.
- **Messages.** Six typed parts: `text`, `artifact` (with an optional anchor of the cited revision), `proposal`, `question`, `evidence_summary` and `mention`. A human message is created `completed`; an agent message is created `streaming` with an origin (`run`, or `ask_turn` in an Ask), never carries a mention, and ends `completed`, `failed` or `cancelled` (a lost lease ends it `failed`). `restrictedSources`, `contextTaint` and an evidence summary's `trustClass` are server-derived; a client cannot send them.
- **Visibility, all-of.** A viewer sees a message only if they can view its subject now (project: goal view; task: task view; Ask: the owner, the owner's Ask envelope for an agent, or the audited admin read), hold `view` on `workspace.conversation.post` for the message fields, and can view every restricted source. An invisible message is omitted: absent from pages and counts, a reply to it reads `replyToMessageId: null`, and no position, revision or timestamp shows a gap. A message has at most 102 view requirements (100 sources plus subject and message view).
- **Streaming.** For each model call the runtime commits its context sources, rechecks every subscriber, and only then sends that call's deltas to the subscribers who passed; a subscriber who fails gets one generic `reset` frame. Deltas are transient and applied in `sequence` order.
- **References.** Every cited ref, anchor, tab artifact, scope resource and context id must be in the trusted organization and workspace, exist at exactly the cited `revision` and `digest`, and be viewable by the actor now; every failure is the same `REFERENCE_NOT_FOUND`.
- **Mentions are scoped requests, never authority.** Checked in order: an agent-authored mention is `AGENT_MENTION_DENIED` before any lookup; a mention in an Ask, a `delegate` outside a task conversation or a duplicate target is `MENTION_NOT_ALLOWED`; at most 10 mention parts; each target must be an active member or installation that can view the subject now (unknown, foreign and no-access targets are the same `REFERENCE_NOT_FOUND`); at most 60 mention notifications per author per workspace per 10 minutes. `notify` needs only `execute` on `workspace.conversation.post`; `task` needs the author's `execute` on `workspace.task.create`; `delegate` needs the author's `delegate` on `workspace.task.delegate` in a task conversation. A mention never issues, widens or transfers a grant, never assigns, and never answers or approves.
- **Inbox.** Eight kinds (question, approval, access_request, exception, assignment, mention, stop_notice, stop_proposal), each with a fixed decision machine. Read state is per recipient and separate from decision state: marking never changes a decision, and deciding never changes read state. `open` comes from the fixed table; a `failed_operation` exception and every informational item are never open. Items are re-filtered at read time by the recipient's current subject view, and context ids are null unless viewable; the owner's `stop_notice` is never target-filtered (ADR-0005). A stop proposal's status is derived (executed > dismissed > expired > open); a dismissal needs `execute` on the proposal's kill switch over every target.
- **Projects.** A project is a pinned Goal, never a tenant or permission boundary, read with goal view; one project per goal. Pins are workspace-wide (at most 20), and each viewer sees the pinned projects they can view ranked densely from 0. Unviewable tabs are omitted.
- **Access requests.** Human only; a request never grants anything. Deciders are eligible reviewers of the would-be `governance.grants.revise` proposal (ADR-0011 Q5) and never the requester; the requester withdraws with their own `execute` on `governance.access.request`. P05.T02b links a request to a grant-revision proposal; only the committed, reviewed grant revision grants anything, and `proposalRef` then names the approved (possibly derived) proposal. A pending request expires after 7 days; at most 20 pending per requester.

### Admin reads of Asks (ADR-0016 item 5)

- **Who.** A human member who currently holds `administer` on `workspace.conversation.create` over W with fields `storeId` and `subject`. No role title, template name, owner designation, other `administer` grant, governance capability or reviewer status qualifies. Agents never qualify, including an agent acting for an admin.
- **What.** Read-only and paged: the workspace's Ask list, an Ask's conversation record and its message pages. Message visibility stays all-of, so a message citing a source the admin cannot view is omitted. No stream, no Ask events, no inbox items, no post and no mention.
- **Audit.** Each admin read (one list page, one conversation fetch or one message page) writes exactly one content-free `AskAdminReadRecord` in the read's transaction, and content leaves only after that commit; a failed or unknown commit returns no content. A list record names every other member's Ask on the page in page order, the reader's own left out; an empty page still writes one record. Records are append-only, carry no message text, keep the 365-day content-free audit retention and are exported through `governance.audit.export`. An owner reading their own Ask writes no record.
- **Disclosure.** The `ask_conversation` route shows `AskPrivacyNotice`: workspace admins can read Asks, and each admin read is audited. A member who is neither owner nor admin gets `REFERENCE_NOT_FOUND`; an admin may learn that an Ask exists.
- **Issuance.** The grant goes only into owner template v2 (`owner-bootstrap-v2`) and `workspace-admin-v2`; no `workspace-member-*` template, no v1 template and no other template ever carries it. `askAdminTemplateViolations` in `@morrow/contracts/work-permissions` is the binding template check and is default-deny: it reports every template carrying the grant whose id is not in `askAdminTemplateIds`, and a later owner or admin template version joins that list in the reviewed PR that adds it.

### Permission rows and errors

The rows are `collaborationPermissions` in `@morrow/contracts/work-permissions`, beside the ADR-0010 work vocabulary, and pass the same contract check (`tests/collaboration-contracts.test.mjs` AC09). The data carries the whole rule, so a consumer that plans checks from the table misses nothing: `message.read` and `message.post` carry `subject`, the subject view by subject kind (project: `project.subjectView`; task: `task.subjectView`; Ask: `ask.read`, or for reads also the audited `ask.adminRead`), and `everySource`; `references` names the inputs whose ids must pass the reference rule (tab artifacts, the pin anchor, cited parts and reply, the Ask store, and an access request's scope and context). The access-request decider row requests every `governance.approval.decide` input field (`approvalDecideFields`), exactly as the ADR-0011 Q5 reviewer rule does, so a partial decide grant never makes a decider, and its read shape returns the AccessRequest under that reviewer rule. Errors use the v1 ErrorEnvelope with fixed safe messages: `REFERENCE_NOT_FOUND` is 404 `denied`/`never` (dismissal uses the kill-switch `TARGET_NOT_FOUND`); `AGENT_MENTION_DENIED` and `PERMISSION_DENIED` are 403 `denied`/`never`; `MENTION_NOT_ALLOWED` and `CURSOR_INVALID` are 400 `missing_input`/`never`; `PROJECT_EXISTS`, `LIMIT_REACHED` and `RESTRICTIONS_EXCEEDED` are 409 `conflict`/`never`; stale revisions, `ACCESS_REQUEST_NOT_PENDING` and `STOP_PROPOSAL_NOT_OPEN` are 409 `conflict`/`recheck_before_retry`; `RATE_LIMITED` is 429 `rate_limited` with `retryAfterSeconds`. Commands use per-actor `(commandId, requestDigest)` idempotency; mark and dismissal are idempotent target states without `expectedRevision`.

Accepted disclosures (ADR-0016 item 5): a viewer may learn that a streamed message started; a pinner may learn that the workspace holds 20 pins; an admin may learn that an Ask exists.
