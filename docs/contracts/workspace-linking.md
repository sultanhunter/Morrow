# Workspace and installation linking

Canonical plan sequence 22. Version-one draft contract, reviewed through synthetic fixtures; real authentication/merchant qualification remains pending.

Workspace-first and install-first paths separately verify Morrow membership and Shopify installation. A single-use handoff binds principal, installation, workspace, nonce, purpose, ownership revision and expiry. Atomically consume after verification; repeated callbacks return the already linked result or denial without reassignment. Email equality grants nothing. Connector context cannot become workspace authority. Resume existing authorized records in standalone Morrow.

Closed schemas and fixtures live in schemas/v1/core.schema.json and fixtures/P01.A02.json. Current identity, grants, scope, revisions, budgets and policy are resolved by the backend. UI placement cannot confer authority.

P05.T03a at canonical68 implements the private first-claim persistence boundary with controlled fixtures. An unassigned stable provider subject is not a tenant-owned StoreInstallation; the private association establishes real organization/workspace ownership without inventing connector/vault fields. One current human connect/administer grant and a separately reviewed five-minute handoff must bind the same command, actor/session, nonce, target, installation generation, exact requested scope/proof and expected revisions. Fresh commands cannot overwrite an existing owner; cross-host resume and reconnect are separate integrations. Exact committed replay only reconciles its immutable result after current authority and ownership checks. See the canonical Page and docs/packets/P05.T03a.md for the active protocol; frozen v1 schemas remain unchanged.

## The `shopify_oauth` issuer (M2 PR-2; P09.T02a; ADR-0022 items 3 and 5)

A Shopify install writes a `linking_candidates` row with `proof_kind` `shopify_oauth` for the app's invited workspace (its founding principal as the provisional eligible principal) and an install continuation. The SPA strips `#handoff=<token>` from `/w/:ws/connections` at once, keeps it in memory with one command key, and posts `{handoffToken}` to `POST /workspace/:ws/store-links/preview`. Before the unchanged lookup, the issuer reads the actor's authority as `morrow_identity_linking`, the TypeScript human kernel decides `governance.connection.connect` `administer` on the workspace resource (fields `installationProof`, `providerId`, `scope`) and picks the grant, and `issue_shopify_link_handoff` rechecks under locks: the continuation (its digest is the handoff nonce) unconsumed and unexpired, the continuation's workspace equal to `:ws` and to the installation's tenant, the installation unlinked on a development store of an active app, the actor's own current connect/administer grant, and a fixed `morrow_direct` route. It rebinds the candidate's proof to the actor (a new proof revision), writes the P05.T03a review (evidence `shopify_oauth`) and the 5-minute handoff, and consumes the continuation. The same session, workspace, command and nonce replay as `exists`; anything else is `linking_not_found`, except an unpaid route after the session and grant passed, which is 409 `billing_route_required`. The connect obligation is satisfied by that review bound to the exact handoff, command and proof digest, with the person's Link click as the decision.

`link_workspace_store` (forward-replaced in 0026, same signature) refuses every candidate kind unless the route is `morrow_direct` (`billing_route_required`) and never sets `shopify_bound_at`. For a `shopify_oauth` candidate it also requires the installation unlinked and of the handoff's tenant (`installation_ineligible`); when applied it marks the installation linked and issues the store-link template (`store_link_grants_v1()`, the twin of `packages/policy/src/store-link-template.ts`) to the linking actor on the store resource: `catalog.products.read` {view, delegate}, `catalog.content.propose` {execute, delegate} and `catalog.content.publish` {propose, approve, execute, delegate} with the listing field paths, and `agents.installation.activate` {execute} with its input names, issued by the service `morrow.linking`. A denied link issues nothing. `GET /workspace/:ws/connections` (WorkspaceConnections@1) lets any session-eligible member read the installations; the install link is offered only when the kernel allows connect/administer, an active app invites the workspace, the route is `morrow_direct` and no store is linked.
