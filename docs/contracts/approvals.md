# Exact proposal approvals

Version: 1.0.0 candidate. Owner: Morrow platform owner. Review: Codex semantic self-review plus schema/fixture checks; integration qualification remains required. Canonical plan sequence: 13. Consumer: P11.

## Shape and ownership

Schemas: Proposal, Approval, CrossHostResume. Exact field types, nullability, required properties and closed object validation are in schemas/v1/core.schema.json; capability bodies are in capabilities.schema.json. State actors and guards are in state-transitions.json. Representative valid/invalid fixtures are in fixtures/P01.A02.json. Payload references are immutable scope/revision/digest bindings, not storage URLs or bearer credentials.

## Command and query semantics

Compute proposal digest from canonical content using a RFC 8785 JSON Canonicalization Scheme ([specification](https://www.rfc-editor.org/rfc/rfc8785/)) and SHA-256. Bind resource/account/field/parameter/cost/prior-version/review-policy contents. Decisions identify reviewer and current eligibility, exact digest, scope digest and expiry. Selected-item approval creates an exact selected change set. Changes invalidate review. Approval itself requires an eligible decision grant, not a recursively approved approval. Execution still needs an independent eligible grant and current provider authority.

## Failure invariant

Wrong revision, changed ceiling, replayed handoff, expired review or ineligible reviewer blocks dispatch. Failures use ErrorEnvelope and must not leak inaccessible content. Current policy and resource checks apply to all reads, mutations and derived artifacts.

## Compatibility and evidence

Every command/read declares schema version 1. Unknown fields and invalid enum values fail validation; no implicit coercion/default authority. Breaking fields/states/meaning require a new version and explicit migration with retained workflow histories. Additions remain opt-in via negotiated schema versions, not silently accepted fields. Consumers pin reviewed contract revisions. Run npm run verify:contracts and npm run test:contracts for contract fixture evidence; these do not prove production authorization or provider access. Open provider/region/retention/billing targets remain in the decision register and block consumers that need them.

## Contract v1.1: kill switches (P01.T02a PR-A)

ADR-0005 makes five capabilities kill switches: `ads.campaign.pause`, `agents.installation.disable`, `governance.membership.revoke`, `governance.connection.disconnect` and `agents.release.revoke`. Each is `human_only`, with `review_required: false`, so it executes without a second approver and creates no Approval. It still needs a current eligible human grant for `execute`. Its v1.1 input carries a `KillSwitchControl`: a reason with at least one non-whitespace character, and an optional `sourceProposalRef`. The human evaluator returns the `kill_switch_record` obligation in place of `exact_approval`: the effect commits with an append-only `KillSwitchRecord`, and the owner notification derives from that record (P05.T01z, P11.T05). An agent may propose a stop. A human executing it from that proposal passes the proposal as `sourceProposalRef`, which is rechecked for the same tenant, the same capability and covering targets, and confers nothing (`packages/policy/src/kill-switch.ts`).

Reversals keep review: unpause (`ads.campaign.activate`), re-enable (`agents.installation.activate`), reconnect (`governance.connection.connect`), re-invite (`governance.membership.invite`), re-grant (`governance.grants.revise`) and republish (`agents.release.publish`) still require `exact_approval`. The review policy (ReviewPolicy, Proposal@2, Approval@2) is PR-B under ADR-0011, below. Versioning is described in contract-versions.md.

## Contract v1.1: review policy and exact proposals (P01.T02a PR-B)

ADR-0011 makes ADR-0005 §3 exact. The contracts are core v1.1 `Proposal` (Proposal@2) and `Approval` (Approval@2), both declared replacements of the v1 shapes, plus `ReviewPolicy`, `ReviewPolicyRules`, `ReviewRule`, `RestrictedReviewRule`, `ApprovalDecision`, `ReviewDecisionInput`, `ProposalTarget`, `TargetSelection` and the ceiling types. The rules live in the pure review library `packages/policy/src/review.ts` (`@morrow/policy/review`), which P11.T01 imports; it does no I/O and reads no clock.

- **Exact proposals.** The server builds every proposal. `risk` comes from the fixed effect-to-risk table in `review-policy-defaults.json` (ADR-0011 Q9); `irreversible` is the catalogue flag (Q4); `proposedBy`, `taskId`, `requestedBy` (the task initiator or mandate owner, or the proposer when `taskId` is null under ADR-0018; always a human), `beneficiaryPrincipalIds` and `contextTaint` equal trusted facts; `reviewPolicyRef` is the workspace's single current policy (`storeId` null). `checkProposal` gives each mismatch its own code, `TENANT_MISMATCH` for any reference outside the trusted organization, workspace and proposal store (a store-scoped proposal's scope names exactly its store), and `PARAMETERS_DIGEST_MISMATCH` when `parametersRef.digest` differs from `parametersDigest`. Each target carries `maximumCredits` (integer string) and `maximumCost` (non-negative money or null); the totals are their exact BigInt sums, and the digest is SHA-256 of the RFC 8785 canonical proposal without `proposalDigest`, so every field is bound.
- **Proposals without a task (ADR-0018).** `taskId` may be null only for a human-made Governance-domain proposal, such as an invitation or a grant change that has no work task. Its `requestedBy` is then the proposer, who stays in the conflict set in both roles. Agents, and any other non-human proposer, always name a task, including work under a mandate. With a null `taskId` the schema requires a `governance.*` capability and a `HumanActorRef` proposer (no installation or mandate). `checkProposal` gives `TASK_REQUIRED` for a missing task outside the Governance domain, `TASK_MISMATCH` when the proposal's task differs from the one the producer attached, and `REQUESTED_BY_MISMATCH` unless a task-less proposal's `requestedBy` is the proposer. Schema validity alone does not establish ADR-0018 compliance, because JSON Schema cannot express requester equals proposer: every reader relies on `checkProposal` or the P06.T01b CHECK. Whether a human governance proposal has a task is the producer's choice; `TASK_MISMATCH` only keeps the stored proposal consistent with it. Derived proposals inherit the task, null included.
- **Review rules.** `ReviewPolicy.rules` holds a rule per risk class plus an `irreversible` overlay merged field by field, taking the stricter value (`effectiveRule`). Communication, financial, access_change and irreversible rules can never allow self-approval. Defaults (seeded by P11.T01 as revision 1): internal and external allow self-approval, the restricted classes use solo-owner confirmation; quorum 1; pending 7 d, 72 h and 24 h; approved validity 24 h, 24 h and 1 h; a 300 s cool-down and a 24 h quiet period.
- **Reviewers.** A reviewer is a human member holding `approve` on `governance.approval.decide` and `approve` on the proposal's capability for every decided target (`reviewerEligible`), inside the rule's reviewer list when it is set. The reviewer is checked first: an ineligible, unlisted or foreign-workspace reviewer gets one uniform `REVIEWER_DENIED`, whatever the review's state. The proposer, the requester and every beneficiary are conflicted: they pass only under `allowed`, or as the solo owner with the exact typed phrase. Under `allowed` they therefore count toward a reachable quorum. Any eligible reviewer may reject.
- **Solo owner.** The designated owner (the ADR-0009 owner record), when the only active human member and outside the quiet period after any membership change, may approve their own restricted-class proposal by typing `approve N change(s) for C credits` (plus ` and A CUR` with a cost). The approval takes effect after the cool-down, can be cancelled until then, and is rechecked at `effectiveAt` and at dispatch (`SOLO_OWNER_STATUS_LOST`).
- **Partial approval.** A reviewer may approve a strict subset of an `allowed` proposal's targets. `previewSelection` (also `governance.approval.preview`) returns the deterministic derived proposal: the selected targets, a scope narrowed to their resources and fields (so its scope digest differs from the parent's), re-summed ceilings, inherited timestamps and expiry, `derivedFrom` and a new digest; the decision binds that digest. The derived proposal keeps the parent's parameters artifact, so a dispatcher applies only the derived `targets` (the parent indexes in `derivedFrom.selectedTargetIndexes`) and never the parent's parameters for an unselected target. A family (root plus derivations) has at most one approved member; approving one invalidates every other pending member, and rejecting the root closes the family by invalidating every pending derivation.
- **Decisions.** `foldDecisions` is idempotent per (`commandId`, `requestDigest`): the recorded reviewer's replay returns the recorded result, and the same command with another digest or from another reviewer gives `COMMAND_CONFLICT`. A reviewer decides once per approval; approving the whole proposal and then a selection of it are two approvals, each with its own quorum. `requiredApprovals` distinct approvals by reviewers who are still eligible approve; `effectiveAt` is the last decision, or later after a solo cool-down. Pending approvals expire at `min(proposal.expiresAt, createdAt + pendingExpirySeconds)` and approved ones at `min(proposal.expiresAt, effectiveAt + approvedValiditySeconds)`. `dispatchCheck` refuses an approval that is not yet effective, expired, bound to a superseded policy, whose approving reviewers are no longer eligible enough to meet the quorum, or whose solo status is lost. An unknown commit is read back by `commandId`, never resubmitted.
- **Policy revisions.** `governance.review_policy.revise` is a reviewed access_change; a new revision makes approvals bound to the old one stale (`REVIEW_POLICY_NOT_CURRENT`).

Errors map to existence-free ErrorEnvelopes (`reviewError`). State transitions are the v1.1 rows in state-transitions.json; the v1 `exact_digest_scope_and_current_policy` approval rows are superseded in 1.1.

## Persistence (P06.T01b)

Migrations 0017 (identity bridge) and 0018 (approval records) store Proposal@2, Approval@2 and the workspace ReviewPolicy in `morrow_work` on the ADR-0010 tenant data pattern; `@morrow/work/approvals` is the only writer. Revision 1 of a workspace's ReviewPolicy is seeded from `review-policy-defaults.json` by the first submit. Proposals, parameters, decisions, policies and claims are append-only; an approval changes only along the `state-transitions.json` approval rows at v1.1. Targets are the workspace resource only; agent and store-scoped proposals wait for P05.T04b, P09 and P11.T01. Nothing here executes a capability.

- **Digests.** Every canonical text is the Worker's RFC 8785 output and every digest is SHA-256 of its UTF-8 bytes; SQL proves each digest covers the stored bytes and that the text parses to the row.
  - `Approval@2.scopeDigest` = `sha256(JCS(proposal.scope))`.
  - `ApprovalRef.digest` = SHA-256 of the JCS object `{effectiveAt, expiresAt, id, kind:"approval", organizationId, proposalDigest, revision, scopeDigest, status, workspaceId}` of the stored approval at that revision (`effectiveAt` null until approved). Any status, expiry or revision change voids an older reference.
  - A derived proposal's id is `"derived_"` + SHA-256 of the JCS object `{parentRef, selectedTargetIndexes}`.
  - Stored instants are millisecond-truncated and render as `Date.toISOString()` does.
- **Lazy projection.** Stored pending or approved approvals are projected at database time, in this order: a claim in the family (consumed and terminal: the stored status; claims refuse with `APPROVAL_ALREADY_CLAIMED`, commands with `FAMILY_CONFLICT`); `at ≥ expiresAt` (expired, `APPROVAL_EXPIRED`); a bound ReviewPolicy revision older than the current one (invalidated, `REVIEW_POLICY_NOT_CURRENT`); a solo decision whose owner is no longer the only active human member, or after a later membership change (invalidated, `SOLO_OWNER_STATUS_LOST`, before or after `effectiveAt`). Reads show the projected status; commands and claims that observe a projection return its code and roll back. No settlement is persisted until the P06.T03/P11.T01 scheduler.
- **One-use claims.** A consumer (P05.T01z, P05.T02a, later the P11.T02 gateway) calls `prepareApprovalClaim` with the exact ProposalRef and ApprovalRef: the claimant needs its own current `execute` on the capability over every target, and every counted reviewer must still be eligible. The consumer's own work-owned definer then takes the organization interlock and row `FOR UPDATE` first (`command_prelude_exclusive`), calls `approval_claim` (granted to no role), derives its effect input only from the stored proposal and parameters it returns, and applies the effect through identity definers in the same transaction. One claim per approval family; any other outcome rolls back both the claim and the effect, and an unknown commit is read back by the consumer's command ID.
