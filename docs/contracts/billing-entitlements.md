# Billing and entitlements

Owner: Morrow platform owner. Decisions: ADR-0015 (billing routes by origin; supersedes ADR-0006) with its follow-up decisions OQ-1 to OQ-3, and ADR-0011 Q8 (kill switches). Packet: P01.T04a. P01 defines records and semantics; P11.T04a enforces admission and reservations; P18.T01a-c qualify both payment routes. No checkout, charge, purchase, refund, provider call or credential exists in P01.

## Two routes, chosen by origin

Each workspace has exactly one billing route, held server-side in a `WorkspaceBillingRoute` record:

- **`morrow_direct`**: Morrow sells. Stripe Billing collects, Stripe Tax computes tax, and Morrow is the seller of record. Only a website signup that pays before any store is linked reaches it.
- **`shopify_app_pricing`**: Shopify App Pricing collects, with the same tiers. Every other paying workspace, including every merchant who arrives from Shopify.

The route is unset until the workspace's first completed payment and never changes afterwards. A checkout return, return URL, query value, plan handle, browser login, prompt or valid-looking schema never sets or proves it.

### Rules R1-R11

An **association** is an installation's `workspace_store_links` row (migration 0005: one per installation, never reassigned or deleted). A **current link** is an association whose installation is installed and whose connection is not disconnected.

| Phase | Condition | Purchase surface | Paid work |
| --- | --- | --- | --- |
| `open` | no route; origin `website`; no installation ever associated | `morrow` (`subscribe` only) | denied (`BILLING_NO_ROUTE`) |
| `shopify_bound` | no route; origin `shopify_install`, or any installation ever associated | `shopify` while a link is current, else `none` | denied (`BILLING_NO_ROUTE`) |
| `morrow_direct` | route fixed to `morrow_direct` | `morrow` | per entitlement and credits |
| `shopify_app_pricing` | route fixed to `shopify_app_pricing` | `shopify` while a link is current, else `none` | per entitlement and credits |

- **R1 Origin.** Written once, in the creating transaction. `website` only for the website signup flow when no unconsumed install handoff exists for the creating principal or browser family; `shopify_install` for every other or unrecognized flow. The install handoff (P09.T02a) is kept after it expires, so an expired handoff still routes signup to the install continuation. A missing route record reads as `shopify_install`, so a reader gap never offers Morrow checkout.
- **R2 Shopify binding.** The first association of any installation with a workspace that has no route sets `shopifyBoundAt` in the link transaction; it is never cleared. Linking is never denied for billing reasons. The same transaction re-classifies the installation's held payments and enqueues expiry of the workspace's open Morrow checkout sessions.
  - **MVP supersession (ADR-0022 item 5, M2 PR-2).** For the MVP a link needs a route already fixed to `morrow_direct`, in every environment and for every candidate kind: `link_workspace_store` refuses anything else with `billing_route_required`, and the preview issuer answers 409 `billing_route_required`. Linking therefore never sets `shopifyBoundAt` (0020's variant check requires it null on a `morrow_direct` route), and nobody is granted UPDATE on it. Install-first and Shopify-route workspaces are refused. An install continuation exists only for an already-existing invited workspace and is bound to no browser family before sign-in, so `installHandoffPending` stays false and 0021's `signup_billing_route()` is unchanged. The route is read through `morrow_billing.link_route_current` (0025), a one-row read bridge for the identity owner's definers.
- **R3 Completed payment.** Money actually collected: a verified event with `amountPaid > 0`. A $0 invoice (trial, 100% coupon, customer balance, credit note), Stripe `trialing`, an App Pricing trial or null `currentBillingCycle`, a free plan, a 100% discount and a $0 development-store contract never fix a route or grant credits. The route fixes once, in the transaction that accepts the first completed payment: a Stripe `subscription_period` fixes `morrow_direct` only in phase `open`; an App Pricing `subscription_period` of an associated installation fixes `shopify_app_pricing` only in phase `shopify_bound`. Morrow's serialized route-row lock orders them, never provider timestamps.
- **R4 Immutability.** No API, client input, provider event or operator flag switches a fixed route. Moving a paying workspace needs a new owner decision.
- **R5 Payers.** `morrow_direct`: one storeless BillingAccount for the workspace (one Stripe customer and subscription) pays for work on every currently linked store. `shopify_app_pricing`: one BillingAccount per associated installation, created at its first completed payment and kept across disconnects; its credits are spendable only while its link is current. Another shop's subscription never pays for work on this shop.
- **R6 Multi-store.** Linking or disconnecting never changes the route, creates a `morrow_direct` payer, or writes a reservation, liability or meter event. Shopify-route multi-store work declares an explicit allocation. No account of another workspace is ever charged.
- **R7 No double billing.** A Stripe payment for a `shopify_bound` or `shopify_app_pricing` workspace (including one completed before a link but verified after it), an App Pricing payment on any installation of a `morrow_direct` workspace, a second subscription for the same payer while the current one is not terminal, a payment on a terminal subscription and a top-up without a billable subscription are **route conflicts**. A conflict fixes, entitles and grants nothing, and is keyed by `(workspace, payment route, subscriptionKey)` (or `paymentKey` for a top-up), so repeat invoices attach to one open conflict.
- **R8 Held payments.** A verified payment that cannot be classified yet is held by `paymentKey`: never dropped, never refunded automatically. Reasons: `INSTALLATION_NOT_ASSOCIATED` (re-classified in the link transaction), `CUSTOMER_NOT_MAPPED` and `NOT_MORROW_INITIATED` (resolved only by P18.T01c with owner approval), `TERMS_MISMATCH`, and `SUBSCRIPTION_NOT_CURRENT` (a plan change before its subscription's period is accepted, or a period of a subscription not yet recorded for its payer, including a new subscription after a terminal one; re-classified when that period is accepted or when the entitlement fold records the payer's subscription, in the fold's transaction, so two resubscriptions are never both granted).
- **R9 Mode.** The environment comes from the composition root, never from a request or provider event. Stripe mode is the `livemode` of the event and of the object read back, on the account the broker verified. Shopify has no test flag: a record is `test` when the installation's shop is a development store or the cycle's effective price is $0, else `live`. Production accepts only `live`; development and staging only `test`. A record in the other mode neither fixes, entitles nor grants (`PAYMENT_MODE_REFUSED`).
- **R10 Morrow's ledger is the only credit source.** `creditUnits` come only from the versioned `BillingTerms` table, keyed by the price or plan read back from the provider object; a published price key keeps its credit quantity forever. An unknown key, a kind or currency that disagrees, or a plan change with no entry is held as `TERMS_MISMATCH`. Morrow grants once per `(route, mode, paymentKey)`; credits are still reserved before dispatch (P11.T04a). Stripe billing-credit objects are never created or read. `morrow_direct` top-ups are one-off Stripe invoices granted after `invoice.paid`. Shopify-route extra credits are post-paid usage under a Morrow `UsageCap` (zero by default) that bounds each cycle's credits and USD liability, settled as v1 `UsageLiability` and `MeterEvent` records, never a payment event or a grant.
- **R11 Reversals.** A verified refund or dispute of a granted payment is a `PaymentReversal`. While it is `open`, the payer is not billable even though Stripe reports the subscription `active`; existing reservations follow the retained-work contract. A reversal of a payment that granted nothing is recorded only; one verified before its payment is granted (webhooks arrive in no order) blocks the payer once the grant lands.

## What is paid work (implemented in P01.T04a PR-A)

`docs/contracts/paid-work.json` is the one table. `isPaidWork(capabilityId, verb)` (`@morrow/policy/paid-work`) is true when the capability is unknown (fail closed), or when its effect is `billable_job`, `spend`, `external_write` or `communication`, it is not a kill switch and the verb is not `view`, `propose`, `approve` or `delegate`. `execute` and `administer` are therefore gated on 27 catalogue capabilities (28 have a paid effect; `ads.campaign.pause` is a kill switch). The human evaluator returns `entitlement_denied` only when `!entitlementAllowed && isPaidWork`, so reads, setup, linking, invitations, approvals, exports, privacy and every kill switch never read entitlement; `provider_denied` still comes first for every capability. The agent kernel is unchanged: every agent operation is metered model work, so it checks entitlement on every operation (`agent-authority.md`).

`inspectPaidWork` (`npm run verify:billing`) enforces PW1 (closed table, unique enum members, `execute` and `administer` always gated, `view` and `approve` never), PW2 (no kill switch is paid), PW3 (every `budget_reservation` capability is paid), PW4 (no `read`, `internal_write` or `control` capability is paid) and PW5 (no row of `owner-bootstrap-v1`, `workspace-member-v1` or `workspace-admin-v1` is paid with its template verbs; the lists are in `fixtures/P01.T04a.json`). Narrowing the table is a billing change and needs an ADR.

**Entitlement writers.** `entitlementAllowed` is set only by the billing constraints reader (`createBillingConstraintsReader`, PR-B) and copied by its two forwarders, `createHumanPolicyService` and `createWorkspacePermissionBoundary`. Every other product builder under `apps/` and `packages/` passes a literal `false`. `inspectEntitlementWriters` (`npm run verify:boundaries`) fails any other write with `ENTITLEMENT_WRITER_UNAPPROVED:<file>:<line>`. A later reader (P05.T04b) adds itself to the allowlist in its own reviewed PR.

## Test entitlement seed (ADR-0015 follow-up decision OQ-2 (a))

`TestEntitlementSeed` is an owner-run, audited, capped and expiring test entitlement for one workspace and named stores (`mode` is always `test`). `evaluateTestEntitlementSeed` (`@morrow/policy/billing-state`) accepts it only in `development` and `staging`, between `validFrom` and `validUntil`, and only for its own tenant. An accepted seed covers the named stores and gives one storeless seed payer whose `creditUnits` is the cap. Production readers refuse every seed without reading it (`SEED_REFUSED_IN_PRODUCTION`). A seed fixes no route, creates no account on either route and is never a payment. The M4 packets build its table and writer; each use on hosted staging needs a per-action owner approval. The OQ-3 review allowance (one named development store in production, per-action owner approval) extends the writer later (P18.T01b/P18.T05); it is not accepted by this contract.

## Staging operator test entitlement (ADR-0022 item 5 amendment, 2026-10-21)

Not a seed. While the Stripe switch is off, the owner's operator command (`staging:test-entitlement`, staging-card-1 E13, approved and recorded per use) puts one named staging workspace on the beta plan without Stripe. In one transaction (`morrow_billing.operator_test_entitlement_grant`, migration 0035) it:
- fixes the route to `morrow_direct` in test mode with the same columns and guards a verified payment's fix uses, naming `morrow:operator_entitlement:<id>` (an `OperatorEntitlementKey`) in place of a payment key;
- creates the storeless account and an operator grant record (`operator_test_entitlements`);
- funds the wallet from that record with the credits of the current terms' one `operator_test_entitlement` entry (300, R10);
- writes one active snapshot, valid for 30 days, whose `subscriptionId` is the same key.

No receipt, `VerifiedPaymentEvent` or `CreditGrant` is written. Readers treat the result as a Morrow-direct payer (billable on staging; `mode_refused` in production under R9); the billing period is the snapshot's. The database refuses outside a database marked `staging` (`platform_environment`, written once by `staging:seed-platform`), refuses every runtime login and session, and refuses a workspace that is not in phase `open` (R2, R3): any route already fixed or Shopify-bound, any store association (an M2 PR-2 store installation that is or was linked, read through `morrow_identity.work_store_installations`, which migration 0034 lets the work owner call), an account or an earlier operator grant (`route_conflict`), or any Stripe customer, operation, checkout or receipt (`stripe_conflict`).

Renewal (v1 build order PR 6, ADR-0035 items 3 and 4; migration `staging-test-credits-renewal`; `staging:test-credits -- renew`): only for the owner's workspace (the one the live-store app invites), named with its grant in the committed record `docs/decisions/test-credits-staging.json`. `morrow_billing.operator_test_entitlement_renew` renews the grant for the 720-hour period that contains the database's clock, on the grid that starts where the grant's period ended, once per period (`current` writes nothing). A period's credits come only from the current terms' one `operator_test_entitlement` entry, read exactly as the grant reads it (R10); no argument or record names an amount. It writes an `operator_test_entitlement_renewals` record with the terms revision its credits came from, tops the wallet's unspent credits (available plus reserved) up to those credits and never above them, and writes the account's next snapshot (same key, active for that period, the renewal's digest as `providerEvidenceRef`). Raising them (more than the grant's 300 a period, ADR-0035 item 4) is a new staging `BillingTerms` revision, published only with the owner's per-use approval, which the revision names as its committed owner record (`ownerRecord`: the revision, the credits and the owner's words naming them; `verify:billing` and `seed-platform` refuse operator credits other than 300 without it, PR 6 review R2); the next renewal reads it, and the period already written keeps its credits. Terms without the one operator entry refuse a due period (`terms_missing`). The route, the account and the grant record are unchanged, and no receipt, `VerifiedPaymentEvent` or `CreditGrant` is written. A renewal record written any other way must be the one the renewal would write at that moment (its INSERT guard, PR 6 review R1), the wallet takes a renewal's funding only as the room below the current terms' operator credits, and an operator snapshot's successor needs an active account. `staging:test-credits -- renew` renews only while the database's terms are the staging revisions committed at verified main (each raise with its owner's committed record): a stored revision the committed file lacks, or one that differs from it, is `STAGING_SEED_DRIFT` before the renewal runs (PR 6 review T1).

## Contracts

`schemas/v1.1/billing.schema.json` (`urn:morrow:contracts:billing:v1.1`) is the billing layer of contract v1.1; billing v1 stays byte-identical, and a billing definition resolves to the newest billing layer that defines it (`contract-versions.md`). It adds `BillingRoute`, `PaymentMode`, the canonical keys (`PaymentKey`, `SubscriptionKey`, `PriceKey` and their per-route forms), `WorkspaceBillingRoute`, `VerifiedPaymentEvent`, `PaymentReversal`, `BillingTerms`, `UsageCap`, `UsdBillingMoney`, `TestEntitlementSeed` and `OperatorEntitlementKey` (the staging operator test entitlement, above), and replaces `BillingAccount`, `EntitlementSnapshot`, `CreditGrant`, `AllocationShare` and `CostAllocation` (`changes.json`, ADR-0015). Route couplings are `oneOf` branches of closed objects: a Morrow-direct account, entitlement and share are storeless; a Shopify one names its installation and store; a Shopify event is never a top-up; keys must match the route; Shopify-route amounts and currencies are USD. Every key is a valid core `Id`. `CreditWallet`, `CreditReservation`, `UsageLiability`, `MeterEvent` and `VendorCostReservation` keep their v1 shapes; `MeterEvent.subscriptionId` holds a `SubscriptionKey`. JSON Schema rejects only an exactly repeated terms entry; a terms table that repeats a `(route, mode, priceKey)` with different values is rejected by the billing library (`BILLING_INPUT_INVALID`, PR-B). `AllocationShare@2` carries no route, so the schema accepts an allocation that mixes a storeless share with a store-bound one; the billing library rejects it (see Consumer obligations).

### Provider payment to event kind and amount

Stripe `billing_reason` `subscription_create` or `subscription_cycle` is a `subscription_period`; `subscription_update` (a proration invoice) is a `plan_change`; `manual` on a Morrow top-up invoice is a `top_up`; any other reason maps to `TERMS_MISMATCH` (`stripePaymentKind`): such an invoice is not a `VerifiedPaymentEvent`, so P18.T01a's ingress records it as held `TERMS_MISMATCH` by its payment key and never drops it. `amountPaid` is the invoice's `amount_paid` on a `paid` invoice that was not paid out of band. On Shopify, a period's amount is the cycle's effective recurring price once the cycle has started and while the subscription is not frozen; P18.T01b confirms against the Partner API reference which record proves each cycle's charge before it emits any Shopify event.

## Persistence requirements (no migration in P01.T04a)

1. **Route row.** One per workspace, inserted in the creating transaction with the origin from `originForCreation`. P01.T04a PR-B ships that function; PR-A does not, so PR-A alone triggers no route-row work. P05.T01x Part B merged first, so the first billing child writes the row (not `create_first_organization`) and backfills `website` only for workspaces that predate the install handoff. A trigger refuses changes to a set `origin`, `route`, `mode` or `route_fixed_at`, and any clearing of `shopify_bound_at`. The link writer sets `shopify_bound_at` under the row lock.
2. **Install handoff (P09.T02a).** Bound to the installation, the receiving browser family and, after sign-in, the principal; consumed only by the install continuation; retained after expiry; read by signup in its creating transaction.
3. **Accounts and customers.** One `morrow_direct` account per workspace, created in the route-fixing transaction; one Shopify account per installation, created at its first completed payment. The Stripe customer mapping is one-to-one (`UNIQUE (workspace_id)`, `UNIQUE (stripe_customer_id)`); the customer is created in the broker with an idempotency key before the first checkout, and Checkout always passes it, never `customer_email`.
4. **Grants.** `UNIQUE (route, mode, payment_key)`; the grant and its wallet credit commit together; a duplicate insert is a replay.
5. **Ingress and provider reads.** The event writer has no browser session. Stripe: one public api route forwards the raw body and `Stripe-Signature` unparsed over the service binding to the broker, which verifies the signature over the raw bytes (5-minute tolerance; the previous secret only during a rotation roll), checks `livemode` and the account, deduplicates by event id and reads the object back before any write. The tenant comes only from the customer mapping, cross-checked against the OperationLedger operation named in metadata. Shopify App Pricing sends no subscription webhooks: the welcome-link redirect's `shop` and `plan_handle` only schedule a Partner API read; the shop id comes from the OAuth-verified installation. Handlers acknowledge after commit and read back an unknown commit.
6. **Outbound Stripe writes and unknown outcomes.** Each carries an idempotency key bound to its OperationLedger operation and the operation id in metadata. On an unknown outcome: read back first; replay with the same key only after proven absence and under 23 hours; otherwise hold for P18.T01c; never send with a new key.
7. **Checkout intent and the link race.** Checkout intents are recorded under the route-row lock with the route revision, one open session per workspace. The success return proves nothing; the broker reads the session and invoice back. A payment completed at Stripe but verified after a link is `ROUTE_MISMATCH`.
8. **Reader.** The billing facts reader runs in the same tenant-scoped transaction as the identity read, under FORCE RLS, with no tenant or actor parameter.
9. **Conflicts.** Append-only, one open conflict per key; P18.T01c's first remediation (owner-approved per action) stops the renewal, and refunds follow.
10. **Held payments.** Append-only by `paymentKey`, never deleted or refunded automatically. Every writer that folds a payer's entitlement (P18.T01a, P18.T01b, P18.T01c reconciliation) re-classifies that payer's held `SUBSCRIPTION_NOT_CURRENT` payments in the same transaction.
11. **Reversals.** `charge.refunded`, `charge.dispute.created` and `charge.dispute.closed` trigger a readback; rows are append-only by revision.

### As built in M5 PR-1 (Morrow-direct, test mode)

Migration `billing-records` (work owner) and `billing-identity-bridge` (identity owner) realise items 3-8 for the Stripe route; `docs/contracts/billing-api.md` is the route and webhook contract.

- **Item 1** was delivered by M2 PR-1 (the signup route-row trigger); `create_first_organization` is replaced to issue owner template v2 and the trigger still fires.
- **Associations.** The billing records read a workspace's associations through M2 PR-2's identity bridge `morrow_identity.work_store_installations`: an association is a store installation that is or was linked (its `linked_at` is set, so it has its `workspace_store_links` row); it is current while its status is `linked`. An installation that was never linked is not an association, so it blocks neither checkout nor the route fix. Checkout and the route fix refuse any association (lab:billing D8, D8b).
- **Item 3.** `billing_accounts` (BillingAccount@2, one `morrow_direct` account per workspace, created in the route-fixing commit); `stripe_customers` (one per workspace, unique customer id, recorded only when the broker settles the customer operation, never an email).
- **Item 4.** `credit_grants` (CreditGrant@2, unique per route, mode and payment key, funding exactly one wallet revision in the same commit) and `credit_wallets` (CreditWallet@1 per account; `wallet_guard` admits a grant-funded increase or a move that keeps available + reserved + consumed). Credit units come only from `billing_terms`. Grants carry no expiry: unused credits roll over while the subscription is active (ADR-0022 item 11 amendment).
- **Item 5.** `stripe_event_receipts`: the broker's own login records each verified event with the closed normalised object (ids, amounts, statuses and times only) and its digest; the tenant comes only from the customer mapping of that mode. The api applies a receipt only through the receipt-only ingress definers (ADR-0022 item 9 amendment): `receipt_begin`, `receipt_apply` and `receipt_status`, which refuse any session or lease context and re-derive the payment key, mode, amount, price, period, operation and credit units in SQL. `receipt_applications` keeps each receipt's one outcome; `verified_payment_events` (VerifiedPaymentEvent@1) keeps attributed subscription-period payments with their outcome, including held and conflict outcomes.
- **Item 6.** `stripe_operations` names the purpose of each `stripe_write` operation; `stripe_op_begin` sets the send fence before any call and `stripe_op_settle` never promotes an uncertain operation without a provider result. Reconciliation is on the client's retry with the same `Idempotency-Key` (no background reconciler in M5); uncertain operations stay visible. A first send's refusal fails an operation only while it is still `dispatching`. A customer operation still uncertain once no replay or send can run (24 hours after creation, an hour after its send fence, re-checked on the database clock) is reconciled by the strongly consistent customer list over every time it could have been created: one customer is read back and verified, none settles it `absent` (`verified_no_effect`; every open intent it serves fails, so the next checkout starts a new customer operation), and anything Stripe cannot prove (several customers of the operation, or more than five pages) holds it (`held_at`). A held operation is never reconciled again until the operator resolves it: checkout answers `customer_held` and the billing view shows `setupHold`. The operator (`staging:billing-customer-resolve`, the owner's audited script, per-action approval and a live record) either retries after correcting Stripe (the broker's proof runs again) or abandons it after deleting or finding no customer of the operation (a failure, never a success); each resolution is recorded in `stripe_operation_resolutions`.
- **Item 7.** `checkout_intents`, one open or completed intent per workspace (partial unique index), recorded under the route row's lock; an open intent past its Stripe expiry plus five minutes is closed lazily by the next checkout, and `checkout.session.expired` closes it.
- **Item 8.** `createBillingFactsReader` reads the tenant's own rows in the session transaction under FORCE RLS, with no tenant parameter, and also returns the billing period, the wallet and the open intent.
- **Item 9** is derived: open conflicts are the `ROUTE_MISMATCH` and `DUPLICATE_SUBSCRIPTION` outcomes recorded on `verified_payment_events`; remediation (P18.T01c) is later.
- **Items 10 and 11** are M6: a held `SUBSCRIPTION_NOT_CURRENT` payment (a resubscription after cancellation, for example) stays held and logged, and checkout in `morrow_direct` stays refused until re-classification exists; reversals are not ingested.
- **Terms.** `billing_terms` holds `BillingTerms@1` revisions with display offers and the published digest of `docs/decisions/billing-terms.json`; revisions are contiguous and immutable.

## Denials, surfaces and obligations

Billing denials use frozen ErrorEnvelope rows (`BILLING_DENIAL_ENVELOPES`, P01.T04a PR-B). No message names a provider, price or checkout, so a denial cannot expose Morrow checkout to a Shopify-origin merchant, and every payer denial shares one envelope.

| Codes | `code` / `retryClass` | Safe message |
| --- | --- | --- |
| `BILLING_NO_ROUTE` | `denied` / `recheck_before_retry` | "Paid work starts once this workspace has an active plan." |
| `BILLING_NOT_ACTIVE`, `STORE_NOT_BILLABLE` | `denied` / `recheck_before_retry` | "A plan covering this work is not active." |
| `STORE_NOT_LINKED` | `denied` / `recheck_before_retry` | "This store is not connected to this workspace." |
| `ALLOCATION_REQUIRED`, `PAYER_SELECTION_REQUIRED` | `missing_input` / `recheck_before_retry` | "Choose which store pays for this work." |
| `PAYER_NOT_BILLABLE`, `PAYER_OUTSIDE_WORK_SCOPE`, `DUPLICATE_PAYER_OR_STORE` | `denied` / `recheck_before_retry` | "This payer cannot pay for this work." |
| `ENTITLEMENT_NOT_CURRENT` | `conflict` / `recheck_before_retry` | "Billing changed; review the work again." |
| `PURCHASE_ROUTE_MISMATCH` | `denied` / `never` | "Manage this workspace's plan where it was purchased." |
| `SUBSCRIPTION_EXISTS` | `conflict` / `never` | "This workspace already has a plan; change it instead." |
| `SUBSCRIPTION_REQUIRED` | `missing_input` / `recheck_before_retry` | "Choose a plan first." |
| `BILLING_FACTS_INVALID`, `BILLING_INPUT_INVALID` | `unavailable` / `safe_read_retry` | "Billing status is unavailable. Try again." |

Payment outcomes, held reasons, conflict codes and `PAYMENT_MODE_REFUSED` are internal and never shown. `CREDITS_EXHAUSTED` (`budget_exhausted`) stays with P11.T04a.

**Call-to-action rule.** A purchase link or purchase wording on any Morrow surface comes only from `billingCallToAction` (PR-B): P14 screens, notifications, inbox items, emails, the Coordinator's and agents' billing tool results, and P11.T04a's `CREDITS_EXHAUSTED` message. In a Shopify phase it never returns a Morrow billing path, the word "checkout", a provider name, a price or a currency. Connector screens show none and never describe off-platform billing, even for stores of `morrow_direct` workspaces.

## One work-credit balance and accounting

CreditGrant distinguishes included and purchased credits, the payment it came from, the terms revision, effective time and optional expiry. CreditWallet projects available, reserved and consumed whole internal units. Credits price complete work; they are neither cash nor provider tokens. Extra credits need an explicit purchase or an owner-authorized capped mandate; top-ups default off. Prices, tiers, credit quantities, trials, proration, refunds and top-up terms are P18 pricing decisions (ADR-0015 item 4); no provisional price is active.

Reserve all allocation shares atomically before paid work. CreditReservation holds maximum credits; payer liabilities and VendorCostReservation hold separate cash ceilings. UsageLiability separates merchant credits, merchant cash liability and actual vendor cost; unknown vendor cost is uncertain, never zero. MeterEvent binds reconciled usage to the original subscription and meter; a submitted or uncertain event never gets a new id or a blind retry. Cancellation and suspension stop new paid dispatch; unsent reservations release; submitted liabilities reconcile without new commercial work. Credit exhaustion never blocks reads, approvals, exports, privacy handling or stops.

## Validation and evidence

Reject unknown fields, coercion, invalid revisions, float credit counts and unspecified currencies. Money is an exact decimal string; credits are exact integer strings; never infer FX. Service failures use the core ErrorEnvelope. `scripts/billing-checks.mjs` is a deterministic contract simulator; it cannot prove concurrent transactions, provider ordering or invoice acceptance. Since P01.T04a PR-B it checks contract v1.1 allocations against the route, the environment's mode, current links, open reversals and Shopify-route usage caps, and grants only through the billing library's `classifyPayment`. The reviewers' specifications of `classifyPayment` and `purchaseDecision` are the first-match rule lists in `decision-tables/*.rules.json`; `scripts/billing-decision-tables.mjs` generates the checked-in tables from them, and the tests check the library against every row. Run `npm run verify:billing` (under tsx: paid work, the tables' `--check` and five walkthroughs), `npm run verify:contracts`, `npm run verify:boundaries` and `npm run test:billing`.
