# Shopify projection and reconciliation

Version: 1.0.0 candidate. Owner: Morrow platform owner. Review: Codex semantic self-review plus schema/fixture checks; integration qualification remains required. Canonical plan sequence: 13. Consumer: P09.

## Shape and ownership

Schemas: StoreInstallation, SnapshotRef, Evidence. Exact field types, nullability, required properties and closed object validation are in schemas/v1/core.schema.json; capability bodies are in capabilities.schema.json. State actors and guards are in state-transitions.json. Representative valid/invalid fixtures are in fixtures/P01.A02.json. Payload references are immutable scope/revision/digest bindings, not storage URLs or bearer credentials.

## Command and query semantics

Pin the Admin GraphQL version after P01.T03 qualification. Authenticate Shopify entry using supported server flows. Minimum/optional scopes are feature-specific. Bulk bootstrap tracks checkpoints while webhooks persist into a deduplicated inbox; verify raw-body signature first. No webhook delivery/order assumption: reconcile authoritative reads and maintain tombstones. Order-age and protected-data gaps remain coverage rather than invented facts. Refresh races serialize per credential version.

## Failure invariant

Late update cannot resurrect a deleted product; scope changes block affected reads/writes immediately. Failures use ErrorEnvelope and must not leak inaccessible content. Current policy and resource checks apply to all reads, mutations and derived artifacts.

## Compatibility and evidence

Every command/read declares schema version 1. Unknown fields and invalid enum values fail validation; no implicit coercion/default authority. Breaking fields/states/meaning require a new version and explicit migration with retained workflow histories. Additions remain opt-in via negotiated schema versions, not silently accepted fields. Consumers pin reviewed contract revisions. Run npm run verify:contracts and npm run test:contracts for contract fixture evidence; these do not prove production authorization or provider access. Open provider/region/retention/billing targets remain in the decision register and block consumers that need them.

## MVP connector protocol (M2 PR-2; ADR-0022 items 4-6; ADR-0008 as amended 2026-10-20)

One custom-distribution app per beta development store, registered in `morrow_identity.shopify_apps` (app key, public client id, the SHA-256 digest of the intended `*.myshopify.com` domain, the invited workspace, the install link). The install link names the shop, so it is store content: retirement clears it and `shop/redact` clears it (M2 PR-3). A shop with an installation that is not uninstalled cannot be registered again or installed through another app. The connector Worker (`apps/shopify-connector/worker/`) runs on its own hostname, binds only `MORROW_ENVIRONMENT`, the reviewed identifiers, the broker's `ConnectorBroker` entrypoint and two Workers rate limits, and holds no secret or Shopify library. Without its identifiers it is 503 on every path.

- **Ingress limits** (M2 PR-2 review): every request that would reach the broker is first counted per client address (`CF-Connecting-IP`, hashed), launch, status and callback at 20 a minute and webhooks at 300 a minute (Shopify's delivery addresses carry every store's webhooks); over the limit is 429, and a missing address or a failed limiter is 503. In the broker, nothing reaches the vault login unless it is shaped like Shopify's request; an isolate that holds the app's secret (read within the last 60 s) verifies Shopify's HMAC before the registry read; and per isolate at most one ingress transaction whose signature could not be checked first, and three in all, run at once (more are held: 503, and Shopify retries webhooks).

- **Launch** `GET /shopify/a/:appKey/launch`: `ConnectorBroker.shopifyLaunchVerify` checks the query HMAC (sorted, form-encoded parameters without `hmac` and `signature`, constant-time compare, timestamp window) with the app secret from the vault and the shop against the registry digest. A linked installation shows a status page and starts no OAuth. Otherwise the connector opens one OAuth state as `morrow_connector_ingress` (`connector_oauth_state_open`: the digest only, 10 minutes, single use, at most 10 open per app), sets `__Host-morrow_shopify_state` (Secure, HttpOnly, SameSite=Lax, Path=/, Max-Age=600) and redirects to `https://<verified shop>/admin/oauth/authorize` with the client id, the fixed scopes `read_products,write_products`, the exact callback `redirect_uri` and the state, and no per-user option (an offline token).
- **Callback** `GET /shopify/a/:appKey/callback`: the cookie must equal the query's state before any broker call; the cookie is always cleared. `ConnectorBroker.shopifyInstallComplete` then, in order: in one transaction committed alone, reads the app secret, checks Shopify's HMAC and timestamp, and only then claims the state (so an unsigned or stale callback consumes no state, and a replay or an expired state never reaches Shopify); checks that the shop is the claimed one; exchanges the code once (`POST https://<shop>/admin/oauth/access_token`; a lost reply is `exchange_uncertain`, never retried); requires the expanded granted scopes to equal the requested ones exactly (`write_products` implies `read_products`; an extra scope is refused); reads the one fixed `ShopIdentity` document (Admin API 2026-10) and refuses a store that is not a Partner development store; then, in one transaction on the vault login, seals the token (AES-256-GCM; the additional data binds environment, tenant, credential, subject = installation, version and KEK version), stores the credential version (a re-authorisation destroys the previous one) and, through identity bridges, the installation, the `shopify_oauth` linking candidate (first install only) and a 5-minute install continuation whose digest only is stored. A lost COMMIT acknowledgement is `outcome_unknown`; the merchant relaunches. The merchant lands on `https://<api>/w/<invited workspace>/connections#handoff=<continuation>`; the fragment never reaches a server.
- **Status** `GET /shopify/a/:appKey/status`: a Shopify-signed GET; a status page with no workspace data.
- **Webhooks** `POST /shopify/a/:appKey/webhooks`: the raw body (at most 256 KiB) and the selected `X-Shopify-*` headers go to `ConnectorBroker.shopifyWebhookVerify`, which checks the base64 HMAC over the raw bytes before any parse and the topic allowlist. A bad signature is 401 with no state change. M2 PR-3: in the same vault transaction the broker minimises the body to its topic's closed shape (`app/uninstalled` and `shop/redact` keep the shop id; `customers/*` keep the shop id, a keyed digest of the customer id and, for a data request, its id; `app/scopes_update` keeps the previous and current scopes) and records it in `morrow_identity.shopify_webhook_inbox` (unique app, shop and webhook id; 7 days) with a compliance topic's `privacy_requests` row, under the tenant the app registry names for the verified shop. The connector answers 200 only once that row exists (a duplicate is 200 too), 400 for a body that is not its topic's and 503 when the record failed or its outcome is unknown (Shopify retries; the retry finds the row). After the response it applies the row on its own login (`connector_inbox_apply`) and asks `ConnectorBroker.shopifyCredentialDestroy` to destroy the token when the applier says so; a five-minute cron re-applies rows still received after two minutes and re-destroys tokens whose destruction is not recorded. By topic: `customers/*` complete "no customer data held"; `app/uninstalled` ends the installation, stops its connection (revoking its leases) and destroys the token; `app/scopes_update` ignores `write_products`-implies-`read_products` and otherwise suspends the installation with the same stop; `shop/redact` ends the installation first if the uninstall has not arrived, runs every store-content handler and completes once nothing is outstanding. The generated app TOML subscribes `app/uninstalled` and `app/scopes_update` and the three compliance topics to this path.
- **Reads** (M2 PR-3): `ApiBroker.shopifyRead` and `RuntimeBroker.shopifyRead` run one fixed Admin GraphQL document under a live lease (the collections and products pages for the api's catalogue routes; one product's listing fields for a run) and return closed minimised JSON (`docs/contracts/work-api.md`, "Catalogue routes").
- **Link**: the P09.T02a issuer and `link_workspace_store` admit only the organization's owner (its founding principal), to whom the store-link template's grants go (ADR-0022 item 3); the connections read offers the install link to the owner only.

All provider calls in CI go to the synthetic oracle (`scripts/fixtures/shopify-oracle.mjs`); `lab:shopify-install`, `lab:shopify-connect-workers` and (M2 PR-3) `lab:shopify-privacy` cover the protocol against PostgreSQL 17.
