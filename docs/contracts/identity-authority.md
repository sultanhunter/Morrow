# Identity and authority

Version: 1.0.0 candidate. Owner: Morrow platform owner. Review: Codex semantic self-review plus schema/fixture checks; integration qualification remains required. Canonical plan sequence: 13. Consumer: P05.

## Shape and ownership

Schemas: ActorRef, Scope, Grant, PolicyDecision. Exact field types, nullability, required properties and closed object validation are in schemas/v1/core.schema.json; capability bodies are in capabilities.schema.json. State actors and guards are in state-transitions.json. Representative valid/invalid fixtures are in fixtures/P01.A02.json. Payload references are immutable scope/revision/digest bindings, not storage URLs or bearer credentials.

## Command and query semantics

Trusted identity resolves organization/workspace membership. Installation tokens are provider authority, not human authority. Effective permission is the intersection of current human/automation owner, initiating task envelope, installation grants, resource/field grants, provider constraints and policy. Verbs view/propose/approve/execute/delegate/administer are distinct. No wildcard grants in this baseline. Declared ownership/responsibility never grants access. Revocation increments policy revision and invalidates cached allow decisions before later retrieval or dispatch.

## Failure invariant

Wrong-tenant identifiers return a redacted denied result. Reviewer cannot approve an action to which no eligible execution grant exists. Failures use ErrorEnvelope and must not leak inaccessible content. Current policy and resource checks apply to all reads, mutations and derived artifacts.

## Compatibility and evidence

Every command/read declares schema version 1. Unknown fields and invalid enum values fail validation; no implicit coercion/default authority. Breaking fields/states/meaning require a new version and explicit migration with retained workflow histories. Additions remain opt-in via negotiated schema versions, not silently accepted fields. Consumers pin reviewed contract revisions. Run npm run verify:contracts and npm run test:contracts for contract fixture evidence; these do not prove production authorization or provider access. Open provider/region/retention/billing targets remain in the decision register and block consumers that need them.


## Internal workspace access revocation

Canonical61/P05.T01c adds a local persistence primitive with a separate dedicated executor. It is not a public capability implementation or an organization-wide membership command. No production receipt issuer or approval issuer exists; only isolated laboratory maintenance can seed synthetic authorization receipts.

The exact receipt pins organization, workspace, initiating human membership and session digest, target membership, command ID, request digest, expected organization policy revision, immutable approval-evidence ID and expiry, plus a validated authorizing-grant payload. Every binding must match; a request digest, session digest or receipt ID alone grants no authority. The narrow SQL function checks current locked authority and pinned grant facts after serialization waits. Its private receipt/result tables use tenant foreign keys and FORCE RLS. Neither the ordinary API database role nor agent runtime can invoke it, assume its executor role or write these tables.

One committed transaction deactivates the selected workspace membership, revokes that workspace's target grants, increments organization policy revision and saves receipt consumption plus attributable audit/result. It preserves organization membership, organization-scoped sessions, principal activity and other workspace grants. A preserved session immediately fails current identity resolution in the revoked workspace. Existing permission reads reload current SQL facts and never cache allows.

Exact repeated commands return their original result only after current initiating authority is rechecked. Changed bindings cannot replay that result. Exactly bound expected denials commit a redacted terminal audit without an access mutation. Unexpected database failures roll back; a lost COMMIT acknowledgement remains uncertain, even if a later rollback succeeds. Reconcile the same stable command before creating any new operation. Do not treat an unavailable reply as evidence that revocation failed.

This local operation does not return the public capability's affectedRuns field or cancel runs. Full approval issuance, organization-wide revocation, grant issuance, provider identity and command/dispatch fencing remain separate qualification work.


## Private PKCE and code admission

Canonical69/P05.T01d adds a private pre-authentication admission ledger with exact owner application/configuration and browser/PKCE commitments. One fresh committed reservation is correlation only; it creates no principal, session, membership, grant or provider success. Exact repeats and read-only reconciliation return held correlation, never a second reservation. Unknown commit/release remains uncertain and is not automatic retry authority. Future provider broker/issuer/HTTP transport remain separately qualified. Immutable migration6 excludes PKCE-managed challenges from the old legacy consumer while leaving its historical-only behavior available. No raw code/verifier/browser state is persisted or logged. The detailed canonical protocol and bounded packet govern its SQL roles, locks, late expiry rollback and checks.

## Contract v1.1: human executors and kill switches (P01.T02a PR-A)

`HumanActorRef` (core v1.1) is an ActorRef with kind `human`, a workspace and a membership, and no installation or mandate. It is the actor of every `KillSwitchRecord`. The human evaluator (`packages/policy/src/index.ts`) allows a current human grant holder to execute a kill switch with no approval, returning `recheck_at_dispatch` and `kill_switch_record` (plus `provider_effect_verification` for the external pause). A dispatcher that does not implement an obligation denies dispatch.

Kill-switch targets are checked by `checkKillSwitchTarget` after the evaluator allows `execute`. Every ref and every record an ID resolves to must be in the trusted organization and workspace, and every target, of every kind, must fit within one of the actor's current execute grants for the kill switch (`KillSwitchGrantCoverage`; grants are never unioned): a storeless target needs a storeless grant, a target with a store needs that store, and a campaign or connection needs its connection. Unknown, foreign-tenant and ungranted targets give the same `TARGET_NOT_FOUND` result. Target kinds are v1 `ResourceRef` kinds (`campaign`, `installation`, `member`, `release`), except `connection`, which v1 `ResourceRef` lacks; P05.T01z settles how a disconnect's KillSwitchRecord names it before the Tier 3 sign-off. Until P05.T01z replaces it with the KillSwitchRecord path, the migration-0004 workspace revocation path (`packages/identity/src/workspace-access-revocation.ts`) still requires approval evidence (`approval_evidence_id`) and an `expectedRevision`. The designated owner's membership cannot be revoked through the kill switch (`OWNER_MEMBERSHIP_PROTECTED`); ownership must first move by a reviewed transfer (P05.T01z). Every revocation is flagged as a membership change, which advances `lastMembershipChangeAt` in `WorkspaceOwnershipFacts` (`packages/policy/src/review-facts.ts`). Only trusted readers fill those facts; P05.T01z supplies them from the ADR-0009 owner record and enforces owner protection in SQL.

## Contract v1.1: reviewers and the solo owner (P01.T02a PR-B)

Approval@2 names its reviewers as `HumanActorRef`s. A reviewer is eligible when the human evaluator allows `approve` on `governance.approval.decide` for the workspace and `approve` on the proposal's capability for every decided target (`reviewerEligible` in `packages/policy/src/review.ts`); previewing also needs `view` on `governance.approval.preview`. P05.T01x template v1 grants both to the first owner (ADR-0009 item 7). A recorded decision confers no authority: an earlier approval counts toward the quorum, and an approved proposal dispatches, only while its approving reviewers are still eligible (`eligibleReviewerPrincipalIds` in `DecisionAttempt` and `DispatchFacts`; otherwise `REVIEWER_DENIED`, which invalidates the approval). An ineligible, unlisted or foreign-workspace reviewer gets the same `REVIEWER_DENIED` whatever the review's state. The review library reads `WorkspaceOwnershipFacts` for the solo-owner rule: the reviewer must be the designated owner, the only active human member, and outside the quiet period after the last membership change. Solo status is checked at the decision, at `effectiveAt` and at dispatch, and a membership change after the decision loses it (`SOLO_OWNER_STATUS_LOST`). Like the kill-switch facts, these come only from trusted readers (P05.T01z).

## Self-service enrollment and first-owner signup (P05.T01x Part B, ADR-0009)

Migration 0013 splits self-service into two definer transactions. Neither reads, stores or matches an email, and token claims (`email`, `org_id`, `roles`, `permissions`) never select or create anything.

- **Enrollment** (`admit_account_family`, executor `morrow_identity_sessions`). Account login carries no workspace (`POST /auth/login {"schemaVersion":2}`). At the callback the signature-verified evidence (subject, provider session, profile tuple) admits a browser family. An unmapped `(provider, environment, subject)` enrolls only while the profile's latest `self_service_revisions` row enables it (no row means disabled) and inside the profile's windows (30 per 10 minutes, 500 per 24 hours): principal, mapping and profile binding are created together with an `account_enrollments` row. An existing mapping signs in only through its existing active binding to that exact profile; no binding is ever added to an existing mapping and nothing revoked or inactive is reactivated. Enrollment grants no organization, membership or grant.
- **List** (`account_overview`, executor `morrow_api`, `GET /workspaces`). One read-only statement over one snapshot: the principal derives from the session digest inside SQL (`account_session_principal`, the family half of `session_eligibility`), and every listed workspace is one where `session_eligibility` returns a row. At most 100 entries, ordered by C collation, with `truncated`; `onboarding` is `available` only to a self-enrolled principal with no signup while signup is enabled for its profile. Zero rows answer 401.
- **Signup** (`create_first_organization`, executor `morrow_identity_onboarding`, `POST /organizations`). A human-initiated command: only a browser family can call it. It creates one organization, workspace, owner membership and workspace membership and the fixed grant template `owner-bootstrap-v1` (governance only, workspace scoped, `issuedBy {kind:"service", principalId:"morrow.onboarding"}` as a provenance tag, not a deciding actor). Each principal signs up once (`organization_signups` primary key); the same key and body replay the ids while the founder's workspace membership is active. Signup is the only grant path that bypasses ReviewPolicy.
- **Owner.** The owner of an organization is the principal of its `organization_signups` row while that principal's organization membership is active. Being owner confers no authority; the kernel reads only grants. P05.T01z supplies `WorkspaceOwnershipFacts` from this record.
- **Outcomes.** `outcome_unknown` is answered only after the create statement may have been sent; a same-key retry is the reconciliation. Failures before that (broker lease, connect, role row, BEGIN, a `denied` reply) are `{"code":"unavailable"}`. Replies never set a cookie and never carry CORS headers.
- **Privileges.** `morrow_api` executes only `account_overview` of the new functions and the onboarding executor only `create_first_organization`, whose definer checks `session_user`. No executor reads or writes the four new tables. `create_login_flow_intent`, `admit_browser_family` and `resolve_provider_subject_selection` are no longer executable by their former roles, and the login wiring no longer leases `morrow_identity_resolution`.
- **Kernel.** Performing `governance.connection.connect` still needs `administer`, never `execute`; `approve` on it is now also evaluated (ADR-0011 Q5, ADR-0009 item 7), so a connect proposal's reviewer can be eligible.
