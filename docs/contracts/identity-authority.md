# Identity and authority

Version: 1.0.0 candidate. Owner: Morrow platform owner. Review: Codex semantic self-review plus schema/fixture checks; integration qualification remains required. Canonical plan sequence: 13. Consumer: P05.

## Shape and ownership

Schemas: ActorRef, Scope, Grant, PolicyDecision. Exact field types, nullability, required properties and closed object validation are in schemas/v1/core.schema.json; capability bodies are in capabilities.schema.json. State actors and guards are in state-transitions.json. Representative valid/invalid fixtures are in fixtures/P01.A02.json. Payload references are immutable scope/revision/digest bindings, not storage URLs or bearer credentials.

## Command and query semantics

Trusted identity resolves organization/workspace membership. Installation tokens are provider authority, not human authority. Effective permission is the intersection of current human/automation owner, initiating task envelope, installation grants, resource/field grants, provider constraints and policy. Verbs view/propose/approve/execute/delegate/administer are distinct. No wildcard grants in this baseline. Declared ownership/responsibility never grants access. Revocation increments policy revision and invalidates cached allow decisions before later retrieval or dispatch.

## Failure invariant

Wrong-tenant identifiers return a redacted denied result. Reviewer cannot approve an action to which no eligible execution grant exists. Failures use ErrorEnvelope and must not leak inaccessible content. Current policy and resource checks apply to all reads, mutations and derived artifacts.

## Compatibility and evidence

Every command/read declares schema version 1. Unknown fields and invalid enum values fail validation; no implicit coercion/default authority. Breaking fields/states/meaning require a new version and explicit migration with retained workflow histories. Additions remain opt-in via negotiated schema versions, not silently accepted fields. Consumers pin reviewed contract revisions. Run npm run verify:contracts and npm run test:contracts for contract fixture evidence; these do not prove production authorization or provider access. Open provider/region/retention/billing targets remain in the decision register and block consumers that need them.


## Internal workspace access revocation

Canonical61/P05.T01c adds a local persistence primitive with a separate dedicated executor. It is not a public capability implementation or an organization-wide membership command. No production receipt issuer or approval issuer exists; only isolated laboratory maintenance can seed synthetic authorization receipts.

The exact receipt pins organization, workspace, initiating human membership and session digest, target membership, command ID, request digest, expected organization policy revision, immutable approval-evidence ID and expiry, plus a validated authorizing-grant payload. Every binding must match; a request digest, session digest or receipt ID alone grants no authority. The narrow SQL function checks current locked authority and pinned grant facts after serialization waits. Its private receipt/result tables use tenant foreign keys and FORCE RLS. Neither the ordinary API database role nor agent runtime can invoke it, assume its executor role or write these tables.

One committed transaction deactivates the selected workspace membership, revokes that workspace's target grants, increments organization policy revision and saves receipt consumption plus attributable audit/result. It preserves organization membership, organization-scoped sessions, principal activity and other workspace grants. A preserved session immediately fails current identity resolution in the revoked workspace. Existing permission reads reload current SQL facts and never cache allows.

Exact repeated commands return their original result only after current initiating authority is rechecked. Changed bindings cannot replay that result. Exactly bound expected denials commit a redacted terminal audit without an access mutation. Unexpected database failures roll back; a lost COMMIT acknowledgement remains uncertain, even if a later rollback succeeds. Reconcile the same stable command before creating any new operation. Do not treat an unavailable reply as evidence that revocation failed.

This local operation does not return the public capability's affectedRuns field or cancel runs. Full approval issuance, organization-wide revocation, grant issuance, provider identity and command/dispatch fencing remain separate qualification work.


## Private PKCE and code admission

Canonical69/P05.T01d adds a private pre-authentication admission ledger with exact owner application/configuration and browser/PKCE commitments. One fresh committed reservation is correlation only; it creates no principal, session, membership, grant or provider success. Exact repeats and read-only reconciliation return held correlation, never a second reservation. Unknown commit/release remains uncertain and is not automatic retry authority. Future provider broker/issuer/HTTP transport remain separately qualified. Immutable migration6 excludes PKCE-managed challenges from the old legacy consumer while leaving its historical-only behavior available. No raw code/verifier/browser state is persisted or logged. The detailed canonical protocol and bounded packet govern its SQL roles, locks, late expiry rollback and checks.

## Contract v1.1: human executors and kill switches (P01.T02a PR-A)

`HumanActorRef` (core v1.1) is an ActorRef with kind `human`, a workspace and a membership, and no installation or mandate. It is the actor of every `KillSwitchRecord`. The human evaluator (`packages/policy/src/index.ts`) allows a current human grant holder to execute a kill switch with no approval, returning `recheck_at_dispatch` and `kill_switch_record` (plus `provider_effect_verification` for the external pause). A dispatcher that does not implement an obligation denies dispatch.

Kill-switch targets are checked by `checkKillSwitchTarget` after the evaluator allows `execute`. Every ref and every record an ID resolves to must be in the trusted organization and workspace, and every target, of every kind, must fit within one of the actor's current execute grants for the kill switch (`KillSwitchGrantCoverage`; grants are never unioned): a storeless target needs a storeless grant, a target with a store needs that store, and a campaign or connection needs its connection. Unknown, foreign-tenant and ungranted targets give the same `TARGET_NOT_FOUND` result. Target kinds are v1 `ResourceRef` kinds (`campaign`, `installation`, `member`, `release`), except `connection`, which v1 `ResourceRef` lacks; P05.T01z settles how a disconnect's KillSwitchRecord names it before the Tier 3 sign-off. Until P05.T01z replaces it with the KillSwitchRecord path, the migration-0004 workspace revocation path (`packages/identity/src/workspace-access-revocation.ts`) still requires approval evidence (`approval_evidence_id`) and an `expectedRevision`. The designated owner's membership cannot be revoked through the kill switch (`OWNER_MEMBERSHIP_PROTECTED`); ownership must first move by a reviewed transfer (P05.T01z). Every revocation is flagged as a membership change, which advances `lastMembershipChangeAt` in `WorkspaceOwnershipFacts` (`packages/policy/src/review-facts.ts`). Only trusted readers fill those facts; P05.T01z supplies them from the ADR-0009 owner record and enforces owner protection in SQL.

## Contract v1.1: reviewers and the solo owner (P01.T02a PR-B)

Approval@2 names its reviewers as `HumanActorRef`s. A reviewer is eligible when the human evaluator allows `approve` on `governance.approval.decide` for the workspace and `approve` on the proposal's capability for every decided target (`reviewerEligible` in `packages/policy/src/review.ts`); previewing also needs `view` on `governance.approval.preview`. P05.T01x template v1 grants both to the first owner (ADR-0009 item 7). A recorded decision confers no authority: an earlier approval counts toward the quorum, and an approved proposal dispatches, only while its approving reviewers are still eligible (`eligibleReviewerPrincipalIds` in `DecisionAttempt` and `DispatchFacts`; otherwise `REVIEWER_DENIED`, which invalidates the approval). An ineligible, unlisted or foreign-workspace reviewer gets the same `REVIEWER_DENIED` whatever the review's state. The review library reads `WorkspaceOwnershipFacts` for the solo-owner rule: the reviewer must be the designated owner, the only active human member, and outside the quiet period after the last membership change. Solo status is checked at the decision, at `effectiveAt` and at dispatch, and a membership change after the decision loses it (`SOLO_OWNER_STATUS_LOST`). Like the kill-switch facts, these come only from trusted readers (P05.T01z).

## Self-service enrollment and first-owner signup (P05.T01x Part B, ADR-0009)

Migration 0013 splits self-service into two definer transactions. Neither reads, stores or matches an email, and token claims (`email`, `org_id`, `roles`, `permissions`) never select or create anything.

- **Enrollment** (`admit_account_family`, executor `morrow_identity_sessions`). Account login carries no workspace (`POST /auth/login {"schemaVersion":2}`). At the callback the signature-verified evidence (subject, provider session, profile tuple) admits a browser family. An unmapped `(provider, environment, subject)` enrolls only while the profile's latest `self_service_revisions` row enables it (no row means disabled) and inside the profile's windows (30 per 10 minutes, 500 per 24 hours): principal, mapping and profile binding are created together with an `account_enrollments` row. An existing mapping signs in only through its existing active binding to that exact profile; no binding is ever added to an existing mapping and nothing revoked or inactive is reactivated. Enrollment grants no organization, membership or grant.
- **List** (`account_overview`, executor `morrow_api`, `GET /workspaces`). One read-only statement over one snapshot: the principal derives from the session digest inside SQL (`account_session_principal`, the family half of `session_eligibility`), and every listed workspace is one where `session_eligibility` returns a row. At most 100 entries, ordered by C collation, with `truncated`; `onboarding` is `available` only to a self-enrolled principal with no signup while signup is enabled for its profile. Zero rows answer 401.
- **Signup** (`create_first_organization`, executor `morrow_identity_onboarding`, `POST /organizations`). A human-initiated command: only a browser family can call it. It creates one organization, workspace, owner membership and workspace membership and the fixed grant template `owner-bootstrap-v1` (governance only, workspace scoped, `issuedBy {kind:"service", principalId:"morrow.onboarding"}` as a provenance tag, not a deciding actor). Each principal signs up once (`organization_signups` primary key); the same key and body replay the ids while the founder's workspace membership is active. Signup is the only grant path that bypasses ReviewPolicy.
- **Owner.** The owner of an organization is the principal of its `organization_signups` row while that principal's organization membership is active. Being owner confers no authority; the kernel reads only grants. P05.T01z supplies `WorkspaceOwnershipFacts` from this record.
- **Outcomes.** `outcome_unknown` is answered only after the create statement may have been sent; a same-key retry is the reconciliation. Failures before that (broker lease, connect, role row, BEGIN, a `denied` reply) are `{"code":"unavailable"}`. Replies never set a cookie and never carry CORS headers.
- **Privileges.** `morrow_api` executes only `account_overview` of the new functions and the onboarding executor only `create_first_organization`, whose definer checks `session_user`. No executor reads or writes the four new tables. `create_login_flow_intent`, `admit_browser_family` and `resolve_provider_subject_selection` are no longer executable by their former roles, and the login wiring no longer leases `morrow_identity_resolution`.
- **Kernel.** Performing `governance.connection.connect` still needs `administer`, never `execute`; `approve` on it is now also evaluated (ADR-0011 Q5, ADR-0009 item 7), so a connect proposal's reviewer can be eligible.


## Session lifecycle (P05.T01y, ADR-0004)

Migration 0016 gives every new browser family a 12-hour absolute limit and every generation at most 30 idle minutes, never past its family. Families admitted before 0016 keep the 15-minute shape and never rotate.

- **Rotate.** `POST /auth/rotate` (exact Origin, `application/json`, `X-Morrow-Request: 1`, same-origin or absent Fetch Metadata, no `Idempotency-Key`, body exactly `{"schemaVersion":1}` of at most 256 bytes, then the session cookie under the workspace guard's rules). It runs on the logout configuration, pool and executor (`morrow_identity_logout`) through one definer, `rotate_self_browser_generation`. A current generation older than 60 seconds is retired and generation n+1 is issued in one subtransaction with one `rotated` audit: 200 `SessionRotationResult` `rotated` and one cookie `__Host-morrow_session=<new secret>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=<min(1800, ⌊idleRemainingMs/1000⌋)>`. A younger one is 200 `current` with no cookie and no write. The new secret is a fresh 32-byte CSPRNG value; only its digest leaves the Worker, and it is delivered once, only after the commit. Remaining times are milliseconds relative to the server's delivery instant.
- **Reuse.** Rotating with a retired generation of a live family revokes the whole family (`reuse_detected` audit). Workspace reads deny a retired generation with the ordinary 401 and no side effect; the client session keeper answers every such 401 with one rotate, which presents the retired generation, so a thief who rotates first is detected on the victim's next request. Two concurrent rotations of one generation leave one `rotated` and one `reuse_revoked`; the keeper's cross-tab lock prevents that inside one browser.
- **Refusals.** Denied, reused, expired, unknown, ambiguous or foreign cookies and a cookie with under one second left all answer 401 `{"code":"authentication_required"}`, byte-identical to the workspace routes, with no cookie. Request-proof, body, path and method failures are 403, 400, 404 and 405 `rotation_unavailable`; 503 is `rotation_unavailable` before the statement is sent and `rotation_outcome_unknown` after it. An unknown rotation is never retried or delivered late; if it committed, the old cookie's next request leads to a reuse revocation, so a session is never extended.
- **Logout.** Logout keeps its outcomes and bodies. Only plans produced after the SQL call was invoked carry exactly `__Host-morrow_session=; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=0`: 200 `session_ended`, the SQL 403 and the dispatcher's 503 `logout_outcome_unknown`. Request-proof, body and cookie refusals and every fallback outside the dispatcher carry none, so a cross-site request cannot clear the cookie. Any generation of a family, current or retired, ends that family only.
- **Fixed-name limitation.** A delayed logout from an old tab, arriving after a new sign-in, revokes only its own family on the server, but its clear also drops the newer cookie of the same name in that browser. The newer family then idles out within 30 minutes.
- **Organization sign-out.** Deactivating, deleting or reassigning an active organization membership writes an append-only watermark (`organization_session_signouts`): the trigger locks the principal `FOR SHARE` and then takes the watermark as the later of the clock and every existing family's `created_at` for the principal, and every admission reads its creation instant after locking the principal `FOR UPDATE`, so no family committed before the removal resolves a workspace of that organization again, even after the same membership is reactivated and even if the database wall clock stepped backward. Legacy `sessions` rows of the pair are excluded too. Families still resolve the person's other organizations. P05.T01z's membership commands and P05.T01aa's SCIM inherit this through the trigger.
- **Workspace removal.** `revoke_workspace_access` stops that workspace in every family and generation; it writes no watermark and revokes no family. A later re-add is current authority.
- **Nothing revives.** A revoked or expired family, a revoked binding and a maintenance-revoked generation never rotate; the generation insert trigger and the family-advance branch of the preservation trigger refuse any other shape.
- **Digest-bound flows.** Workspace-access receipts, linking handoffs and reviews, the linking apply and the linking lookup and status bind the generation digest. After a rotation the old digest resolves nothing, so those flows fail closed (a receipt is consumed with a durable `denied` result) and the person repeats the flow under the new cookie. Rebinding them to the family is a follow-up (P09.T01a/T02a for linking, P05.T01z for the receipt).
- **Custody.** Rotation widens ADR-0007 R1 in two ways, both inputs to the production custody ADR (ADR-0007 item 9), which should weigh a dedicated issuer role, Worker (P04.T02b) or query proxy before production mapping. (1) Minting: the `morrow_identity_logout` password plus any live current-generation digest older than 60 s mints a bearer whose secret the caller chooses (the definer stores the caller's new digest), valid for up to the family's remaining 12 hours. Before P05.T01y the role could only end families. (2) Exposure: the issuer-class logout password is now leased on every keeper rotation, about once per 5 active minutes per person, instead of only at logout. EXECUTE is granted only on `rotate_self_browser_generation`; no other privilege widens. The owner accepted both widenings for staging on 2026-10-19 ("Accept for staging (Recommended)"); the production custody decision (ADR-0007 item 9) revisits them.

## Sign-in abuse protection (P05.T01ab, ADR-0019 items 6–8)

The api Worker runs a guard (`apps/api/src/abuse-guard.ts`) before its router and before any SQL. It selects requests with the router's own matcher (`managedApiRoute`, exact WHATWG pathnames): login start (`/auth/login`), the callback (`/auth/workos/callback`) and signup (`/organizations`), for every method the router dispatches to them. A trailing slash or a percent-encoded letter is another path, and a query string is the same path.

- **Counted requests.** Only a request its handler could accept on headers alone is counted, so no third-party page can spend a visitor's budget with requests a browser sends cross-site without a preflight. Another method (anything but POST on login start and signup, anything but GET on the callback) goes uncounted to the router's own 405. A POST without `X-Morrow-Request: 1` gets the route's own 403 (`login_unavailable`, or `{"code":"request_denied"}` on signup) from the guard, with no limit and no verification. A callback GET whose Fetch Metadata, when present, is not a top-level document navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) gets the handler's own 303 to `/auth/result` from the guard, uncounted.
- **Per-address limit.** Workers Rate Limiting: login start 10, the callback 20 and signup 5 per 60 s, per address. The key is the route name plus 32 hex characters of a SHA-256 over the `CF-Connecting-IP` address; an IPv6 address is first cut to its /56 prefix, and an IPv4-mapped one is its IPv4 address. The address is never stored, logged or used for authority. Over the limit: 429 `{"schemaVersion":1,"outcome":"rate_limited"}` with `Retry-After: 60`. The limits are eventually consistent per Cloudflare location, a speed bump beside the per-profile windows above, not a quota.
- **Challenge.** On a counted POST to login start or signup only, the request header `X-Morrow-Challenge` (`ChallengeToken`: 1–2048 bytes of `[A-Za-z0-9._-]`) must hold a single-use Turnstile token. A missing or malformed header is 403 `{"schemaVersion":1,"outcome":"challenge_required"}` with no verification call. Otherwise exactly one `ApiBroker.challengeVerify(action, token, budgetMs)` call decides, with no retry: `passed` forwards the request with only that header removed and its body unread; `failed` is 403 `{"schemaVersion":1,"outcome":"challenge_failed"}`. The callback is only rate-limited. The 403 and 429 bodies are `SignInGuardOutcome` (contract v1.1); every guard reply is `no-store`.
- **Fail closed.** A missing or unparsable address, a `limit()` that throws or answers anything but `{success: boolean}`, and a held, late or non-verdict verification each answer 503 with the route's existing body (`login_unavailable` on login start and the callback, `{"code":"unavailable"}` on signup) and one fixed-code `morrow_edge_guard` line (`ADDRESS_MISSING`, `ADDRESS_INVALID`, `LIMITER_FAILED` or `CHALLENGE_HELD`). Rejections (403, 429) log nothing, except the broker's one `morrow_challenge` line for a failed verification (ADR-0019 item 9 as amended 2026-10-19).
- **Configuration route.** `GET /auth/challenge` (`LoginChallengeConfiguration`, no-store) returns `{"schemaVersion":1,"provider":"turnstile","siteKey","actions":{"login","signup"}}`, or `{"provider":"none"}` where no challenge is configured. An api that did not map serves it like every other route of the deny-all instance (503).
- **Where it is required.** The api mapper (step 10) requires `LOGIN_CHALLENGE_JSON` and the four limiter bindings (the three above and the session routes' `SESSION_LIMITER`, below) in staging and production and fails closed with `API_ENV_ABUSE_GUARD_MISSING`; in development each part is optional, a present part must be valid, and the limiters come all four or none. The mapper still refuses every credential-like binding, so the Turnstile secret can never bind to the api.
- **Broker.** `challengeVerify` is the fourth `ApiBroker` method, a pre-authentication call under the v0 trust model (ADR-0007 items 1, 3 and 4 as amended by ADR-0019 item 6). It accepts a configured action, a token of the header's shape and an integer budget from 1 to 5000 ms, and makes one POST to the fixed `https://challenges.cloudflare.com/turnstile/v0/siteverify` carrying only `secret` and `response`. No redirect is followed (workerd allows only `follow` or `manual`, so it uses `manual` and holds every non-200 reply), and a reply over 4096 bytes is held. `passed` needs `success === true`, the configured hostname (the login origin's), the expected action and a `challenge_ts` within 300 s plus 30 s of skew; any other decoded reply is `failed` and logs one `morrow_challenge {code:"failed"}` (at most 15 a minute per IPv4 address or IPv6 /56 through the limiters; not capped for a client that rotates addresses; about $0.60 per 1M lines; kept by the owner on 2026-10-19, ADR-0019 item 9). Errors are `BROKER_HELD`. The secret `TURNSTILE_SECRET_KEY` must match `^0x[0-9A-Za-z_-]{20,128}$`, which refuses Cloudflare's published dummy keys; it binds only to the broker. A staging or production broker without the challenge capability reports `health()` false.
- **Browser.** The SPA reads `GET /auth/challenge`, loads only `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` (the CSP admits that origin for `script-src` and `frame-src`, and `form-action 'self'`), renders one invisible widget per guarded form, the sign-in screen and the create-organization form (`execution: "execute"`, shown only if Turnstile needs an interaction), and sends a fresh token with every POST, Try again and Check again included, resetting the widget afterwards. A challenge that yields no token sends nothing. On sign-in, that, `challenge_*` and 429 show the existing "Sign-in couldn't start. Try again in a moment." On signup, no token and `challenge_*` show the existing "Couldn't save. Nothing was changed." with Try again (never the terminal refusal), and 429 is the existing hold for `Retry-After`; after an unknown outcome a guard refusal leaves the signup unknown.

## Session-route limit (ADR-0019 item 8 applied to the session routes)

The pre-publication sweep (2026-10-22) found that the routes behind the session cookie had no per-address limit and reached the database for any well-formed unknown session secret. The api Worker now counts them too (`apps/api/src/session-limit.ts`), after the sign-in guard and before the router, so before any broker lease or SQL. It selects with the router's matcher: the workspace handler's paths (`/workspaces`, `/workspace` and `/workspace/*`, the runs, work, billing, agents and catalogue APIs included; the Stripe webhook, `/api/billing/stripe/webhook`, is not a session route), `/auth/logout` and `/auth/rotate`. Signup keeps its own, stricter `SIGNUP_LIMITER`.

- **Counted requests.** Only a request carrying exactly one canonical `__Host-morrow_session` cookie (`sessionCookieSecret`, the parser every session handler uses) is counted. Every other request reaches its handler uncounted, which refuses it with its own 401 or 403 before any lease or SQL (logout's cookie rule is stricter still); a malformed cookie was already refused before the database, and is now also never counted. A third-party page cannot make a visitor's browser attach the SameSite=Lax cookie to a subresource, a fetch or a cross-site POST, so it cannot spend the visitor's budget.
- **Limit.** Workers Rate Limiting, 120 per 60 s per address on each of three keys in the one namespace: `session` (the workspace handler's paths), `session_logout` and `session_rotate`, each followed by `:` and 32 hex characters of a SHA-256 over the same address subject as the sign-in limits (IPv6 cut to its /56). Read and work traffic therefore cannot hold an address's sign-out or the session keeper's rotation (the PR review, 2026-10-22). Over the limit: 429 with `Retry-After: 60`, in the route family's shape: `{"schemaVersion":1,"outcome":"rate_limited"}` (`SignInGuardOutcome`) on the identity routes, logout and rotate, and the `ErrorEnvelope` (`rate_limited`, `retryAfterSeconds` 60, `safe_read_retry` on GET, otherwise `recheck_before_retry`) on a path of the work, billing, agents or catalog row of the api's dispatch table (`apiDispatch`, one matcher). The SPA reads a 429 as "nothing was done", never as an unknown outcome: logout as unavailable, and the store-link preview, apply and status as a `rate_limited` hold (a key already uncertain stays uncertain). A 429 logs nothing.
- **Shared addresses (accepted trade-off).** Everyone behind one public IPv4 address or IPv6 /56 (mobile CGNAT, a campus, an office, a café) shares each budget, as on the sign-in routes. A peer there needs no account to empty a bucket: about 2 requests a second carrying random canonical session cookies are counted, then refused. Flooding the `session` key holds every workspace read, work command and store link from that address; flooding `session_logout` or `session_rotate` itself holds sign-out or rotation, for as long as the peer keeps sending. A held sign-out shows "not done" (unavailable) and keeps the cookie, so the person knows the session is still live; it idles out 30–35 minutes after the last input. Counting by session instead would need the database, which is what the limit protects. Up to 360 counted requests a minute per address (120 per key, per Cloudflare location) reach a handler.
- **Fail closed.** A missing or invalid address or a failed limiter answers the route's existing 503 (`{"code":"unavailable"}`, `logout_unavailable`, `rotation_unavailable`, or the `unavailable` envelope of the work, agents and catalogue APIs or of the billing API) with no cookie, and one fixed-code `morrow_edge_guard` line (`ADDRESS_MISSING`, `ADDRESS_INVALID` or `LIMITER_FAILED`).
- **Configuration.** `SESSION_LIMITER` in namespaces 7006, 7106 and 7206 (development, staging, production), pinned by `npm run edge:check` (`EDGE_API_RATELIMITS`, `edgeRateLimits`); the mapper requires it outside development. Like the sign-in limits it is eventually consistent per Cloudflare location: a speed bump, not a quota.
