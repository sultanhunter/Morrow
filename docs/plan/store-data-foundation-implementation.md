# Store-data foundation for installable agents: implementation plan

- Records:
  - [ADR-0043](../decisions/adr/ADR-0043-store-events-schedules-standing-policies.md) (store events, schedules and standing action policies) and [ADR-0044](../decisions/adr/ADR-0044-collaboration-grants-installed-agents.md) (collaboration grants for installed agents), both Accepted 2026-10-26 as recommended (OD-2026-10-26-11);
  - the dated note on [ADR-0031](../decisions/adr/ADR-0031-data-retention-visibility-regions.md) item 1 (the store-data classes and clocks), decided the same day;
  - their decision sheet, Q-store-data-foundation (17 questions), answered by OD-2026-10-26-11, which also chose no paging vendor yet and the paid Neon plan (the owner bought it on 2026-10-26);
  - ADR 0042 (connected services and customer contact), approved by the owner as recommended on 2026-10-26, on branch `claude/adr-0042-connected-services` with its plan, `connected-services-implementation.md` (rows CS1 to CS16). Its CS2 records the approval with its OD number.
- The owner's direction, given with that approval: COD Confirmation will be an agent people install; the agent itself is not built now; the foundation must be solid enough for agents that consume live store data, such as orders, and perform scheduled actions. With the production-grade rule of the same day (OD-2026-10-26-6), this plan builds the shared parts once, for every such agent, instead of inside COD.
- Written 2026-10-26 from `origin/main` at `4b7063b1` (ADR-0040 and ADR-0041 accepted), beside the harness plan (`harness-foundations-implementation.md`, rows H1 to H20), ADR 0042's plan and the v1 build order (`v1-build-order.md`, PRs 1 to 26); brought up to `2107859d` (#83, catalogue version 4) with the owner's answers.
- Source: a foundation gap report of 2026-10-26 that merged four read-only audits, one per kind of agent (COD Confirmation; an order-operations agent on schedules, events and deadlines; customer retention; inventory and purchasing), against ADR-0040, ADR-0041 and ADR 0042. The table at the end maps each gap to its row.
- Rules (CLAUDE.md):
  - each PR is small, behind a switch committed off, on a short-lived `claude/` branch, with its tests;
  - each PR gets one AI review (separate context, same model family), with the security lens for authority, RLS, migrations, credentials, provider adapters, approvals, budgets or durable execution;
  - stacks are at most two PRs deep;
  - sizes: S is a day or less, M is two to three days, L is a week (usually two PRs);
  - each row adds its own lettered child to `build-plan.md` when it starts (a routine lettered split, ADR-0002); packages, parent task IDs and acceptance IDs stay.
- **What may start, and when.** The owner has answered, so no row waits on an owner decision any more, except the CLAUDE.md words in SD2. Rows marked "now" are routine under ADR-0002 (fixes, refactors and capacity work behind default-off switches, on classes and scopes already approved) and start as soon as their other "Starts after" entries allow. A row that carries out ADR-0043 or ADR-0044 starts after SD1, which records the acceptance, and a row that carries out an amendment of another record also waits for SD2's dated note in that record, which the row names.

## ADR 0042's rows, now that the agent waits

The owner asked for the foundation, not the COD agent, so ADR 0042's plan splits in two.

- **Built now, as shared foundation, behind switches committed off:** CS1b and CS2 (records); CS3 to CS7 (contracts, service connections, sealed entry, inbound events, health and limits), with SD20's changes; CS8 (order events), on SD6 and SD7; CS9 (call plans and the contact gateway), on SD14 and SD17 with SD21's changes; CS11 (order tags and cancellation proposals), on SD13a and SD17; CS12 (the contact classes' deletion path), on SD4.
- **Two changes the gap report gave CS2 land in these rows instead**, since CS2 records only the approval:
  - **ADR-0038 item 2.** ADR 0042 item 8's health checks and item 18's missed-order sweep name ADR-0038's cron object, whose item 2 runs only the connector's existing re-drives, and neither ADR 0042 nor ADR-0043 amends it. Item 18's sweep becomes SD7's orders consumer and runs from the orchestrator's cron (ADR-0043 item 6, which amends ADR 0042 item 18). CS7's health, settlement and holdout sweeps run the same way, as per-tenant Queue work from the orchestrator's cron under explicit budgets (ADR-0038's consequence note), and ADR 0042 item 8 gets a dated note saying so with SD2's notes on ADR 0042. CS7 does not start before that note.
  - **The customer's phone.** ADR 0042 item 11 reads the phone from the shipping address, then the order, then the customer record. CS8 checks on a development store whether `read_orders` alone reads the customer record's phone. If it does not, CS9's dispatch drops that third fallback, because `read_customers` stays Support's (ADR-0023 decision 4), and the dated note on ADR 0042 item 11 records the narrowing with SD2's notes on ADR 0042.
- **Deferred until the owner asks for the COD agent:**
