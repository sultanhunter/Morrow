## Goal (observable product delta)

1. **Exact proposals.** A registered `ProposalProducer` (trusted server code) submits a Proposal@2 whose server-derived fields come only from SQL facts and the SQL-held catalogue. It is stored immutably with its canonical JSON, digest, scope digest and parameters, plus a pending Approval@2 bound to the workspace's current ReviewPolicy (revision 1 seeded from `review-policy-defaults.json` on first use). Until P05.T01z registers a producer this is visible only through test fixtures.
2. **Persisted decision fold.** `POST /workspace/:ws/work/proposals/:id/decision` applies `governance.approval.decide` under ADR-0011: reviewer verbs, conflict set, solo owner with typed confirmation and cool-down, quorum, partial approval into a derived proposal, family exclusivity, `cancel_before_effective`, expected revision and per-actor `commandId`+`requestDigest` idempotency. Decisions are append-only; status, `effectiveAt` and `expiresAt` change atomically with each decision.
3. **Reads.** `GET /proposals/:id` (optionally with a selection) and `GET /approvals?status=pending` return validator-checked objects, with an `approvalRef`, to eligible reviewers and the proposer.
4. **Lifecycle without a scheduler.** Reads project three outcomes: expiry, a stale ReviewPolicy, and lost solo-owner status. A command or claim that observes one returns its code and rolls back; nothing is persisted. Persisted settlement arrives with the P06.T03/P11.T01 scheduler.
5. **One-use consumption.** `approval_claim()` binds exactly one consumer effect to one approval family, inside that effect's transaction, and hands the consumer the stored proposal and parameters. Consumers: P05.T01z (membership), P05.T02a (grants), later the P11.T02 gateway.

**Honest scope.** Only access_change (effect `control`) has real producers, arriving with P05.T01z and P05.T02a. Targets are the workspace resource W only. Store-scoped and agent-authored proposals come with P09, P05.T04b and P11.T01. The UI is P14.T03.

## Design

### 1 What is decided where

- **Pure library** (`review.ts`), imported and never re-implemented: derivation, effective rule, conflict set, solo status, phrases, fold, selections, dispatch codes.
- **Kernel** (`createHumanPolicyService`), in the Worker: every grant question, including candidates' and counted reviewers' grants.
- **SQL, structurally:** tenancy; database time; freshness (`work_lock_and_recheck`, plus §4's counted-reviewer check); immutability; transition edges; catalogue facts; quorum count; one decision per reviewer; one approved member per family; one claim per family.
- **SQL, independently rechecked:** every data-only rule (conflict set, solo facts, phrase digest, effective rule, document match, derived id and subset, ceilings, expiry formulas). A Worker/SQL mismatch returns `invalid` and writes nothing. SQL never interprets grants; it selects grant rows by capability id only (ADR-0010 item 2).
- **Database time.** `db_now()` = `date_trunc('milliseconds', clock_timestamp())`, read after the last lock wait. It sets `decided_at`, `effective_at`, expiry, projection and claim comparisons; `now()`/transaction time are never used. Every stored timestamp is millisecond-truncated (CHECK), and `utc_text(t)` renders `YYYY-MM-DDTHH:MI:SS.MSZ`, matching `Date.toISOString()`.

**Document checks and digests** (IMMUTABLE; fixed templates; record ids, FieldPaths, hex digests, enum words and `utc_text` need no JSON escaping):
- `policy_document_matches`: exactly the keys `{schemaVersion:1, id, organizationId, workspaceId, storeId:null, revision, createdAt, updatedAt, rules}`, with `createdAt = updatedAt = utc_text(created_at)` and `rules` = the column. Revision 1 must equal the defaults row (cmd_proposal_submit).
- `proposal_document_matches`: schema version 2; `id`, tenant, `storeId` null, revision 1, `createdAt = updatedAt = utc_text(created_at)`, `expiresAt`, task, capability, risk, `irreversible`, `partialApproval`, target count; every target resource is exactly W (`valid_scope`'s W object) — **W-only targets here**; `maximumCredits` and `maximumCost` as written and equal to the exact numeric sums of the targets; proposer and requester HumanActorRefs; beneficiaries; `derivedFrom`; `contextTaint:"none"`; no `proposalDigest` key; `reviewPolicyRef = {O,W,null,"policy",id,revision,digest}`; `parametersRef = {O,W,null,"artifact",parameters_id,1,parameters_digest}`; `parametersDigest = parameters_digest`; `scope = scope_canonical::jsonb = {O,W,[],[],[W], sorted (COLLATE "C") distinct union of target fields}`.
- **`scopeDigest`** (Approval@2 `scopeDigest`, undefined until now) = `sha256(JCS(proposal.scope))`, stored as `scope_canonical`; jsonb equality with the document's `scope` plus the digest CHECK bind it.
- **`derived_proposal_id`** = `'derived_' || h(format('{"parentRef":{"digest":"%s","id":"%s","kind":"proposal","organizationId":"%s","revision":1,"storeId":null,"workspaceId":"%s"},"selectedTargetIndexes":[%s]}', …, array_to_string(indexes, ',')))`, which is the RFC 8785 form of P01.T02a §7 item 8 (keys in code-unit order).
- **`ApprovalRef.digest`** (undefined until now) = `approval_ref_digest(row)` = `h` of the JCS object `{"effectiveAt":E|null,"expiresAt":X,"id":I,"kind":"approval","organizationId":O,"proposalDigest":P,"revision":R,"scopeDigest":S,"status":T,"workspaceId":W}` for the approval at revision R. A claim compares it, so any status, expiry or revision change voids an old ref.
- The canonical texts are the Worker's RFC 8785 output. SQL proves each digest covers those bytes and that they parse to the row; a wrong canonicalization fails closed (reads 503; decide `DIGEST_MISMATCH`). AC22 pins TS = SQL vectors. IDs (proposal, approval, parameters) are Worker `crypto.randomUUID()` values.

**Retention.** R02, as P06.T01a; P06.T04 prunes. P09.T05 erasure needs a reviewed append-only exception (beneficiaries, comments and parameters are personal data).

### 4 Functions, grants and locks

**api-executable SECURITY DEFINER** functions, owned by `morrow_work_command`; tenant and actor come only from `current_tenant()` (S5). Read definers:
- `review_context(p_capability)`: the current policy or null, the defaults row, the catalogue row, `work_ownership_facts`, and `db_now()`.
- `review_candidates(p_capability, p_exclude text[] ≤ 102, p_after, p_limit 1..25)` and `reviewer_snapshot(p_capability, p_principals text[] ≤ 5)`: wrap the bridge and return `evaluated_at = db_now()`.

Commands run P06.T01a's prelude unchanged (scalars → `current_tenant()` → `commands` replay → `work_lock_and_recheck` → stream `FOR UPDATE`):
- `cmd_proposal_submit(command_id, request_digest, task_id, task_basis, policy_canonical, policy_digest, parameters_canonical, parameters_digest, proposal_canonical, proposal_digest, scope_canonical)`;
- `cmd_approval_decide(command_id, request_digest, proposal_id, expected_revision, decision, selected int[], expected_decision_digest, derived_canonical, derived_digest, derived_scope_canonical, phrase_digest, comment, counted jsonb)`;
- `cmd_approval_withdraw(command_id, request_digest, proposal_id, expected_revision)`.

**INVOKER helpers**, owned by the command role, granted to nobody: `db_now`, `utc_text`, `effective_rule` (mirrors `effectiveRule`), `solo_phrase`, `conflicted`, `approval_projection` (§5), `counted_current`, and `approval_claim` (§5).

**Counted reviewers and freshness.** `counted` is `{evaluatedAt, reviewers:[{principalId, membershipId, grantsDigest}]}` (≤ 4 on decide, exactly the counted set on claim), taken from `reviewer_snapshot` and kept only for reviewers the kernel found eligible. `counted_current` requires, under lock, for each: an `approve` decision row on the family member; a `work_reviewer_grants` row with the same membership and `grants_digest`; and no grant `expiresAt` in `(evaluatedAt, db_now()]`, the window `work_lock_and_recheck` applies to the caller. Otherwise `stale_authority`, or `REVIEWER_AUTHORITY_LOST` when the reviewer is no longer a member. A `false` kernel verdict is never persisted: that reviewer stops counting (decide) or the claim returns `REVIEWER_AUTHORITY_LOST` (rollback).

**Lock order.** Advisory → organization `FOR SHARE` (`FOR UPDATE` for claim consumers, taken first, never upgraded) → stream `FOR UPDATE` → task `FOR SHARE` (submit, when a task is named) → family-root approval `FOR UPDATE` → other family approvals in id order → claim insert → identity effect (consumers). `db_now()` is read after the last wait. Facts from the read definers are read **before** `cmd_*` takes the share lock and are not trusted as current. Only what `cmd_*` re-reads under lock (ownership facts, policy revision, task basis, counted reviewers) is stable until COMMIT, because 0004 revocations, P05.T02a grant changes and P05.T01z membership changes take the organization `FOR UPDATE`. Grant expiry takes no lock, hence the window check.

### 5 Command protocol (P06.T01a §4.7: guard, context, replay, target, verb, input, execute, commit)

**Submit** (`submitProposal`, producer code only; no HTTP route):
1. **Producer.** None registered → `producer_missing`, before SQL. `producer.parse` (closed, AOT validators) and `producer.plan` return W targets, ceilings and `beneficiaryPrincipalIds`.
2. **Grants.** The kernel requires `proposerVerb(c)` on `capabilityId` from one grant covering W and every target field; `proposerVerb` is `execute`, or `administer` for `governance.connection.connect` (kernel rule), which this packet still refuses at step 6. Task attach (ADR-0010 ownership rule), when `taskId` is non-null: own task (proposer = initiator) → `execute`, another's → `administer` on `workspace.task.create`, field `status`; `requestedBy` = the task initiator. With a null `taskId` (ADR-0018: a Governance-domain capability and a human proposer, which every proposer in this packet is), there is no task attach and `requestedBy` = the proposer; a null `taskId` with any other capability → `invalid`.
3. **Facts.** `review_context`; the Worker builds revision 1 from the defaults when no policy exists, with `createdAt` = the proposal's.
4. **Build.** Proposal@2: `risk` from `riskClassByEffect`, catalogue `irreversible`, producer `partialApproval`, `contextTaint:"none"`, `reviewPolicyRef`, `parametersRef`, derived scope, `createdAt` = `review_context`'s `db_now()`, `expiresAt = createdAt + pending + coolDown + approvedValidity` of the effective rule.
5. **Check.** `checkProposal` returns no codes; any code, `TASK_MISMATCH` and `TASK_REQUIRED` included, → `invalid`, nothing written. Its `ProposalFacts.taskId` is the request's `taskId` after the step 2 task-attach check (or null) and `requestedBy` that task's initiator (or null), never values copied from the proposal built in step 4. Quorum reachability (liveness only): unless solo can apply, the Worker pages `review_candidates` (excluding proposer, requester and beneficiaries) and counts kernel-eligible candidates until it reaches the quorum; overflowed candidates count as ineligible. Not reached → 409 `quorum_unreachable`, nothing written (**interim** until P01.T02c turns QUORUM_UNREACHABLE into an inbox exception, P01.T02a §7 item 3). More than 1,000 scanned → `limit_reached`.
6. **Write.** `cmd_proposal_submit` validates JSON with `pg_input_is_valid` before any cast; requires `created_at ∈ [date_trunc('ms', transaction_timestamp()), db_now()]`; rechecks the locked task's basis (`stale_authority`) and status when a task is named; inserts the policy revision 1 if absent (an existing row with another digest → retryable `stale_authority`); counts live pending approvals (`expires_at > db_now()` and current policy) against the cap; then inserts parameters, proposal, pending approval, event and command row. CHECKs and triggers enforce the rest.

**Published caps:** 100 targets; 128 KiB canonical proposal; 32 KiB parameters; 1,000 live pending approvals per workspace (`limit_reached`), counting a new derivation that stays pending; 25 derived proposals per family (a 26th → `limit_reached`, in the Worker and again in SQL under the root lock); 5 decisions per approval (a sixth → `limit_reached`).

**Decide** (`POST …/decision`, body `{decision: ReviewDecisionInput, expectedRevision}`):
1. **Input.** Server-built v1.1 input `{proposalRef, decision, expectedRevision}`; `validateCapabilityInput`, else 400. Not visible (§6) → 404.
2. **Reviewer.** `approve` on decide (W; `proposalRef`, `decision`, `expectedRevision`) and `approve` on `capabilityId` from one grant covering W and every decided target's fields; membership in `eligibleReviewerPrincipalIds` when set. Else `REVIEWER_DENIED`.
3. **Selection.** `previewSelection`. If the derived proposal exists, the decision applies to its approval at that approval's revision (preview returns it).
4. **Counted.** For quorum > 1, `reviewer_snapshot` over earlier approvers; the kernel re-evaluates each; a no-longer-eligible approver **stops counting** (its row remains).
5. **Fold and phrase.** `foldDecisions(state,[attempt])`; phrase digest = `sha256(NFC(input))`, sent only when it equals `confirmationPhrase`, else `CONFIRMATION_MISMATCH` before SQL.
6. **SQL, under lock, in order:** revision and digest; a claimed family (`FAMILY_CONFLICT`); `approval_projection` (code → rollback); family in the library fold's order (an approval while a member is approved → `FAMILY_CONFLICT`; the target or root approval no longer pending → `APPROVAL_NOT_PENDING`); conflict set against the stored proposer, requester and beneficiaries; solo facts at `db_now()` with `phrase_digest = h(solo_phrase(row))`; `DUPLICATE_REVIEWER`; `counted_current`; quorum = |counted| + 1.
7. **Write:** decision row and new status; on approval `counted_reviewer_principal_ids`, `effective_at = decided_at` (+ cool-down when solo) and the expiry formula; approving any member moves every other pending member to invalidated (`superseded_by_partial_approval`); rejecting the root moves pending derived members to invalidated (`family_closed`); events (actor: the deciding reviewer); COMMIT. `cancel_before_effective`: only the confirming solo reviewer while `db_now() < effective_at` and projected approved; else `CANCEL_NOT_ALLOWED`.

**Withdraw** (`POST …/withdraw {expectedRevision}`): v1 row `pending→cancelled` (owner, `current_revision`), proposer only, holding `proposerVerb(c)`; a claimed family → `FAMILY_CONFLICT` before any projection, as for decide; withdrawing the root also closes pending derived members (`family_closed`).

**Projection** (`approval_projection(row, has_claim, current_policy_revision, facts, at)` in SQL; `projectApproval` in TS, mirror-tested). It applies only to stored pending or approved rows, in this order. Commands and claims use `at = db_now()`, return the code and roll back; reads display the projected status and never write.

| Condition at `at` | Projected | Code |
| --- | --- | --- |
| A claim exists | stored status (consumed; terminal) | `APPROVAL_ALREADY_CLAIMED` (claims) |
| `at ≥ expires_at` | expired | `APPROVAL_EXPIRED` |
| bound policy revision < current | invalidated | `REVIEW_POLICY_NOT_CURRENT` |
| solo decision and not (`soloOwner(facts, at)` and `last_membership_change_at ≤ decided_at` or null) | invalidated, at once, before or after `effective_at` | `SOLO_OWNER_STATUS_LOST` |

Each condition is monotone, so a projected status never reverts. That requires P05.T01z to record every removal and principal deactivation as a membership change. Reviewer-authority loss is a claim-time refusal, not a status.

**Claim (consumer contract):**
1. Consumer TS calls `prepareApprovalClaim(tx, a, {proposalRef, approvalRef, capabilityId})`, naming the one capability the consumer executes (a constant, never request input). Visibility; the exact refs and capability (else `DIGEST_MISMATCH`); a claimed family (`APPROVAL_ALREADY_CLAIMED`, before any projection, as in SQL); projection; the kernel checks the claimant's `execute` on `capabilityId` (one grant covering W and every target field) and re-evaluates every counted reviewer through `reviewer_snapshot` → `REVIEWER_AUTHORITY_LOST` if any fails.
2. The consumer's own api-executable definer (in `morrow_work`, owned by `morrow_work_command`, created by the consumer's migration) runs the prelude with `work_lock_and_recheck_exclusive`, so it holds the organization `FOR UPDATE` before the stream and never upgrades. It then calls `approval_claim(approval_id, approval_revision, approval_digest, proposal_id, proposal_digest, capability, consumer, consumer_command_id, counted)`.
3. `approval_claim` locks the family root then the approval, reads `db_now()`, and requires: matching revision, `approval_ref_digest`, proposal digest and capability (else `DIGEST_MISMATCH`); no claim in the family (`APPROVAL_ALREADY_CLAIMED`), except the caller's own: the same approval, claimant, consumer and `consumer_command_id` → `replayed` with the stored proposal and parameters, nothing written; projection; status approved (`state_conflict`); `db_now() ≥ effective_at` (`APPROVAL_NOT_EFFECTIVE`); `counted_current` for exactly the counted set. It inserts the claim (family-unique) and `approval.claimed`, and returns the stored proposal and parameters as jsonb.
4. The consumer derives its effect input **only** from those stored documents. It then calls identity effect definers that grant EXECUTE to `morrow_work_command` (the P06.T01a bridge direction; work and identity roles stay non-members of each other). Any non-applied outcome rolls back the whole transaction: no claim, no effect. An unknown commit is read back by `consumer_command_id`: the consumer resends its definer call with the same prepared values and command ID (no new prepare), `approval_claim` returns `replayed`, and the consumer returns the effect it recorded under that ID; a consumer that also records its own P06.T01a `commands` row replays through it first.

The lab fixture consumer (AC12) proves this contract; P05.T01z and P05.T02a build theirs on it.

**Unknown outcomes** follow P06.T01a: a failure after `markSubmitted()` → 503 `uncertain`/`reconcile_before_retry`; a same-key retry replays or applies once; one command never folds two decisions.

Wrong phrase → `CONFIRMATION_MISMATCH`. `SELF_APPROVAL_DENIED` for each of: a back-dated 0004 result in O1 23 h old (25 h old allows solo); a second active human member of O1 who is not in W1 (org-level count); an inactive signup-owner membership with another sole member; an owner-seeded organization without a signup row. A direct call with the digest of "approve 2 changes…" is refused.
- **AC07 At `effectiveAt`** (O1, fixture policy with a 60 s cool-down, bound before submit). Just after a solo approval: a claim → `APPROVAL_NOT_EFFECTIVE`, nothing written. On a second approval, cancel → cancelled. After one 61 s wait: cancel → `CANCEL_NOT_ALLOWED`; with facts unchanged, the claim succeeds. A third approval, with a member added to O1 after `decidedAt`: reads project invalidated (`solo_owner_status_lost`) at once, both before and after `effectiveAt`; the claim → `SOLO_OWNER_STATUS_LOST` and rolls back; the stored status stays approved.
- **AC08 Quorum and fold** (fixture policy revision 2, access_change quorum 2). B approves → pending, one decision; replay identical; same `commandId` with another digest → `COMMAND_CONFLICT`; B under a new key → `DUPLICATE_REVIEWER`; D approves → approved, `counted [B,D]`. Stale earlier approver: B approves a second proposal, B is removed by 0004, D approves → still pending, `counted [D]`; R approves → approved, `counted [D,R]`. A counted approver's fixture grant expires between `reviewer_snapshot` and the command (2 s expiry, hook pause 3 s) → `stale_authority`; so does a counted approver's grant edited after the snapshot without a revision bump. With the Worker bypassed, `cmd_approval_decide` refuses a counted reviewer with a wrong grants digest or a future `evaluatedAt` (`stale_authority`), another membership (`REVIEWER_AUTHORITY_LOST`), and a reviewer without an approve decision, the decider itself or a duplicate (`invalid`); a claim's counted set must equal the stored set exactly (a subset, superset or other set → `invalid`). Reject → rejected; stale `expectedRevision` → conflict. Stored decisions equal `foldDecisions` over the same attempts.
- **AC09 Partial approval and families** (fixture policy whose irreversible rule is 43200 s pending and 1800 s validity). A three-target erase proposal stores the merged snapshot (43200/1800). B selects [0,1] → one `derived_<hash>` proposal: idempotent, byte-identical to `GET ?selected=0,1`, with id equal to the SQL template and the TS vector. Its approval inherits the parent approval's `expires_at`; it is approved, and the parent's approval is invalidated (`superseded_by_partial_approval`). Then approving the parent, or deriving [2] → `FAMILY_CONFLICT`. [0] with the [0,1] digest → `DIGEST_MISMATCH`. [1,0], [0,0], [3], a derivation of a derivation, or an `all_or_nothing` parent → `SELECTION_INVALID` or `PARTIAL_APPROVAL_NOT_ALLOWED`. With quorum 2 (a further fixture revision, new proposal): B derives [0] (pending, with the root approval's `created_at` and `expires_at`); D rejects the root → root rejected and [0] invalidated (`family_closed`); a later derivation → `APPROVAL_NOT_PENDING` (the library fold's code when no member is approved; SQL agrees). With quorum 2 and five targets, 25 derivations apply and a 26th → `limit_reached` in the Worker and directly in SQL. Owner SQL: a derived approval with a later `expires_at` fails `approval_bind`; a second approved member violates `approvals_one_approved_per_family`.
- **AC10 Expiry.** A back-dated pending fixture (created 24 h + 1 s ago) projects `expired` in `GET /proposals/:id` and is absent from `GET /approvals?status=pending`. Deciding or withdrawing it → 409 `approval_expired`, nothing written, stored status unchanged. `approval_projection` at `expires_at − 1 ms` → pending; at `expires_at` → expired. A claim on a back-dated approved fixture past `expires_at` → `APPROVAL_EXPIRED`.
- **AC11 Policy revision.** Proposal bound to revision 1; the owner installs revision 2. Deciding → `REVIEW_POLICY_NOT_CURRENT`, nothing written. Reads project invalidated, and the pending list excludes it. New proposals bind revision 2.
- **AC12 One-use claim** (fixture consumer). A claims B's approved grants-revise approval: one claim row with `family_root_id`; one effect row whose beneficiary comes from the stored parameters; one `approval.claimed`; approval status and revision unchanged. A second claim of it or of any family member → `APPROVAL_ALREADY_CLAIMED` (Worker and SQL), no second effect; a lost COMMIT reply is read back by the same consumer command ID (`replayed`, the same effect), and by no other claimant. A consumer naming another capability → `DIGEST_MISMATCH`. Withdrawing a claimed root → `FAMILY_CONFLICT`. An owner-SQL second claim in the family hits the unique index. Any UPDATE of the claimed approval raises. After its expiry, no decision or derivation in the family succeeds (`FAMILY_CONFLICT`). Wrong `approvalRef` revision or digest, or proposal digest → `DIGEST_MISMATCH`. Claimant without `execute` → denied. Counted reviewer B removed by 0004 → `REVIEWER_AUTHORITY_LOST`, rolled back. An effect error after the claim leaves neither row. The api role cannot call `approval_claim`. A 0004 revocation in O waits on the consumer's organization lock.
- **AC13 Unknown outcome.** A fault proxy drops the reply to `cmd_approval_decide` or to COMMIT → 503 `uncertain`. A same-key retry replays or applies once; both branches are forced. A command never has more than one decision row.
- **AC14 Withdraw.** The proposer withdraws a pending root → cancelled, and its pending derived members → invalidated (`family_closed`). B → 403. After approval → `state_conflict`. Replay after the proposer loses `execute` → 404.
- **AC15 Visibility.** X, Y, a grant-less beneficiary and a reviewer without preview `view` get a 404 byte-identical to an unknown id. B and A can read. `GET /approvals` returns only visible, live items, at most 25, with a stable `(expires_at, id)` cursor over 120 pending rows plus 30 expired and 30 policy-stale rows, which never appear. No response contains another member's grants.
- **AC16 Tenant isolation.** S1–S6 and P1–P6 pass for every new object and route: forged GUCs return zero rows; any `cmd_*` with O′ IDs → `not_found`, nothing written; a command-role INSERT with O′ values fails `WITH CHECK`; a derived proposal or claim with a W2 parent or approval is unrepresentable.
- **AC17 Races** (a hook pauses after `begin_command`). Each race ends in one consistent outcome: two quorum-1 approvals → one approved, the other a stale revision; two different partial selections → one `FAMILY_CONFLICT`; a decision against a 0004 revocation of its reviewer → the decision commits first, or 401/`stale_authority`; a claim against a 0004 revocation of a counted reviewer → the claim commits first, or `REVIEWER_AUTHORITY_LOST`; a solo claim against a member being added under the organization `FOR UPDATE` → the claim commits first, or `SOLO_OWNER_STATUS_LOST`. Races one and two also run under lock, as direct command-function sessions: the first decision's command has returned and holds its locks until COMMIT, the second's command waits on them and then gets the stale revision.
- **AC18 Sensitive markers.** Markers in the comment, parameters and phrase never appear in the outbox, ErrorEnvelopes, Worker console output or the PostgreSQL log, including for a malformed canonical text (`pg_input_is_valid` precedes every cast). The log has no "Failing row contains" DETAIL.
- **AC19 Immutability and drift.** UPDATE, DELETE and TRUNCATE raise on the five append-only tables and the four platform tables. Approval updates follow only `transition_rules` approval rows. These equal the effective `state-transitions.json` rows at v1.1 by `(machine, from, to, actor, guard)`, both `pending→invalidated`/`work_service` rows included; other machines are unchanged at v1. `review_capabilities` equals `capabilities.json`; `review_risk_by_effect` and the defaults row equal `review-policy-defaults.json`.
- **AC20 Guard and unbound (PR-2).** P06.T01a's AC21 matrix passes on both POST routes, with no SQL opened. With the default `worker.ts` export, every new route returns 401 with no I/O.
- **AC21 Bridge shapes.** All four shapes are pinned. `DROP TABLE` of `organization_signups`, `workspace_revocation_results` or `grants` fails on the recorded dependency. The ownership count is organization-level. Candidates are selected by capability id only: a member whose only decide grant is expired or revoked is returned, and the kernel rejects it. A 65-row candidate is flagged as overflow and counted ineligible. Paging reaches a quorum placed after the first 25 candidates (no false `quorum_unreachable`).
- **AC22 Digests.** TS and SQL agree on `scopeDigest`, `approval_ref_digest`, `derived_proposal_id` and `utc_text` over a vector set (single and 999-wide index lists, millisecond boundaries, null `effectiveAt`).
- **AC23 Live pending cap.** With 1,000 live pending approvals, the next submit → `limit_reached`. With 1,000 back-dated expired pending rows plus 999 live ones, a submit succeeds. A quorum-2 derivation that stays pending counts: at 999 live rows one applies, and the next → `limit_reached`.
- **AC24 Proposals without a task (ADR-0018).** A submits a grants-revise proposal with `taskId: null` → applied; the stored `task_id` is null, `requestedBy` is A, no task lock is taken, and A and the beneficiary C both get `SELF_APPROVAL_DENIED`. A null `taskId` with a non-governance capability → `invalid`, nothing written. An owner-role INSERT of a proposal row with a null `task_id` and a non-governance capability, or with a requester other than the proposer, fails the CHECK. Agent proposers do not exist in this packet; their non-null task is a P05.T04b and P11.T01 obligation.

## Security review checklist

- [ ] Server-derived fields come only from SQL facts and the SQL catalogue. SQL rechecks the conflict set, solo facts, phrase digest, effective rule, document match, derived id and subset, ceilings and expiry formulas, each with a bypass test (AC02, AC05, AC06, AC09).
- [ ] Unreviewed capabilities, kill switches and `governance.connection.connect` cannot become proposals; targets are W only.
- [ ] Proposals, parameters, decisions, policies and claims are append-only. Digests cover the exact stored bytes; `scopeDigest` and `ApprovalRef.digest` are defined and pinned.
- [ ] Approvals confer no authority. A claim needs the claimant's current `execute`, current counted reviewers (kernel plus SQL freshness, including the grant-expiry window), and an exact `approvalRef`. One claim per family, atomic with the effect; ungranted at runtime.
- [ ] Derivation never extends expiry or raises a ceiling. A family is closed once any member is approved or claimed.
- [ ] Commands, claims and reads use `db_now()` after the last lock wait. `createdAt` is bound to transaction time. No production clock override exists.
- [ ] No settlement is persisted from a projection or a kernel boolean. Every non-`applied` outcome rolls back (P06.T01a §4.7 step 9).
- [ ] api functions take tenant and actor only from `current_tenant()`. Only the command role executes the bridges. Helpers and triggers are INVOKER and ungranted. SQL selects grant rows by capability id and never interprets them. No dynamic SQL; fixed `search_path` everywhere.
- [ ] Not-found responses are byte-identical; replay needs current visibility; candidate and reviewer grants are never returned.
- [ ] The §4 lock order holds. Claim consumers take the organization `FOR UPDATE` first, and identity effects are reached only through identity definers granted to `morrow_work_command`. The race hooks pass.
- [ ] Bodies, phrases, comments and parameters are bounded and NUL-free, never logged or put in events, and never cast before `pg_input_is_valid`. Only the phrase digest is stored.
- [ ] The production producer registry is empty; fixtures live only under `tests/`; no execution or OperationLedger write (hard ordering a).
- [ ] The AI review is labelled "AI review (separate context, same model family)".
