## Goal (observable product delta)

1. **Today the policy kernel bills almost everything.** `evaluate()` returns `entitlement_denied` for every non-kill-switch capability when `entitlementAllowed` is false (`index.ts:212`): reads, invitations, approvals, exports and store linking included. **After:** entitlement gates only paid work, meaning `execute` or `administer` on a paid-effect capability that is not a kill switch (§1). A verify step fails when product code sets `entitlementAllowed` outside the billing reader (§2). The agent kernel keeps today's rule.
2. **Billing contracts v1.1 for two routes.** Each workspace has exactly one billing route, `morrow_direct` (Morrow sells; Stripe Billing collects; Stripe Tax computes tax) or `shopify_app_pricing`, fixed server-side at its first payment of collected money and never switched (§3). `schemas/v1.1/billing.schema.json` adds the route record, canonical payment and subscription keys, verified payment events with the amount paid, payment reversals, the terms table and Shopify usage caps, and replaces the shop-only BillingAccount, EntitlementSnapshot, CreditGrant and allocation shapes (§4). Billing becomes a v1.1 layer, which ADR-0015 now names (§4.5).
3. **A pure library, `@morrow/policy/billing-state`.** It sets the origin of a new workspace, derives the route phase and entitlement from trusted facts, decides which purchase surface a workspace may reach, and gives every surface one call to action, so no Shopify-origin workspace is offered Morrow checkout anywhere. It classifies each verified payment into exactly one outcome (credits granted once, held, no charge, conflict or refused), folds entitlement evidence from provider reads, maps provider statuses, and selects payers: the one workspace account on `morrow_direct`, per-shop accounts with explicit allocations on `shopify_app_pricing` (ADR-0015 item 6). A composed constraints reader fails closed (§5–§6).
4. **Executable cases.** Unit tests, a whole-catalogue differential, two exhaustive checked-in decision tables (payment classification and purchase decisions), simulator checks, five `verify:billing` walkthroughs, the entitlement-writer check and a case-to-test table in `docs/acceptance/P01.md`. Follow-on packets inherit binding obligations (§9).
5. **What stays blocked.** M4 (plan step 15, an `external_write` on the development store) is paid work under §1. How it gets an entitlement is OQ-2; this packet adds no dependency edge to step 15. Stripe keys wait for the P08.T02 broker trust model and the package 8 credential-custody ADR (ADR-0007 item 4, ADR-0015 item 7). No live payment exists anywhere until the §9 launch gates pass.

## Design

### 1. What is paid work (`docs/contracts/paid-work.json`)

```json
{"schema_version":1,"adr":["ADR-0015","ADR-0011"],
 "paidEffects":["billable_job","spend","external_write","communication"],
 "neverGatedVerbs":["view","propose","approve","delegate"]}
```

`isPaidWork(capabilityId, verb)` is true when the capability is unknown (fail closed), or when its effect is in `paidEffects`, it is not a kill switch (the catalogue's `kill_switch` field, never a table toggle) and the verb is not in `neverGatedVerbs`. `administer` is gated because it covers transitions of another member's paid record (ADR-0010 item 1). The count is derived from the catalogue (27 today). ADR-0015 item 5 defines paid work as "model, connector-write or execution work"; it is read by effect class, so `external_write` and `communication` fail closed before P11.T04a prices them, although only `spend` and `billable_job` carry `budget_reservation` today. Narrowing the table is a billing change and needs an ADR (OQ-2 (b)).

**Rules** (`inspectPaidWork` in `verify:billing`; failure gives `PAID_WORK_TABLE_INVALID:<rule>`). **PW1** the object is closed; effects and verbs are unique enum members; `execute` and `administer` are never in `neverGatedVerbs`. **PW2** no kill switch is paid for any verb. **PW3** every capability whose `execute` carries `budget_reservation` is paid. **PW4** no read, internal_write or control capability is paid, so linking, exports, privacy and any billing-management capability are never gated. **PW5** no row of the grant templates `owner-bootstrap-v1` (ADR-0009 item 7), `workspace-member-v1` and `workspace-admin-v1` (ADR-0017 item 1, P05.T01z §2.3) is paid with its template verbs. The three lists live in the `templates` section of `docs/contracts/fixtures/P01.T04a.json`; P05.T01x Part B and P05.T01z PR-A make their own template checks assert `!isPaidWork` for every row (§9), so a drift between those modules and the fixture fails in their PRs.

### 3. Route model (rules R1–R11)

The route is a fact of the workspace, written only by trusted server writers (§8). An **association** is an installation's `workspace_store_links` row (migration 0005: one per installation, never reassigned or deleted). A **current link** is an association whose installation is installed and whose connection is not disconnected. The **phase** is derived:

| Phase | Condition | Purchase surface | Paid work |
| --- | --- | --- | --- |
| `open` | no route; origin `website`; no installation ever associated | `morrow`: `subscribe` only | denied (`BILLING_NO_ROUTE`) |
| `shopify_bound` | no route; origin `shopify_install`, or any installation ever associated | `shopify` while a link is current, else `none` | denied (`BILLING_NO_ROUTE`) |
| `morrow_direct` | route fixed to `morrow_direct` | `morrow` (§5 table) | per entitlement and credits |
| `shopify_app_pricing` | route fixed to `shopify_app_pricing` | `shopify` while a link is current, else `none` | per entitlement and credits |

- **R1 Origin.** Written once, in the workspace's creating transaction, by `originForCreation(flow)` (§5). `website` only for the P05.T01x signup flow when no unconsumed install handoff exists for the creating principal or browser family. `shopify_install` for every other flow: the P09.T02a install continuation, a future second workspace inside an existing organization, operator or owner seeding, fixtures, and any flow the function does not recognize. The **install handoff** is a server-side record that P09.T02a writes when the connector returns a merchant to Morrow. It is bound to the OAuth-verified installation, to the browser family that received the return and, once that person signs in, to their principal. Only the install continuation consumes it, and it is kept after it expires, so an expired or abandoned handoff still routes signup to the continuation. The origin never comes from a body, query, header, cookie, return URL or model output. A missing route record reads as `shopify_install`, so a reader gap fails closed (no Morrow checkout).
- **R2 Shopify binding.** The first association of any installation with a workspace that has no route sets `shopifyBoundAt` in the link transaction. It is never cleared: a website workspace that linked a store before paying stays Shopify-billed after a disconnect (ADR-0015 item 2). Linking itself is never denied for billing reasons. The same transaction re-classifies held payments of that installation (R8) and enqueues expiry of the workspace's open Morrow checkout sessions (§8.7).
- **R3 Completed payment and fixing.** A **completed payment** is money actually collected: a verified event with `amountPaid > 0`. None of these ever fixes a route or grants credits: a $0 invoice (a trial, a 100% coupon, a customer balance or a credit note covering it); Stripe `trialing`; an App Pricing cycle during `trialEndsAt` or with a null `currentBillingCycle`; a free plan; a 100% discount; a $0 no-charge development-store contract. Trials stay non-billable unless the owner decides otherwise by ADR, because there is no free tier. The route fixes once, in the transaction that accepts the workspace's first completed payment (§5 `classifyPayment`): a Stripe `subscription_period` on the workspace's mapped customer fixes `morrow_direct` only in phase `open`; an App Pricing `subscription_period` of an installation associated with the workspace fixes `shopify_app_pricing` only in phase `shopify_bound`. Order is Morrow's serialized route-row lock, never provider timestamps.
- **R4 Immutability.** A fixed route never changes. No API, client input, provider event or operator flag switches it; moving a paying workspace needs a new owner decision (ADR-0015 item 2).
- **R5 Payers (ADR-0015 item 6).** `morrow_direct`: exactly one BillingAccount for the workspace, with no installation or store (one Stripe customer and subscription), which pays for work on every currently linked store. `shopify_app_pricing`: one BillingAccount per associated installation, created at its first completed payment, owning its App Pricing subscription and wallet, and kept across disconnects; its credits are spendable only while its link is current. Another shop's subscription never entitles or pays for work on this shop.
- **R6 Multi-store.** Linking or disconnecting never changes the route, creates a `morrow_direct` payer, or writes a reservation, liability or meter event. Work on a store needs the store to be currently linked and, on the Shopify route, its own payer billable. Multi-store work on the Shopify route declares an explicit allocation and never charges an unrelated or unauthorized shop. No account of another workspace is ever charged.
- **R7 No double billing.** Evidence of a second charge path is a **route conflict**: a Stripe payment for a `shopify_bound` or `shopify_app_pricing` workspace, including one completed at Stripe before a link but verified after it (§8.7); an App Pricing payment on any installation associated with a `morrow_direct` workspace; a second subscription for the same payer while its current one is not terminal; a payment on a terminal subscription; or a top-up without a billable subscription. A conflict fixes nothing, entitles nothing and grants no credits. It is keyed by `(workspace, payment route, subscriptionKey)`, or by `paymentKey` for a top-up, so every repeat invoice of that subscription attaches to the one open conflict. P18.T01c's first remediation stops the renewal (§8.9). Paid work on the workspace's own route continues.
- **R8 Held payments.** A verified payment that cannot be classified yet is **held**: never dropped, never refunded automatically, and recorded by `paymentKey`. Reasons: `INSTALLATION_NOT_ASSOCIATED` (a plan chosen on Shopify's hosted plan page, which merchants can reach on their own, before any link), re-classified in the link transaction; `CUSTOMER_NOT_MAPPED` (a Stripe customer with no workspace mapping) and `NOT_MORROW_INITIATED` (an object that traces to no Morrow OperationLedger operation, such as a Payment Link, a Pricing Table, a Dashboard-created invoice or subscription, or an invoice marked paid out of band), resolved only by P18.T01c with owner approval; `TERMS_MISMATCH` (§R10); `SUBSCRIPTION_NOT_CURRENT` (a plan change for a subscription whose period has not been accepted yet, since events arrive unordered), re-classified when that period is accepted.
- **R9 Mode.** The environment comes from the composition root (`MORROW_ENVIRONMENT`), never from a request or provider event. **Stripe:** the `livemode` of the event and of the object read back, and the account the broker verified (§8.5). **Shopify** has no live or test flag (S147): mode is `test` when the installation's shop is a development store (the OAuth-time shop read, P09.T02a) or the cycle's effective price is $0, and `live` otherwise. Production accepts only `live` records and events; development and staging accept only `test`. A record or event in the other mode neither fixes a route, entitles nor grants (`mode_refused`, `PAYMENT_MODE_REFUSED`). App Review installs usually run on development stores, so production refuses them as written: OQ-3.
- **R10 Morrow's ledger is the only credit source.** Providers only collect payment. `creditUnits` come only from Morrow's versioned terms table (§4.1 `BillingTerms`), keyed by the provider price or plan read back from the provider object: a Stripe price id, or an App Pricing plan handle from a Partner API read. A redirect's `plan_handle` and provider metadata are never a source. A price key, once published, keeps its credit quantity forever; a new quantity needs a new key. An unknown key, a kind or currency that disagrees with the entry, or a plan change with no entry is held as `TERMS_MISMATCH`. Morrow grants once per `(route, mode, paymentKey)`, and credits are still reserved before dispatch (P11.T04a). Stripe billing-credit objects are never created or read (S145). `morrow_direct` top-ups are one-off Stripe invoices granted after `invoice.paid`, never a PaymentIntent-only Checkout. **Shopify-route extra credits are post-paid usage, not grants** (ADR-0015 item 4): P11.T04a reserves them against the installation's `UsageCap` for the current cycle, which is zero by default (top-ups default off), and settlement writes v1 `UsageLiability` and `MeterEvent` records bound to the cycle's subscription key and meter. No `VerifiedPaymentEvent` or `CreditGrant` ever represents them.
- **R11 Reversals.** A verified refund or dispute of a granted payment (Stripe `charge.refunded`, `charge.dispute.created` and `charge.dispute.closed`, each read back before any write) is a `PaymentReversal`. While it is `open`, the payer is `payment_reversed` and not billable, so none of its wallet's unspent credits can be reserved; existing reservations follow the retained-work contract. A dispute won, or a resolution P18.T01c records with owner approval, sets it `cleared`. A reversal of a payment that granted nothing is recorded only. A Stripe dispute leaves the subscription `active`, so this rule, not the subscription status, makes the payer non-billable.

**`originForCreation`** returns `website` only for `{kind:"website_signup", installHandoffPending:false}`. Every other kind, an unknown kind, an extra field or a malformed value returns `shopify_install` (the fail-closed value; it never throws, so a creating transaction cannot fall back to a default).

**Payer status** (first match wins; terminal before pending, so P14 reports truthfully): (1) Shopify payer whose association is not current, or whose `associatedAt > now` → `not_linked`; (2) no account → `account_missing`; (3) tenant, route, installation or store disagree across route record, association, account and entitlement → `record_mismatch`; (4) route, account or entitlement mode differs from the environment's → `mode_refused`; (5) account `suspended`, `cancelled` or `uninstalled`, or entitlement `past_due`, `suspended`, `cancelled` or `uninstalled` → `subscription_inactive`; (6) an open reversal → `payment_reversed`; (7) account `pending`, or entitlement null or `pending` → `subscription_pending`; (8) not `verifiedAt ≤ now < validUntil` → `entitlement_stale`; (9) `billable`. **Workspace state:** `no_route` in phases `open` and `shopify_bound`; otherwise `billable` when some payer is billable, else `not_billable`. `coveredStoreIds`: on `morrow_direct` every current link with `associatedAt ≤ now`; on Shopify the stores whose own payer is billable. `purchaseSurface` is `morrow` in `open` and `morrow_direct`, `shopify` in the Shopify phases while a link is current, else `none`. `connectStoreOffered` is false in phase `open` while `checkoutIntentPending`, and true otherwise. **`entitlementFor`** is false on a tenant mismatch or unless `billable`. A storeless request (including a connection-scoped `ad_account`) is then true; a store-scoped request needs its store in `coveredStoreIds`.

**`purchaseDecision`.** Actions: Morrow `subscribe`, `change_plan`, `top_up`, `update_payment_method`, `cancel`, `billing_portal`, `view_invoices`; Shopify `shopify_plan_page` and `shopify_usage_cap` (each with a `storeId`). It decides only; the guard that mounts it on HTTP routes is P18.T01a's.

**`billingCallToAction`** is the only source of a purchase link or purchase wording on any Morrow surface. It returns `{kind:"morrow_plans", href:"/workspace/<W>/billing/morrow/plans"}` when `purchaseSurface` is `morrow`, `{kind:"shopify_plan_page", storeIds}` (the guarded redirect of P18.T01b) when it is `shopify`, and `{kind:"none"}` otherwise, with labels from a frozen route-neutral table ("Choose a plan", "Manage plan"). In a Shopify phase it can never return a Morrow billing path, the word "checkout", a provider name, a price or a currency.

**`canonicalShopifyKey`** parses `gid://shopify/App/<n>` and `gid://shopify/Shop/<n>` strictly (a `/` never reaches a key) and a timestamp it can reduce to whole UTC seconds; anything else throws `BILLING_INPUT_INVALID`. P18.T01b uses it for every Shopify key: a period is `cycle:<currentBillingCycle.startTime>`; a plan change is `update:<SUBSCRIPTION_UPDATED occurredAt>`; a subscription is `created:<SUBSCRIPTION_CREATED occurredAt>`, recorded on the account at first observation and never re-derived, because `activeSubscription` has no subscription id (S148) and `legacySubscriptionId` is nullable and legacy. P18.T01b confirms these fields against the Partner API reference before use and holds any payment whose key it cannot derive.

**`classifyPayment`.** A malformed event or terms table, or an event outside the state's tenant, throws `BILLING_INPUT_INVALID`. Otherwise every verified event ends in exactly one outcome, so no collected payment is silently dropped. Rules apply in order:
1. `refused: PAYMENT_MODE_REFUSED` when the event's mode is not the environment's (R9).
2. `already_granted` when its `paymentKey` is in `grantedKeys` (replay; nothing changes).
3. `held` with the target's reason when the target is `unattributed` (R8).
4. `no_charge` when `amountPaid` is 0 (R3): recorded; no route, no draft.
5. `conflict: ROUTE_MISMATCH` for a Stripe event in `shopify_bound` or `shopify_app_pricing`, or an App Pricing event in `morrow_direct` (R7).
6. `held: TERMS_MISMATCH` when the price key, kind or currency has no matching terms entry, or a plan change has no `planChanges` entry (R10).
7. `top_up` (Stripe only): `grant` (kind `purchased`) on `morrow_direct` while the payer is billable; otherwise `conflict: SUBSCRIPTION_REQUIRED`.
8. `plan_change`: `grant` of the `planChanges` entry's credits when its subscription is the payer's current, non-terminal one; `held: SUBSCRIPTION_NOT_CURRENT` when no payer or subscription matches yet; `conflict: DUPLICATE_SUBSCRIPTION` for a different subscription while the current one is live; `conflict: SUBSCRIPTION_TERMINAL` when it is terminal. A plan change is therefore never a duplicate subscription, never a second full grant and never a silent `already_granted` (its key is its own invoice or update).
9. `subscription_period`: in `open` (Stripe) or `shopify_bound` (Shopify, associated installation) with no payer yet, `fix_route_and_grant`; on a fixed route, `grant` for the payer's current subscription, for a new subscription after a terminal one, or for a Shopify installation with no account yet (its first period, current link or not, R5); `conflict: DUPLICATE_SUBSCRIPTION` for a second subscription while the current one is not terminal; `conflict: SUBSCRIPTION_TERMINAL` for a late payment on a terminal subscription.

A grant is a `CreditGrant` draft without `id` for the paying account (created in the same transaction when it does not exist), carrying `route`, `mode`, `paymentKey`, the entry's `termsRevision` and `creditUnits`; its uniqueness key is `(route, mode, paymentKey)` (§8). A conflict carries its key (R7). Payer status matters only to top-ups: a period paid while a reversal is open is granted, and the payer stays non-billable until the reversal clears.

**Payment decision table.** `docs/contracts/decision-tables/classify-payment.tsv` is checked in. `scripts/billing-decision-tables.mjs` generates it from the ordered first-match rule list in `docs/contracts/decision-tables/classify-payment.rules.json`, which reviewers read as the specification, independently of `billing-state.ts`. Rows are the full cartesian product: phase (4) × event route (stripe, shopify) × kind (3) × mode matches (2) × subscription relation (none, current, other_live, new_after_terminal, current_terminal) × payer (none, billable, not_billable, reversed) × attribution (current link or mapped customer, associated but not current, unattributed) × `amountPaid > 0` (2): 5,760 rows, each with exactly one outcome. Combinations that cannot occur (a Shopify top-up; an associated-but-not-current Stripe payment; a relation other than `none` with no payer; an attributed Shopify event in `open`) have the outcome `input_invalid` and the library must throw on them. Replay and tenant mismatch are precedence rules tested separately. `verify:billing` runs the generator with `--check`.

**`foldEntitlementEvidence`** takes an observation from a fresh provider read: Stripe after a verified webhook; Shopify after the welcome-link redirect, a Partner API `activeSubscription` or `events` read, or periodic reconciliation (§8.5). A webhook or redirect is only the trigger. Same `providerEvidenceRef` → `unchanged`. A different account, route, mode, subscription or installation while the current status is not terminal → `identity_changed`, handled through `classifyPayment`. A terminal subscription observed live again → `terminal_revival_refused`. Otherwise observations are ordered by `observedAt`, then by restriction rank (`uninstalled`, `cancelled` > `suspended` > `past_due` > `pending` > `active`), then by `providerEvidenceRef`, highest last: a higher-ordered observation gives `next` with `revision + 1` and `verifiedAt = observedAt`, and a lower or equal one gives `stale_observation`. Two observations with equal `observedAt` and different evidence therefore resolve to the more restrictive one, whatever their arrival order. Any permutation of the same observations ends with the same status, evidence and `verifiedAt`; only revision numbers may differ. An unknown read outcome produces no observation; the caller re-reads (reconcile before retry).

**`spendingScope`** (recorded interpretation; it only narrows). Over grants passing `isCurrentGrant` for the request's capability and verb in the actor's tenant: `workspace` is true when any exists, and `storeIds` are the stores listed in their `scope.storeIds`. It is empty when `!isPaidWork`. An actor may charge only for work they could run, and no ADR template holds paid grants. P11.T04a's capped mandates may only narrow it.

**`selectPayers`** takes `{organizationId, workspaceId, workStoreIds, spending, allocation}`: 0..100 unique stores from the task's or Proposal@2's bound resources, `spending` from `spendingScope` over current SQL grants, and an allocation that is null only before review or admission. Each rule runs across all stores or shares before the next:
0. A tenant mismatch → `PAYER_NOT_BILLABLE`. 1. `no_route` → `BILLING_NO_ROUTE`; `not_billable` → `BILLING_NOT_ACTIVE`. 2. A work store not currently linked → `STORE_NOT_LINKED`; on Shopify, a work store whose own payer is not billable → `STORE_NOT_BILLABLE`, even when another shop pays.
3. **Candidates:** on `morrow_direct` the workspace payer if `spending.workspace`; on Shopify the billable payers whose store is in `spending.storeIds`. Other payers are invisible from here on.
4. **No allocation:** on `morrow_direct` the candidate gives `implicit` (none → `PAYER_NOT_BILLABLE`). On Shopify: one work store whose payer is a candidate → `implicit`; two or more work stores → `ALLOCATION_REQUIRED`; storeless work with one candidate → `implicit`, none → `PAYER_NOT_BILLABLE`, several → `PAYER_SELECTION_REQUIRED`.
5. **Allocation:** a duplicate account or non-null store → `DUPLICATE_PAYER_OR_STORE`; a share not exactly matching a candidate's account, installation and store → `PAYER_NOT_BILLABLE`, identical for unknown, foreign, unlinked, unauthorized, inactive and reversed payers; on Shopify, store-scoped work with a share outside `workStoreIds` → `PAYER_OUTSIDE_WORK_SCOPE`; a stale `entitlementRevision` → `ENTITLEMENT_NOT_CURRENT`; otherwise `explicit`, in share order.

`implicit` only feeds a one-share CostAllocation that Proposal@2 or the admission record binds before review; reservation and dispatch always pass the bound allocation, so a payer change after approval needs a new review. `selectPayers` reads no wallet and reserves nothing.

### 8. Persistence requirements (no migration here)

1. **Route row.** One per workspace, inserted in the creating transaction with the origin from `originForCreation`, which PR-B ships (PR-A alone triggers no route-row work). 2. **Install handoff (P09.T02a).** A server-side row bound to the installation, the receiving browser family and, after sign-in, the principal; consumed only by the install continuation; retained after expiry. Signup reads it in its creating transaction.
3. **Accounts and customers.** One `morrow_direct` account per workspace, created in the route-fixing transaction; one Shopify account per installation, created at its first completed payment and kept across disconnects (migration 0005 already makes an association unique and permanent). The Stripe customer mapping is one-to-one: `UNIQUE (workspace_id)` and `UNIQUE (stripe_customer_id)`. P18.T01a creates the customer in the broker, with an idempotency key, before the workspace's first checkout; Checkout always passes that `customer` and never `customer_email`.
4. **Grants.** `UNIQUE (route, mode, payment_key)`; the grant and its wallet credit commit together; a duplicate insert is a replay, never a second credit.
5. **Ingress and provider reads.** The event writer has no browser session.
   - **Stripe.** The broker has no public route (ADR-0007 item 1). One public api route forwards the raw request body and the `Stripe-Signature` header unparsed over the service binding to a broker method (the ADR-0008 item 2 pattern). The broker verifies the signature over the raw bytes with a 5-minute tolerance (S144) against the current signing secret and, during a rotation roll, also the previous one, which is removed when the roll ends. It checks `livemode` and the event's account against the environment's configuration, deduplicates by event id, and reads the object back (invoice, subscription, charge or dispute) before any write. The tenant comes only from the customer mapping, cross-checked against the OperationLedger operation named in the object's or its subscription's metadata; metadata is a lookup key, never authority. A mismatch, a missing mapping or a missing operation is held (R8).
   - **Shopify App Pricing** sends no subscription webhooks and no `charge_id` (S147). Triggers are the welcome-link redirect, whose `shop` and `plan_handle` are untrusted hints that only schedule a read; Partner API `activeSubscription` and `events` reads; and periodic reconciliation (P18.T01c). The `shopId` comes from the installation's OAuth-verified shop id (`linking_candidates.shop_id`), never from the redirect parameter. The Partner API token is a broker-only provider credential under ADR-0007 item 4 and the P08 credential-custody ADR; it is not one of ADR-0008's app credentials.
   - The handler acknowledges after commit and reads back an unknown commit.
6. **Outbound mutations and unknown outcomes.** Every Stripe write (customer, checkout session, top-up invoice, plan change, cancel, refund) carries an idempotency key bound to its OperationLedger operation and the operation id in the object's metadata (ADR-0015 item 7). On an unknown outcome, in this order: (1) read back first, by the operation id, with a list read over the mapped customer (search results may lag); (2) only if absence is proven and the original send is under 23 hours old by Morrow's clock, replay with the same key, because Stripe replays a saved response for the same key, a 500 included, and may prune keys after 24 hours (S143), so a replayed saved error is not absence and holds; (3) otherwise hold for P18.T01c; (4) never send with a new key.
7. **Checkout intent and the link race.** P18.T01a records each checkout intent under the route-row lock together with the route revision, and reuses one open session per workspace (idempotency key over workspace, action and terms revision). On the success return, the broker reads the session and its invoice back synchronously; the return itself proves nothing. The link writer enqueues expiry of the workspace's open sessions in its own transaction. A payment completed at Stripe but verified after a link is `ROUTE_MISMATCH` and goes to remediation and refund; this conservative outcome is deliberate, because the payment did not precede the link in Morrow's order.
8. **Reader.** It runs in the same tenant-scoped transaction as the identity read, under FORCE RLS, with no tenant or actor parameter; the §6 reader then takes the identity read scope.
9. **Conflicts.** Append-only rows with one open conflict per `(workspace, payment route, subscription key or top-up payment key)`; repeat invoices attach to it. On detection, P18.T01c raises the per-action owner approval for its first remediation, which stops the renewal: on Stripe, cancellation now or `cancel_at_period_end`; on Shopify, a downgrade instruction to the merchant. Refunds follow, each a per-action owner approval in production.
10. **Held payments.** Append-only rows keyed by `paymentKey`, never deleted and never refunded automatically; re-classified as R8 says.
11. **Reversals.** `charge.refunded`, `charge.dispute.created` and `charge.dispute.closed` trigger a readback; reversal rows are append-only by revision.

### 9. Error mapping and consumer obligations

`BILLING_DENIAL_ENVELOPES` (exported, frozen) maps each code to `{code, retryClass, safeMessage}`. No message names a provider, price or checkout, so a denial cannot expose Morrow's checkout to a Shopify-origin merchant, and every payer denial shares one envelope.

| Codes | `code` / `retryClass` | Safe message |
| --- | --- | --- |
| `BILLING_NO_ROUTE` | `denied` / `recheck_before_retry` | "Paid work starts once this workspace has an active plan." |
| `BILLING_NOT_ACTIVE`, `STORE_NOT_BILLABLE` | `denied` / `recheck_before_retry` | "A plan covering this work is not active." |
| `STORE_NOT_LINKED` | `denied` / `recheck_before_retry` | "This store is not connected to this workspace." |

Work on {A} with a share on B gives `PAYER_OUTSIDE_WORK_SCOPE`. C linked but cancelled: work on {A, C} with A paying gives `STORE_NOT_BILLABLE`. Shares on a W′ store, an unknown store, an unlinked store, a store outside spending, a cancelled payer and a reversed payer give deep-equal `PAYER_NOT_BILLABLE`; storeless work with spending [] does too. A duplicate share gives `DUPLICATE_PAYER_OR_STORE`. An allocation mixing a storeless Morrow-direct share with a store-bound Shopify share gives `PAYER_NOT_BILLABLE` on either route, and `inspectAllocation` gives `PAYER_ROUTE_INVALID` for it.
- **P01.T04a-AC23 (losing a shop and review binding).** A [iA] allocation is bound before review. iA then uninstalls: (i) with the association kept and the account `uninstalled`, W is `not_billable`; (ii) with the link no longer current, the payer is `not_linked` and W is `not_billable`. In both, the route stays Shopify, Morrow actions stay refused, and the bound allocation gives `PAYER_NOT_BILLABLE` even after iB subscribes and W is `billable` through B; a revision change gives `ENTITLEMENT_NOT_CURRENT`. Spending: an `execute` grant on `creative.image.generate` scoped to [A] gives storeIds [A]; revoked, expired, other-capability, view-only and other-workspace grants contribute nothing.
- **P01.T04a-AC24 (tenant, input binding, coverage and retained work).** A W′ state makes `entitlementFor` false for W requests and `selectPayers` `PAYER_NOT_BILLABLE`; W′ facts give `BILLING_FACTS_INVALID`; a W′ payment event, 101 associations, duplicate installations, an unknown field or a schema-invalid record give `BILLING_INPUT_INVALID` or `BILLING_FACTS_INVALID`. On a billable W with 0 credits available the simulator reservation gives `CREDITS_EXHAUSTED`. Dispatch of reserved work after cancellation gives `PAYER_INACTIVE`; an unsent reservation releases once and an uncertain one is retained (existing `billing.test.mjs` :70-72, cited); `governance.approval.decide` `approve` stays allowed.
- **P01.T04a-AC25 (no retroactive charge; Shopify post-paid usage).** A link refresh leaves reservations, liabilities, meter events and wallets deep-equal; usage observed before a reservation's `createdAt` gives `USAGE_PREDATES_RESERVATION` with the ledger deep-equal; fixing the route at t creates no liability for earlier usage. On a Shopify payer with an empty wallet, reservation without a `UsageCap` gives `CREDITS_EXHAUSTED`; with a cap it succeeds up to the cap and gives `USAGE_CAP_EXCEEDED` above it; settlement drafts a `UsageLiability` and a `MeterEvent` bound to the cycle's subscription key, and no `CreditGrant`. The schema rejects a `UsageCap` on a `morrow_direct` account or in a currency other than USD.
- **P01.T04a-AC26 (fail-closed reader at the SQL boundary).** With the fake pool of `tests/workspace-policy.test.mjs` and a throwing billing reader, `governance.usage.read` `view`, `governance.approval.decide` `approve`, `governance.membership.revoke` `execute` and `workspace.goal.create` `execute` are allowed with zero billing calls; `creative.image.generate` `execute` rejects with `IDENTITY_UNAVAILABLE` and the client is released. Through `createHumanPolicyService` the throwing reader gives `POLICY_AUTHORITY_UNAVAILABLE`.

## Security review checklist

- [ ] Only `execute` and `administer` on the catalogue-derived paid set read entitlement; unknown capabilities are paid; setup, linking, invitations, onboarding, reads, approvals, exports, privacy, stops and every ADR template row never do (AC01–AC05, AC08).
- [ ] Only the billing reader and its two forwarders set a non-false `entitlementAllowed` in product code (AC29).
- [ ] Kill switches skip entitlement but not `provider_denied`; the agent kernel is unchanged (AC04).
- [ ] Origin is `website` only for signup without a pending install handoff; every other or unknown flow is `shopify_install` (AC06). Residual risk, recorded: a merchant who installs, never signs in during the handoff, and signs up on another device gets a `website` workspace; linking that store before paying still binds it to Shopify (R2), and the App Review install path always passes through the continuation.
- [ ] The route comes only from trusted writers, fixes once at the first payment of collected money, never changes, and no request schema can carry it (AC10–AC12).
- [ ] Shopify-bound and Shopify-route workspaces are refused every Morrow purchase action, and every surface derives purchase links only from `billingCallToAction`; a missing route record fails closed; denials name no provider (AC07, AC27, AC28).
- [ ] No double billing: cross-route, duplicate, terminal, unlinked and racing charges grant nothing, become one keyed conflict per subscription, and stop renewal first; held payments are never dropped or refunded automatically; credits are granted once per `(route, mode, paymentKey)` from the terms table only (AC12–AC17).
- [ ] Refunds and disputes make the payer non-billable even while Stripe reports `active` (AC18).
- [ ] Test mode only outside production and live only in production, with the environment from the composition root and Shopify mode derived from the development-store flag or a $0 contract (AC19).
- [ ] Entitlement folding is idempotent, monotonic, order-independent and tie-broken towards the more restrictive status; unknown reads change nothing (AC20).
- [ ] One payer on `morrow_direct`; on Shopify, explicit allocations, no pooling, no unrelated or unauthorized shop, one envelope for every payer denial; payer changes need a new review (AC09, AC22, AC23).
- [ ] Non-paid requests never call the billing reader; paid requests fail closed (AC26).
- [ ] No retroactive charge; liabilities are retained; Shopify extra usage stays within a Morrow-enforced cap (AC24, AC25).
- [ ] No migration, provider call, checkout, charge or credential; credits use BigInt; pure functions read no clock; validators are generated ahead of time.
- [ ] The Tier 2 review is labelled "AI review (separate context, same model family)".

## PR-A implementation notes

PR-A is implemented on `claude/p01-t04a-a-paid-work-gate` (from `main` `400aa44`). It delivers §1, §2, §4 (with §4.4, since OQ-2 was answered (a)) and §10, the §8 and §9 requirements in `billing-entitlements.md`, and AC01–AC04, the policy parts of AC05, AC11, AC29, AC30, AC31 and AC33; AC31 and AC30's workerd clause are pending the hosted labs (`lab:group:pg-core`, `lab:workers`); `lab:permissions` passed once locally. PR-B delivers the rest (AC05's library parts, AC06–AC10, AC12–AC28, AC32). Refinements of the design, none of which changes a rule:

- **Schema.** Each key has a per-route definition (`StripePaymentKey`, `ShopifyPeriodKey`, `ShopifyPlanChangeKey`, `StripeSubscriptionKey`, `ShopifySubscriptionKey`, `StripePriceKey`, `ShopifyPriceKey`) under the umbrella `PaymentKey`, `SubscriptionKey` and `PriceKey`, so every record's keys must match its route, and a Shopify period and plan change have distinct key forms. Shopify GID tails have no leading zeros, so one provider object has one key. `UsageCap.maximumLiability` uses a new `UsdBillingMoney`, as do the Shopify branches of `VerifiedPaymentEvent.amountPaid` and `PaymentReversal.amount`; a Shopify terms entry and a Shopify account have currency `USD` (App Pricing prices are USD only, S30). `AllocationShare@2` is a superset of v1 (a v1 share is a valid store-bound share); it is stored only inside `CostAllocation@2`, whose `schemaVersion` keeps the versions apart, and `changes.json` records the exception. `WorkspaceBillingRoute` has three branches: unfixed; `morrow_direct` only with origin `website` and `shopifyBoundAt` null (R3 fixes it only in phase `open`); `shopify_app_pricing` only with `shopifyBoundAt` set (R2, R3). A Stripe event's `operationId` may be null, because an object that traces to no Morrow operation must still be representable to be held `NOT_MORROW_INITIATED`. Tenant ids on events and reversals are null together. A Shopify grant is always `included`, and a Shopify terms entry is always a `subscription_period`. JSON Schema can reject only an exactly repeated terms entry (`uniqueItems`); a repeated `(route, mode, priceKey)` with different credits is rejected by PR-B's terms parser (`BILLING_INPUT_INVALID`).
- **AC05 and the connect rule.** `governance.connection.connect` `approve` (a row of `owner-bootstrap-v1` and `workspace-admin-v1`) was `capability_denied` under the pre-Part B connect rule. Since the merge with `main` (P05.T01x Part B's rule allows `administer` and `approve`), AC05 asserts that every template row is allowed without an entitlement, that row included.
- **PW1** also requires `view` and `approve` to stay never-gated (ADR-0015 item 5: reads and approvals continue). PW2 holds by construction (kill switches come from the catalogue), so a spending kill switch is reported by PW3. `paid-work.ts` repeats PW1 at import (`paidWorkTableValid`), so a malformed table never loads.

It runs over the same `apps/` and `packages/` walk as the other boundary checks. As defence in depth, `createWorkspacePermissionBoundary` copies a `CurrentConstraintsReader` result only when it is a plain, closed pair of booleans; anything else fails closed (`IDENTITY_UNAVAILABLE` at the boundary).

Production refuses before reading the record; only evaluations the module returned can entitle, and an accepted evaluation stops entitling at the seed's `validUntil`, so a retained evaluation cannot outlive its seed. - **Siblings.** Part B (PR #10) and P06.T01a (PR #12) merged before this PR, so the merge with `main` applies the "merges first" coordination: the `!isPaidWork` template v1 check lands in `tests/account-onboarding.test.mjs` with this PR (§9), the route row goes to the first billing child (§8.1), and `packages/work/src/permissions.ts` passes `entitlementAllowed: false` (otherwise `verify:boundaries` fails), with `tests/work-unit.test.mjs` asserting that no work operation is paid work. `P05.T01x.md` records the outcome in its coordination outputs.
