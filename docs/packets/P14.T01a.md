### 4.4 Design-system port
- **Tokens.** `scripts/generate-ui-tokens.mjs` turns `tokens.json` into two files: `tokens.css`: `--color-*`, `--space-1..6`, `--radius-*`, `--width-{sidebar,conversation}`, `--type-*` and `--motion-duration`; `tokens.ts`: the 1120 and 760 breakpoints. `--check` runs in `verify:design`. Any hex, `rgb()` or `hsl()` literal outside `tokens.css` fails.
- **CSS.** The prototype styles are ported into stylesheets, so the P04.T02a CSP is unchanged. There is no inline `<style>`, no `style=` and no CSS-in-JS. System fonts, `color-scheme: light`, and `aria-hidden` inline SVG icons.
- **Layout.** The sidebar is 232 px. The 336 px task side pane becomes an `aria-pressed` pane switch (Task · Conversation · Activity) below a 1120 px content width. Below a 760 px viewport, navigation becomes a labelled modal drawer. Focus is trapped, the background is `inert` (React 18.3.1 needs the string `inert=""`), and Escape restores focus. There is no page-level horizontal scroll at 320 px. Motion runs 120 ms and is off under reduced motion. Targets are at least 24×24 px.
- **Components.** Shell: `AppShell`, `Navigation`, `NavDrawer`, `WorkspaceSwitcher` (menu button), `ProvisionalNote`, `Tabs`, `PaneSwitch`. Controls: `Button`, `TextField`, `TextArea`, `Dialog` (native `<dialog>`). Feedback: `StatusRegion`, `OutcomeNotice`, `ReentryNotice`. `StateView` states: loading, empty, denied, not_found, unavailable, not_in_build, offline, session_expired, workspace_unavailable. Display: `Tag`, `PersonLabel`, `Time`, `Icon`.
- **Labels.** Every screen, at every width, carries a `role="note"` that cannot be dismissed: "Provisional workspace · design under review". Fixture builds add "Fixture data · not connected to Morrow" and scenario controls.
- **Copy.** Actions name their effect, and nothing reads as success before a confirmed response. "Answering doesn't approve any change." Home carries the ADR-0015 pre-payment notice: "Paid work starts once this workspace has an active plan. Plans aren't available in this provisional build." It names no checkout or store route, so it stays true on both billing routes and never points a Shopify-origin workspace to Morrow checkout. User text renders as React text with `dir="auto"`. There is no `dangerouslySetInnerHTML`, and no data-built `href`.

### 4.5 Routing, the `account` route, the intended route
- **Router.** `router.ts` uses `pushState` and `popstate`. Links come from `buildWorkspacePath`, and back and forward restore the logical path. Queries and fragments carry no state. Unknown and `operator` paths render NotFound. `document.title` comes only from the route title.
- **Implemented routes.** `account` `/`, `home`, `work`, `task`, `inbox` and `question`. Other routes render `UnavailableDestination`.
- **The `account` entry.** Whichever of PR-1 and Part B lands first adds it. As built, it is byte-identical to the entry on the Part B branch (`claude/p05-t01x-b-signup`), so either PR can land first without a catalogue conflict:
  ```json
  {"id":"account","pattern":"/","title":"Account","data":["workspaces","onboarding"],"journey":"J01","hosts":["standalone"],"namespace":"merchant","states":["loading","empty","ready","permission_denied","recoverable_error","uncertain_operation","offline"],"ui_status":"P14.T01a must qualify interactions","parent":null,"components":["AccountHeader","WorkspacePicker","OrganizationSignupForm"]}
  ```
- **Root case.** The same change adds a root case to `matchWorkspacePath`, with a `/` test. `"/"` matches only the route whose pattern is `"/"`, and no other path matches that route. `buildWorkspacePath(c,"account",{})` returns `"/"`. With this, the round trip, the `components.length && data.length` check and `verify-contracts` `hosts.sort()` all pass.
- **Workspace scope.** Entering `/w/:workspaceId` calls `workspace.bootstrap` once. Caches are keyed by workspace and dropped on a switch or sign-out. Nothing records an "active workspace".
- **Intended route.** `sessionStorage["morrow.intended.v1"]` holds one path. The path must start with `/w/` and pass `matchWorkspacePath` (standalone). After the callback's 303, `/` reads it once, re-validates it, deletes it, sets the in-memory `restoredThisLoad` flag and navigates. Full URLs, `//x`, `/w/a/../b`, encoded slashes and queries are refused (P02.A01 vectors).

### 4.6 Sign-in, workspace 401s, sign-out
- **Start.** One `POST /auth/login`. At `loginBodyVersion` 1 the body is `{"schemaVersion":1,"workspaceId":W}`, with W from the current or intended route. At `/` with neither, the button is disabled with "Open the workspace link you were given to sign in". At version 2 the body is `{"schemaVersion":2}`. On 200, `location.assign` runs only if `authorizationUrl` has origin `https://api.workos.com`, path `/user_management/authorize`, and no credentials or fragment. Anything else, including 503 `login_unavailable`, shows "Sign-in couldn't start. Try again in a moment." There is no navigation and no rate-limit state.
- **401 on `account.overview`** → `session_expired`.
- **401 on a workspace-scoped request** (bootstrap or `work.*`). Foreign, revoked, non-member and expired cannot be told apart, and a valid v2 session may still hold other workspaces (ADR-0004 item 4).
  - **PR-2 (overview composed):** exactly one `GET /workspaces` probe. 200 → `WorkspaceUnavailable` ("This workspace isn't available to you", with a link to `/`). The intended route is deleted and no sign-in is offered. 401 → `session_expired`. Anything else → unavailable with Retry.
  - **PR-1:** if `restoredThisLoad` is set → `WorkspaceUnavailable` with a Sign in button and no stored intended route. Otherwise → `session_expired`.
  - Either way, one failed restore discards the intended route, so sign-in cannot loop.
- **`session_expired`.** Private screens unmount. The current path becomes the intended route, unless it was just restored. Drafts are dropped ("Unsent text wasn't kept"), but uncertain commands keep their markers (§4.9). There is no client timer, and the leave guard is bypassed.
- **Sign-out.** Sends `{"schemaVersion":1}`. 200 `session_ended` or 403 `logout_unavailable` → clear memory and every `morrow.*` sessionStorage key, then show SignedOut. 503 `logout_unavailable` → keep the session and show "Sign-out didn't complete" with Try again. 503 `logout_outcome_unknown` → clear private state and storage locally, then show "We couldn't confirm you were signed out" with Try again. The retry gets 200 or 403, and either ends in SignedOut. The stale cookie remains until P05.T01y's `Max-Age=0`, but it no longer resolves.

### 4.7 Port and request client (TypeScript)
```ts
// packages/workspace-ui/src/port.ts — screens see only this.
export type Outcome<T> =
  | { kind: "ok"; value: T; replayed: boolean }
  | { kind: "unauthenticated" }                                      // 401 → §4.6
  | { kind: "denied"; message: string; reference: string | null }    // 403
  | { kind: "not_found" }                                            // 404: absent, foreign or not viewable
  | { kind: "conflict"; recheck: boolean; message: string }          // 409
  | { kind: "invalid"; field: string | null }                        // 400
  | { kind: "rate_limited"; retryAfterSeconds: number }              // 429 (signup only)
  | { kind: "unavailable"; offline: boolean }                        // reads; commands never yet uncertain
  | { kind: "uncertain" }                                            // §4.9: only a decoded terminal reply ends it
  | { kind: "not_in_build" };
export interface Command<B> { readonly key: string; readonly body: Readonly<B> } // lowercase UUID v4; reused verbatim
export interface WorkspacePort {
  session: { startSignIn(workspaceId: Id | null): Promise<Outcome<{ navigateTo: string }>>;
    signOut(): Promise<Outcome<"ended">>; keepAlive(): Promise<Outcome<null>> };       // keepAlive: not_in_build (§4.14)
  workspace: { bootstrap(ws: Id): Promise<Outcome<WorkspaceView>> };
  account: { overview(): Promise<Outcome<AccountOverviewView>>;
    createOrganization(c: Command<{ organizationName: string; workspaceName: string }>): Promise<Outcome<{ workspaceId: Id }>> };
  work: { listGoals(ws: Id, after: string | null): Promise<Outcome<Page<GoalView>>>; getGoal(ws: Id, id: Id): Promise<Outcome<GoalView>>;
    createGoal(ws: Id, c: Command<{ objective: string; criteria: readonly string[] }>): Promise<Outcome<{ goalId: Id }>>; // 1–20
    listTasks(ws: Id, goalId: Id, after: string | null): Promise<Outcome<Page<TaskView>>>; getTask(ws: Id, id: Id): Promise<Outcome<TaskView>>;
    createTask(ws: Id, c: Command<{ goalId: Id; objective: string }>): Promise<Outcome<{ taskId: Id }>>;
    markReady(ws: Id, id: Id, c: Command<{ expectedRevision: number }>): Promise<Outcome<{ revision: number }>>;
    assign(ws: Id, id: Id, c: Command<{ assigneeId: Id; expectedRevision: number }>): Promise<Outcome<{ revision: number }>>;
    listTaskQuestions(ws: Id, taskId: Id, after: string | null): Promise<Outcome<Page<QuestionView>>>;
    ask(ws: Id, taskId: Id, c: Command<{ question: string; respondentId: Id }>): Promise<Outcome<{ questionId: Id }>>;
    listMyOpenQuestions(ws: Id, after: string | null): Promise<Outcome<Page<QuestionView>>>; getQuestion(ws: Id, id: Id): Promise<Outcome<QuestionView>>;
    answer(ws: Id, id: Id, c: Command<{ text: string; expectedRevision: number }>): Promise<Outcome<{ answerRevision: number }>>;
    cancelQuestion(ws: Id, id: Id, c: Command<{ expectedRevision: number }>): Promise<Outcome<{ revision: number }>>;
    getAnswer(ws: Id, id: Id): Promise<Outcome<AnswerView>> };
  people: { list(ws: Id): Promise<Outcome<readonly PersonRef[]>> };                    // not_in_build (§4.14)
}
// model.ts — UI-internal view models, not contracts.
export interface PersonRef { principalId: Id; kind: "human" | "agent" | "service"; label: string | null; isSelf: boolean | null } // null until people.list
export interface TaskView { id: Id; goalId: Id | null; objective: string; status: string /* any v1 TaskStatus; unknown → shown as text */; owner: PersonRef; revision: number; updatedAt: string }
export interface Page<T> { items: readonly T[]; next: string | null }
```
- **`client.ts`.** `createClient({ transport = fetch })` sends `transport(path, {method, credentials:"same-origin", cache:"no-store", redirect:"error", headers, body, signal})`. The T01y keeper's `request` may replace `transport`.
- **No `mode` override.** Under the page's `no-referrer` policy, a non-GET request whose mode is not `cors` sends `Origin: null` (Fetch, "append a request Origin header"), which every P05/P06 guard rejects with 403. The default `cors` mode sends the page origin and `Sec-Fetch-Mode: cors`, which every guard accepts. Same-origin paths never trigger CORS.
- **Paths.** Ids are validated against `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` and inserted **unencoded**. The pattern is path-safe, and the guards match the raw pathname, so `%3A` would 404. Paths are relative and start with `/`. The only query parameters are the documented ones: `after` (encoded), `limit`, `goalId`, `respondent=me`, `status=open`.
- **Headers.** Every request carries `X-Morrow-Request: 1`. POSTs add `Content-Type: application/json`. Work and account commands add `Idempotency-Key`. Login and logout never do. GETs carry no body, `Content-Type` or key. No request carries `Authorization`.
- **Bodies.** Closed literals, exactly as in P05.T01x §9 and P06.T01a §4.9. No `organizationId`, `workspaceId` or `principalId` key. `storeIds` and `allowedResources` are `[]`. Criteria number 1–20, each `{description, verificationCapabilityId:null, evidenceRequired:false}`. Byte limits are checked before sending: 512 for login, 2048 for signup, 64 KiB for work.
- **Timeouts.** Reads abort on navigation or after 10 s. Commands are never aborted by navigation; after 15 s a command is `uncertain`.
- **Single flight (`pending.ts`).** `run(command)` is keyed by `command.key`: a second caller gets the in-flight promise. A double click, a StrictMode double effect, or Check again pressed twice therefore sends one request. A new key is minted only after a terminal outcome, when the person edits and submits again.

### 4.8 Decoders and outcome mapping
- **Two hand-written decoders.** Neither uses eval or schema compilation, and both ignore unknown properties. **`identity-decoders.ts`** reads the `{schemaVersion:1, outcome}` and `{code}` bodies. It maps each (status, outcome) pair to fixed copy in `copy.ts` and shows no server text or reference. For signup's 429 it reads `Retry-After` as an integer from 1 to 86400, defaulting to 600. **`work-decoders.ts`** reads the v1 `ErrorEnvelope`. It shows `safeMessage` and "Reference: <correlationId>", and never parses them.
- **Statuses** decode as any string. Every v1 enum value has a label; unknown values render as text.
- **Parity test.** The 1.6 MB validators are not bundled. Instead, a parity test requires every valid P01/P06 fixture to pass both its validator and the decoder, and every invalid fixture for a rendered field to fail the decoder.

| Response | Read | Command |
| --- | --- | --- |
| 2xx that decodes | `ok` | `ok`, with `replayed` from the body. **Terminal** |
| 2xx that does not decode, non-JSON, or a redirect | `unavailable` | `uncertain` |
| 400 | `invalid`; `invalid_name` maps to the name field | same; terminal |
| 401 | `unauthenticated` (§4.6) | same; an uncertain command keeps its marker |
| 403 | `denied`; `signup_unavailable` shows onboarding as unavailable | same; terminal |
| 404 | `not_found`, one copy for absent, foreign and no access | same; terminal |
| 409 `recheck_before_retry` | `conflict`: refetch and show current values | terminal; the form keeps its input, and resubmitting uses a new key |
| 409 `never`, `already_onboarded`, `idempotency_conflict` | `conflict` with fixed copy; `already_onboarded` refetches | terminal |
| 429 | `rate_limited`, disabled until `Retry-After` | if never uncertain: `rate_limited`. Once uncertain: **stays `uncertain`** |
| 503 `unavailable`, or a pre-send failure | `unavailable` (`offline` = `!navigator.onLine`) | if never uncertain: "Couldn't save. Nothing was changed.", and Try again resends the **same key and body**. Once uncertain: **stays `uncertain`** |
| 503 `uncertain`, `outcome_unknown` or `logout_outcome_unknown`; network error or timeout after the send | `unavailable` | **`uncertain`** |

### 4.9 Unknown outcomes, re-entry markers, leave guard
- **Uncertain.** A persistent `OutcomeNotice` (`role="status"`) reads "We couldn't confirm whether this was saved. Check again before doing anything else." Its only action is **Check again**: one single-flight resend of the identical key and body, which *is* the reconciliation (ADR-0010 item 3; P05.T01x §10; P06.T01a §4.7). The notice ends **only on a decoded terminal response**: a 2xx (success is shown once), or a 400, 403, 404 or 409. A 503 of any code (including P06's still-in-flight 503 `unavailable`), a 429, a network error or a timeout keeps the notice and the key. There is no automatic retry and no new key. The form stays filled and disabled.
- **Re-entry marker.** When a work command becomes uncertain, `pending.ts` writes a text-free entry to `sessionStorage["morrow.unconfirmed.v1"]`: `{workspaceId, kind:"goal"|"task"|"ready"|"assignment"|"question"|"answer"|"cancel", at}`. There are at most 20 entries. They hold no key, body, record id or text. An entry is removed on a terminal response, Dismiss, sign-out or `session_ended`. After a reload, a 401 or a return to the tab, the screen in that workspace shows `ReentryNotice`: "A change you started earlier (a new goal) may have been saved. Check Work before creating it again." Signup needs no marker. Because a principal can create only one organization, a fresh key after a reload gets 201, or 409 `already_onboarded` followed by a refetch. The packet does not persist {key, body}. That would keep tenant text in storage across session loss, and another person signing in on the same tab could resend it under their own identity.
- **Leave guard** (workspace-routes.md: "guard unsaved input"). While a form is dirty or a command is pending or uncertain, in-app navigation opens a Dialog: "Leave this page? Unsent text will be lost.", with **Stay** (focused) and **Leave**. This covers links, the switcher, and back and forward (`popstate` re-pushes the current path), and `beforeunload` is registered. A 401 or a sign-out bypasses the guard.

### 4.11 Fixture mode (dev-only; cannot ship)
- **Separate entry.** The only path to fixture code is `fixture.html` → `fixture-main.tsx` → `fixtures/adapter.ts`. `vite.config.ts` sets `rollupOptions.input` per mode: `main` normally, and `fixture` only under `--mode fixture`. - **Can never ship.** (a) `boundary-checks` rejects imports of `src/fixtures/**` except from `fixture-main.tsx` and `tests/`. (b) `scripts/workspace-web-checks.mjs` (`verify:workspace-web`, run after `build`) fails if `dist/**` contains the canary `MORROW_FIXTURE_BUILD_CANARY` or `fixture.html`. (b) also fails when a Vite plugin's report (each chunk's `moduleIds`, written to `$MORROW_ARTIFACTS_DIR/workspace-web/modules.json`, never to `dist`) lists a module under `src/fixtures/`, `node_modules/axe-core/` or `node_modules/playwright`, or `runtime-validators`. ## 8 Security review checklist (Tier 2, with `/security-review`)
- [ ] No tenant, workspace or actor authority comes from the client. Path ids only select, and bodies carry no tenant keys (invariants 1, 22).
- [ ] Requests are same-origin with the default `cors` mode, so the exact `Origin` is sent under `no-referrer`. Each request carries `credentials:"same-origin"`, `redirect:"error"` and `X-Morrow-Request`, so the P05/P06 guards pass unchanged. There is no CORS and no `Authorization`.

- [ ] `document.cookie` is banned. sessionStorage holds only the intended path and the text-free markers. No bearer, cookie, token or tenant text is stored anywhere.
- [ ] `uncertain` ends only on a decoded terminal response. It keeps its key, has no automatic retry, and is single-flight. Re-entry never resends.
- [ ] A 401 removes private content. Non-member, foreign and revoked workspaces get one view. Sign-out, including the unknown case, clears local state.
- [ ] Content renders as text, with no HTML sinks. The CSP is unchanged.
- [ ] Fixture code cannot reach `dist` (§4.11 a–e). The URL allowlist is exact, and reports live outside `dist`.
