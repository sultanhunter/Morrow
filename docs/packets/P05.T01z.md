## Goal
**Today:** memberships and grants come from owner SQL or the signup template. The only removal primitive (0004) is an owner-seeded, receipt-based local path. There is no invitation, role change or ownership transfer, and `WorkspaceOwnershipFacts` has no SQL reader.
**After this packet:**
1. A member holding `execute` on `governance.membership.revoke` removes a member from one workspace, or from the whole organization at once. A reason is required and no second approver. The effect, one `KillSwitchRecord` and one stop event commit together. The owner cannot be removed until ownership is transferred.
2. An admin proposes an invitation (an allowlisted email plus a named template). A non-conflicted reviewer approves it through P06.T01b, or the solo owner does with the typed phrase and cool-down. Applying it claims the approval once and issues a one-use invitation that expires after 7 days. A separate send command delivers it through the delivery port, which mints the token; Morrow stores only its digest.
3. The invitee signs in (enrolling at first sign-in, ADR-0009 item 10) and presents the token, and Morrow checks that the provider-verified email matches. The invitee then holds exactly the frozen template's grants in that workspace, and nothing else. An existing organization member can be added to another workspace the same way.
4. Template change (the "role change") and ownership transfer run as reviewed access_change proposals.
5. SQL supplies `WorkspaceOwnershipFacts` to the review library and to P06.T01b, for every organization, including ones created after this migration.

## Design

### 1 Model
- **Authority is grants only.** A "role" is a named grant template. The template a member last received in a workspace is recorded. It is shown, and it is used only to restrict (§2.3); the kernel never reads it.
- **Owner** is the latest `organization_owner_designations` row while its membership is active and its principal an active human. It is seeded from `organization_signups` and kept current by a trigger on new signups (ADR-0009 item 3). It confers no authority. It decides owner protection, the `stop_notice` recipient and solo status. With no current designation, nobody is protected or solo, and P07.T03 addresses the notice to the record's actor (§11).
- **An invitation reserves a membership id** in its proposal parameters. Until the invitation closes, that id names the invitation as a kill-switch target, and revoking it cancels the invitation. A new member's membership gets the reserved id. A rejoining person (0001's unique key) gets their old row back, so `accepted_membership_id` differs. After acceptance the reserved id names the membership when the two are equal, and nothing (404) otherwise.

| Command | Capability (executor) | Review | Effect, atomic with its records |
| --- | --- | --- | --- |
| Remove from workspace W | `governance.membership.revoke` (human_only, kill switch) | none | W membership inactive; the target's W grants revoked; (PR-B) its live W invitations as issuer cancelled |
| Remove from organization O | same, authority in every active workspace of O (§2.2) | none | O membership inactive (which writes the P05.T01y watermark once T01y is applied); every workspace membership and grant in O revoked; (PR-B) every live invitation it issued in O cancelled |
| Cancel an invitation (PR-B) | same; target = reserved id | none | invitation `cancelled` |
| Invite (PR-B) | `governance.membership.invite` (human_only) | access_change | invitation issued (`delivery_pending`) |
| Send (PR-B) | `governance.membership.invite` | none (delivers an approved invitation) | one port attempt; `pending` with the token digest, or `delivery_failed` |
| Accept (PR-B) | none: token possession plus a matching verified email | none | O membership (new, existing, or the old row reactivated), the W membership and the frozen template grants |
| Template change (PR-B) | `governance.grants.revise`, variant `membership.template_change` | access_change | the target's live W grants replaced by the template's; its live W invitations cancelled |
| Ownership transfer (PR-B) | `governance.grants.revise`, variant `owner.transfer` | access_change | designation revision + 1 |

`organizations.policy_revision` advances once per command that changes authority or ownership: an effective removal, acceptance, template change and transfer. Issue, send and cancel change no authority and leave it alone, so in-flight P06 commands do not fail `stale_authority`. Quiet-period membership changes (ADR-0011 Q2: "any revocation or ownership change") are effective removals, template changes (they revoke grants) and transfers.

### 2 Authority rules
1. **Kernel requests** use resource W (`{O,W,null,null,"workspace",W}`), as P06.T01a does, with the capability's effective input property names as fields: revoke `membershipId, control`; invite `identity, grantProposal`; grants.revise `proposalRef, approvalRef`. Owner template v1 covers all three (P05.T01x §3.4). Provider is allowed (no provider effect). Entitlement: invite and grants.revise are control effects, which are never paid work (P01.T04a §1, `isPaidWork`), so a workspace in the ADR-0015 item 5 pre-payment state may invite and manage grants; stops skip it in the evaluator from P01.T02a PR-B (ADR-0011 Q8).
2. **Removal** (ADR-0005; P01.T02a §5).
   - **Workspace scope:** `execute` on revoke in W, then `checkKillSwitchTarget` with W's facts.
   - **Organization scope:** (a) the actor needs an active membership and the same kernel allow in **every** active workspace of O, each against that workspace's own grants, never unioned; otherwise 403 `organization_scope_denied`. (b) `checkKillSwitchTarget` runs in each active workspace where the target holds a workspace membership row (active or not); W must be one of them, otherwise 404. (c) In inactive workspaces, the target's memberships and grants are revoked without an authority check and get no target entry, since they confer nothing. (d) More than 100 active workspaces in O → 409 `limit_reached`, nothing written (the record's 100-target cap; P05.T01aa may batch).
   - The owner membership gives `OWNER_MEMBERSHIP_PROTECTED` in TypeScript and again in SQL under the organization lock. A `sourceProposalRef` is rechecked and confers nothing. In PR-A it never resolves (404); PR-B resolves it through P06.T01b's `readProposal`.
3. **Templates** (`@morrow/contracts/membership-templates`, Q1). Each is a frozen list of `{capabilityId, verbs, fields}`; digest `sha256(JCS(list))`; the `grantProposal` GrantRef is `{O,W,null,"grant","template:<id>",1,<digest>}`; every grant is scoped `{O,W,[],[],[W-ref],fields}` with `expiresAt: null`. Governance-bearing: `owner-bootstrap-v1` (signup, ADR-0009 item 7) and `workspace-admin-v1`. The member's current template id is the latest template-bearing change-log row in W, or `owner-bootstrap-v1` for the signup owner's W, else null.

| Work capability (fields: the P06.T01a §4.8 union, copied literally into the module) | member-v1 verbs | admin-v1 verbs |
| --- | --- | --- |
| `workspace.goal.create` {objective, scope, status, owner, successCriteria, taskIds, storeIds} | view, execute | view, execute, administer |
| `workspace.task.create` {goalId, parentTaskId, status, objective, scope, initiatingPrincipal, owner, dependencyIds, acceptedArtifactRefs, completionEvidenceRefs, leaseGeneration, activeRunId, allowedResources} | view, execute | view, execute, administer |
| `workspace.task.assign` {taskId, assigneeId, expectedRevision} | execute | execute, administer |
| `workspace.question.request` {taskId, status, prompt, answerSchemaRef, eligibleRespondentIds, blocksTask, expiresAt, answerRef, answeredBy, answer, question, answerSchema, respondentId} | view, execute | view, execute, administer |
| `workspace.question.answer` {questionId, answer, expectedRevision} | execute | execute |

   `workspace-admin-v1` also holds the eight `owner-bootstrap-v1` governance rows, literally: invite [execute, approve] {identity, grantProposal}; revoke [execute, approve] {membershipId, expectedRevision, control}; grants.revise [execute, approve] {proposalRef, approvalRef}; connection.connect [administer, approve] {providerId, installationProof, scope}; connection.disconnect [execute, approve] {connectionId, expectedRevision, control}; approval.decide [approve] {proposalRef, decision, expectedRevision}; approval.preview [view] {proposalRef, selectedTargetIndexes}; usage.read [view] {scope, period}. `workspace-member-v1` holds no governance row. A contract check pins both lists; once template v2 exists, a second check asserts that v2 covers every (capability, verb, field) of `workspace-admin-v1`, so a v2 owner can issue both.
4. **No amplification and recipients** (catalogue: "Invitation cannot delegate authority beyond inviter scope"). Proposing or applying an invitation or template change requires that, for every template grant `g`, the actor holds each verb of `g` on `g.capabilityId` with `g.fields`, by kernel decision at W; otherwise 403 `amplification_denied`. A v1-only signup owner therefore cannot invite with either template until it holds template v2. Expiry rule: template grants carry `expiresAt: null`; later expiry or revocation of the issuer's grants does not shorten the invitee's grants, but the issuer's live invitations are cancelled when the issuer is removed or its template changes (here) and when P05.T02a revokes an issuer grant in W (consumer obligation, §11). Invitation emails must be on the injected recipient allowlist (labs: a fixture list; unset: refuse all); otherwise 403 `recipient_not_allowed`, checked before P06.T01b stores any parameter.
5. **Acceptance** needs all of: a current account family (`account_session_principal`); a token whose digest matches a `pending`, unexpired invitation whose issuer membership is still active; and the provider-verified email of the family's WorkOS subject, normalized (§9.1), equal to the invitation's, with `verified:true`. Email alone, token alone, or token claims (`email`, `org_id`, `roles`) never select or grant anything. A mismatch leaves the invitation pending for its real recipient. An active W member gets 409 `already_member`; an active O member without an active W membership is added to W.
6. **Review** follows ADR-0011 through P06.T01b, unchanged. Conflict set: the proposer and requester always. Beneficiaries: none for an invitation (the invitee is not yet a principal, or is an existing member named only by email); the target for a template change; the incoming owner for a transfer. Solo owner: the typed phrase (`approve 1 change for 0 credits`), 300 s cool-down, rechecked at claim. A consequence of ADR-0011, not a new rule: in a two-member organization where only the owner holds reviewer verbs, no access change can be approved, and P06.T01b refuses at submission (`quorum_unreachable`). Recovery: invite the second person as `workspace-admin-v1` while still solo.
7. **Owner rules.** A template change of the owner's membership must keep a governance-bearing template, and a transfer's incoming owner must currently hold one in W; otherwise 403 `owner_template_required`. Invitations approved by a later-removed reviewer stay live, because the approval was valid when claimed.

**KillSwitchRecord canonical text.** SQL builds it under the lock (the record's `createdAt` and `priorStateObserved` exist only there), in JCS key order, through one fixed function over this closed shape. Strings go through `to_json(text)`. PostgreSQL and RFC 8785 (`JSON.stringify`) agree on escapes: `\b \t \n \f \r` short forms, other C0 controls as lowercase `\u00xx`, and U+2028/2029 unescaped; NUL cannot reach SQL (the P06.T01a parser rejects it). `createdAt` is `YYYY-MM-DDTHH:MM:SS.sssZ` from a millisecond-truncated `clock_timestamp()`. The Worker asserts `JCS(JSON.parse(canonical)) === canonical` and `validateCurrentDefinition("KillSwitchRecord", …)` before disclosing one; otherwise 503. `KillSwitchRecordRef` (P01.T02c) = `{O,W,null,"kill_switch_record",id,1,digest}`.
**Retention** (`data-lifecycle.md` classes; no retention increase). The current designation is live organization state. Superseded designations and the change log are content-free audit (365 days), with subject associations pseudonymized on principal erasure. `membership_invitations` and `invitation_acceptances` are personal data (email, principal association) in R02, erased through `membership_preserve_record()` once P09.T05 replaces it. The invitee email is also in P06.T01b's proposal parameters, so those parameters join the P09.T05 erasure plan (§11). Kill-switch records are R02 (the P06.T01a class).

### 4 Functions, roles and grants

### 5 Lock order (every writer; targeted interleavings are tested, deadlock freedom is not claimed)
(1) the command advisory (P06.T01a `begin_command`; acceptance: `invitation-accept:<principal>`) → (2) organization `FOR UPDATE` (`membership_lock`; acceptance locks the invitation's organization after an unlocked read and rechecks) → (3) W's stream `FOR UPDATE` only (work commands; organization scope touches no other stream) → (4) the P06.T01b family-root approval and its claim (apply only) → (5) invitations, in id order → (6) acceptance only: `lock_session_eligibility(digest, NULL, principal, O)`, the 0008 chain → (7) `memberships` (the P05.T01y watermark trigger fires here) → (8) `workspace_memberships`, in workspace-id order → (9) `grants`, in id order → inserts only. This extends 0008's "organization first" order. P06.T01a commands and P06.T01b decisions take the organization `FOR SHARE` before the stream, so all of them serialize on (2); `membership_lock` takes `FOR UPDATE` directly and never upgrades. `cmd_invitation_send` and `invitation_send_record` change no authority: they use P06.T01a's `work_lock_and_recheck` (`FOR SHARE`), then the stream, then the invitation.

### 6 Command protocol (P06.T01a §4.7: guard → context → replay → target → verb → input → execute → commit)
**6.1 Common.** Each transaction is one P06.T01a prologue on the request's single connection, with its 5 s limits; no transaction is open during a port call. `requestDigest = sha256(JCS(["morrow.work.command",1,type,ws,pathIds,body]))`. Denials and conflicts persist nothing, except an `already_stopped` stop (6.2). `markSubmitted()` is called immediately before the `cmd_*` statement; a loss after it gives 503 `uncertain`, and a same-key retry reconciles, because the command row commits atomically with the effect.
**6.2 Remove** (`POST /members/:membershipId/revoke`, body `{scope, control}`).
1. `membership_context(scope)`; the replay check.
2. The kernel allows `execute` with obligations exactly `recheck_at_dispatch` and `kill_switch_record`, in every affected workspace (§2.2(a)).
3. The server builds `{membershipId, control}`; `validateCapabilityInput` must pass.
4. `membership_target` → `checkKillSwitchTarget` per workspace (§2.2(b)).
5. `cmd_member_revoke`:
   - `membership_lock` rechecks, against the snapshot GUC, that the session digest still resolves in W, that the active-workspace set and every per-workspace grants digest are unchanged, and that no grant expired since `evaluated_at`; otherwise `ineligible` or `stale_authority`. The organization `policy_revision` is deliberately **not** compared, so an unrelated change never blocks a stop;
   - W's stream; owner protection from the current designation; the target state under lock;
   - the §1 effect through `membership_revoke_apply` and `grant_rows_revoke`; one change-log row per affected workspace (`already_removed` when nothing changed); `policy_revision + 1` only when state changed;
   - **one** KillSwitchRecord in W: `targets` = `{O,w,null,null,"member",M}` for each §2.2(b) workspace, `priorStateObserved` = `active` if anything changed, else `already_stopped`;
   - the event `kill_switch.executed {capabilityId, sourceProposalId|null}` (aggregate `kill_switch_record`, P01.T02c registry) in W's stream; the command row.

   Response: 200 `{schemaVersion:1, revocationId, affectedRuns:[], scope, workspaceIds, priorStateObserved}`, where `revocationId` is the record id. The output validates against the capability. There are no runs before P12, so `affectedRuns` is `[]`.
**6.3 Propose and apply (PR-B).** `POST /members/proposals` `{change}`, where `change` is `{kind:"invitation", email, templateId}`, `{kind:"template_change", membershipId, templateId}` or `{kind:"ownership_transfer", toMembershipId}`. The route calls P06.T01b `submitProposal` with T01z's producers (§8).
- **Parameters.** Invitation: `{kind, reservedMembershipId: randomUUID(), email: normalized, templateId, templateDigest}`. The others carry the target and template, or the from- and to-membership.
- **Target.** One, W, with the §2.1 fields, `maximumCredits "0"`, `maximumCost null`, `partialApproval: "all_or_nothing"`. `expectedSourceRevision` binds what the reviewer saw: `invitation:new`, `grants:<sha256 of the target's sorted live W grant ids>`, or `owner:<current designation revision, 0 if none>`.
- **Checks before submission**, each writing nothing: the allowlist (403 `recipient_not_allowed`); §2.4 and §2.7 (403 `amplification_denied`, `owner_template_required`); `membership_plan_facts`: 409 `invitation_exists` (an open invitation for that email digest in W), 409 `limit_reached` (100 open invitations in O), 404 (the target is not an active member of W).

`POST /members/proposals/:proposalId/apply` `{expectedProposalDigest}`:
1. P06.T01b `readProposal`, then `prepareApprovalClaim` (the claimant's current `execute` on the capability, and current reviewers).
2. The server rebuilds and validates the capability input: invite `{identity: email, grantProposal: GrantRef(template)}`; grants.revise `{proposalRef, approvalRef}`. The §2.4 and §2.7 checks run again.
3. `cmd_membership_apply`: `membership_lock` with the strict P06.T01a recheck (revision and digest from `enter_context`'s snapshot); W's stream; `approval_claim(…, 'p05.membership', cmd, reviewers_current)`, which settles first, so expiry, a stale policy, lost solo status and lost reviewer authority each return their code and apply nothing; `expectedSourceRevision` must still hold, else `source_revision_stale`; then the bridge effect:
   - **issue:** at most 50 per O per rolling 24 h (429 `Retry-After: 3600`); insert `delivery_pending` with the frozen `template_grants`, channel `synthetic`, and the change log;
   - **template change:** `grant_rows_revoke` on the target's live W grants, `grant_rows_insert` of the template (`issuedBy` = the applier's HumanActorRef), cancel the target's open W invitations (`issuer_changed`), change log with `template_id`, `policy_revision + 1`;
   - **transfer:** the incoming owner must be an active human member of W holding a governance-bearing template; designation `revision + 1` (`source 'transfer'`), change log, `policy_revision + 1`;
   - the event `membership.changed {kind, subjectMembershipId}`; the command row.
4. 201 `{schemaVersion:1, kind, invitationId|membershipId|ownerRevision}`; an invitation is then `delivery_pending` until sent. A replay returns the stored result.
**6.4 Send (PR-B)** (`POST /invitations/:invitationId/delivery {action:"send"}`, its own key; the channel, not Morrow, mints the token).
1. Context; replay: a same-key replay returns the invitation's current state and never calls the port.
2. The kernel allows `execute` on invite (§2.1 fields).
3. `markSubmitted()`; `cmd_invitation_send`: the invitation `FOR UPDATE` must be `delivery_pending`, unexpired and with `send_started_at` null, else 409 `delivery_uncertain` (a send already started without an outcome) or 409 `invitation_state`; set `send_started_at`; the command row; COMMIT.
4. `port.deliver` once, with a fixed 3 s budget and no transaction open.
5. A new transaction: `invitation_send_record`, idempotent: `delivered {tokenDigest}` → `pending`; `not_sent` → `delivery_failed`; `uncertain` → unchanged. If this step fails, the invitation stays `delivery_pending`, and its token can never be accepted (acceptance needs `pending` and the digest). The remedy is to cancel it (revoke the reserved id) and propose again; the reconcile and retry machinery belongs to the channel child (§9.3).
6. 200 `{schemaVersion:1, invitationId, state}`.
**6.5 Accept** (`POST /invitations/accept`, account route; T01x §9 guard; body `{schemaVersion:1, token}`, at most 1 KiB; lowercase-UUID `Idempotency-Key`):
1. Parse; `tokenDigest = sha256("morrow.invitation-token.v1:" + token)`; drop the token.
2. A READ ONLY transaction: `account_invitation_subject`. No row → 404 `invitation_unavailable`, with no port call. COMMIT.
3. `VerifiedEmailPort.read(subject)` → `{verified, emailDigest}`, with no transaction open; failure → 503 `unavailable`.
4. `markSubmitted()`; a READ WRITE transaction: `cmd_invitation_accept`:
   - advisory; replay by `(principal, command)`: the same digest → `replayed` while the membership is active, else `invitation_unavailable`; another digest → `idempotency_conflict`;
   - organization `FOR UPDATE`, then the invitation `FOR UPDATE`: `pending`, `now < expires_at`, the issuer membership active, the email digest equal and `verified` true;
   - the family chain lock, then a recheck of the principal;
   - an active W membership → 409 `already_member` (the invitation stays pending). Otherwise one of: insert the O membership with the reserved id and the W membership (`member_joined`); for an active O member, insert or reactivate the W membership (`workspace_joined`); for an inactive O membership, reactivate that row and insert or reactivate the W membership (`member_rejoined`);
   - `grant_rows_insert` of the frozen template: `issuedBy` the issuing human, `validFrom` now, `expiresAt` null, `policyRevision` the new revision; old revoked grants stay revoked;
   - the invitation becomes `accepted` (`accepted_membership_id` = the row used); the acceptance row; the change log with `template_id`; `policy_revision + 1`. No outbox event is written: there is no tenant context, and P07 projections read the change log through a later bridge.
5. 201 `{schemaVersion:1, outcome:"created"|"replayed", organizationId, workspaceId, signInRequired}`. `signInRequired` is true for `member_rejoined`: families from before the removal stay excluded by the P05.T01y watermark, so the person signs in again.

### 9 Delivery and verified email
**9.1 Email rule.** ASCII only, lowercased, no surrounding whitespace, at most 254 octets (local part at most 64), one `@`, dot-atom local part, LDH domain labels with a dot. Shared by TypeScript and SQL. A non-conforming provider email reads as `verified:false`.
**9.2 Synthetic ports (PR-B).** The delivery port mints 32 random bytes in base64url, keeps the token in a test-only sink and returns its digest; a fault mode returns `not_sent` or `uncertain`. The verified-email port returns fixture values per subject. The token never appears in an HTTP response, a log line, an event or a database column. The production mapper rejects both outside development (P04.T02a §D6), so hosted acceptance returns 503 until §9.3.
**9.3 Hosted channel (not in this packet).** A follow-up lettered child (proposed P05.T01ab; a routine split) owns it, gated on its own owner question, P04.T02a and P06.T01c. Options it must weigh: WorkOS invitation emails through keyed broker methods (amends ADR-0007 items 1 and 3; lookups must be by the stored provider invitation id, never by email, because all organizations share one WorkOS environment; and the verified-email check should be a broker-side comparison returning only `{verified, matches}`, never an unkeyed email digest); or a Morrow-minted 256-bit link returned once on a fresh send, never on replay (needs an ADR, because the load-bearing rule bars returning secrets). It also owns reconcile, retry, provider withdrawal, the hosted allowlist variable and `live/` evidence.

## Acceptance cases
Real PostgreSQL 17 and workerd. Every denial also asserts that nothing was written, except an `already_stopped` stop. **Fixtures** (owner SQL unless stated): O with workspaces W and W2, plus an inactive workspace W4. A is O's signup owner in W (template v1, plus owner-SQL grants equal to `workspace-admin-v1`'s work rows, standing in for template v2) and holds `workspace-admin-v1` in W2. B holds `workspace-admin-v1` in W and W2; L holds `workspace-member-v1` in W and W2 and a grant in W4; X is a member of W with no grants. O1 has one workspace W1: S is its signup owner (v1 plus the same stand-in work grants) and Z a `workspace-member-v1` member. O2 has W3, whose signup owner F holds only template v1. O′ with Y is foreign. Families come from P05.T01x account admission. The recipient allowlist holds the `*.example.test` addresses used here.

**PR-A**
- **P05.T01z-AC01 Migrations.** Both commit on top of the chain, with every earlier migration's bytes unchanged. Each `organization_signups` row whose owner membership is active has designation revision 1 with `recorded_by = session_user`. A signup after the migration gets revision 1 in its own transaction. `work_ownership_facts` has the P06.T01b shape whether it was created or replaced. A missing P06.T01a role, an identity-role membership or a missing 0013 object raises `MEMBERSHIP_PREREQUISITES_INVALID` and creates nothing.
- **P05.T01z-AC02 Ownership facts.** `work_ownership_facts` and `readOwnershipFacts` agree: owner A; the count of active human W members; `lastMembershipChangeAt` = the latest quiet-period change or 0004 `applied` result in O, else null; the result validates as `WorkspaceOwnershipFacts`. An owner-seeded organization without a designation gives a null owner pair: `checkKillSwitchTarget` accepts it and protects nobody, and `GET /members` reports `ownerless:true`.
- **P05.T01z-AC03 Workspace removal.** B removes L from W with reason "Left the team". L's W membership is inactive and L's W grants carry `revokedAt`; `policy_revision` is + 1. One KillSwitchRecord validates, with `JCS(parse(canonical)) === canonical`, `targets` `[member L@W]` and B's HumanActorRef. One `kill_switch.executed` event and one `workspace_removed` row exist; the response is 200 with `affectedRuns: []`, and no Approval exists. L's next W bootstrap → 401; L's W2 membership still resolves, and L's O membership stays active.
- **P05.T01z-AC04 Organization removal.** B, holding revoke grants in W and W2, removes L organization-wide from W. L's O membership, both workspace memberships and every grant in O (W4's included, with no target entry) are revoked. There is exactly one record, in W, whose `targets` name L@W and L@W2, one event and one command row; W2's stream is untouched. Every live family of L gets 401 in W and W2 while still resolving L's workspace in O′, and no family, generation or binding row is revoked. Each of these writes nothing: B lacking a revoke grant in W2 → 403 `organization_scope_denied`; a target with no membership row in W → 404; a fixture organization with 101 active workspaces → 409 `limit_reached`.
- **P05.T01z-AC05 Immediate in every session.** Two families of L, in two browsers, both get 401 on their next request. A P06.T01a command of L holding the organization `FOR SHARE` delays the removal until it commits; one started after the removal commits gets `ineligible`.
- **P05.T01z-AC06 Owner protection.** Revoking A at either scope → 403 `OWNER_MEMBERSHIP_PROTECTED`, from `checkKillSwitchTarget` and, when `cmd_member_revoke` is reached with forged facts, from SQL. Nothing is written.
- **P05.T01z-AC07 Idempotency and re-revocation.** The same key and body (keys reordered) → an identical 200 replay; the same key with another body → 409 `command_conflict`. A new key against already-removed L → 200 `already_stopped`, a new record, an `already_removed` row, and no change to `policy_revision` or `lastMembershipChangeAt`. A replay by an actor who has since been removed → 401.
- **P05.T01z-AC08 Targets.** An unknown id, a membership of O′ and any non-null `sourceProposalRef` (PR-A) give a 404 byte-identical apart from `correlationId`.
- **P05.T01z-AC09 Stale versus unrelated changes.** An unrelated membership change between context and command does not fail the stop. Revoking B's own revoke grant in W2 in between → 409 `stale_authority`, and so does a workspace of O becoming active during an organization-scope removal. Unit: `revokeMember` with an agent-kind authority → kernel `origin_denied`, and no SQL call.
- **P05.T01z-AC10 Unknown outcome.** A fault proxy drops the reply to `cmd_member_revoke` and to COMMIT, each → 503 `uncertain`. A same-key retry replays or applies once; no command ever has two records.
- **P05.T01z-AC11 Members read.** B sees `items` with `isOwner` on A, `templateId` (`owner-bootstrap-v1` for A, the fixture's id or null otherwise) and `email` null for owner-SQL members. X → 403. A foreign `ws` → 401. No response contains grants.
- **P05.T01z-AC12 Q11 contract.** A `ConnectionRef` is valid. A KillSwitchRecord targeting a connection validates. `id ≠ connectionId` → library-invalid. Kind `connection` in a v1 ResourceRef → invalid. `checkKillSwitchTarget` on a foreign connection → `TARGET_NOT_FOUND`. `contracts:generate --check`, the drift checks and `inspectDeclaredReplacements` pass.
- **P05.T01z-AC13 Canonical vectors.** For reasons containing `\u0001`, `\t`, U+2028, Arabic, emoji and quote characters, the SQL canonical text equals `JCS` of the parsed object, and `createdAt` has exactly three fractional digits.
- **P05.T01z-AC14 Privileges (PR-A).** Only `morrow_work_api` executes the api functions and only `morrow_work_command` the bridges; `morrow_api` and every P05 executor get permission denied. No runtime role can SELECT or write the new tables. UPDATE, DELETE and TRUNCATE raise on designations, the change log and kill-switch records. The 0004 primitive still works for its existing callers.

**PR-B**
- **P05.T01z-AC15 Invite proposal.** B proposes `{invitation, "new.person@example.test", workspace-member-v1}` → 201. The Proposal@2 validates: capability invite, risk `access_change`, one W target with fields `identity, grantProposal` and `invitation:new`, beneficiaries `[]`, the parameters digest bound. Each of these writes nothing: L proposing → 403; F (template v1 only) proposing either template in W3 → 403 `amplification_denied`; an off-allowlist address → 403 `recipient_not_allowed`, with the address absent from every table; `"New@Example.test "` → 400; a second open invitation to that address in W → 409 `invitation_exists` (the same address in W2 is allowed); a 101st open invitation in O → `limit_reached`.
- **P05.T01z-AC16 Review and apply.** B cannot approve their own proposal (`SELF_APPROVAL_DENIED`); A approves. Apply → 201: the invitation is `delivery_pending`, the approval claimed, one change-log row, and `policy_revision` unchanged. A second apply → 409 `APPROVAL_ALREADY_CLAIMED`; an edited `expectedProposalDigest` → 409 `DIGEST_MISMATCH`. The 51st issue in O within 24 h → 429 `Retry-After: 3600`, and its approval stays unclaimed.
- **P05.T01z-AC17 Quiet period and solo owner** (W1; database-clock fixture). S removes Z from W1. Within 24 h, S's invitation proposal → 409 `quorum_unreachable`, writing nothing; a re-revocation of Z (`already_stopped`) does not restart the period. After 24 h, S's phrase `approve 1 change for 0 credits` approves; apply 1 s before `effectiveAt` → 409 `APPROVAL_NOT_EFFECTIVE`, after it → 201. In a second run, a member joining (owner SQL) between decision and apply → `SOLO_OWNER_STATUS_LOST`, and nothing is issued.
- **P05.T01z-AC18 Send.** The synthetic port returns `delivered`, `not_sent` and `uncertain`, giving `pending` (digest stored), `delivery_failed` and `delivery_pending`. After `uncertain`, a new send key → 409 `delivery_uncertain` and no port call; a same-key replay returns the current state with no port call. Sending a `pending` or expired invitation → 409 `invitation_state`. A failure injected into `invitation_send_record` leaves `delivery_pending`, and that token is then refused at acceptance. Token markers never appear in any response, event, log line or column.
- **P05.T01z-AC19 Accept.** L2, a fresh enrolled principal whose synthetic verified email matches, accepts → 201. The membership id equals the reserved id and the W membership is active. The grants equal the frozen template exactly, by kernel decisions: every template (capability, verb) is `allowed`, while `administer`, any governance capability and an extra field are denied. `issuedBy` is the issuing human, `expiresAt` null; `policy_revision` is + 1; the change log carries `template_id`; bootstrap of W → 200, `GET /workspaces` lists W, and `GET /members` shows L2's template and email.
- **P05.T01z-AC20 Silent denials.** Each gives the byte-identical 404 and writes nothing: an unknown token, an expired one (the boundary at `expires_at`), a cancelled one, a `delivery_pending` one, one whose issuer has since been removed, a token already accepted (by another principal, or by the same principal under a new key), a verified email that does not match, and `verified:false`. - **P05.T01z-AC21 Email is never authority.** A principal whose verified email matches but who holds no token reaches no membership: no route accepts an email alone. Token claims carrying the invitee's `email` or `org_id` change nothing. Of two principals sharing an email, only the one presenting the token joins.

## Security review checklist
- [ ] The principal, organization and workspace come only from the session digest through `session_eligibility`, `current_tenant()` or `account_session_principal`. No body, header or claim supplies a tenant, actor or subject; the snapshot GUC is a freshness claim, never authority.
- [ ] Kill switch: no Approval, but a current eligible grant in every affected workspace (never unioned), a reason, one KillSwitchRecord and the event in the same transaction, written only in the request workspace. Owner protection holds in TypeScript and in SQL; a null owner protects nobody.
- [ ] Reviewed changes claim the approval exactly once, atomically with the effect, after settlement. `expectedSourceRevision` blocks applying to a changed target.
- [ ] No amplification; templates frozen at issue; invitees get exactly the template; the owner keeps a governance template; issuer removal or template change cancels the issuer's open invitations.
- [ ] Acceptance needs token possession **and** a matching provider-verified email. Neither alone, nor any token claim, grants anything. Every denial is byte-identical; the token is stored only as a domain-separated digest. The email condition is asserted by the Worker (`email_digest`, `email_verified`), so under the ADR-0010 §4.3 residual risk a compromised api Worker voids it, but not the token condition.
- [ ] Organization removal is immediate in every family (membership join plus the P05.T01y watermark) and never revokes families globally; rejoin cannot revive a pre-removal family. Workspace removal stays scoped (ADR-0004 item 4).
- [ ] Lock order §5; `FOR UPDATE` without upgrade; no transaction open across a port call; the race hooks pass.
- [ ] Unknown outcomes: the `markSubmitted()` latch; command-id reconciliation; a started send is never re-sent.
- [ ] Definer hygiene; bridges executable only by `morrow_work_command`; the two account definers check `session_user` and an empty tenant context and are the only new S5 exceptions; FORCE RLS, REVOKE and immutability (TRUNCATE included); the erasure hook is replaceable.
- [ ] ADR-0007: no new leased role, secret or broker method; R1 and R2 do not widen.
- [ ] Personal data: the allowlist runs before any email is stored; emails are absent from events, logs and errors; the retention rows of §3 hold.
- [ ] The AI review is labelled "AI review (separate context, same model family)".
