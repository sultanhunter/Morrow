## Goal
1. **Formatting.** `npm run format:check` is `prettier --check .`. One reviewed `.prettierignore` says what is out of scope, replacing the two 197-path lists in `package.json`. A new code file is formatted by default.
2. **Unit concurrency.** `npm test` runs the parallel-safe test files concurrently and isolates the timing-sensitive files in a named serial list, each with a reason. The two suites that failed under parallel files (2 of 2,252 tests; `d177cd7`, `docs/development/ci.md`) are identified by measurement, not guessed.
3. **Template harness.** One pinned PostgreSQL 17 container per run builds a template database once from `migrations/manifest.json`, honouring `executeAs`, pinned prerequisites and a fresh connection per migration. Each suite gets `CREATE DATABASE … TEMPLATE` with the template's database ACL replayed, connects as restricted login roles through `docker exec psql` (the per-feature pool idiom made generic) with a scripted fault plan for lost replies, and leaves cluster state unchanged.
4. **Heavy faults.** `.github/workflows/heavy-faults.yml` runs on `workflow_dispatch` and weekly (OQ-1). It holds `heavy:*` matrices (repeated unit stress, harness stress) and is never a required check. P06.T01a registers its soak and full race matrices there.

### 2 Unit-test concurrency (PR-A)
- **Runner** `scripts/run-tests.mjs` (no shell, no network, about 150 lines):
  - `node scripts/run-tests.mjs [--set=unit|postgresql] [--shard=i/n] [--concurrency=k] [--repeat=r] [--junit=<artifact dir>] [--list]`. PR-A ships `unit` only; PR-B adds `postgresql` (§3.6).
  - `unit` lists top-level `tests/*.test.mjs` (sorted) and reads `tests/serial-tests.json`; the parallel set is every file not listed.
  - **Sharding is computed by the runner**, not by `--test-shard`: file j (0-based, sorted) of each set goes to shard `(j mod n) + 1`. Each spawn passes an explicit, non-empty file list. **A set or shard with no files is never spawned**, because `node --test` without files falls back to default discovery (and would pull in `tests/postgresql/`, which needs Docker).
  - It spawns `process.execPath --import tsx --test --test-concurrency=<k> <parallel files>`, then the same with `--test-concurrency=1` for the serial files. It runs both and exits 1 if either failed.
  - Defaults: `k = min(4, os.availableParallelism())` (bounds 1..16; hosted private-repository runners have 2 vCPUs), `r=1` (1..10; heavy only; each repetition is a fresh child). `--junit` adds the built-in `junit` reporter under `MORROW_ARTIFACTS_DIR` via `artifactPath`. `--list` prints `{set, parallel, serial, concurrency, shard}` as JSON and runs nothing.
  - It rejects unknown flags, out-of-range values, and a serial entry that is missing, duplicated or outside `tests/*.test.mjs`, or whose reason is under 20 or over 300 characters.
- **`tests/serial-tests.json`**: `{"schemaVersion":1,"serial":[{"file":"tests/<name>.test.mjs","reason":"<the wall-clock dependency>"}]}`.
- **Scripts.** `"test": "node scripts/run-tests.mjs"`; `"test:shard": "node scripts/run-tests.mjs --shard=$TEST_SHARD"`. CI's `unit` job is unchanged (two shards).
- **Isolation rule.** A file is listed only when Phase 0 M1 shows it failing under parallel files and passing 5 of 5 times alone, and its reason names the timing dependency. Static review predicts `tests/workos-authentication-operator-native.test.mjs` (a 100 ms "close did not settle" race and 5 ms ordering sleeps) and `tests/controlled-neon-login-pool.test.mjs` (1,000 ms deadline windows and the late-ACK fence). Other wall-clock users stay parallel unless M1 shows a failure. If M1 reproduces nothing, the list starts empty and the weekly unit-stress leg (§4) finds a flaky file by name.
- **Hygiene.** Every test server today listens on port 0 and every written temporary root is under `mkdtemp` or a random UUID. `tests/run-tests.test.mjs` keeps it that way: every `.listen(` in `tests/**/*.mjs` must be exactly `.listen(0, "127.0.0.1"`. This also refuses `listener.listen()` on the fixed-port 4110 objects from `scripts/workos-{,authentication-}operator-listener.mjs`, which tests may construct and close but never start.

### 3 PostgreSQL template harness

**3.1 Manifest metadata (PR-A; no new migration).** Every row carries a **required** `executeAs`; rows that need administrator setup carry `prerequisites: [{file, sha256}]`. Rows 1–12 get `"executeAs":"morrow_identity_owner"`. Row 1 gets `infra/identity-role-prerequisites.sql`, row 10 `infra/identity-login-role-prerequisites.sql` and row 11 `infra/identity-logout-role-prerequisites.sql`, each with its SHA-256 (today's fixture order). SQL bytes and row `sha256` are unchanged.
```json
{ "sequence": 10, "file": "0010.login-flow-custody.sql", "sha256": "51c6…0475", "reviewRef": "…", "executeAs": "morrow_identity_owner",
  "prerequisites": [{ "file": "infra/identity-login-role-prerequisites.sql", "sha256": "17c25b45…c541b" }] }
```
- `inspectMigrations(manifest, files, prerequisites = {}, {prerequisiteDirectory = "infra"} = {})` stays pure; the caller passes prerequisite bytes by path. New codes: `INVALID_EXECUTE_AS` (missing, or not `^morrow_[a-z][a-z0-9_]{0,47}$`); `INVALID_PREREQUISITE` (path not `^<dir>/[a-z0-9-]+-prerequisites\.sql$`, or bytes missing); `PREREQUISITE_CHECKSUM`; `DUPLICATE_PREREQUISITE` (a file on more than one row).
- `verify:delivery` adds one deliberate negative per new code. `tests/migration-history.test.mjs` pins the three prerequisite `{file, sha256}` pairs beside the migration rows: a published prerequisite file is immutable like a migration, and a later role goes in a new file on its new row.
- **Hosted use.** The metadata is available to P04.T01i, which designs hosted application itself (on Neon the administrator is not a superuser, and in PostgreSQL 16+ a CREATEROLE creator gets ADMIN but not SET by default).

**3.2 Harness configuration (PR-B)** `infra/labs/postgres-harness.json`:
`{"schema_version":1,"templateDatabase":"morrow","loginRoles":["morrow_api","morrow_identity_lifecycle","morrow_identity_linking","morrow_identity_login","morrow_identity_login_maintenance","morrow_identity_logout","morrow_identity_preauth","morrow_identity_resolution","morrow_identity_sessions"],"objectOwnerRoles":[],"memberships":[]}`
- The template must be named `morrow`, because `identity-role-prerequisites.sql` grants `CREATE ON DATABASE morrow`.
- `loginRoles` are declared, not inferred. `objectOwnerRoles` are owners besides `executeAs` roles (P06.T01a adds `morrow_work_command`). `memberships` lists `{member, role, inherit:false, set:true}` (P06.T01a adds its two). Sets are disjoint: a login role is never an `executeAs` or owner role.

**3.3 Service and template build** (`startPostgresService`):
0. **Static plan, before any Docker call.** Read the manifest, harness configuration, every migration and every prerequisite once into memory; run `inspectMigrations` and the configuration checks. Failure → `PG_HARNESS_MANIFEST_INVALID` with the inspection codes. Only these verified in-memory bytes are applied later.
1. **Container.** Same pinned digest and hardening as `localPostgresLab`, through a shared argument builder exported from `local-postgres-lab.mjs`; the `lab` profile's argv is unchanged, which a test pins. The `service` profile differs only in pids 256, 1.5 GiB memory, 2 CPUs, a 512 MiB data tmpfs and these flags: `listen_addresses=`, `log_statement=none`, `log_min_error_statement=panic`, `log_error_verbosity=terse`, `max_connections=64`, `max_wal_size=96MB`, `min_wal_size=32MB`, `checkpoint_timeout=30s`. Labels `morrow.harness=<32 hex token>` and `morrow.packet=P03.T04e-harness`. It verifies `docker inspect` (NetworkMode `none`, read-only root, user `999:999`, CapDrop `ALL`, no mounts, no port bindings) and server version `17.11`.
2. **Template.** Admin connection to `morrow_lab`: `CREATE DATABASE morrow;`.
3. **Rows, in order.** For each row: each prerequisite runs as `postgres` on `morrow` in its own `psql -X -v ON_ERROR_STOP=1`; the `executeAs` role must exist and be NOLOGIN, NOSUPERUSER, NOINHERIT and NOBYPASSRLS; the migration runs in a **fresh** psql process on `morrow`, stdin `SELECT pg_backend_pid(), backend_start …;` + `SET ROLE <executeAs>;` + the verified bytes. Timeout 60 s per row.
4. **Template checks, connected to `morrow` before sealing** (the catalogs are per database):
   - **Ownership.** Allowed owners are the `executeAs` roles plus `objectOwnerRoles`, each NOLOGIN, NOSUPERUSER and NOBYPASSRLS. Every row of `pg_namespace`, `pg_class`, `pg_proc`, `pg_type`, `pg_operator`, `pg_collation`, `pg_conversion`, `pg_opclass`, `pg_opfamily`, `pg_ts_config`, `pg_ts_dict`, `pg_statistic_ext`, `pg_default_acl`, `pg_foreign_data_wrapper`, `pg_foreign_server`, `pg_largeobject_metadata` and `pg_extension` (except built-in `plpgsql`) has an allowed owner. Excluded: `pg_catalog`, `information_schema`, toast and temp schemas, and the `public` schema row itself; objects **inside** `public` are checked. `pg_event_trigger`, `pg_publication` and `pg_subscription` are empty. Invariant: nothing is owned by `postgres`, a superuser or any LOGIN role.
   - **Roles.** `pg_auth_members` equals `memberships` exactly. `pg_db_role_setting` has no row for `morrow`.
5. **Seal.** `ALTER DATABASE morrow WITH ALLOW_CONNECTIONS false IS_TEMPLATE true;`.
6. **Login roles.** `ALTER ROLE <r> LOGIN` for each (no password; trust over the in-container socket). Afterwards the set of LOGIN roles other than `postgres` equals `loginRoles`, each with `rolsuper`, `rolcreaterole`, `rolcreatedb`, `rolbypassrls`, `rolreplication` and `rolinherit` false. For every login role L and every `executeAs`, owner or superuser role R, `pg_has_role(L, R, 'SET')` and `'USAGE'` are false; only declared `memberships` give any SET path.
7. **Snapshot.** `pg_roles` attributes, `pg_auth_members`, `pg_db_role_setting`, the `morrow` row of `pg_database` (including `datacl`) and `pg_postmaster_start_time()`. `stop()` compares again and fails the run (`PG_HARNESS_CLUSTER_STATE_CHANGED`) before removing the container.
8. **Report.** `writeArtifact("pg-harness/service-<token8>.json", {image, version, rows:[{sequence, file, sha256, executeAs, prerequisites, backendPid, ms}], checks, buildMs})`. No SQL, output or error text.

**3.4 Suites.**
- `openSuite()` runs `CREATE DATABASE morrow_s_<16 hex> TEMPLATE morrow;` (generated, checked against `^morrow_s_[a-f0-9]{16}$`, never caller-supplied). It then replays the template's ACL: `REVOKE ALL … FROM PUBLIC`, then one `GRANT` per `aclexplode(coalesce(datacl, acldefault('d', datdba)))` row of `morrow` other than the owner's (grantee `PUBLIC` or a `%I`-quoted existing role), and asserts the suite's sorted `aclexplode` equals the template's and that it has no `pg_db_role_setting` rows. Any mismatch → `PG_HARNESS_SUITE_FAILED`, and the database is dropped.
- `close()` runs `DROP DATABASE … WITH (FORCE)` and confirms absence.
- Suites are isolated by database. Roles are shared and frozen by the snapshot.
- **Fixture helpers are async** (each a fresh `docker exec psql -X -v ON_ERROR_STOP=1 -c <sql>` against the suite; one simple query, so several statements form one implicit transaction): `owner(sql, executeAs?)` prefixes `SET ROLE` to an `executeAs` or owner role; `superuser(sql)` runs as `postgres`. Both refuse text that starts with `\`, or matches `\b(CREATE|ALTER|DROP)\s+(ROLE|USER|DATABASE)\b|\bALTER\s+SYSTEM\b`; `superuser` also refuses `pg_stat_activity`, `pg_locks`, `pg_terminate_backend` and `pg_cancel_backend`, which go through the scoped helpers. These guards prevent accidental cross-suite effects; they are not a security boundary (the snapshot is the control).
- **Suite-scoped helpers**, all filtered by `datname = suite.database`: `activity()` (pid, role, application name, state, wait event type, open transaction), `locks()` (pg_locks joined on pid; mode, granted, lock type, relation name) and `terminate(applicationName)`.

**3.5 Exec transport** `suite.connect(role, {statements, queryTimeoutMs, faultPlan})`: one persistent `docker exec --interactive -e PGAPPNAME=morrow_h_<32 hex> <id> psql -X -qAt -v ON_ERROR_STOP=0 -U <role> -d <suite>`. `ON_ERROR_STOP` is **off**, so an error leaves the session open as a driver would.
- **Start.** The first exchange reads `pg_backend_pid()`, `current_user`, `session_user` and `standard_conforming_strings` (must be `on`).
- **Allowed text.** Allowlisted statement texts (1..256 entries, each 1..8,192 characters with no `\`, `;` or NUL, none mentioning `standard_conforming_strings` or `backslash_quote`), plus `BEGIN`, `BEGIN READ ONLY`, `COMMIT` and `ROLLBACK`. Anything else is rejected before any write.
- **Protocol per statement** (fixed template; `<m>` is a per-connection 128-bit marker, `<n>` a counter):
```
PREPARE h_<n> (text, …) AS <wrapped statement>;
\if :ERROR
\echo <m> <n> :SQLSTATE
\else
EXECUTE h_<n>('<value with '' doubled>', NULL, …);
\echo <m> <n> :SQLSTATE
\endif
```
  Statement names are unique per connection. Outside a transaction block the harness follows with `DEALLOCATE h_<n>`. Inside one, names accumulate and the harness sends `DEALLOCATE ALL` right after the reply to the `COMMIT` or `ROLLBACK` that ends it. `LAST_ERROR_SQLSTATE` is never used.
- **Values.** `string | null`. NUL, lone surrogates and values over 64 KiB → `PG_HARNESS_VALUE_UNSUPPORTED`.
- **Rows.** `SELECT`/`WITH` results come back JSON-wrapped, one JSON object per line, as today. A data-modifying `WITH` is unsupported. A marker line is accepted only in its exact `<m> <n> <5-character SQLSTATE>` form.
- **Errors.** A failing statement rejects with `PG_HARNESS_QUERY_FAILED` carrying only `sqlstate`. The transaction stays aborted until `ROLLBACK`. A `COMMIT` after an error resolves with `command: "ROLLBACK"`, as a driver reports it. stderr is drained and discarded.
- **Fault plan** (`faultPlan?: (c: {index: number; text: string}) => "pass" | "drop_before_send" | "drop_reply"`). `drop_before_send` writes nothing. `drop_reply` waits for the marker, so the server outcome is settled, then withholds it. Both run the discard sequence and reject with `PG_HARNESS_CONNECTION_LOST`. This is the deterministic commit-reply loss that P06.T01a-AC16 and P05.T01x-AC22 need: drop the reply to `COMMIT` and the commit stands; drop an earlier reply and termination rolls the transaction back.
- **Discard sequence** (`discard()`, a timeout, an abort signal, a client exit, or a fault): (1) mark the connection dead and reject pending work; (2) SIGKILL the host client; (3) from a fresh admin session, `pg_terminate_backend(pid, 1000)` restricted to the recorded pid, `datname = <suite>` and `application_name = <app>`; (4) poll `pg_stat_activity` every 50 ms until that `(datname, application_name)` is absent, at most 5 s. Once absence is observed, the outcome can no longer change: a transaction not yet committed has rolled back. A timeout or abort after a write rejects with `PG_HARNESS_OUTCOME_UNKNOWN`; the harness never retries. Absence not observed → `PG_HARNESS_CLEANUP_UNVERIFIED`, and the suite is poisoned (every later call refuses, while `close()` still drops it).
- **Close.** `close()` ends stdin, waits for the client to exit and confirms that the backend is absent the same way.

**3.6 Sharing, budgets and location (PR-B).**
- **Runner.** `run-tests.mjs --set=postgresql` lists `tests/postgresql/*.test.mjs`, never spawns an empty set, adds `--test-global-setup=tests/postgresql/global-setup.mjs`, has no serial list, and passes `MORROW_PG_HARNESS_PROCESSES=<k>` to the global setup.
- **Global setup** starts one service and exports `MORROW_PG_HARNESS={"containerId","token","template":"morrow","sessionBudget","suiteBudget"}`. `globalTeardown` stops it; a throw there fails the run.
- **Budgets.** Service-wide: 48 test sessions (exec connections and helpers) and 24 open suites, split evenly across the `k` processes. Each process enforces its share with a FIFO semaphore; a wait over 10 s → `PG_HARNESS_BUDGET_EXHAUSTED`, with nothing spawned. Harness-internal admin work (create, drop, terminate, snapshot) runs one at a time per process outside the budget, so cleanup never waits on a test. Worst case 52 sessions sit under `max_connections=64` minus 3 reserved, and about 120 processes under pids 256.
- **Attach.** `attachPostgresService()` accepts the variable only if the container id is 64 hex, the container is running and its `morrow.harness` label equals the token. Otherwise → `PG_HARNESS_ATTACH_REFUSED`.
- **Direct runs.** With the variable unset (one file run directly), `openSuite` starts a private service with the full budget and stops it in `after()`. Tests that break a service on purpose (AC12, AC15) always use a private one.
- **Location.** Suites that need Docker live in `tests/postgresql/*.test.mjs`, never in the unit set, so `npm test` still needs no Docker.

**3.7 Module API** (`scripts/postgres-harness.mjs`, plain ESM with JSDoc types):
```ts
export interface AppliedMigration { sequence: number; file: string; sha256: string; executeAs: string; prerequisites: readonly { file: string; sha256: string }[]; backendPid: number; ms: number }
export function planTemplateBuild(o?: { manifest?: HarnessManifestPath }): Promise<Readonly<{ rows: readonly AppliedMigration[] }>>; // static; no Docker
```

**3.8 Denial and unknown-outcome semantics.** Every error carries a fixed `PG_HARNESS_*` code plus at most a sequence number, a SQLSTATE, inspection codes or a `localPostgresFailureDiagnostic` projection. None contains SQL, values, stdout, stderr or arguments.

| Situation | Outcome |
| --- | --- |
| Manifest, prerequisite or configuration invalid | `PG_HARNESS_MANIFEST_INVALID`; no Docker call is made. |
| Image absent | Pull before `run` (as today). A failed pull → `PG_HARNESS_IMAGE_UNAVAILABLE`; no container exists. |
| `docker run` times out or returns no valid id | Unknown container: remove by label `morrow.harness=<token>`, then fail (`PG_HARNESS_START_UNKNOWN`). Never start a second container first. |
| Prerequisite, `executeAs` or migration failure | `PG_HARNESS_MIGRATION_FAILED:<sequence>`; the container is removed; no partial template is ever used. |
| Ownership, membership, setting or login-role check fails | `PG_HARNESS_TEMPLATE_UNSAFE`; the container is removed. |
| `CREATE DATABASE` fails or times out, or ACL parity fails | `PG_HARNESS_SUITE_FAILED`; the name is dropped if present. The caller may retry and gets a fresh name; `stop()` drops any orphan `morrow_s_*`. |
| Budget wait over 10 s | `PG_HARNESS_BUDGET_EXHAUSTED`; nothing spawned. |
| `docker exec` spawn fails before any write | `PG_HARNESS_CONNECT_FAILED`; nothing was sent. |
| Spawn or client fails, times out or is aborted after a write | `PG_HARNESS_OUTCOME_UNKNOWN` after the discard sequence; never retried; the test observes state. |
| Teardown | Cluster state differs, the postmaster restarted, a psql process remains (`docker top`), a suite backend or database remains, or label removal leaves a container: the run fails with `PG_HARNESS_CLEANUP_UNVERIFIED` or `PG_HARNESS_CLUSTER_STATE_CHANGED`, after the primary failure. |
