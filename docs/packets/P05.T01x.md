### 2 Identity decision and plan amendments (ADR-0009)
**Decision:** enroll at the first verified sign-in, and make signup a second, separate command. Reasons: there is one bearer type and no onboarding ticket without a principal. Invitations (T01z) need a principal before the invitation can be accepted. A lost callback commit is reconciled at the next sign-in through `UNIQUE (provider, environment, subject)`. A new principal has no memberships, so it has no authority.
**Enrollment rules:** Inputs are signature-verified evidence only: subject, provider session and profile tuple. **No email is read, stored or matched.** A mapping and its profile binding are created together, never one without the other. An existing mapping needs an existing active binding to the signing profile. It is never extended to another WorkOS application or client. Revoked or inactive records are never reactivated.
**Plan-r1 amendments** (made in the Part B PR): **(a)** In the P05.T01x bullet (Package 05 remaining children), replace "…in one definer transaction" with: "one definer transaction at the first verified sign-in enrolls the subject (principal, mapping, profile binding); a second one, at signup, creates the organization, workspace, owner memberships and default owner grants; each is idempotent". **(b)** Replace "a mapped subject only signs in" with the eligibility rule in §3.1. **(c)** Keep `GET /workspaces` and add `POST /organizations`. **(d)** The acceptance becomes: "no plan-number protocol, configuration or connection identifier remains in the current catalog (constraint and function definitions) or in shipped code. Lock keys 69001/69002 and SQLSTATEs P6901/P8101/P8410 inside the applied 0006–0010 bodies are opaque constants. New functions use the neutral SQLSTATE class `MR`."; **(e)** Depends-on gains P01.T02a, for Part B's merge. The bullet is already about 1,770 characters, so the Part B PR also splits it into sub-bullets to stay within `plan:check`'s 2,000-character line limit. **P06.T01a.** Its §4.8 and OQ-1(c) already state issuance as template v2, as ADR-0010 accepted, so no further edit is needed there.

### 3 Authority decisions recorded in ADR-0009
**3.1 Eligibility (Q4b).** A principal may create one organization if it has an `account_enrollments` row (it self-enrolled) and no `organization_signups` row. Owner-seeded principals are never eligible. Invited principals (T01z) enroll at their first sign-in, so each may create one organization of their own.
**3.2 What "owner" means in data.** In this release, the owner of an organization is the principal of its `organization_signups` row, for as long as that principal's organization membership is active. Being owner confers no authority. The kernel reads only grants. Consumers: T01z adds transferable owner designations, seeded from `organization_signups`, plus the last-owner rule. ADR-0005 owner notifications (P11) read the same source. ADR-0011 (Q2) uses this owner as the *designated owner* for the solo-owner rule. A solo owner is this principal, while it is also the only active human member and no membership change has happened within the 24 h quiet period. P05.T01z supplies `WorkspaceOwnershipFacts` from this record.
**3.3 Executor class and provenance.** Signup is a **human-initiated** command: only a browser session family can call it, and agents have no families; the fixed definer executes exactly the person's request. It therefore satisfies ADR-0005 `human_only` and is not an exception to it. `issuedBy {kind:"service", principalId:"morrow.onboarding"}` is a provenance tag that names the fixed template. It is not a deciding actor. ReviewPolicy: signup is the base case, not an `access_change` proposal, because no prior authority exists in the new organization to review it. It is the only grant path that bypasses ReviewPolicy, and it is limited to one fixed template, once per principal. How other tasks treat these grants: P05.T02a revokes them like any other grant. The P05.T02a harness accepts a `service` issuer only for `morrow.onboarding`, and only when a matching `organization_signups` row exists. ADR-0011 reviewer eligibility counts them as ordinary current grants.
**3.4 Grant template v1 (Q2; ADR-0009 item 7).**
Every template grant has this scope:
`{organizationId:O, workspaceId:W, storeIds:[], accountIds:[], resources:[{O,W,storeId:null,connectionId:null,kind:"workspace",id:W}]}`
Verb rule:
- `read` → `view`.
- `governance.approval.decide` → `approve` only. This is the ADR-0011 Q5 reviewer verb, aligned 2026-10-17; the earlier draft used `execute`.
- `connection.connect` → `administer` (the kernel rule).
- Any other control capability → `execute`.
- Every control capability also gets `approve`.

A reviewer also needs `approve` on the proposal's capability, so the solo owner is an eligible reviewer. The extra `approve` is harmless on the unreviewed kill switches.
Field rule: `fields` is the union of the capability's v1 and v1.1 effective input property names, all of which are valid FieldPaths. The catalogue's spaced `field_scope` strings are not valid FieldPaths.

| Capability | Verbs | scope.fields |
| --- | --- | --- |
| governance.membership.invite | execute, approve | identity, grantProposal |
| governance.membership.revoke | execute, approve | membershipId, expectedRevision, control |
| governance.grants.revise | execute, approve | proposalRef, approvalRef |
| governance.connection.connect | administer, approve | providerId, installationProof, scope |
| governance.connection.disconnect | execute, approve | connectionId, expectedRevision, control |
| governance.approval.decide | approve | proposalRef, decision, expectedRevision |
| governance.approval.preview | view | proposalRef, selectedTargetIndexes |
| governance.usage.read | view | scope, period |

`governance.approval.preview` is the P01.T02a PR-B capability (ADR-0011 Q5). Reviewers need `view` on it to preview the exact proposal they decide.
Not in v1: Work grants (the P06.T01a §4.8 vocabulary, ADR-0010) and `governance.review_policy.revise` (v1.1) wait for v2. Store-scoped connect and disconnect grants are issued at link time (T03/P09).
Upgrades: `organization_signups.grant_template` records which template a principal received. Existing owners receive later templates only through P05.T02a's audited grant issuance, a human-initiated `governance.grants.revise` under ReviewPolicy. Signup is the only grant path that bypasses ReviewPolicy (ADR-0009 item 2), so any other path, such as an owner-maintenance call, needs its own ADR. v1 rows are never rewritten.
**3.5 Retention and erasure (`data-lifecycle.md`).** Every new table uses the trigger function `account_preserve_record()`. P09.T05 replaces that function in a later forward migration so that a dedicated privacy-maintenance role can erase rows. This follows the 0010 `login_flow_events` idiom.

| Table | Class and retention | Erasure hook |
| --- | --- | --- |
| `account_enrollments` | Identity association; principal lifetime | P09.T05 deletes it after principal erasure |
| `account_session_commands` | Content-free audit, 365 days; the tuple holds subject and provider-session ids | Pseudonymize the tuple after family expiry plus 30 days (production) or 7 days (staging); P09.T05 or T01y |
| `organization_signups` | Audit and replay record; organization lifetime | Pseudonymize the principal association on erasure |
| `self_service_revisions` | Platform configuration audit; at least 365 days, latest row kept | None; `approval_ref` must not be personal data |

**3.6 Claims and activation gates.** Ownership binds only to the WorkOS user id. Token `email`, `org_id`, `roles` and `permissions` claims never select or create anything. WorkOS may link sign-in methods by email upstream. Activating any environment therefore requires: WorkOS email verification before any linking; sign-up restricted to the owner's allowlisted accounts in development and staging; no real users until the P09.T05 deletion path covers principal, mapping and enrollment (ADR-0003 hard ordering (b)). Q5 (ADR-0009 item 10) keeps the hosted gate, and production enablement needs its own ADR.
**3.7 Dedicated executor `morrow_identity_onboarding` (kept).** `morrow_api` is the read-only reader used on every request: `withIdentityRead` opens `READ ONLY` and asserts the role. Keeping write EXECUTE off `morrow_api` lets P05.T02a's harness assert that it executes no mutating function. `morrow_identity_sessions` already mints families. Adding organization creation to it would concentrate both high-value writes on the lease used in every callback. The cost is neutral: the login wiring drops `morrow_identity_resolution`, so the broker role map stays at 7 roles and `secrets.required` stays at 8; when IMP-11's `SET LOCAL ROLE` arrives, only `onboarding_role_safe()` changes.
The api Worker never holds a role-password binding. It gets only a short-lived broker lease for each connect (P04.T02a D2, ADR-0007, invariant 11).

**Display names.** SQL `display_name_valid(text)`, TS `normalizeDisplayName` and P05.T01x-AC30 share one rule: 1–100 code points, and `IS NFC NORMALIZED`. The first and last code points are not in **W** = U+0009–000D, 0020, 0085, 00A0, 1680, 2000–200A, 2028, 2029, 202F, 205F, 3000. No code point is in **F** = U+0000–001F, 007F–009F, 061C, 200E, 200F, 2028, 2029, 202A–202E, 2066–2069, FEFF.
How each layer applies it: **TS** normalizes to NFC, strips leading and trailing **W** with that explicit regex (not `String.prototype.trim`), checks the string is well-formed, and counts code points. **SQL** never trims. A non-NFC rejection in SQL maps to 400, because workerd ICU and PG17 may disagree on NFC. **Storage:** names live only in `organizations` and `workspaces`, under the existing CHECK of 1..200. The bootstrap's 1..200 UTF-16 limit fits 100 astral code points.

**Retired entry points.** Revoke EXECUTE on `create_login_flow_intent` from login, `admit_browser_family` from sessions and `resolve_provider_subject_selection` from resolution. `reconcile_browser_admission` stays for legacy commands.
**`admit_account_family`.** The tuple is `[command, provider, environment, application, client, issuer, tokenRevision, tokenDigest, subject, providerSession, issuedMs, observedMs, expiresMs, keysetDigest, observationDigest, secretDigest, profileId, profileRecordRevision, familyId, generationId]`. The steps follow the §7 lock order.
1. Run `browser_sessions_role_safe()` and the 0008 shape checks, minus workspace, mapping, membership and policy. Require `sha256(json tuple) = p_request_digest`.
2. Take advisory lock `browser-command:<cmd>`. A prior `account_session_commands` row returns replayed, conflict or denied, as in 0008. The same id in `browser_session_commands` or `browser_session_audits` returns conflict.
3. Take advisory `browser-provider:[…]`, then `provider-subject:[provider,env,subject]`. Lock the provider binding `FOR UPDATE`; it may be absent.
4. Lock the profile `FOR UPDATE` (the 0008 idiom). It must match the exact evidence tuple and be active, and its `record_revision` must be equal; otherwise return `revision_conflict`.
5. Lock the mapping by `(provider, env, subject) FOR UPDATE`. **Mapping present:** the `(mapping, profile)` binding must exist and be active, the mapping must be active, and the principal (`FOR UPDATE`) must be active and human; otherwise return `identity_ineligible`. A binding is never inserted for an existing mapping. **Mapping absent:** `self_service_current(profile).enrollment` must be `'enabled'`, else `enrollment_disabled`. The profile must have fewer than 30 enrollments in the last 10 minutes and fewer than 500 in 24 hours, else `enrollment_limited`. The profile row lock serializes this count.
6. Recheck the evidence window with `clock_timestamp()` (`evidence_expired`). Then check provider-binding identity, revocation and any legacy digest collision exactly as 0008 does.
7. In one subtransaction: If the mapping was absent, insert the principal (human, active), mapping (active, rev 1), binding (active, rev 1) and `account_enrollments`. Insert the provider binding if absent, then the family and generation (15 minutes, generation 1), the audit and the command (`enrollment` = enrolled or existing). Run a late check that raises `MR001`. `MR001` becomes `evidence_expired`, and `unique_violation` becomes `identity_conflict`. Either one rolls back every insert, then only the denied audit and command are written.

It returns 0008's shape `(outcome, family_id, generation_id, provider_binding_id, expires_at_ms, audit_id)`, so the TS decoders are reused.
**`create_first_organization`.** Denials write nothing.
1. Run `onboarding_role_safe()` (like `login_role_safe`, with `session_user='morrow_identity_onboarding'`). Check shapes: the digest is hex64, the command is a lowercase UUID and the profile is a `rid`. Otherwise return `denied`.
2. Both names must pass `display_name_valid`, else `invalid`. Compute `request_digest = sha256(json ['morrow.onboarding.organization','1',command,profile,org,ws])`.
3. Preflight `account_session_principal(digest)`. Return `unauthenticated` if there is no row or its profile ≠ `p_profile`.
4. Take advisory lock `onboarding-principal:<id>`. Then call `lock_session_eligibility(digest, NULL, principal, NULL)`; its family branch locks the provider advisory, binding, profile, mapping, profile binding, principal, family and generation. Re-run step 3, which must return the same principal and profile; otherwise return `unauthenticated`.
5. Check for an existing `organization_signups` row. Same command and digest: return `replayed` with its ids while the founder's workspace membership is active, otherwise `already_onboarded`. Same command with a different digest: return `idempotency_conflict`. A different command: return `already_onboarded`. This step runs before steps 6–7, so a replay still succeeds after the switch is disabled or the window is exhausted.
6. Check eligibility. An `account_enrollments` row must exist, else `not_eligible`. `self_service_current(profile).organization_signup` must be `'enabled'`, else `signup_disabled`.
7. The profile must have fewer than 20 signups in 10 minutes and fewer than 200 in 24 hours, else `rate_limited`. The profile lock from step 4 serializes this count.
8. In one subtransaction, with ids from `gen_random_uuid()`: insert the organization (active, `policy_revision` 1), workspace, membership and workspace membership (all active); insert one `grants` row per template entry and the `organization_signups` row; check the family has not expired (`MR001` becomes `unauthenticated`). A `unique_violation`, including a UUID collision, rolls back the whole subtransaction and returns `already_onboarded`.

It returns `(outcome, organization_id, workspace_id)`. Grant payload:

```json
{"id":G,"principal":{"kind":"human","principalId":P,"organizationId":O,"workspaceId":W,"membershipId":M,"installationId":null,"mandateId":null},
 "capabilityId":C,"verbs":V,"scope":{…§3.4,"fields":F},"issuedBy":{"kind":"service","principalId":"morrow.onboarding","organizationId":O,
 "workspaceId":W,"membershipId":null,"installationId":null,"mandateId":null},"validFrom":"<UTC ms Z>","expiresAt":null,"revokedAt":null,"policyRevision":1}
```

**`account_overview`.** A single statement over one snapshot.
- The principal comes from `account_session_principal`.
- `workspaces` lists `{organizationId, organizationName, workspaceId, workspaceName}` for the principal's active workspace memberships. It is filtered by `EXISTS session_eligibility(digest, w.id)`, so authority has a single source.
- Ordering is `o.display_name COLLATE "C", o.id, w.display_name COLLATE "C", w.id`, with a limit of 101.
- `onboarding = 'available'` iff an enrollment row exists, no signup row exists, and signup is enabled for the family's profile.

**`reconcile_login_flow` wrapper.** Same signature and return type.
- **Workspace flow:** return `reconcile_workspace_login_flow(…)` unchanged.
- **Account flow** (`workspace_id IS NULL`): Call the renamed function for the admission and phase checks. If it returns `held`, return that. If a `browser_session_commands` row exists for the issuer command, return `held`. Otherwise read `account_session_commands`. Check the digest, tuple elements 0–7 and 16–17 against the configuration, and the audit row. If the command was admitted, also check the family, generation and binding against elements 8, 9, 18 and 19. Return `observed` with the issuer fields. Any mismatch returns `held`.

### 7 Lock order (all writers; documented, plus targeted interleavings)
(1) command or onboarding-principal advisory → (2) `browser-provider` advisory → (3) `provider-subject` advisory → (4) `provider_session_bindings` → (5) `identity_verification_profiles` → (6) `provider_subject_mappings` → (7) `provider_subject_profile_bindings` → (8) `principals` → (9) `browser_session_families` → (10) `browser_session_generations` → then only inserts of new rows. Absent steps are skipped; this is the 0008 order with (1) and (3) added. `self_service_revisions` and the window counts are read after (5) and never locked; their only writer, the insert trigger, takes (5) first. **Owner maintenance must use the same order:** profile, mapping and binding revisions and switch inserts lock (5)→(6)→(7)→(8). Organization-first writers (`revoke_workspace_access`, linking) lock an existing organization before (2); signup and admission lock no existing organization. Tests check the likely conflicts; they cannot prove that no deadlock exists.

### 9 HTTP routes
Both routes share the managed guard's single 5 s attempt and these rules: **Origin.** HTTPS with the exact origin; `Origin` must equal it. A query string, credentials or a different Host gets 403. **Fetch metadata (as on the logout route).** `Sec-Fetch-Site` must be `same-origin` or absent, `Sec-Fetch-Mode` `cors`, `same-origin` or absent, and `Sec-Fetch-Dest` `empty` or absent. **Required headers.** `X-Morrow-Request: 1` and exactly one canonical `__Host-morrow_session`. **Rejected headers.** `Authorization` or `Proxy-Authorization` gets 401, as in the existing guard. `Transfer-Encoding` or `X-Morrow-CSRF` gets 400. **Responses.** `standaloneJson` headers, no CORS, never `Set-Cookie`. Any other method gets 405 with `Allow`.
**`GET /workspaces`** takes no body, `Content-Type` or `Idempotency-Key`. It returns 200 `{"schemaVersion":1,"workspaces":[…≤100],"truncated":bool,"onboarding":"available"|"unavailable"}`.
**`POST /organizations`** needs `Content-Type: application/json` and a lowercase-UUID `Idempotency-Key`. The body is at most 2048 UTF-8 bytes of closed, duplicate-free JSON: `{"schemaVersion":1,"organizationName":s,"workspaceName":s}`. Any other key gets 400.

| Outcome (`create_first_organization`, or pre-SQL) | HTTP | Body |
| --- | --- | --- |
| `created` / `replayed` | 201 / 200 | `{"schemaVersion":1,"outcome":"created"\|"replayed","organizationId","workspaceId"}` |
| `invalid`, or the TS name check fails | 400 | `{"schemaVersion":1,"outcome":"invalid_name"}` |
| `unauthenticated`; GET with zero rows | 401 | `{"code":"authentication_required"}` |
| `not_eligible`, `signup_disabled` | 403 | `{"schemaVersion":1,"outcome":"signup_unavailable"}` |
| `already_onboarded`, `idempotency_conflict` | 409 | `{"schemaVersion":1,"outcome":"<same>"}` |
| `rate_limited` | 429 | `{"schemaVersion":1,"outcome":"rate_limited"}` + `Retry-After: 600` |
| `denied` (unsafe role or shape), or any failure before `markSubmitted()` | 503 | `{"code":"unavailable"}` |
| Any loss or undecodable reply after `markSubmitted()` and before a confirmed COMMIT | 503 | `{"schemaVersion":1,"outcome":"outcome_unknown"}` |

Selection is the URL `/w/{id}`, and `session_eligibility` validates every request. Foreign, revoked and unknown workspaces all get the same 401.

### 10 Idempotency, concurrency, unknown outcomes
**Signup.** Each principal can sign up at most once. The primary key enforces this behind the principal advisory lock. Resubmitting the same key and body *is* the reconciliation. If the first attempt committed, the server returns `replayed`; otherwise it creates. It never creates twice. Keys are scoped per principal, so they never collide or leak across principals. The P14 client keeps `{key, body}` until it gets a terminal response. The server never retries. IMP-14's OperationLedger can register this command later.
**Callback.** If the admission is unknown, the person sees the failed-callback page. A family may exist, but its secret was never delivered, so it expires harmlessly. The next sign-in finds the committed enrollment.
**List.** The list is read-only. Any failure gives 503 with no effect.

### 11 Abuse limits (Q3)
**Limits:** One organization per principal, which means one per WorkOS subject. Enrollment, per profile: 30 in 10 minutes and 500 in 24 hours. Signup, per profile: 20 in 10 minutes and 200 in 24 hours. Login start (0010): 10 per 10 s, and 100 open at once.
**Risk.** The per-profile windows are **global lock-out levers**: someone with many WorkOS accounts can exhaust them for everyone on that profile.
**Mitigations:** The WorkOS sign-up allowlist (§3.6). Turnstile and an edge per-IP limiter are required at launch, before sign-up opens beyond the allowlist (ADR-0009 item 8). They may arrive earlier, as a P04.T01i follow-up. Both are injected as an *optional* dependency, so existing callers do not break.
No IP address is stored.

### 12 Handoff to P14.T01a (onboarding UI slice)
**Scope.** The §1 SPA journey: Sign in, Choose workspace, Create organization and Workspace shell. States: loading, empty, denied, 429, outcome-unknown (retry reuses the stored key) and offline. The slice uses the generated v1.1 validators. It restores an intended route only if that route matches `workspace-routes.json`.
**Local exploration.** Use P04.T02a's `npm run dev:edge`, which serves the built SPA and the API from one loopback HTTPS origin. Vite on `http://127.0.0.1:5173` cannot pass the exact-Origin binding, which requires HTTPS.
**Timing.** P14 slices may start once this contract is reviewed (ADR-0003 §7). If this slice moves ahead of P04.T01i, the M1 smoke test becomes a UI journey.

### 13 Deliberate simplifications
**One authoritative SQL call per command.** There is no double-read selection snapshot. · **No HMAC CSRF token or prepare round trip.** Origin, Fetch Metadata, the custom header, JSON and SameSite=Lax are enough (T01q rationale). · **No status route.** · **No quota table.** The profile `FOR UPDATE` lock serializes the windows. · **The switch history is its own audit.** · **One shared transaction runner.** · **Signup denials are not persisted.** · **The SQL computes the digest.** · **Existing pools are reused, observers included** (IMP-11).
**Kept:** the dedicated executor with its `session_user` check, FORCE RLS, fixed statements, closed parsing and the attempt budget.

### 14 Implementation notes (Part B)

- **Contracts.** The three v1.1 definitions are additions, so `changes.json` (replacements only) is unchanged; the baseline hash was updated.

- **P05.T01x-AC31 Session states.** Each of these → 401 on both routes: no cookie; an expired or revoked family or provider binding; an inactive principal, or a revoked mapping or binding; a changed profile `record_revision`; a legacy `sessions` digest; a digest present in both `sessions` and generations; a family whose profile differs from the configured `profileId`.

**List and selection**
- **P05.T01x-AC32 List correctness.** A principal belongs to two organizations, with some inactive organizations, workspaces and memberships. The list equals the set where `session_eligibility` returns a row. It never includes a foreign workspace and is ordered by "C" collation. With 101 eligible workspaces → 100 entries with `truncated:true`. A revocation committed between two calls never yields a list and an `onboarding` value from different snapshots.
- **P05.T01x-AC33 Selection stays server-side.** Bootstrap of a foreign, revoked or nonexistent workspace returns the same 401 body. Selecting W2 in one tab writes nothing, and a concurrent W1 tab keeps working.
- **P05.T01x-AC34 Revocation.** After `revoke_workspace_access` on the founder's workspace membership: the workspace leaves the list; bootstrap denies; a replay of the signup → 409 `already_onboarded`.

**Privileges, records, pre-install, end to end**
- **P05.T01x-AC35 Privileges.** Of the new functions, `morrow_api` can execute only `account_overview`, and the onboarding role only `create_first_organization`. No executor can SELECT from or write to the new tables. `SET ROLE` to the onboarding role from another login → `denied`. The three retired entry points are no longer executable by their former roles.
- **P05.T01x-AC36 Immutability.** UPDATE, DELETE and TRUNCATE raise on `account_enrollments`, `account_session_commands` and `organization_signups`.
- **P05.T01x-AC37 Pre-install state (ADR-0006).** The new workspace has zero `workspace_store_links` and zero `linking_handoffs` rows. Its grants are exactly template v1. No template capability has effect `spend` or `billable_job`, so no grant can satisfy a `budget_reservation` obligation.
- **P05.T01x-AC38 Workers journey.** In Miniflare with a synthetic provider, run start → callback → empty list → POST → list → bootstrap → logout. There are zero real outbound requests. `/workspaces` and `/organizations` never set `Set-Cookie`. The unconfigured default export → 401 on both routes.

## Security review checklist
- [ ] The principal derives only from the `__Host-morrow_session` digest, inside SQL. Bodies are closed. No client id, email or subject is accepted.
- [ ] Enrollment keys only on a verified `(provider, environment, subject)`. An existing mapping is never bound to a new profile. Nothing is reactivated.
- [ ] Self-service fails closed: no revision means disabled. The switch is append-only, owner-only and audited (who, when, why, approval reference).
- [ ] `morrow_identity_onboarding` is NOLOGIN at migration, NOINHERIT and has no memberships. It can EXECUTE one function, whose definer checks `session_user`. The password arrives only through a broker lease (B1).
- [ ] Definer hygiene: fixed `search_path`, qualified names, no dynamic SQL, shape checks before casts, `clock_timestamp()` after waits, and neutral `MR` SQLSTATEs.
- [ ] New tables have FORCE RLS, an owner-only policy, REVOKE ALL, and immutability triggers that include TRUNCATE. The erasure hook is a replaceable trigger function.
- [ ] The §7 lock order is documented and followed by owner maintenance. The targeted interleavings pass.
- [ ] Each principal can create one organization. Replays disclose ids only to the same principal, and only while its membership is active. There is no cross-principal key namespace.
- [ ] `outcome_unknown` is returned only after `markSubmitted()`. The server never retries; the client's retry is the reconciliation.
- [ ] CSRF: exact Origin, Fetch Metadata (site, mode, dest), the custom header, JSON and SameSite=Lax. No CORS, and no side effects on GET.
- [ ] The list is filtered by `session_eligibility` within one snapshot. Foreign, revoked and unknown workspaces are indistinguishable. Nothing beyond the truncation flag is exposed.
- [ ] One name rule applies: NFC, **W**, **F** and 100 code points. Names render as text. Unicode is allowed only in parameters 3 and 4 of `create`.
- [ ] Bootstrap grants are governance-only and workspace-scoped, have no spend or billable effect, and carry a provenance tag. They are checked by kernel decisions (AC18).
- [ ] Logs and errors carry no cookie, digest, subject, IP or name. Error bodies are fixed.
- [ ] The bytes of 0001–0011 are unchanged. The `NOT VALID` constraint is never validated. The retired entry points are revoked.
- [ ] Tier 2 review is labelled "AI review (separate context, same model family)". `/security-review` is mandatory.
