## 1 Goal

Shopify's `customers/redact` names a customer by their id, email, phone and the orders it lists, never by a name or a Morrow id; `customers/data_request` asks for that customer's data to go to the merchant. Today Morrow answers both "none held" and keeps only a digest of the customer id under the app's own secret, which no class could ever compute, so no class could be matched. After this task:

- each request is kept as the order ids it lists (SD3) and **keyed digests** of the customer id, email and phone under every kept version of the **workspace's own digest key in the broker vault**;
- the **redaction matcher** compares those keys with what each registered class stores (`order_id`, `customer_id_digest`, `email_digest`, `phone_digest`), and a request completes **only when every handler reports zero** rows still matching;
- the **registration surface** is the one place a later class plugs in, by forward migration, with S8 failing any keyed or customer table that has not;
- a data request's matched rows go to the **Owner** as an export, kept 30 days, itself registered as the first customer class (erased by a later `customers/redact`, by `shop/redact` and on its clock);
- the run is **durable, idempotent and audited**: one transaction per delivery under the store's stop key, re-driven by the cron until it completes, with content-free evidence of each handler's count.

## 4 Design

### 4.1 Keyed digests and the workspace's keys

- **Inputs** (`customer-digest.ts`, no `node:` import): `morrow.customer-id.v1|<digits>`; `morrow.customer-email.v1|<local>@<domain>` (NFKC, trimmed, lower case, `+tag` dropped, trailing dot dropped; byte for byte H9a's `customerEmailDigestInput`, so the screen's keyed list and the matcher agree); `morrow.customer-phone.v1|+<E.164>` (separators removed, `00` read as `+`; a number without a country code has no digest, because the contact path dials only E.164 and its digest must be comparable). A digest is HMAC-SHA-256 under one key version.
- **Keys** (`morrow_vault.customer_digest_keys`): one row per version, versions 1 to 8, 32 random bytes sealed by the broker under its KEK; the additional data binds the kind `customer_digest_key`, the tenant and the version (no record or subject id), so a row moved to another workspace or version never opens. Born active at the next contiguous version; the only update erases the material (workspace erasure); no delete or truncate (`customer_digest_key_guard`). FORCE RLS, the vault template (`work_owner`, `vault_broker`), INSERT and SELECT for the command role only.
- **Custody.** Only the broker's login reaches the rows, through `customer_digest_keys_get(app, shop)` and `customer_digest_key_create(app, shop, kek, wrapped, sealed)`, for the workspace the app registered for that shop invites (`work_shopify_app_tenant`, the same lookup the webhook record uses). The first customers/* request of a workspace creates version 1 inside the broker's verifying transaction; a racing request keeps the first (`exists`), and both read it back. The key is opened, imported as a non-extractable HMAC key, its bytes zeroed. Nothing logs it.
- **Why not `morrow_vault.credentials`.** ADR-0042 item 5 names a `contact_digest_key` kind there. That table keeps one active version per credential and erases a version's material when the next is written; a digest key must keep every version active for the workspace's life (the same item). So the key has its own vault table with the same envelope, custody and guard style. CS4 and CS9 use this key (not a second one) for the phone digest, so the matcher finds contact rows. §9 asks the owner to confirm.

### 4.2 The request as stored

The broker (`minimiseShopifyWebhook`) keeps, on the 7-day inbox row and nowhere else:

- `customers/redact`: `{shopId, customerDigests, ordersToRedact}`; `customers/data_request`: `{shopId, customerDigests, dataRequestId, ordersRequested}`;
- `customerDigests`: one entry per kept key version, `{version, id, email, phone}`, each 64 hex characters or null; never the email, phone, name, address or id.

`shopify_webhook_body_valid` admits exactly these (and 0036's shapes for rows recorded before). A customers/* body without the workspace's keys is refused, so Shopify retries.

### 4.3 The matcher

`customer_match_of(topic, body)` builds `{orders, customerIds, emails, phones}` from the broker-recorded row only (every non-null digest of every version, distinct). `customer_match_valid` closes it (20,000 order ids, 8 digests of each kind). A class reads it through `customer_match_orders(match)` and `customer_match_digests(match, kind)` and compares with `= ANY` or `&&`. Every helper is pure and IMMUTABLE.

### 4.4 The registration surface (how a class registers)

A class registers in the pull request that first writes it, in one change:

1. `tests/tenant-conformance/registry.mjs`: its `content` (`customer` for customer data) and `customerKeys` (each key it stores);
2. `packages/work/src/redaction.ts`: a `customerContentHandlers` entry whose `matchers` cover every key (and, for a `customer` table, its `storeContentHandlers` entry for `shop/redact`);
3. a forward identity migration replacing `morrow_identity.customer_handler_tables()` with the class added (the closed list a request's evidence may name);
4. a forward work migration replacing `morrow_work.customer_content_redact` (append the class's handler: `{table, action, rows, remaining}`) and, for a class whose rows go to the customer, `customer_content_export` (append `{table, rows: [...]}`, the customer's own rows without digests), with RLS policies on the context `morrow.connector_customer` = `org|ws|store`; and `store_content_redact` for `shop/redact`;
5. its writer takes the store's stop key shared, so a write racing a redaction commits first (and is redacted) or writes after;
6. its `lab:shopify-privacy` rows (a matching row deleted or blanked, another customer's and another store's kept, the request's evidence).

S8 enforces 1 to 3 (`contentProblems`, `customerColumnProblems` against the live catalog, and `customer_handler_tables()` equal to the registry). The lab's phases L and X perform steps 3 and 4 with a simulated class, exactly as a class pull request would.

### 4.5 The deletion run

`connector_inbox_apply_v2` (dropped and created again with its grant and owner) takes the delivery from the broker-recorded row; the tenant, installation and store come only from it. For either customer topic: under the store's stop key held exclusively, in the customer redaction context for that store alone, it runs the surface; a request completes only when every handler reports `remaining = 0`, with evidence `{kind, handlers [{table, action, rows}], outstanding []}` (`customer_redacted`, `customer_exported`, or `none_held` when no installation holds the shop). Otherwise it returns `pending`: the delivery stays received, its request open, its inbox row (order ids and digests) kept past 7 days, and the connector's cron re-drives it every five minutes; the deadline check logs it past its target. The identity layer enforces the same rule on its own: `work_privacy_request_complete` (revised) completes a `customers/redact` request of an installation only with evidence naming exactly the registered handlers (`customer_handler_tables()`), so 0037's applier, which the connector's login can still call and which answers "none held", is refused for it (K6). It is idempotent (a re-run recomputes from the state now held; a redelivery of a data request is ignored as a duplicate; one export per delivery, `UNIQUE (inbox_id)`), durable (one transaction; a failure rolls back and is re-driven) and audited (the request's content-free evidence for 365 days, the inbox row's effects for 7). Every other topic is 0054's, unchanged.

### 4.6 The export to the Owner

`morrow_work.customer_data_exports` (content `customer`): the rows each class exported, the Owner it is for (the organization's founding principal, from the installation's health target), the request's keys (so a later redact of the same customer finds it), 30 days from delivery (CHECK). Erased in place, never deleted: the document and keys emptied, the document's digest, ids, counts and times kept (`customer_export_guard`). The Owner reads it through `customer_data_exports_open()` (session only; recipient equals the session principal; unerased and unexpired; at most 20). FORCE RLS: the read-only session template, and connector policies that admit only the customer context (write, erase on redact), the redaction context (erase on `shop/redact` and the 48-hour deletion) and the clean-up job's per-export expiry context.

### 4.7 Clocks

The clean-up job (`connector_privacy_purge`, behind the connection clean-up switch, committed off) deletes settled inbox rows past 7 days whose request is not open (the inbox's own guard re-checks each), and erases exports past 30 days, each under a setting naming its tenant and id alone (listed under the job's own sweep setting). Both report counts only (`purged`, `held`, `erased`; the cron logs `INBOX_EXPIRED_HELD`).

## 5 H9d's interface

H9d registers the harness classes that may hold a customer's name typed as free text (messages, run turns, contexts, checkpoints, summaries, memory), `content: customer`, on this surface (§4.4). Shopify's request carries no name, so H9d adds its own key: a new `CustomerKey` and `CustomerMatcher` in `redaction.ts` and S8's column rule, a new field of the match document (`customer_match_valid` and `customer_match_of` replaced by forward migration; the broker's minimiser adds the field computed in its verifying transaction, for example from a lookup while the customer is still readable, as H9d's brief decides), and its classes' handlers in `customer_content_redact`. Workspace-scoped classes match within the request's workspace and need not carry a store. Nothing here constrains that decision.

## 6 Security invariants touched

None is weakened.

- **Tenant isolation (FORCE RLS, server-derived tenancy).** New tables are FORCE RLS with composite tenant keys; every context names one tenant and store (or one export), written only by the definer from the broker-recorded row and cleared after; the connector login holds no table privilege, so a setting it forges reaches nothing (K4, K5, P10). S1 to S8 pass with every new object registered.
- **Credentials readable only by the broker.** The digest keys open only in the broker, under its KEK, bound to the tenant and version; no other login executes the definers or reads the table (K5, `customer-digest.test.mjs`).
- **Customer data only after its deletion path.** Nothing writes customer data at this head; the export, the only customer class, has every deletion path before any row can be written (X3 to X6, S10). The request's digests are pseudonymous and live only on the 7-day inbox row.
- **Unknown outcomes; never promote.** A request is never completed while a handler reports a remaining row (L4); a lost apply is re-driven, never assumed.
- **Default deny.** The clean-up switch stays off; with it off nothing is purged or expired, and the redaction still runs.
- **Immutable migrations.** Forward only; replaced texts pinned by md5.

## 9 Open questions

1. **The digest key's table.** ADR-0042 item 5 names a `contact_digest_key` kind in `morrow_vault.credentials`; this task keeps the per-workspace key in its own vault table (`morrow_vault.customer_digest_keys`), because that table's one-active-version rule cannot keep every version active, which the same item requires. Recommended: confirm this as the ADR's per-workspace digest key (one key for customer id, email and phone digests, which CS4 and CS9 then use), by a dated note on ADR-0042 item 5 in SD2's notes.
2. **Re-ingestion after a redact.** A projection or event that arrives after `customers/redact` for a listed order is new data; whether each order class keeps a tombstone of redacted orders is that class's decision (V1-PR22, CS8, SD9b), recorded with its handler.
3. **The Owner's screen.** The export's api route and Inbox item land with the first class that exports rows; until then no export can hold a row.
4. **`lab:retention`.** ADR-0031 names a retention lab; the two clocks this task adds are proven in `lab:shopify-privacy`. Recommended: create `lab:retention` with the first 90-day customer class, and move these rows there.
5. **The screen's keyed email list (H9a, pull request 93).** Its digest input is this task's email input, byte for byte, so the two agree. Binding its `CustomerEmailDigestList` port is a follow-up once H9a merges: the broker digests each input under every kept version of the workspace's key and asks one definer whether any registered class holds that email digest. Until a class holds one the answer is always "not listed", which is what H9a's empty list says today.
6. **The M2 applier and data requests.** 0037's `connector_inbox_apply`, which the connector's login can still execute, answers every customers/* request "none held". The identity layer now refuses that for a `customers/redact` of an installation (K6), but it cannot tell a true "none held" data request from a skipped export, because a data request's evidence names only the classes that exported rows. The connector Worker calls only `_v2`. Recommended: before the first class that exports rows is switched on, a forward migration revokes the M2 applier from the connector's login (`_v2` calls it as its owner) and moves the labs that call it directly (`lab:listings-runs`, `lab:listings-authority`, K1 and K6 here) to `_v2`.
