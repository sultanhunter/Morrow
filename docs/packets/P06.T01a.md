## 1 Goal (observable product delta)
This packet adds work routes under `/workspace/:ws/work/*` on the api Worker (workerd + PostgreSQL 17). A signed-in member whose current grants allow it can: create goals and move them between draft, active, paused and cancelled; create tasks under a goal, mark them ready, and assign them to another eligible member; ask an eligible member a question that only that member can answer, and cancel it; read goals, tasks, questions and answers as validator-checked v1 objects, with grants covering every returned field; list "questions waiting for me".
- **Command guarantees.** Every command is idempotent per actor and key. It rechecks authority under lock and commits its outbox event in the same transaction, which delivers the persistence half of P06.A02.

- **Hardening budget.** This PR is a product delta, so it satisfies the ADR-0003 hardening-budget rule.

## 4 Design
### 4.1 Database access pattern (OQ-2, ADR-0010 item 2; P05 untouched)
| Concern | P05 per-role pools | **P06+ (this packet)** |
| --- | --- | --- |
| Connections | Primary plus a same-role observer, per role | **One** Neon WebSocket `Client` per request, never reused |
| Credentials | One broker lease per role | One lease for login `morrow_api_worker`. Only the broker holds the password (B1). |
| Privilege | One role per connection | The fixed prologue runs `SET LOCAL ROLE morrow_work_api`. The login is NOINHERIT with no privileges, and holds its membership `INHERIT FALSE, SET TRUE`. |
| Write isolation | A check in each function | Functions owned by `morrow_work_command` under tenant `USING`/`WITH CHECK` |
| Unknown commit | An observer proves the backend is gone | Command-ID reconciliation: the `commands` row commits atomically with the effect |
| Role verification | A `pg_roles` query per transaction | `enter_context` checks `session_user`; S5 checks the rest at CI and deploy |
| Hyperdrive / pooler | Incompatible | **Not qualified.** P6 covers only a raw reused backend; Hyperdrive needs its own qualification. |

**Prologue** (one fixed, parameter-free simple-protocol string; request deadline 5 s; the lab asserts PG17 `transaction_timeout` fires): `BEGIN ISOLATION LEVEL READ COMMITTED {READ ONLY|READ WRITE}; SET LOCAL ROLE morrow_work_api; SET LOCAL statement_timeout='2s'; SET LOCAL lock_timeout='1s'; SET LOCAL idle_in_transaction_session_timeout='5s'; SET LOCAL transaction_timeout='5s'`
### 4.2 Roles and grants (`infra/work-role-prerequisites.sql`; administrator; idempotent)
```sql
CREATE ROLE morrow_work_owner   NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION; -- owns schema/tables; migrations
CREATE ROLE morrow_work_command NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION; -- owns API functions; tenant RLS applies
CREATE ROLE morrow_work_api     NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION; -- SET target of the api login only
CREATE ROLE morrow_api_worker   LOGIN   NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION; -- no PASSWORD clause, ever
GRANT morrow_work_api     TO morrow_api_worker WITH INHERIT FALSE, SET TRUE;
GRANT morrow_work_command TO morrow_work_owner WITH INHERIT FALSE, SET TRUE;  -- only so migrations can ALTER … OWNER TO morrow_work_command
GRANT CREATE ON DATABASE morrow TO morrow_work_owner;
```
- **Password.** P04 provisioning sets it out of band. It lives only in the broker secret `MORROW_DB_PASSWORD_MORROW_API_WORKER` and is leased per request (ADR-0007).
- **Separation.** No work role and identity role are members of each other, in either direction.
- **Not created here.** No relay, maintenance or operations role, and no orchestrator login.
- **Manifest.** Entries gain an optional `executeAs` (default `morrow_identity_owner`) and `reviewRef: docs/packets/P06.T01a.md`. Checksum and BEGIN/COMMIT rules are unchanged.
- **Runner.** Each migration runs on a fresh connection, because a `SET ROLE` before `BEGIN` is session-level.
### 4.3 Tenant context and what each layer enforces
**GUC values never establish authority.** PG17 lets any role set them. They carry only the bearer-equivalent digest, passed as a bind parameter, and every policy and function re-resolves it through `session_eligibility()`, so a forged GUC yields zero rows. The binding GUC is dropped: `set_config(…, true)` is already transaction-local, and P6 proves it.
```sql
-- Owned by morrow_work_command; SECURITY DEFINER; SET search_path = pg_catalog, morrow_work, pg_temp; REVOKE ALL FROM PUBLIC.
CREATE FUNCTION morrow_work.enter_context(p_digest text, p_workspace text)          -- EXECUTE: morrow_work_api
RETURNS TABLE(principal_id text, organization_id text, workspace_id text, membership_id text, policy_revision text,
              grants jsonb, grant_count int, grants_digest text, database_now_us text)
-- 1 Deny unless session_user = 'morrow_api_worker' with NOSUPERUSER/NOBYPASSRLS/NOCREATEROLE/NOINHERIT (one pg_roles read). 2 Deny if already set this transaction.
-- 3 a := morrow_identity.work_actor_authority(p_digest, p_workspace), unlocked; no row ⇒ empty result (401).
-- 4 set_config(…, true): digest, workspace and the snapshot (policy revision, grants digest, evaluated_at). 5 Return a; TS denies grant_count > 1000.
CREATE FUNCTION morrow_work.current_tenant() RETURNS TABLE(organization_id text, workspace_id text, principal_id text, membership_id text, policy_revision bigint)
  STABLE; -- EXECUTE: morrow_work_api (its policies). = morrow_identity.work_session_context(current_setting('morrow.work_session_digest',true), current_setting('morrow.work_workspace',true))
-- Also api-executable definers (tenant/actor only from current_tenant()): begin_command(type, command_id, digest); cmd_goal_create, cmd_goal_transition,
--   cmd_task_create, cmd_task_ready, cmd_task_assign, cmd_question_request, cmd_question_answer, cmd_question_cancel; target_member(target_principal_id).
CREATE POLICY tenant_read ON morrow_work.<t> FOR SELECT TO morrow_work_api                    -- tenant-readable class; one InitPlan, row comparison
  USING ((organization_id, workspace_id) = (SELECT c.organization_id, c.workspace_id FROM morrow_work.current_tenant() c));
CREATE POLICY tenant_command ON morrow_work.<t> TO morrow_work_command USING (<same>) WITH CHECK (<same>);   -- every tenant table
CREATE POLICY work_owner ON morrow_work.<t> TO morrow_work_owner USING (true) WITH CHECK (true);             -- maintenance only; no runtime path
```
- **SQL enforces** tenant isolation for reads and (via `WITH CHECK`) for writes, along with eligibility, freshness, edges, revisions, ownership basis, target membership and caps.
- **The `packages/policy` kernel decides grants**, in the Worker. There is no SQL grant interpreter (the 0004 rule).
- **Residual risk.** A compromised api Worker holding a live victim session could exceed that victim's grants within the victim's workspace. It cannot cross tenants or outlive a revocation. This is the same boundary as P05.
### 4.4 Identity bridge (`NNNN.work-identity-bridge.sql`, `executeAs morrow_identity_owner`)
**Grants.**
- `USAGE` on `morrow_identity` to `morrow_work_owner` and `morrow_work_command`.
- Column `REFERENCES` to `morrow_work_owner` on `workspaces(organization_id,id)`, `memberships(organization_id,id,principal_id)` and `workspace_memberships(workspace_id,membership_id)`. FK checks run as the referenced table's owner.

**Functions.** Four SECURITY DEFINER functions. Each has a fixed `search_path`, `REVOKE ALL FROM PUBLIC`, and EXECUTE for `morrow_work_command` **only**.
- **`work_session_context(digest, ws)`** is `LANGUAGE sql BEGIN ATOMIC SELECT * FROM session_eligibility(…) WHERE <pattern guards> END`. Because PostgreSQL records the dependency, P05.T01y cannot drop or re-type `session_eligibility` without replacing this bridge in the same migration (AC24).
- **`work_actor_authority(digest, ws)`** returns: the identity row; `grants`, ordered by id, `LIMIT 1001`; `grant_count`; `grants_digest = sha256(grants::text)`; `database_now = clock_timestamp()`.
- **`work_lock_and_recheck(digest, ws, principal, membership, revision, grants_digest, evaluated_at)`** takes the organization interlock shared (a heavyweight advisory lock on the organization) and then the organization row `FOR SHARE`, then re-resolves. The bridge migration also gives the three identity functions that lock an organization `FOR UPDATE` (revocation, store linking and browser admission; their 0008 definitions) the interlock exclusively, before that row lock. PostgreSQL queues a new shared request behind a waiting exclusive one, so overlapping commands cannot starve a revocation; a row `FOR SHARE` alone would let each new command in past the waiting `FOR UPDATE` (review finding, 2026-10-18). It returns: `ineligible` if the session, membership or actor has changed; `stale` if the revision or digest changed, or if some grant's `expiresAt` falls in `(evaluated_at, clock_timestamp()]`; `current` otherwise.
- **`work_member_authority(org, ws, principal)`** returns `membership_id`, `grants` (`LIMIT 1001`) and `grant_count` for an active human with active organization and workspace memberships. Otherwise it returns no row. It is used for eligibility (§4.8).

### 4.6 State machines, guards and caps
- **Goal.** `draft→active` (scope and criteria CHECKs). `active⇄paused`; leaving `paused` requires current grants. `draft→cancelled`. `{active,paused}→cancelled` requires every child task to be terminal. v1 tasks cannot reach a terminal state from draft or ready, so goals with tasks cannot be cancelled until a later P06 migration persists the ADR-0010 cancel edges (OQ-5). `active→achieved` always fails with `guard_failed` until P07/P11.
- **Task.** Create requires a goal in draft, active or paused; `allowedResources ⊆ goal.scope.resources = [W]`; and fewer than 200 tasks on the goal (a published cap, below v1's 1000 `taskIds`). `draft→ready` requires a goal that is not cancelled or achieved. No other edge is reachable.
- **Question.** `open→answered`: only the designated respondent, at the expected revision, with a valid `morrow.answer.text` body (1–8192 chars, no NUL). `open→cancelled`: the requester or an administrator. `expired` is unreachable until P06.T03.
- **Caps** (published; race-free under the stream lock; `limit_reached`): 10,000 goals per workspace, 200 tasks per goal, 50 open questions per task.
- **System actors.** API callers can never act as `work_service`, `runtime`, `action_service`, `connector` or `budget_service`. SQL is the only enforcement point.
### 4.7 Command protocol: replay first, then authority, then a locked write
Each command uses one connection and one READ WRITE transaction.
1. **Guard**, with no I/O (§4.9). Parse the body strictly. Compute `requestDigest = sha256(canonicalJson(["morrow.work.command",1,type,ws,pathIds,body]))`. Canonical JSON sorts keys, so a reordered body replays. Mint a `correlationId`.
2. **Context.** Run the prologue, then `enter_context`. No row → 401. More than 1000 grants → 403.
3. **Replay check.** `begin_command(type, commandId, requestDigest)` takes `pg_advisory_xact_lock(hashtextextended(json[org,ws,principal,commandId],0))`, then reads `commands`. One of three outcomes follows:
   - *replay*: requires only the step-2 session plus view on the aggregate's read capability (field `status`). It returns 200 `replayed:true`, or 404 without view. Ownership is never consulted, which fixes AC12.
   - *conflict*: same actor and key, different digest → 409.
   - *new*: continue to step 4.
4. **Target.** Read the target under RLS, then check view with the route's full field list. Absent or not viewable → 404.
5. **Verb.** Ownership *selects* the verb (`own` → execute, `other` → administer), but a grant is always required. `createHumanPolicyService` decides, with clock = `database_now`. Denied → 403.
6. **Eligibility** (assign, question.request). `target_member(targetPrincipalId)` takes its tenant from `current_tenant()` and returns the target's grants and their digest; the kernel checks the grants (OQ-4) and the digest goes to the command function. Not a member → 404, identical to an unknown id. Member without the grant → 409 `target_ineligible`.
7. **Input.** Build the v1 capability input on the server (§4.9) and run `validateCapabilityInput`. Failure → 400.
8. **Execute.** Call `markSubmitted()`, then `SELECT * FROM morrow_work.cmd_<type>(…)`. Parameters are closed text, with no organization, workspace or actor. The prelude: (a) validates scalars → `invalid`; (b) takes tenant and actor from `current_tenant()` → `ineligible`; (c) re-checks `commands`; (d) runs `work_lock_and_recheck` against the GUC snapshot → `ineligible` or `stale_authority`; (e) runs `INSERT workspace_streams … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE`. This **serializes all commands in the workspace**; (f) locks goal → task → question `FOR UPDATE`; (g) checks revision (`revision_conflict`), edge and guard (`state_conflict`, `guard_failed`), caps (`limit_reached`), the `own` basis against the locked owner (`stale_authority`), and target membership (`not_found`) and the target's grants digest and expiry window, as for the actor (`stale_authority`); (h) writes at revision+1, then `append_event` and `record_command` → `applied`.
9. **Commit.** `applied` → COMMIT → 201. Anything else → ROLLBACK and the mapped error. **Denials and conflicts persist nothing.**

**Lock order** (deadlock-free): advisory → organization interlock (shared) → organization `FOR SHARE` → stream `FOR UPDATE` → goal → task → question.
- Revocation (0004), store linking and browser admission take the organization interlock exclusively, then the organization `FOR UPDATE`, and never touch work rows. The stream lock stays after the interlock: the first command of a workspace inserts its stream row, whose foreign-key check holds the workspace row `FOR KEY SHARE`, which the revocation locks `FOR UPDATE`.
- Logout takes no organization lock, so a race with it is benign.
- The shared interlock is held only from the command function until COMMIT, never across TS round trips. A waiting revocation waits only for the commands already holding it, each bounded by `lock_timeout` and `transaction_timeout`.

**Unknown outcomes.** A failure after step 8 is sent and before the COMMIT reply arrives → 503 `uncertain`. That covers a deadline, a lease `revocationSignal`, or socket loss. A same-key retry is the reconciliation (no observer): the original committed → the retry replays it; the original rolled back → the retry applies once; the original is still in flight → the retry waits on the advisory lock until `lock_timeout`, then returns 503 `unavailable`.

**Reads.** READ ONLY prologue, `enter_context`, view checks, fixed SELECTs under RLS, COMMIT. No locks are taken.
### 4.8 Permissions: one vocabulary module (OQ-1, ADR-0010 item 1)
`packages/contracts/src/work-permissions.ts` is the single table, exported as `@morrow/contracts/work-permissions`. It is imported by `@morrow/work`, by P05.T01x template v2, and by P05.T02a issuance.

### 4.9 HTTP API (OQ-3, ADR-0010 item 3; Workers only)
**Routing.** `worker.ts` sends `^/workspace/<Id>/work(/|$)` to `createWorkApiHandler` and everything else to the unchanged P05 handler. The work routes therefore share P05's namespace, which `run_worker_first` already covers. The Node dev listener, with its 8 KiB cap, does not serve them. **Mapping to v1 objects.**
- **Goal.** `storeId` is null, and `owner` comes from the A() columns. `taskIds` is derived, so a new task does not bump the goal revision; clients refetch the goal on `task.created`.
- **Task.** `parentTaskId` and `activeRunId` are null, the reference lists are `[]`, and `leaseGeneration` is 0.
- **Question.** `eligibleRespondentIds = [respondent]`, `blocksTask:false`, `expiresAt:null`, and `answerSchemaRef = {O,W,null,"schema","morrow.answer.text",1,<constant digest>}`.
- **Validation.** Every object passes `validateDefinition("core", …)` before it is sent; otherwise the response is 503. Responses are `{schemaVersion:1, …, replayed?}`, and a replay returns 200.

**Guard (`http-guard.ts`).** It reuses the P05 cookie digest through the additive `@morrow/identity/request-primitives`.
- **Origin.** HTTPS exact origin. `Host` and `Origin` must match exactly, and POST requires `Origin`.
- **Fetch metadata.** `Sec-Fetch-Site` must be same-origin or absent; `-Mode` cors, same-origin or absent; `-Dest` empty or absent.
- **POST headers.** `Content-Type: application/json`, `X-Morrow-Request: 1`, and a lowercase-UUID `Idempotency-Key`. A GET that carries a body, `Content-Type` or key is rejected.
- **Other headers.** `Authorization` or `Proxy-Authorization` → 401. `Transfer-Encoding` → 400. Exactly one `__Host-morrow_session` cookie is accepted.
- **Body.** At most 64 KiB, decoded as fatal UTF-8. It then goes through the strict `parseWorkosSessionStatusJson`, which rejects duplicate keys and lone surrogates; a `\u0000` → 400. Finally, closed-record parsers built on the generated leaf validators; there is no runtime compilation.
- **Limits.** `successCriteria` ≤ 20, `allowedResources` ≤ 1, plus the §4.6 caps.
- **Responses.** `no-store`, `nosniff`, `no-referrer`. Never `Set-Cookie`, never CORS. The deadline is 5 s.

**Errors** use the v1 `ErrorEnvelope` with a fixed `safeMessage`.

| Condition | HTTP | code / retryClass |
| --- | --- | --- |
| No valid session, not a member, or revoked (`ineligible`) | 401 | denied / never |
| Malformed path, query or body (`invalid`) | 400 | missing_input / never |
| Guard failure; verb, field or scope denied; more than 1000 grants | 403 | denied / never |
| Absent, foreign or not viewable. **Byte-identical apart from `correlationId`.** | 404 | denied / never |
| `revision_conflict`, `state_conflict`, `guard_failed`, `stale_authority` | 409 | conflict / recheck_before_retry |
| `command_conflict`, `target_ineligible`, `limit_reached` | 409 | conflict / never |
| Database unavailable before the command function was sent | 503 | unavailable / recheck_before_retry (reads: safe_read_retry) |
| Command function or COMMIT sent, reply lost | 503 | uncertain / reconcile_before_retry |

Database error text and DETAIL are never logged or returned. The Worker logs one fixed line per request: `{event, route, outcome, correlationId}`.
### 4.10 Outbox (write side only)
`append_event()` runs last in each command. It increments `head_position` on the stream row, which is already locked, then inserts the outbox row. Positions are therefore **gap-free and commit-ordered per workspace**; that is the declared ordering scope. Aggregate revisions order each aggregate.
**Event payloads** (IDs and statuses only): `goal.created` `{status}`; `goal.status_changed`, `task.status_changed` `{from,to}`; `task.created` `{goalId,status}`; `task.assigned` `{assignmentId,ownerPrincipalId}`; `question.requested` `{respondentPrincipalId}`; `question.answered` `{answerId}`; `question.cancelled` `{}`.
- **Aggregate.** Each event sits on its own aggregate, at that aggregate's new revision. `causation_id` is null for human commands.
- **Deferred.** The envelope mapping, `payloadRef` and all readers belong to P06.T02a.
- **Known limit.** Commands within one workspace serialize for about one COMMIT round trip.

### 4.12 Tenant-isolation conformance (`tests/tenant-conformance/`, outside any product package)
**Registry.** `registry.mjs` holds the entries. Routes come from `workRoutes`, so identity never imports `@morrow/work`.

**Table classes:** `tenant_readable`: goals, tasks, questions, question_answers; `tenant_internal`: workspace_streams, task_assignments, commands, outbox_events; `platform`: transition_rules.

**Static checks.** Any miss fails CI.
- **S1.** Every object is registered.
- **S2.** Every table has ENABLE and FORCE RLS.
- **S3.** Tenant tables have NOT NULL org and workspace columns, a PK that starts with them, and a composite FK to a registered parent. Their policies use the `current_tenant()` row comparison. Platform tables have no tenant columns and no api grants.
- **S4.** The api role has only column SELECT, and only on readable tables. The command role has no DELETE or TRUNCATE. Views use `security_invoker`.
- **S5.** Functions and roles: no function has PUBLIC EXECUTE. SECURITY DEFINER is used only by the registered api functions and `current_tenant`. These are owned by the command role and have a `search_path` proconfig. Helpers and triggers are INVOKER and have no grants. api functions take no org, workspace or actor parameter. The one exception is `enter_context(digest, workspace)`, which is resolved through `session_eligibility`. Bridge functions are executable only by the command role. Role attributes match §4.2. No relay, maintenance or operations role exists. `pg_auth_members` holds exactly the two §4.2 rows (inherit false, set true). Each role may also have at most one *provisioning row*: member = the configured administrator, admin true, inherit false, set false. This is the PG16+ CREATEROLE self-grant on Neon; a local superuser setup has none.
- **S6.** `workRoutes` and the registry match one-to-one.

**Probes.**
- **P1, unset context.** Both roles see zero rows, and every api function returns `ineligible`.
- **P2, forged context.** A random digest, A's workspace with B's digest, a session-level `SET morrow.work_*`, and forged snapshot GUCs all yield zero rows or `ineligible`. None survives a revocation.
- **P3, foreign IDs.** Every route called with B's or A2's IDs returns a byte-identical 404. Every command function in A's context with B's IDs returns `not_found` and writes nothing. A direct command-role INSERT or UPDATE with B's tenant fails `WITH CHECK`.
- **P4, revoked member.** After a 0004 revocation, the next request gets 401. An unlocked READ ONLY transaction on the same connection sees zero rows. Replaying an old key discloses nothing.
- **P5.** See AC15.
- **P6, connection reuse.** On one connection, run as A, then as B, then with no context; each sees only its own rows or none. `current_user = session_user` after COMMIT and after ROLLBACK. The login cannot SET to the owner, command or identity roles.

P05 tables get probes only, and P05.T02a registers them. The connector-context and cross-store probes register later.
### 4.13 Session lifecycle (P05.T01y)
This section applies ADR-0004 (browser session lifecycle defaults).
- **Idle limit.** Work routes record no activity (their reads are READ ONLY) and never set cookies, so they do not extend the 30-minute idle limit.
- **Idle extension and rotation** happen only on P05.T01y's dedicated auth route, which the SPA calls while the user is active. This is recorded as a requirement on T01y, so a person who only uses work screens is not signed out.
- **Rotation is transparent.** Every request re-resolves the current generation.
- **Coupling.** AC24 pins the shape of the `session_eligibility` result.
### 4.14 Deliberate simplifications versus P05
- **Removed:** the per-transaction role query, observers, the request-scope and capsule machinery, and the HMAC synchronizer token.
- **CSRF protection** is exact Origin, Fetch Metadata, a custom header and JSON, with no CORS (as in P05.T01x §13.2). The security review must confirm it.
- **Fewer mechanisms.** Denials persist nothing. One RLS template and one resolver serve every table. Grant decisions are made only in the kernel.

## 6 Acceptance cases
**Fixtures.** Organization O has workspaces W and W2; organization O' has W'. Grants are seeded through owner SQL and pass both the 0002 CHECK and the Grant validator.
Principals: **A** owner, every OQ-1 verb · **A1** task.create view+execute, task.assign execute without administer · **B** views + question.answer execute · **C** task.create view+execute · **D** task.create view+administer · **V** all views, all fields · **V2** goal view without `successCriteria` · **E** views only (not an eligible respondent) · **X** member with no grants · **Y** member of O' only.

- **P06.T01a-AC01 Create.** A sends `POST /goals` with a fresh key and gets 201 `{goalId, revision:1}`. One commit writes a draft goal with scope `{O,W,[],[],[W],[]}`, one `goal.created` event at head+1, and one `commands` row.
- **AC02 Replay and canonicalization.** The same key and the same body, with reordered keys and different whitespace, gets 200 `replayed:true` and an identical result. No new rows.
- **AC03 Key misuse.** A sends its key with a different body: 409 `conflict`/`never`, nothing written. B sends the same key value: it applies as B's own command and discloses nothing about A.
- **AC04 Concurrent duplicates.** The same key sent on two connections produces one effect. The other request gets `replayed`.
- **AC05 Optimistic concurrency.** Two transitions at `expectedRevision:r`: one gets 200 (revision r+1), the other 409 `recheck_before_retry`.
- **AC06 State machine.** Table-driven over every goal and question pair not in the JSON: each is refused both through the functions and through a direct owner UPDATE. Task statuses other than draft and ready fail the CHECK. INSERTs with a non-initial status or a revision other than 1 are refused. `transition_rules` equals the JSON.
- **AC07 Guards.** These return `guard_failed`: `draft→ready` under a cancelled goal; goal `active→cancelled` with a draft or ready child; `active→achieved`; task create under a cancelled goal. The 201st task, or the 51st open question, returns 409 `limit_reached`.
- **AC08 Races (critique 18).** A hook pauses one transaction after `begin_command`. Three races each end in one consistent outcome with the invariants intact: goal cancel against task create; goal cancel against `draft→ready`; two creates for the 200th slot. A nightly soak of 4×500 commands has zero deadlocks.
- **AC09 Nested scope.** `allowedResources` of `[]` or `[W]` succeeds. These fail with 400 before SQL: a foreign organization or workspace, a non-null store or connection, a kind other than workspace, a duplicate, a partial object. The same values sent straight to `cmd_task_create` return `invalid`, and a direct command-role INSERT violates `valid_scope`. `storeIds:["s1"]` → 403.
- **AC10 View and fields.** V reads everything and gets 403 on every command. X gets 403 on lists and a 404 on `GET /tasks/:id`, byte-identical to a nonexistent id. V2 gets 403 `field_denied` on goal reads; no partial object is ever returned. Every object passes the v1 validators.
- **AC11 Ownership selects the verb.**
  - A acting on A's own task → 200.
  - C (execute, not the owner) → 403.
  - D (administer) → 200.
  - An owner whose grants were revoked after assignment → 403.
- **AC12 Lost reply on an assign by a non-admin owner (critique 1).** A1 owns T and assigns it to B, but the COMMIT reply is dropped: 503 `uncertain`. A same-key retry gets 200 `replayed:true` with the original result, even though A1 no longer owns T. After A1 loses view, the same retry gets 404 and discloses nothing.
- **AC13 Assign.** Assigning to B makes B the owner, adds one revision, emits `task.assigned`, and leaves grants unchanged. Assigning to Y, to an unknown principal, or to a member of W2 only all return identical 404s. Assigning to X returns 409 `target_ineligible`.
- **AC14 Questions.** A asks B. B answers, and the question becomes `answered` with `AnswerRef.digest = sha256(body)`. `question.answered` commits in the same transaction. A answering for B → 403, even with administer. A second answer → 409. Asking E → 409 `target_ineligible`. Asking Y → 404. The requester can cancel. C cancelling A's question → 403. `?respondent=me&status=open` lists only B's open questions.
- **AC15 Mid-request authority (critique 4).** Deterministic, using a hook between `enter_context` and `cmd_*`, or before COMMIT. (a) A's command is paused before COMMIT. A revocation of A waits on the share lock. The command commits, then the revocation applies. A's next request → 401. (b) A's revocation commits inside the window → 401 `ineligible`, nothing written. (c) Another member of O is revoked inside the window → 409 `stale_authority`, nothing written. A same-key retry then applies. (d) A maintenance edit to A's grant, or that grant's `expiresAt` passing, inside the window → 409 `stale_authority`, nothing written.
- **AC16 Commit unknown.** A fault proxy drops the reply to the command function or to COMMIT: 503 `uncertain`. A same-key retry replays or applies once. Both branches are forced, and there is never more than one effect. A lease `revocationSignal` after the send also gives 503 `uncertain`.
- **AC17 Sensitive markers.** Markers are placed in objective, criteria, prompt and answer. With TS bypassed, failures are forced: oversize values, NUL, a wrong-tenant scope, an answer after cancel. Each returns `invalid`, `not_found` or a conflict before any CHECK fires. Markers never appear in the outbox, ErrorEnvelopes, Worker console output, or the default PostgreSQL log, and the log contains no "Failing row contains" DETAIL.
- **AC18 Write isolation (critique 12).** Probe P3 runs over every command function and over direct command-role INSERT and UPDATE.
- **AC19 Harness.** S1–S6 and P1–P6 pass for every registration. The snapshot GUCs persist after `enter_context` and vanish at COMMIT.
- **AC20 Outbox write.** 4 connections × 50 commands produce positions 1..200, gap-free and in commit order. Each applied command writes exactly one row, in its own commit. Revisions are contiguous per aggregate, and payloads carry only allowlisted keys.
- **AC21 Request guard (P05.T01x-AC28 matrix).** No case below opens a SQL connection. **403:** missing or foreign Origin; `Sec-Fetch-Site` cross-site, same-site or none; `Sec-Fetch-Mode: navigate`; `Sec-Fetch-Dest: document`; no `X-Morrow-Request`; wrong `Content-Type`. **401:** `Authorization` or `Proxy-Authorization`; zero or two cookies. **400:** `Transfer-Encoding`; a body over 64 KiB; malformed UTF-8; duplicate keys; a lone surrogate; `\u0000`; an unknown or tenant key (`organizationId`, `workspaceId`, `principalId`); a missing or uppercase `Idempotency-Key`; a GET with a body, `Content-Type` or key. **405** with `Allow`.
- **AC22 M2 on fixtures (Miniflare + PostgreSQL 17).** A creates a goal and a task, marks the task ready, assigns it to B and asks B a question. B lists open questions and answers. A reads the answer. B, now the owner but without a task.create grant, tries a status change and gets 403.
- **AC23 Unbound artifact.** With the default `worker.ts` export, every `/workspace/:ws/work/**` request gets 401 with no network or database access. P05 routes and suites are unchanged.
- **AC24 Session coupling.** The test asserts the five column names, types and order of `session_eligibility(text,text)`. `DROP FUNCTION` on it fails because of the bridge dependency.
- **AC25 Grant overflow.** An actor with 1001 grants gets 403 on reads and commands, and nothing is written.

## 8 Security review checklist (Tier 2, mandatory)
- [ ] api functions take tenant and actor only from `current_tenant()`, per the S5 parameter rule. Helpers and triggers are INVOKER and ungranted.
- [ ] Writes run as `morrow_work_command` under `WITH CHECK` tenant policies, and P3 covers every command function. The owner policy is never reached at runtime.
- [ ] Every function has a fixed `search_path`, no dynamic SQL, no PUBLIC EXECUTE, and only registered grantees. Only the command role can execute the bridge.
- [ ] The digest travels only as a bind parameter into transaction-local GUCs. It is never logged or returned, and a forged GUC confers nothing.
- [ ] Composite FKs and `valid_scope` make cross-tenant references, including nested ResourceRefs, unrepresentable.
- [ ] Not-found responses are byte-identical. Replay needs current view. Denials persist nothing. An unknown outcome is never reported as success or as denial.
- [ ] The lock order is advisory → organization interlock (shared) → organization share → stream → goal → task → question. The shared interlock is held only within the command function, and the identity writers take it exclusively before their organization lock. The race hooks and the soak pass.
- [ ] The login is NOINHERIT, with one SET-only membership and no path to the owner, command or identity roles. `SET LOCAL ROLE` reverts (P6). No Hyperdrive claim is made.
- [ ] Reads request every field they return. Target grants are read server-side for eligibility only and are never returned.
- [ ] Events, errors and logs carry IDs only (AC17). Bodies are bounded, strict, closed and NUL-free.
- [ ] CSRF protection without a synchronizer token is justified (§4.14). There are no CORS headers and no `Set-Cookie`.
- [ ] The password is leased per request; expiry and revocation are honoured, and the lease is released via `waitUntil`. There is no raw secret binding (B1).
