# P01.T02a — Contract v1.1 foundation: executor classes, kill switches, review policy and exact proposals

**Task.** P01.T02a is a lettered child of P01.T02, a routine split under ADR-0002. This draft packet was revised on 2026-10-17 after critique. Conversation, inbox, project, route, model-call and evidence contracts move to P01.T02c and P01.T02b; §9 binds the critique's fixes for them.

**Delivery.** One packet, delivered as two PRs into `main` (ADR-0014). Each PR gets a Tier 2 "AI review (separate context, same model family)" plus `/security-review`.

Apart from the kill switches, these assignments only narrow what agents can do. - **PR-B "Review policy and exact proposals".** Covers ADR-0005 §3 plus material additions: credit ceilings, server-derived review fields, the solo-owner definition, the kill-switch billing exemption and two new capability IDs. ADR-0001/0002 required owner approval of these (Q0–Q9) before any PR-B code. **Resolved 2026-10-17:** the owner accepted the recommended answers as **ADR-0011**, "Contract v1.1: review policy and exact proposals", so PR-B may start. **ADR number (final, 2026-10-17).** ADR-0011, `docs/decisions/adr/ADR-0011-review-policy-and-contract-v1-1.md`. It and its index row land with the governance ADR set; this packet adds no ADR file. Sibling numbers: ADR-0007 and ADR-0008 (P04.T02a), ADR-0009 (P05.T01x), ADR-0010 (P06.T01a).

## Goal (observable product delta)

1. **PR-A, agent restriction.** An agent holding every otherwise-sufficient grant is denied every verb on `human_only` capabilities. The only exception is `propose`, and only where a proposal path exists.
2. **PR-A, kill switches.** A human with a current grant executes a kill switch with no approval obligation, but with the new `kill_switch_record` obligation. Reversals still require `exact_approval`.
3. **PR-A, contract artifacts.** The catalogue moves to `schema_version:2` with `executor` and `kill_switch`. The v1.1 schema files and generated kill-switch input validators are added. The v1 bytes are unchanged.
4. **PR-A, version.** `GET /health` on the api and the workers scaffold reports `contracts:"morrow.contracts.v1.1"`.
5. **PR-B.** Generated ReviewPolicy, Proposal@2 and Approval@2 validators, plus a pure typed review library in `@morrow/policy`. It covers derivation, the effective rule, the decision fold, the dispatch check and solo-owner status. P11.T01 imports it rather than re-implementing it. No route, UI, SQL, gateway or dispatcher is built here; P05.T01z, P11 and P14 build the flows.

## Design

### 1. Versioning (honest, not "additive")

**Contract set.** `morrow.contracts.v1.1` is: the three v1 files, byte-identical; `schemas/v1.1/core.schema.json`, with `$id urn:morrow:contracts:core:v1.1`; `schemas/v1.1/capabilities.schema.json`, with `$id urn:morrow:contracts:capabilities:v1.1`. Billing stays at v1. v1.1 may `$ref` v1 by absolute URI; billing's is `https://morrow.local/contracts/v1/billing.schema.json`. v1 never refers to v1.1.

**Replacements.** New types start at `schemaVersion` const 1. Replaced definitions (Proposal@2, Approval@2) and overridden capability bodies (the five kill switches in PR-A, `governance.approval.decide` in PR-B) are **not compatible in either direction**: the shapes are closed; the const versions differ; required properties are dropped or retyped. Each one is listed in `schemas/v1.1/changes.json` as `{kind:"definition"|"capability_body", name, replaces, reason, adr}` and stated plainly in the ADR. Nothing is deployed, so writers emit only current shapes. v1 selectors remain for the frozen baseline and historical fixtures.

**Effective selection.** A definition resolves to `core-v1.1:<Name>` if it exists, otherwise `core:<Name>`. A body resolves to `capabilities-v1.1:<id>.<io>` if it exists, otherwise `capabilities:<id>.<io>`. Later children may extend v1.1 while it is a candidate, through a deliberate baseline edit. Once it is frozen they open `schemas/v1.2/`.

**Baseline.** `release-baseline.json` keeps its flat `schemas` map of path → sha256, so `inspectCompatibility` is unchanged. It adds the two v1.1 files, `"current":"morrow.contracts.v1.1"` and `"versions":{"…v1":{"status":"frozen"},"…v1.1":{"status":"candidate_owner_signoff","extends":"…v1"}}`. Generation never writes the baseline.

**New `boundary-checks.mjs` checks.**
- `inspectBaselineCoverage`: a `docs/contracts/schemas/**/*.schema.json` file missing from `schemas` gives `UNBASELINED_SCHEMA:<path>`. Today such files escape the hash check.
- `inspectDeclaredReplacements`: a v1.1 definition reusing a v1 name, or a body override, must appear in `changes.json`, and every entry there must exist. Otherwise `UNDECLARED_REPLACEMENT:<name>`.
- `inspectSupersededUse`: in TypeScript under `packages/**` and `apps/**`, `validateDefinition("core", <replaced>)` or a `Core_<replaced>` type reference gives `SUPERSEDED_CONTRACT_USE:<file>:<name>`. Replaced names are read from `changes.json`, so T02b/T02c's Evidence@2 and EventEnvelope@2 are covered automatically. This stops P11 and other consumers from accepting v1-shaped proposals.

**Authoring rules.** Ajv `strict:true`, closed objects, every property required; `anyOf[…,null]` for nullable fields, bounded strings and arrays; annotations only in `description` or `$comment`.

### 2. Generators and validators (ahead-of-time only)

**`scripts/contract-sources.mjs`** exports `contractVersion` and an append-only `schemaSources` list of `{kind, path, prefix}`. Appending keeps existing validator names stable.

**`generate-contracts`** writes `export const contractVersion` into `domain.ts`, which `packages/contracts/src/index.ts` re-exports, so there is one version source; builds `CapabilityBodies` from the effective bodies; emits `Current_<Name>` aliases, such as `Current_Proposal = CoreV1_1_Proposal`; and writes a manifest with `schema_version:2`, `contract_version`, `replacements`, hashes and derived counts.

**`generate-runtime-validators`** uses one Ajv2020 instance with today's options; adds the selector prefixes `core:`, `capabilities:`, `billing:`, `core-v1.1:` and `capabilities-v1.1:`; emits frozen `currentDefinitionSelectors` and `capabilityBodySelectors` in the same bundle, typed in `.d.mts`. The PR reports bundle growth over today's ~1.59 MB.

```ts
export type DefinitionSchema = "core" | "billing" | "core-v1.1";
export function validateDefinition(schema: DefinitionSchema, name: string, value: unknown): boolean;                 // exact selector (history, tests)
export function validateCurrentDefinition(name: CurrentDefinitionName, value: unknown): boolean;                     // effective; product code
export function validateCapabilityInput<K extends CapabilityId>(id: K, value: unknown): value is CapabilityInput<K>; // effective body
export function validateCapabilityOutput<K extends CapabilityId>(id: K, value: unknown): value is CapabilityOutput<K>;
```

### 3. Catalogue (`capabilities.json` `schema_version: 2`)

**New fields.** Every capability gains: `executor`: one of `human_only`, `agent_after_approval`, `agent_direct_write` or `agent_direct_read`; `kill_switch`: a boolean; `irreversible`: a boolean, added in PR-B. `plan_sequence` is removed only after P03.T04c removes its consumers.

**Executor defaults by effect:** read → `agent_direct_read`; internal_write, billable_job → `agent_direct_write`; external_write, spend, communication → `agent_after_approval`; control → `human_only`. These are also `human_only`: `workspace.task.takeover`, `workspace.knowledge.approve`, `creative.image.approve`, `governance.audit.export`, `governance.privacy.export` and `ads.campaign.pause`.

**"Delegation changes" (ADR-0005; interpretation confirmed by ADR-0011 Q7, 2026-10-17).** These are two things, both control and so both `human_only`: grants that carry `delegate` (`governance.grants.revise`); mandate activation (`workspace.routine.activate`). `workspace.task.delegate` and `workspace.routine.configure` stay `agent_direct_write`, because they dispatch or configure bounded work inside existing grants and envelopes (agent-authority.md). This keeps today's behaviour. If the owner says no, a follow-up makes them `human_only`.

**Kill switches.** These five get `kill_switch:true`, `review_required:false` and `human_only`: `ads.campaign.pause`; `agents.installation.disable`; `governance.membership.revoke`; `governance.connection.disconnect`; `agents.release.revoke`, which keeps its `operator_*` principal, so the merchant evaluator still denies it.

**Reversals** keep `review_required:true`, with default executors: `ads.campaign.activate` → `agent_after_approval` (spend); `agents.installation.activate`, `governance.connection.connect`, `governance.membership.invite`, `governance.grants.revise`, `agents.release.publish` → `human_only` (control).

**Risk class (PR-B, Q9).** `docs/contracts/review-policy-defaults.json` holds a fixed `riskClassByEffect` table: read, internal_write, billable_job → `internal`; external_write → `external`; spend → `financial`; communication → `communication`; control → `access_change`. There is no per-capability field, because `effect` already classifies and one table is easier to keep consistent.

**Irreversible (PR-B, Q4).** `lifecycle.campaign.send`, `support.reply.send`, `orders.refund.create`, `orders.cancel`, `orders.fulfillment.create`, `governance.privacy.erase` and `agents.installation.uninstall`.

**`validateCatalogue` rules.** These replace "consequential action without review gate". The existing required-field checks stay.

| Rule | Condition | Requirement |
| --- | --- | --- |
| R1 | always | `executor` is in the enum; `kill_switch` is a boolean |
| R2 | read | `agent_direct_read` or `human_only` |
| R3 | internal_write or billable_job | not `agent_direct_read` |
| R4 | external_write, spend or communication | `agent_after_approval` or `human_only` |
| R5 | control | `human_only` |
| R6 | `agent_after_approval` | review required |
| R7 | kill switch | `human_only`, unreviewed, and effect external_write or control |
| R8 | unreviewed external_write, spend or communication | must be a kill switch |
| R9 | `eligible_human_*` | `human_only` |
| R10 (PR-B) | irreversible | effect is not read |
| R11 | always | catalogue fields equal the effective body's `properties`/`required`, and the `schema-types.json` URI equals its `$ref` |

### 4. Policy guards (PR-A, in the same commit as the catalogue change)

- **Agent kernel.** In `allowedOperation`, a `human_only` capability returns `op.verb === "propose" && (c.kill_switch || c.review_required)`, on top of the existing conditions. Every other verb gives `capability_denied`, including `view`, so human_only reads are covered. `propose` is denied where no proposal path exists, as for `workspace.task.takeover`.
- **Human evaluator.** `ExecutionObligation` gains `"kill_switch_record"`. A kill switch with `execute` gets `recheck_at_dispatch` and `kill_switch_record`, plus `provider_effect_verification` for external_write. It never gets `exact_approval` or `budget_reservation`. Entitlement checking is unchanged in PR-A (no worse than today). In PR-B (Q8), kill switches skip `entitlementAllowed`; `provider_denied` still applies.
- **What `kill_switch_record` requires**, implemented by P05.T01z and P11.T05: a reason (KillSwitchControl); an append-only KillSwitchRecord, committed together with the effect; an owner notification derived from that record (a T02c inbox kind).
- **Gateway stops.** P11.T05's tenant, installation and platform stops are operational controls, not capability executions, so `human_only` does not apply to them.
- **`inspectAuthority`** adds `HUMAN_EXECUTOR_REQUIRED` and `KILL_SWITCH_REASON_REQUIRED`, and never requires `EXACT_APPROVAL_REQUIRED` for kill switches.

### 5. Kill switches: types, inputs, targets (PR-A)

```ts
type HumanActorRef = {kind:"human"; principalId: Id; organizationId: Id; workspaceId: Id; membershipId: Id; installationId: null; mandateId: null}; // structurally an ActorRef
type KillSwitchControl = {reason: string(1..1024, pattern "\\S"); sourceProposalRef: ProposalRef | null};
type CampaignRef = {organizationId: Id; workspaceId: Id; storeId: Id|null; connectionId: Id; kind:"campaign"; id: Id};  type CampaignRefs = CampaignRef[1..100] /*uniqueItems*/;
type KillSwitchRecord = {schemaVersion:1; id; organizationId; workspaceId; storeId: Id|null; revision: 1 /*append-only*/; createdAt: UtcTime; capabilityId: CapabilityId;
  actor: HumanActorRef; control: KillSwitchControl; targets: ResourceRef[1..100]; commandId: Id; requestDigest: Digest; priorStateObserved: "active"|"already_stopped"};
```

**Input overrides** (`capabilities-v1.1`, replacements; outputs unchanged).

| Capability | v1.1 input |
| --- | --- |
| `ads.campaign.pause` | `{campaigns: CampaignRefs, control}` |
| `agents.installation.disable` | `{installationId, control}` |
| `governance.membership.revoke` | `{membershipId, control}` |
| `governance.connection.disconnect` | `{connectionId, control}` |
| `agents.release.revoke` | `{releaseRef, control}`; `control.reason` replaces the v1 `reason` |

**No `expectedRevision`.** A stop is an idempotent target state, so an unrelated revision bump never fails it. An already-stopped target returns the existing output and records `already_stopped`. Commands stay idempotent per (workspace, `commandId`, `requestDigest`) from the CommandEnvelope. The same `commandId` with a different digest gives `conflict`.

**Target rules.** The pure function `checkKillSwitchTarget(input, facts)` lives in `packages/policy/src/kill-switch.ts`.
- **Tenant and existence.** Every ref (campaigns, `releaseRef`, `sourceProposalRef`), and every record an ID resolves to, must be in the trusted organization and workspace. Every target, of every kind, must fit within one of the actor's grants (never a union): its store, with a storeless target needing a storeless grant, and the connection of a campaign or of a disconnected connection. Unknown, foreign-tenant and ungranted targets all give the identical `TARGET_NOT_FOUND` result and safe message.
- **`sourceProposalRef`.** It must be in the same tenant, its `capabilityId` must be this capability, and its targets must include the input's targets. Otherwise `TARGET_NOT_FOUND`. A stop executed from an agent proposal creates no Approval.
- **Owner protection.** The designated owner membership cannot be revoked through the kill switch (`OWNER_MEMBERSHIP_PROTECTED`). Removing an owner needs a reviewed ownership transfer first (access_change, P05.T01z). Every revocation advances `lastMembershipChangeAt`.

**`WorkspaceOwnershipFacts`** (`packages/policy/src/review-facts.ts`) are filled only by trusted readers. P05.T01z supplies them from the owner record that P05.T01x creates (ADR-0009 item 3). Shape: `{ownerPrincipalId, ownerMembershipId, activeHumanMembershipCount, lastMembershipChangeAt: UtcTime|null}`. A "membership change" means any revocation or ownership change.

### 6. Review contracts (PR-B, core-v1.1)

```ts
type NonNegativeDecimal = string /*^(0|[1-9][0-9]{0,17})(\.[0-9]{1,6})?$*/;  type NonNegativeMoney = {amount: NonNegativeDecimal; currency: Currency};
type CreditUnits = billing:v1 CreditUnits /*integer string; BigInt only*/;      type RiskClass = "internal"|"external"|"communication"|"financial"|"access_change";
type SelectionIndexes = Count[1..999] /*uniqueItems; strictly increasing checked by the library*/;
```

**New capabilities (Q5).** Both use: provider D01, standalone only; the standard `resource_scope`, `source_authority`, `failure_behavior` and `layout` texts; R02, J13, and activation `blocked_until_contract_and_provider_qualified`.

| ID | Effect / executor / review | Eligible principal | Input → output | Field scope; verification | Tasks; cases |
| --- | --- | --- | --- | --- | --- |
| `governance.review_policy.revise` | control / human_only / yes (access_change) | `human_or_bounded_installation_with_explicit_capability_grant` (agents may only propose) | `{proposalRef, approvalRef}` → `{policyRef}` | review rules, quorum, expiry, self-approval; "a new revision invalidates approvals bound to the old one" | P11.T01; P01.A01, P11.A01 |

**Reviewer verbs (ADR-0011 Q5).** A reviewer holds `approve` on `governance.approval.decide` (matching the P05.T01x template v1, ADR-0009) and `approve` on the proposal's capability. Preview also needs `view` on `governance.approval.preview`, which P05.T01x template v1 grants (applied 2026-10-17).

### 7. Review semantics (PR-B): pure library `packages/policy/src/review.ts`

The library does no I/O and uses no clock or randomness. It takes frozen, closed values plus trusted facts from `review-facts.ts`, which are never decoded from HTTP or model input. The `P01.T02a.json` fixtures run through it, and P11.T01 imports it.

```ts
export function checkProposal(p: Current_Proposal, f: ProposalFacts): readonly ReviewCode[];
export function previewSelection(parent: Current_Proposal, selected: readonly number[] | null): {proposal: Current_Proposal} | {code: ReviewCode};
export function effectiveRule(rules: ReviewPolicyRules, risk: RiskClass, irreversible: boolean): EffectiveRule;
export function confirmationPhrase(p: Current_Proposal): string;
export function foldDecisions(state: ReviewState, attempts: readonly DecisionAttempt[]): {state: ReviewState; results: readonly AttemptResult[]; invalidate: readonly ApprovalRef[]};
export function dispatchCheck(state: ReviewState, f: DispatchFacts): "ok" | ReviewCode;
// ProposalFacts: trusted org/ws/store; catalogue effect + irreversible; authenticated proposer; requestedBy (task initiator or mandate owner);
//   beneficiaryPrincipalIds; contextTaint (from consumed evidence, P13); the workspace's current ReviewPolicy; eligibleNonConflictedReviewerCount.
// DecisionAttempt: {commandId, requestDigest, reviewer, input, expectedRevision, at, reviewerEligible, ownership}.  DispatchFacts: {now, currentPolicyRef, ownership}.
```

1. **Server-derived fields.** The server builds every proposal, and each mismatched field has its own code. `risk` must equal `riskClassByEffect[effect]` (`RISK_CLASS_MISMATCH`). `irreversible` must equal the catalogue value (`IRREVERSIBLE_MISMATCH`). `requestedBy`, `beneficiaryPrincipalIds` and `contextTaint` must equal the facts (`REQUESTED_BY_MISMATCH`, `BENEFICIARIES_MISMATCH`, `CONTEXT_TAINT_MISMATCH`). `proposedBy` must be the authenticated actor. `reviewPolicyRef` must equal the workspace's single current ReviewPolicy: same id, revision and digest, with `storeId` null. Otherwise `REVIEW_POLICY_NOT_CURRENT`. Unlike v1 `inspectBinding`, this is not tied to the proposal's store. Every ref (scope, targets, `parametersRef`, `reviewPolicyRef`, `derivedFrom.parentRef`) must lie in the trusted organization, workspace and proposal store (`TENANT_MISMATCH`).
2. **Ceilings.** `maximumCredits` must equal the BigInt sum of the target credits (`CREDITS_SUM_MISMATCH`). `maximumCost` is null exactly when every target cost is null. Otherwise there must be one currency, and the exact decimal sum (BigInt ×10^6) must match (`COST_SUM_MISMATCH`). Ceilings are non-negative by type. The digest is `sha256(JCS(proposal minus proposalDigest))`, so every new field is bound.
3. **Effective rule.** Start from `rules[risk]`. If the proposal is irreversible, merge `rules.irreversible`, taking for each field the stricter value: the maximum quorum; the minimum expiries; the stricter of `denied` > `solo_owner_typed_confirmation` > `allowed`; the intersection of reviewer lists. `checkProposal` returns `QUORUM_UNREACHABLE` when eligible non-conflicted reviewers are fewer than the quorum and solo confirmation cannot apply. T02c turns this into an inbox exception.
4. **Eligibility.** `reviewerEligible()` composes the existing human evaluator. The reviewer must: be a HumanActorRef with a current membership; hold `approve` on `governance.approval.decide`; hold `approve` on `proposal.capabilityId` covering every decided target's resource, store, account and fields; appear in `eligibleReviewerPrincipalIds` when that list is set. Otherwise `REVIEWER_DENIED`.
5. **Conflict set.** A reviewer is conflicted when their `principalId` is one of: `proposedBy`; `requestedBy`; any of `beneficiaryPrincipalIds`. For access_change these are the principals receiving the grant, membership or ownership, plus the requester of any originating access request. A conflicted reviewer passes under `allowed`. Under `solo_owner_typed_confirmation` they pass only with solo status (item 6) **and** the exact phrase. Otherwise the result is `SELF_APPROVAL_DENIED`, or `CONFIRMATION_MISMATCH` for a wrong phrase.
6. **Solo owner.** `soloOwner(f, t)` holds when all of these are true: `reviewer.principalId === f.ownerPrincipalId`; `f.activeHumanMembershipCount === 1`; `lastMembershipChangeAt` is null, or `t ≥ lastMembershipChangeAt + quietPeriodSeconds`. The phrase is NFC, case-sensitive and exact: `approve ${n} ${n===1?"change":"changes"} for ${maximumCredits} credits`, plus ` and ${amount} ${currency}` when there is a cost, with amounts copied as written. The server stores `phraseDigest` and sets `effectiveAt = decidedAt + coolDownSeconds`. This single decision meets the quorum.
7. **Decision fold** (ordered attempts). A replay of the same `(commandId, requestDigest)` returns the recorded result and changes nothing. The same `commandId` with a different digest gives `COMMAND_CONFLICT`. A reviewer who already decided, under any command, gives `DUPLICATE_REVIEWER`. A stale `expectedRevision` gives `conflict`. An `expectedDecisionDigest` that differs from the digest of the proposal being decided (parent or derived) gives `DIGEST_MISMATCH`. Any eligible reject sets `rejected`. `requiredApprovals` distinct eligible approvals set `approved`, with `effectiveAt` equal to the last `decidedAt`, or later under a solo cool-down.
8. **Partial approval.** An `all_or_nothing` parent gives `PARTIAL_APPROVAL_NOT_ALLOWED`. The selection must be strictly increasing, in range and a strict subset, and the parent must not be derived. Otherwise `SELECTION_INVALID`. The derived proposal is the parent with: `id = "derived_" + hex(sha256(JCS({parentRef, selectedTargetIndexes})))`; revision 1; `createdAt`, `updatedAt` and `expiresAt` inherited; targets filtered in order; ceilings re-summed; `derivedFrom` set; `all_or_nothing`; and a new digest. `requestedBy`, `proposedBy` and beneficiaries are inherited. It is asserted that derived ceilings are ≤ the parent's and derived `expiresAt` equals the parent's. `governance.approval.preview` returns this deterministic proposal before the decision.
9. **Family.** A family is a root proposal plus its derivations, and at most one member can be approved. Approving a member when another is approved gives `FAMILY_CONFLICT`. An approval puts every other pending member approval into `invalidate` (`superseded_by_partial_approval`). Unselected targets return to draft (P06/P11). Locking the root row is P11.T01's job.
10. **Expiry and dispatch.** Pending `expiresAt = min(proposal.expiresAt, approval.createdAt + pendingExpirySeconds)`; approved `expiresAt = min(proposal.expiresAt, effectiveAt + approvedValiditySeconds)`. `dispatchCheck` returns: `APPROVAL_NOT_EFFECTIVE` when `now < effectiveAt`; `APPROVAL_EXPIRED` when `now ≥ expiresAt`; `REVIEW_POLICY_NOT_CURRENT` for a stale policy ref, which invalidates. This is distinct from the organization-level `POLICY_CHANGED`. For solo approvals, `SOLO_OWNER_STATUS_LOST` (invalidated via the existing `approved→invalidated` row) unless `soloOwner(f, now)` holds and `lastMembershipChangeAt ≤ decidedAt` (or is null). The check runs at `effectiveAt` (P11 scheduler) and again at dispatch.
11. **Cancel.** `cancel_before_effective` by the confirming solo reviewer while `now < effectiveAt` gives `cancelled`. Otherwise `CANCEL_NOT_ALLOWED`.
12. **Policy revision.** `governance.review_policy.revise` is an access_change proposal under the current policy. A new revision makes pending approvals bound to the old one stale. P11.T01 owns the record and seeds revision 1 per workspace from the defaults.
13. **Errors.** These map to `denied`/`never` with an existence-free message: `REVIEWER_DENIED`, `SELF_APPROVAL_DENIED`, `CONFIRMATION_MISMATCH`, `TARGET_NOT_FOUND`, `OWNER_MEMBERSHIP_PROTECTED`, `CANCEL_NOT_ALLOWED` and the item-1 codes. These map to `conflict`/`recheck_before_retry`: `DIGEST_MISMATCH`, `COMMAND_CONFLICT`, `DUPLICATE_REVIEWER`, `FAMILY_CONFLICT`, a stale revision and `REVIEW_POLICY_NOT_CURRENT`. `APPROVAL_EXPIRED` maps to `approval_expired`. An unknown commit is read back by `commandId`, never resubmitted.
