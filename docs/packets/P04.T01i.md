## Design

### D1 Origin and wrangler configuration

- **Origin.** `https://morrow-staging-api.sultanibneusman0.workers.dev`. Only the api is public, and HTTPS is forced because `.dev` is on the HSTS preload list. **Uses.** This one string is `LOGIN_CONFIGURATION_JSON.origin`. It is the base of `redirectUri` (`<origin>/auth/workos/callback`, also the only WorkOS redirect). It is the exact origin for workspace and logout (invariant 22), and it is the Turnstile hostname. **Check.** verify-config requires each use to equal `https://${env.staging.name}.${workers_dev_subdomain}.workers.dev`, read from `infra/environments/staging.json`.
- **Same site.** `workers.dev` is on the Public Suffix List, so every Worker under `sultanibneusman0` is same-site with the api. Two protections still hold: `__Host-` cookies, and invariant 22 (exact Origin, `X-Morrow-Request`, JSON, no CORS). The census at every deploy fails if any other script or Pages project exposes workers.dev or binds `morrow-staging-broker`.
- **Wrangler.** Only `env.staging` changes. Development and production gain only the limiter bindings, namespaces 7001–7003 and 7201–7203. The api's staging block:

```jsonc
"staging": { "name": "morrow-staging-api", "workers_dev": true, "preview_urls": false,
  "observability": { "enabled": true, "head_sampling_rate": 1, "traces": { "enabled": false },
    "logs": { "enabled": true, "invocation_logs": false, "head_sampling_rate": 1, "persist": true } },
  "vars": { "MORROW_ENVIRONMENT": "staging", "LOGIN_CONFIGURATION_JSON": "…", "WORKSPACE_CONFIGURATION_JSON": "…",
    "LOGOUT_CONFIGURATION_JSON": "…", "MORROW_DATABASE_BINDING_JSON": "{…\"branchId\":\"br-…\",\"hostname\":\"ep-….us-east-1.aws.neon.tech\",\"database\":\"morrow\"}",
    "LOGIN_CHALLENGE_JSON": "{\"schemaVersion\":1,\"provider\":\"turnstile\",\"siteKey\":\"0x…\",\"actions\":{\"login\":\"account_login\",\"signup\":\"organization_signup\"}}" },
  "services": [{ "binding": "BROKER", "service": "morrow-staging-broker", "entrypoint": "ApiBroker" }],
  "ratelimits": [ { "name": "LOGIN_START_LIMITER", "namespace_id": "7101", "simple": { "limit": 10, "period": 60 } },
    { "name": "LOGIN_CALLBACK_LIMITER", "namespace_id": "7102", "simple": { "limit": 20, "period": 60 } },
    { "name": "SIGNUP_LIMITER", "namespace_id": "7103", "simple": { "limit": 5, "period": 60 } } ],
  "secrets": { "required": [] } }
```

- **Broker.** Settings: `workers_dev:false`, `preview_urls:false`, and the same observability block. Vars: `MORROW_ENVIRONMENT`; `LOGIN_CONFIGURATION_JSON` and `MORROW_DATABASE_BINDING_JSON`, each byte-equal to the api's; and `TURNSTILE_CONFIGURATION_JSON` `{schemaVersion:1, hostname, actions}`. `secrets.required` has ten names: `WORKOS_API_KEY`, `TURNSTILE_SECRET_KEY`, and eight `MORROW_DB_PASSWORD_<ROLE>`.
- **Orchestrator and connector.** No workers.dev, no previews and no routes. The connector stays a 503 placeholder (ADR-0008). The queues `morrow-staging-dispatch` and `morrow-staging-dispatch-dlq` are created first (E4).
- **Database binding.** It names the **direct** endpoint of the `staging` child branch. The runner refuses a `-pooler` host, because advisory locks need a session.
- **Rules.** `LOGIN_CHALLENGE_JSON` avoids KEY, SECRET and TOKEN, so P04.T02a D6 step 3 is unchanged. verify-config (AC01, AC02) allows `workers_dev:true` only on the staging api, and requires exact observability and `ratelimits` per environment and per-Worker var allowlists. P04.T02a AC24 narrows: staging vars hold only `environment_…`, `app_…`, `client_…`, `br-…`, `ep-….aws.neon.tech`, a `0x…` site key and the origin. The CSP in `_headers` adds `https://challenges.cloudflare.com` to `script-src` and `frame-src`, plus `form-action 'self'`.
- **`staging.json`.** It gains the account, `workers_dev_subdomain`, the origin, the Neon project, root branch, `staging` branch and region, and `plan: "Free"` with the observed history window (about 6 h). This amends `deployment-policy.json` (Launch, `pitr_staging` 7) for staging until P04.T04 (ADR-0019 item 10).

### D2 Deploy pipeline

- **Workflow.** `.github/workflows/deploy-staging.yml` runs `on: workflow_run` of "Morrow foundation", with `types: [completed]` and `branches: [main]`. That event always runs the default branch's copy of the workflow. **Job condition.** `conclusion=='success'`, `event=='push'`, `head_branch=='main'` and `head_repository.full_name==github.repository`. **Settings.** `concurrency: {group: deploy-staging, cancel-in-progress: false}` and `contents: read`. Actions are pinned by SHA. **Setup.** Checkout of `head_sha` with `persist-credentials: false`. `setup-node` **without an npm cache**, then `npm ci --ignore-scripts`.
- **Shape by OQ-2 answer.**

| OQ-2 | Token and variables in | Workflow | Commands |
| --- | --- | --- | --- |
| A, Pro | `staging` environment (main-only branch policy) | `environment: staging` | `gh secret` and `gh variable` with `--env staging` |
| B, Free | repository secret and variables | no `environment:` | the same, without `--env` |
| C, no CD | repository variables only; no CI token | file not added | local `staging:deploy` only |

PR-B builds the shape for the answer given before it merges, and records it as `github.scope` in `staging.json`.

- **Step 1 runs without the Cloudflare token**, because `edge.mjs` refuses it. Gate 1: if the sha is no longer the `main` tip, exit 0 (superseded). Gate 2: if `STAGING_DEPLOY_ENABLED` is not `1`, exit 0. Gate 5: `npm run build`, `edge:check` and `edge:dry-run` must pass.
- **Step 2 is the only step whose `env` holds the token.** Gate 3 (schema): `staging.mjs schema-head` hashes the ordered `(sequence, file, sha256, executeAs, prerequisites)` list. A mismatch with `STAGING_SCHEMA_HEAD` fails with "run staging:migrate, then `gh run rerun`". Gate 4 (login configuration): the login parser's `configurationDigest` for the committed staging configuration must equal `STAGING_LOGIN_CONFIGURATION_DIGEST`. Otherwise the run fails with "keyring rotation needed". Gate 6 (broker secrets): the broker's deployed secret names (`wrangler secret list`, parsed to names) must equal `brokerRequiredSecrets` exactly.
- **Deploy.** `wrangler deploy --env staging --message <sha>` runs for the broker, orchestrator, connector and api, in that order. Broker methods are only ever added. **The flag is re-read just before and just after the api deploy.** If it is no longer `1`, the job disables the api's workers.dev and fails. `/healthz` must report `ready:true` within 90 s. Otherwise the run fails and records both api version ids. **Trimmed by ADR-0021:** there is no `wrangler rollback`; card effect E11 is suspended and staging rolls forward (PR-B notes). Then the unattended smoke (D7) and the census run. The report (sha, version ids, durations, gates; no values) goes through `artifacts.mjs` and `scan-artifacts` and is uploaded with 90-day retention (ADR-0012). The clean-tree gate runs last.
- **Migration-bearing merges.** These stop at gate 3. Under the card, the operator runs `staging:migrate`, then reruns the deploy. Migrations stay expand-first, contract-later.
- **Local `staging:deploy -- [--first | --api-keyring]`.** **Preconditions.** It runs `git fetch` and requires a clean tree with HEAD equal to `origin/main`, plus a successful `foundation` check run on that sha (`gh api repos/sultanhunter/Morrow/commits/<sha>/check-runs?check_name=foundation`). It honours gates 2–6, re-reads the flag around the api deploy, and always dry-runs first. **Token.** It reads the token only from `~/.config/morrow/staging/cloudflare-operator-token`. **`--first`.** Deploys the broker with `--secrets-file tmp/broker-secrets.json` and the api with `tmp/api-secrets.json`. **`--api-keyring`.** Deploys only the api, with `api-secrets.json`, then sets the digest variable and records the rotation version. Both files are unlinked on success. **CD never deploys a keyring.**
- **Rollback (deferred past launch, ADR-0021; not in the trimmed PR-B).** `staging:rollback -- --worker <n> [--version <id>]` wraps `wrangler versions list` and `wrangler rollback`. Versions carry their own secrets, so it refuses to roll the broker past its last role-password or Turnstile rotation, or the api past its last keyring rotation. **A Worker rollback is not a database rollback.** Migrations are forward-only, and passwords and WorkOS configuration are never undone. Database recovery is the owner-run reset (D3).
- **Secret handling.** **Token isolation.** `scripts/staging.mjs` first imports `scripts/staging-token.mjs`. That module moves `CLOUDFLARE_API_TOKEN` into a closure and deletes it from `process.env` before any other module loads. The token then reaches only each wrangler child's environment, which is the only way wrangler accepts it; ADR-0019 item 14 records this exception. **Errors.** Every credential read, parse or connect error becomes a fixed code with no message or `cause`. This matters because Node 24's `JSON.parse` quotes its input and `ERR_INVALID_URL` carries `input`. **Output.** Raw wrangler, neonctl and gh output is never relayed. Only parsed names and ids, or a fixed code with the exit status, are shown.
- **Residual risk until branch protection.** Anyone who can push to `main` can rewrite `deploy-staging.yml`, `ci.yml` or `staging.mjs` in the same push, and so controls the deploy token. A token that can deploy the broker can deploy code that reads every broker secret. Secret APIs returning names only is not a control. **Mitigations.** Only the owner's account pushes, and every other app, token, deploy key and collaborator is removed first (D9 step 3), except the platform GitHub Apps accepted in the ADR-0019 item 5 exception. Under OQ-2 A, protection went on at once (2026-10-19); it requires `foundation` and no review, so a principal with write access can still change CI through a merged pull request.

### D3 Hosted migrations, roles and platform seed

- **Neon layout.** The project is `morrow-staging` (PG17, AWS us-east-1, Free). Its **root branch** (Neon's default name `production`; not a production resource, ADR-0019 item 10) holds Neon's default empty database `neondb` and the empty database `morrow`, owned by `neondb_owner` (D9 step 4(d)), and is never migrated. The child branch **`staging`** is the only branch that is migrated and bound.
- **Reset (owner-run, card R1).** First run `staging:kill` (E12; anyone): `STAGING_SCHEMA_HEAD` still names main's head after a reset, so otherwise a green push to `main` would pass gate 3 against the empty database. Then run `neonctl branches reset staging --parent`, which keeps the branch id and host (M-N4). Claude then reruns `migrate`, `provision-roles --rotate all` and `seed-platform`, then `unkill` under the card.
- **Claude's Neon effects.** These are only throwaway branches (with an expiry) and reads. They use a **project-scoped API key** from `neon-project-api-key`, passed as `NEON_API_KEY` to the neonctl child only, never the owner's organisation-wide login. If Neon offers no project-scoped key, these effects become owner-run.
- **Credentials and refusals.** `staging.mjs migrate` runs only while the card is active. **URL file.** It reads the owner URL only from `neon-owner-url`: mode 0600, operator-owned, not a symlink, in a 0700 directory. The URL is never printed, never in argv and never in the environment. **Connection.** It uses the pinned `@neondatabase/serverless` Client over WebSocket (TLS). **Refusal.** It stops with a fixed code unless all of these hold: the host, database and project equal the committed binding; the server is PG17; the session user is `neondb_owner`; the tree is clean; `migrations/` and `infra/*prerequisites*.sql` equal `origin/main`; `foundation` passed on that sha.
- **Chain module.** `scripts/migration-chain.mjs` reads the manifest, verifies every migration's sha256 and every pinned prerequisite's sha256, and yields `{sequence, file, text, executeAs, prerequisites}`. The runner, `delivery-checks.mjs` and the conformance harness all use it, and the harness's private map is retired (routine).
- **Ledger.** `morrow_migrations.applied(sequence int PRIMARY KEY, file, sha256, execute_as, prerequisites jsonb, source_commit, applied_at timestamptz, applied_by)`. The administrator owns it, with `REVOKE ALL` from PUBLIC and from every Morrow role. It is tooling outside the manifest (ADR-0019 item 12), excluded in the conformance registry.
- **Algorithm.** (1) Take `pg_advisory_lock(<fixed key>)` on a dedicated session. (2) If any ledger row differs from the manifest, stop with `MIGRATION_LEDGER_DRIFT`. (3) For each pending entry: check that the file starts with `BEGIN;` and ends with `COMMIT;`. Run each prerequisite only if none of its roles exist. If some exist, stop with `PREREQUISITE_PARTIAL`. The identity files are plain `CREATE ROLE`, and row 1's file is cumulative, so it is valid only on a fresh database. The work file is idempotent. Run `GRANT <executeAs> TO neondb_owner WITH INHERIT FALSE, SET TRUE` (ADR-0020). **Write the ledger atomically.** On one fresh connection, send `SET ROLE <executeAs>;`, the file minus its final `COMMIT;`, then `RESET ROLE; INSERT INTO morrow_migrations.applied …; COMMIT;`. (4) Revoke the SET rows, so only self-grant rows remain at rest. (5) Publish `STAGING_SCHEMA_HEAD`.
- **Unknown outcomes.** If the connection is lost around `COMMIT`, the runner reconnects and reads the ledger. A row means the migration committed with it. No row means it rolled back. This reconciles against committed state; nothing is promoted (invariant 10). A prerequisite with an unknown outcome is settled from the catalog: all roles present means done, none means run it again, and partial stops for an owner reset. A rerun with nothing pending is a no-op.
- **Hosted-shape replay (lab).** `lab:staging-runner` applies the chain up to the last sequence on `origin/main`. It then runs `provision-roles` in hosted shape (LOGIN, limits, timeouts, TEMP revoke), then applies the rest. When a PR adds no migration, the lab applies 1..N−1, provisions, then applies N. A later check such as `NOT rolcanlogin` therefore fails in CI rather than on staging.
- **Compensating controls (ADR-0007 item 5).** Each of the eight leased roles gets LOGIN with a SCRAM verifier (M-N3), `CONNECTION LIMIT 10`, `statement_timeout='5s'` and `idle_in_transaction_session_timeout='10s'`. Then `REVOKE TEMP ON DATABASE morrow FROM PUBLIC`. Each control is verified from the catalog.
- **`provision-roles [--first | --rotate <role|all>]`.** **Passwords** are 32 random bytes, base64url-encoded and generated in-process. Only verifiers reach SQL. **`--first`** writes the plaintexts, plus the Turnstile and WorkOS values, to one 0600 `tmp/broker-secrets.json`. **`--rotate`** pipes JSON on stdin to `wrangler secret bulk --env staging`, which creates one broker version, and records its id. If 4.116.0 lacks stdin input, it writes a 0600 temporary file and unlinks it at once. **Partial failure.** Rotate again. Expect seconds of 503 (P04.T02a AC20).
- **`seed-platform`.** It writes only platform configuration rows: the WorkOS verification profile, built from the committed ids, and the configuration rows the 0007–0013 definers read. The single `self_service_revisions` row (card E7) is written only after the owner confirms in chat that WorkOS email verification is on and public sign-up is off (ADR-0009 item 11). The seed is idempotent and follows the P05.T01x §7 lock order. Every write goes into the live record.

### D5 Sign-in abuse protection (P05.T01ab)

- **Decision** (ADR-0019 items 6–8). Turnstile and per-IP limits are required before hosted login is activated in any hosted environment. This amends ADR-0009 item 8 and resolves the STATUS sign-off on P05.T01x §11.
- **Guard.** `apps/api/src/abuse-guard.ts` runs before any SQL. It selects requests with **the router's own route matcher**, never a separate string compare. That covers login start (`POST /auth/login`), signup (`POST /organizations`) and the callback, for every method the router dispatches, HEAD included. Tests cover a trailing slash, `%6C`, a query string, and HEAD on the callback. Only a request its handler could accept on headers alone is counted (step 0, added after the Tier 2 review; see "PR-C implementation notes").
- **Step 1: the limiter.** **Key.** `<route>:` plus 32 hex characters of SHA-256 over the client address. An IPv6 address is first truncated to a reviewed prefix of **/56** (the constant may be 48, 56 or 64). **Address.** It comes from `CF-Connecting-IP` and is never stored, logged or used for authority. **Over the limit:** 429 `{"schemaVersion":1,"outcome":"rate_limited"}`, with `Retry-After: 60` and no-store. **Fails closed.** A missing `CF-Connecting-IP`, or a throwing `limit()`, gets 503 with the route's existing body and one `morrow_edge_guard {code}`.
- **Step 2: the challenge** (POST routes only). **Header shape.** `X-Morrow-Challenge` must be 1–2048 bytes of `[A-Za-z0-9._-]`. Otherwise the response is 403 `{"schemaVersion":1,"outcome":"challenge_required"}`, with no broker call. **Verification.** Exactly one `BROKER.challengeVerify(action, token, budgetMs)` call. `passed` deletes the header and forwards the request otherwise unchanged; `failed` gives 403 `challenge_failed`; held or timed out gives 503 with the route's existing body. **No retry, and no body read.** **No logging of rejections,** except the broker's one `morrow_challenge` line for a failed verification (D6; ADR-0019 item 9 as amended 2026-10-19). The free Workers metrics already count 429 and 403.
- **`GET /auth/challenge`** returns `{"schemaVersion":1,"provider":"turnstile","siteKey","actions"}`, or `{"provider":"none"}`.
- **Mapper step 10.** In staging and production, a missing or invalid `LOGIN_CHALLENGE_JSON` or limiter binding gives `API_ENV_ABUSE_GUARD_MISSING`, and the api fails closed. In development the guard is optional.
- **Broker `challengeVerify`.** This is the fourth `ApiBroker` method: a pre-authentication call under v0 (ADR-0019 item 6). **Inputs.** A configured action, a token with the header's shape, and an integer budget from 1 to 5000. **Call.** One POST to the fixed `https://challenges.cloudflare.com/turnstile/v0/siteverify`, carrying only `secret` and `response`, with `redirect:"error"` and a reply of at most 4096 bytes. **`passed`** requires `success===true`, the configured `hostname`, the expected `action`, and a `challenge_ts` within 300 s plus 30 s of skew. **Anything else** is `failed` and logs `morrow_challenge {code:"failed"}`. Errors are `BROKER_HELD`. **Secret format.** The secret must match `^0x[0-9A-Za-z_-]{20,128}$`. Labs use a synthetic siteverify and need no dummy secret.
- **SPA.** **Widgets.** PR-C adds the hook and an invisible widget (`execution:"execute"`) to PR-1's sign-in screen and to P14.T01a PR-2's create-organization form. **Tokens.** Each POST gets a fresh token, and the widget resets afterwards. **Errors.** On sign-in, `challenge_*` and 429 show the existing "Sign-in couldn't start. Try again in a moment." On signup they show that form's existing errors: "Couldn't save. Nothing was changed." with Try again for `challenge_*`, and the 429 hold. **Allowlist.** `verify:workspace-web` allows only the `api.js?render=explicit` URL. **Journey lab.** The P14 journey lab stubs `window.turnstile` by fulfilling that URL with `context.route` before its abort-all route, so zero aborts still holds.
- **Contracts.** `docs/contracts/identity-authority.md` and the generated contracts gain `/auth/challenge`, `X-Morrow-Challenge` and the three outcomes.

## PR-C implementation notes (P05.T01ab, 2026-10-19)

Branch `claude/p05-t01ab-abuse-guard`, merged with `main` at `890099a` on 2026-10-20 (#18 to #24), ready for its pull request. It implements D5 as written, plus step 0 from the Tier 2 AI review (separate context, same model family). None of the points below weakens a rule; each is a clarification the design left open, a runtime fact or a review fix.

- **Shared matcher.** `managedApiRoute` (in `packages/identity/src/managed-workspace-api.ts`) is now the route table the composed router dispatches by, and the guard selects by the same function. Router behaviour is unchanged. Both compare the exact WHATWG pathname, so `/auth/login/`, `/auth/%6Cogin` and `/organizations/` are not guarded routes, and `/auth/login?x=1` is. P05.T01y's `/auth/rotate` joined the table at the merge with `main` as the class `rotate`: it goes to the workspace handler with logout and is never guarded (`tests/abuse-guard.test.mjs` AC01).
- **Methods and step 0 (review fix).** The guard selects every method the router dispatches to the three routes, HEAD included, but before the limiter it counts only a request its handler could accept on headers alone. Otherwise any third-party page could spend a visitor's bucket, and that of everyone behind the same NAT or IPv6 /56, with requests a browser sends cross-site without a preflight (`<img>` loads, `no-cors` or simple POSTs, preflights), and lock them out of sign-in. **Another method** (GET, HEAD or OPTIONS on login start or signup; anything but GET on the callback) goes uncounted to the router's own 405, as before; it reaches no SQL, and the challenge never applied to it. **A POST without `X-Morrow-Request: 1`** gets the route's own 403 from the guard (`login_unavailable`, or `{"code":"request_denied"}` on signup), with no limit, no broker call and no router. A cross-site page can send that custom header only after a preflight, which the router refuses. **A callback GET that Fetch Metadata marks as no top-level document navigation** (when present, `Sec-Fetch-Mode` other than `navigate` or `Sec-Fetch-Dest` other than `document`, the handler's own rule) gets the handler's own 303 to `/auth/result` from the guard, uncounted. The guard answers the last two itself, so they cannot reach the broker or the router whatever the handlers later accept. A direct client can still send those headers, so real abuse is still counted. D5's "every method" therefore means selected, not counted. The challenge applies only to counted POSTs on login start and signup.
- **503 bodies.** The callback had no 503 body (its failures are 303 `/auth/result`), so login start and the callback both fail closed with the login handler's `login_unavailable` body. Signup uses `{"code":"unavailable"}`.
- **Fail-closed causes.** These are `ADDRESS_MISSING`, `ADDRESS_INVALID`, `LIMITER_FAILED` and `CHALLENGE_HELD`. Two go beyond the packet, and both are stricter. An unparsable `CF-Connecting-IP` fails closed like a missing one. A limiter reply without a boolean `success` counts as a throwing `limit()`. A held or late verification, or any reply that is not a verdict, is `CHALLENGE_HELD`.
- **Redirects.** workerd refuses `redirect: "error"` ("use manual and check the response status code"; measured on Miniflare 4.20260730.0). The broker therefore fetches with `redirect: "manual"` and holds every non-200 reply, 3xx included, so a redirect is never followed. Unit and lab cases cover 302 and 307.
- **Budgets.** The guard gives the broker `challengeBudgetMs` = 3000 ms. The broker bounds its one fetch and the reply read by that budget. The api waits for the RPC for the budget plus 250 ms.
- **Logging.** `morrow_challenge {code:"failed"}` is emitted for `failed` only. A held verification logs the existing broker line `morrow_broker {method:"challengeVerify", code}` (ADR-0007 item 3's single failure path) and the api's `morrow_edge_guard {code:"CHALLENGE_HELD"}`. Other rejections (403, 429) log nothing. The review found that D6 overstated the cap on the `failed` line: it is 15 per minute per IPv4 address or IPv6 /56, across both routes, and nothing caps a client that rotates addresses (D6 now says so). ADR-0019 item 9 said "rejected requests are not logged", and a `failed` verdict is a 403. The line is kept because D6 specifies it and M-O1 needs it as its probe event. **Owner decision (2026-10-19, chat):** asked "Sign-in protection detail: when someone sends a fake bot-check token, we log one line, which costs a fraction of a cent. The per-IP rate limit already caps volume. The staging rules said rejected requests are never logged. Keep this one log line?", the owner answered "Keep it (Recommended)". ADR-0019 item 9 now allows one fixed-code `morrow_challenge {code:"failed"}` line per failed verification, capped by the per-IP limiter, at about $0.60 per 1M lines (ADR-0019, Amendments). M-O1 keeps its probe event.
- **Broker health.** A staging or production broker without a valid Turnstile secret and configuration reports `health()` false. `/healthz` therefore stays honest, and the D2 health gate catches a missing or malformed secret. Development stays healthy without it. The broker's configuration hostname must equal the login origin's hostname. `morrow_broker_init` gains `challenge: <bool>`.
- **Mapper step 10 in production.** P05.T01ab-AC07's production half ("staging or production without the guard gets `API_ENV_ABUSE_GUARD_MISSING`") cannot be reached through `mapApiEnvironment` while ADR-0007 item 9 stands, because production fails earlier, at step 7, with `API_ENV_CROSS_BINDING_MISMATCH`. Step 10 is therefore the pure `mapAbuseGuard(record, environment)`, and its unit test covers production directly, with the staging rule.
- **Configuration route.** `{"provider":"none"}` is exactly ADR-0019 item 7's shape, with no `schemaVersion`. An api that did not map serves `/auth/challenge` like every route of the deny-all instance (503).
- **Site key.** The site key uses the same `^0x[0-9A-Za-z_-]{20,128}$` rule as the secret, so Cloudflare's dummy site keys are refused too.
- **Wrangler.** The api's `ratelimits` are D1's, per environment (7001–7003, 7101–7103, 7201–7203). verify-config requires them exactly (`EDGE_API_RATELIMITS`, `edgeRateLimits`). The broker's `secrets.required` gains `TURNSTILE_SECRET_KEY` in all three environments (ten names, `brokerRequiredSecrets`), and `smoke:edge-dev` expects the three limiter bindings on the api. No `LOGIN_CHALLENGE_JSON` or `TURNSTILE_CONFIGURATION_JSON` var is committed: they carry the site key and the workers.dev host, which are PR-D identifiers. Until PR-D, a staging api would map to `API_ENV_ABUSE_GUARD_MISSING` (fail closed). PR-B touches the same verify-config rules, `_headers` and broker names, so whichever of PR-B and PR-C merges second reconciles them. PR-B's var allowlists must admit the two JSON vars, with byte-equal `actions`.
- **CSP.** The CSP is D1's: `script-src 'self' https://challenges.cloudflare.com`, `frame-src https://challenges.cloudflare.com` and `form-action 'self'`. In the code and HTML of the dist, `verify:workspace-web` allows exactly `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit`, with near-miss negatives. The dist's `_headers` may name the origin `https://challenges.cloudflare.com` only as a CSP source (`allowedCspSources`).
- **SPA.** `useChallenge(action)` (`@morrow/workspace-ui`) and the `ChallengeHost` service serve both guarded forms. `session.startSignIn(workspaceId, challenge?)` and `account.createOrganization(command, challenge?)` send `X-Morrow-Challenge` only when given a token, and the client refuses a malformed one before sending. `identityOutcome` maps a guard 403 `challenge_*` to unavailable (nothing ran) and the guard's 429 to `rate_limited`. The fixture build asks for no challenge, except in the three signup challenge scenarios below.
- **Sign-up widget (D5, after P14.T01a PR-2 merged).** The create-organization form renders the `signup` widget and sends through `useChallenge`, so every POST /organizations, Try again and Check again included, gets a fresh token and resets the widget afterwards. A widget that yields no token sends nothing. Errors use the form's existing copy rather than the sign-in copy: no token and a 403 `challenge_*` show "Couldn't save. Nothing was changed." with Try again, and the action and the values stay (a `challenge_*` is not the terminal `signup_unavailable` refusal); a 429 is the existing hold for `Retry-After` (60 s from the guard). After an unknown outcome, a guard refusal is not a terminal reply, so the signup stays unknown until Check again decodes one.
