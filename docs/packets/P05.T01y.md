## Goal (observable product delta)
**Today:** a browser family lives exactly 15 minutes (`CHECK (expires_at = created_at + interval '15 minutes')`, 0008). Its generation is fixed (`CHECK (current_generation = 1)`, `CHECK (generation = 1)`). Logout retires the family but sends no `Set-Cookie`. Removing someone's organization membership hides that organization only while the membership stays inactive.
**After this packet:**
- An active person stays signed in for up to 12 hours. Each activity-driven `POST /auth/rotate` issues a new generation and cookie, valid for 30 idle minutes but never beyond the family's 12-hour limit.
- Presenting a retired generation revokes the whole family, including when a thief rotated first: the victim's next request leads the client to present its retired generation.
- Logout clears the cookie with `Max-Age=0` and ends only the captured family.
- Removing an organization membership durably signs that person's existing families out of that organization. Removing a workspace membership stops only that workspace.
- Nothing revives a revoked or expired family.

## Design

### 1 Lifecycle model
| Object | Lifetime | Advances by |
| --- | --- | --- |
| Family (`browser_session_families`) | New: `expires_at = created_at + 12 h`. Legacy (0008/0013 rows): `created_at + 15 min`, generation 1; recognised by that shape, never rotated. | Never extended. Revocation is terminal. |
| Generation (`browser_session_generations`) | `expires_at = least(created_at + 30 min, family.expires_at)` | Rotation: retire generation n, issue n+1 |
| Cookie `__Host-morrow_session` | `Max-Age = min(1800, ⌊idleRemainingMs / 1000⌋)` | Only the callback (generation 1) and a committed rotation |

- **Idle activity is rotation.** Workspace and work routes record no session activity (P06.T01a §4.13). A generation older than 60 s may rotate; a younger one returns `current` and nothing is written. With 12 h and 60 s a family reaches at most 721 generations, so the CHECK caps the number at 1000.
- **Reuse detection runs where writes happen:** on `POST /auth/rotate` a non-current generation of a live family revokes it; logout with any generation of a family ends it. Workspace reads deny a retired generation with the same 401 as an unknown cookie and no side effect, and the keeper (§7) answers every such 401 with one rotate, which presents the retired generation and revokes the family.

### 3 Rotation definer algorithm (denials write nothing; only `rotated` and `reuse_revoked` write)
1. `self_session_role_safe()`; otherwise `denied`.
2. Shapes: `p_command` and `p_new_generation` are distinct lowercase UUIDs; digests are hex64 and `p_presented_digest ≠ p_new_digest`; environment, application and client match the 0011 patterns; the profile is a `rid`; `p_request_digest = sha256(json ['morrow.browser.self_rotate','1',command,configuration,'workos',environment,application,client,profile,presented,new,newGeneration])`.
3. **Unambiguous digests:** `p_presented_digest` occurs exactly once across `sessions` and `browser_session_generations` (0011's `count<>1` rule), and `p_new_digest` occurs in neither.
4. Discover only the immutable ownership (the 0011 join): generation by presented digest, then family, binding and profile, matching profile, environment, client and application. No row → `denied`.
5. **Unlocked fast path:** if the presented generation is current and younger than 60 s and `account_session_principal(p_presented_digest)` returns `p_profile`, return `current` with no lock and no write.
6. **Locks** (§9): `browser-provider` advisory; binding, profile, mapping, profile binding and principal `FOR SHARE`; family `FOR UPDATE`; generations (presented, then current) `FOR UPDATE`. Then `instant := clock_timestamp()`.
7. Family or binding revoked → `denied` (no new audit; nothing revives).
8. Presented not current (`g.generation < f.current_generation`): if `f.expires_at > instant` this is **reuse**: insert the `reuse_detected` family audit, set `morrow.browser_revocation_audit`, set the family's `revoked_at`, return `reuse_revoked`. Otherwise `denied`.
9. `denied` if: the current generation is revoked; the generation or family has expired (`expires_at <= instant`); the family has the legacy shape; `f.current_generation = 1000`; `account_session_principal(p_presented_digest)` (re-run under the locks; the single source of family eligibility) returns no row or another profile; step 3 no longer holds.
10. `instant < g.created_at + 60 s` → `current` with the existing expiries, no writes.
11. One subtransaction: insert the `rotated` generation audit (`recorded_at = instant`) and set the setting; retire generation n; advance the family; insert generation n+1 (`created_at = instant`, `expires_at = least(instant + 30 min, f.expires_at)`); restore the setting; late check `clock_timestamp() < ` the new generation's `expires_at`, else raise `MR001`. `MR001` or `unique_violation` (including a reused command id) rolls the subtransaction back and returns `denied`. Return `rotated`.

### 4 HTTP: routes, bodies and cookies (PR-2)
**`POST /auth/rotate`** is routed by `managed-workspace-api.ts` to the workspace handler, as `/auth/logout` is. It uses the guard's single 5 s attempt, the logout pool and the logout configuration (same origin and profile tuple), so `ManagedWorkspaceApiDependencies` keeps its keys. Order: path, method, request proof (exact Origin; `content-type: application/json`; `X-Morrow-Request: 1`; Fetch Metadata same-origin or absent; no `Idempotency-Key`), body `{"schemaVersion":1}` ≤ 256 bytes, then the session cookie under the workspace guard's rules.

| Condition | Status and body | Set-Cookie |
| --- | --- | --- |
| `rotated`, committed, attempt open, Max-Age ≥ 1 | 200 `{"schemaVersion":1,"outcome":"rotated","idleRemainingMs":n,"absoluteRemainingMs":n}` | `__Host-morrow_session=<43 chars>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=<1..1800>` |
| `current` | 200, same shape, `"outcome":"current"` | none |
| `denied`, `reuse_revoked`, Max-Age < 1, or the session cookie absent, duplicated or malformed | 401 `{"code":"authentication_required"}`, byte-identical to workspace routes | none |
| Request-proof, body, path or method failure | 403, 400, 404 or 405 `{"schemaVersion":1,"outcome":"rotation_unavailable"}` | none |
| Failure before the rotate statement is sent | 503 `rotation_unavailable` | none |
| Statement sent, then the reply, COMMIT or deadline is lost | 503 `{"schemaVersion":1,"outcome":"rotation_outcome_unknown"}` | none; no retry, no late delivery |

Remaining times are the SQL expiries minus the attempt clock at delivery (integers 0..43,200,000), so the client needs no absolute clock. Every response is `no-store`, `nosniff` and `no-referrer`.
**Logout** keeps its outcomes and bodies. Only plans produced by the logout dispatcher after its SQL call was invoked carry exactly `SESSION_COOKIE_CLEAR` = `__Host-morrow_session=; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=0`: 200 `session_ended`, 403 SQL `denied`, and the dispatcher's own 503 `logout_outcome_unknown`. Plans before the SQL call (400, 404, 405, request-proof or cookie 403) carry none, so a cross-site request cannot clear the cookie. The fallbacks outside the dispatcher (the `managed-workspace-request.ts` catch and the `auth-http.ts` 503 unknown paths) never carry a cookie, for logout or rotate.
**The fixed-name limitation is documented.** A delayed logout from an old tab, arriving after a new sign-in, revokes only its own family on the server, but its clear also drops the newer cookie in the browser. The newer family then idles out within 30 minutes.
**Cookie confinement:** the managed handler's sinks (logout: `[]` or `[SESSION_COOKIE_CLEAR]`; rotate: one session cookie only with a 200 `rotated` body; `/workspace/*`, `/workspaces`, `/organizations`: none, else held); and `auth-http.ts` `snapshot` (status set +401; `/auth/rotate` bodies exact; session Max-Age `[1-9][0-9]{0,3}` ≤ 1800 only on the callback 303 and a rotate 200 `rotated`; the clear only on `/auth/logout` 200, 403 and 503). The snapshot cannot tell a SQL 403 from a request-proof 403 (same body), so the dispatcher unit tests own "clear only after SQL".
The new secret is a fresh 32-byte CSPRNG value, as at the callback. Only its digest leaves the Worker, and it is delivered once, never on `current`, a denial or an unknown outcome.
**Unknown rotations.** The browser keeps the old cookie. If the rotation committed, the next request gets 401, the keeper's rotate presents the retired generation, and the family is revoked as reuse. At worst the person signs in again; a session is never extended.

### 5 Revocation scopes
- **Organization.** Any membership deactivation, deletion or reassignment writes a watermark. Every family committed before it never again resolves a workspace in that organization, even after the same membership row is reactivated (0001's unique key). The families still work in the person's other organizations; nothing is revoked globally. Families created after the removal resolve the organization only once a membership is active again. T01z's `governance.membership.revoke` and T01aa's SCIM inherit this through the trigger.
- **Workspace.** Unchanged from 0004: `revoke_workspace_access` deactivates the workspace membership, revokes its grants and advances `policy_revision`; `session_eligibility` stops resolving that workspace in every family and generation. No family revocation and no watermark. A later re-add is current authority (T01z).

### 6 Digest-bound flows after a rotation (compatibility)
`revoke_workspace_access` receipts (`actor_session_digest`), linking handoffs and reviews (`session_digest`), the linking apply, and the 0009 lookup and status all bind the generation digest. After a rotation the old digest resolves nothing, so an apply, a revocation execute, a status read, or the reconciliation of an uncertain apply started under generation n fails closed with zero writes; an uncertain apply stays unknown and is never promoted. The person repeats the flow under the new cookie. The ≥ 5-minute keeper cadence makes this rare. **Follow-ups** (in STATUS.md): rebind linking handoffs, reviews and status to the family in P09.T01a/T02a, and the revocation receipt in P05.T01z.

**The keeper.**
- **Activity.** Only user-input handlers (pointer down, key down, focus, `visibilitychange` to visible) call `noteActivity()`. `request()`, `openStream()`, timers, polling and the P06.T02a event transport never count, so an unattended screen idles out.
- **Schedule.** The anchor is the local monotonic time of the last 200 rotate response, or keeper creation. If there was activity since the anchor, the keeper rotates once `now ≥ anchor + 5 min` (at the first activity after creation it rotates at once; the server answers `current` if the cookie is under 60 s old). The effective idle limit is 30–35 minutes after the last activity while rotations succeed.
- **Locks.** Each rotate runs under `locks.request("morrow.session", {mode:"exclusive", signal: AbortSignal.timeout(10000)})`. `request()` holds the same lock in shared mode from send until response headers arrive; `openStream()` (long-poll, event stream) never takes it. A lock timeout skips the rotate until the next activity, or sends the request unlocked. `locks === null` falls back to single-flight within the tab, a documented residual.
- **Rotate fetch.** `keepalive: true`; the keeper never aborts it, so the server's 5 s attempt always ends first and a late `Set-Cookie` still reaches the jar. The keeper waits at most 15 s (`SESSION_ROTATE_WAIT_MS`) for the reply: a stalled reply settles as unavailable, which releases the exclusive lock and the single flight, and a late reply then changes nothing. A 200 body must pass `validateSessionRotationResult(body)` from `@morrow/contracts/validators/SessionRotationResult`, the compiled validator of the effective `SessionRotationResult` (see Implementation notes).
- **401 recovery.** A 401 from `request()` triggers one rotate under the exclusive lock (concurrent 401s share it). A 200 rotate is reused instead only if it settled after the failing request was sent, and within the last 60 s: only then can it explain the 401. Otherwise the rotate presents the cookie, so a retired generation is caught as reuse. On `rotated` or `current` the original request is retried once if its body is replayable (none, string, `ArrayBuffer`, `Blob`, `URLSearchParams`, `FormData`); a second 401 is returned without signing out (the session is valid, so the workspace is unavailable). A rotate 401 calls `onSignedOut()` once.
- **Other rotate replies.** 400, 403, 404, 405, 503 (unavailable or unknown) and an invalid 200 body: no sign-out; no retry before the next activity and at least 60 s. Only a rotate 401 signs out.
- `absoluteRemainingMs` feeds the sign-in warning (P14.T01a).

### 8 Denial and unknown-outcome semantics
- Unknown, ambiguous, foreign or expired digests, a revoked family or binding, ineligible identity, a legacy family, a new-digest collision: SQL `denied`, zero rows written, then 401. Reuse returns the same 401 bytes.
- Logout keeps 0011's semantics, except that a retired generation now ends its family.
- Rotation never retries. An unknown outcome is never promoted to success, and the secret is dropped when the attempt ends.
- Concurrent rotations of one generation serialize on the family lock: one gets `rotated`, the other `reuse_revoked` (ADR-0004 item 1). The keeper's exclusive lock prevents this inside one browser.

### 9 Lock order
- **Rotation.** `browser-provider` advisory → binding, profile, mapping, profile binding, principal (`FOR SHARE`) → family → generations (`FOR UPDATE`). This is the T01x §7 order without the command and `provider-subject` steps; shared locks let families of one profile rotate in parallel, while admission, `lock_session_eligibility` and owner revision updates (`FOR UPDATE`) still serialize against it. Logout (0011) is unchanged.
- **Membership removal.** Organization → membership → principal (`FOR SHARE`, the trigger). Membership writers lock the organization first (the 0008 shared order), which T01z must keep. Rotation and admission take no organization or membership lock; admission takes its principal `FOR UPDATE` before it reads the clock for `created_at`. Tests check the likely interleavings; they cannot prove deadlock freedom.

## Security review checklist
- [ ] Reuse of a retired generation revokes the whole family, irreversibly and with an audit, including when the thief rotates first (AC32). Workspace reads deny retired generations with no side effect; the keeper turns that 401 into a reuse check. Residual: a thief who only reads, against an offline victim, holds a generation that resolves nothing once the victim rotates, and at most 30 idle minutes otherwise.
- [ ] Rotation never passes the absolute limit and never revives anything: enforced in the definer, the insert trigger and the replaced preserve trigger. Legacy-shape families never rotate.
- [ ] Only digests are stored. A new secret is delivered only on a committed `rotated` within the attempt.
- [ ] `Set-Cookie` is confined per route (AC29). The logout clear is sent only by the dispatcher after SQL, so there is no cross-site logout; fallbacks never clear. The fixed-name limitation is documented and tested (AC28).
- [ ] Denials are byte-identical (`authentication_required`), with no oracle distinguishing expired, unknown, ambiguous, foreign and reuse. Every response is `no-store`, `nosniff` and `no-referrer`.
- [ ] **ADR-0007 R1 widens; Tier 2 states it.** `morrow_identity_logout` becomes issuer-class: its password plus any live current-generation digest (from a backup, a Neon branch or PITR, an owner read, or logged bind parameters) mints a bearer with a secret of the attacker's choosing for that family, until its 12-hour expiry or the victim's next request revokes it. Before T01y the role could only end families. This is recorded as an input to the production custody ADR (ADR-0007 item 9). R2 is unchanged. No new leased role.
- [ ] Organization sign-out is a durable, commit-safe watermark (AC14); reactivation never revives an older family. Workspace removal stays scoped to its workspace (ADR-0004 item 4).
- [ ] Lock order matches §9: rotation shares the common rows and locks only its own family and generations exclusively (AC19); membership removal takes organization → membership → principal.
- [ ] Each replaced body differs only in the reviewed lines; no other body keeps the old time predicate (AC20). `session_eligibility` keeps its OID and shape. Fixed `search_path`; no dynamic SQL, caller SQL or `SET ROLE`.
- [ ] Digest-bound linking and revocation flows fail closed after a rotation (AC21); the follow-ups are recorded.
- [ ] The new table has FORCE RLS, is owner-only and immutable, holds no content, has a retention class and an erasure hook (§10).
- [ ] The AI review is labelled "separate context, same model family".

**Required changes (all applied).**
1. **Thief rotates first.** The keeper answers any 401 with one rotate under the exclusive lock, retries once on `rotated`/`current`, and signs out only on a rotate 401 (§1, §7). AC31 covers it; AC32 is the end-to-end case.
2. **Missing cookie.** Rotate reads the cookie under the workspace guard's 401 rules, with identical bytes (§4, AC23). The keeper treats 400 and 403 as unavailable (§7).
3. **Global lock.** Common rows are taken `FOR SHARE`; only the family and generations `FOR UPDATE`; `current` has an unlocked fast path (§3 steps 5–6). AC06 and AC19 cover it.
4. **Watermark race.** The trigger locks the principal `FOR SHARE` before reading the clock; the admission invariant is stated (§2). "Locks nothing" is gone; the order is in §9. AC14 tests both interleavings.
5. **Digest-bound flows.** §6 states the fail-closed behaviour and the P09.T01a/T02a and T01z follow-ups. AC21 covers it.
6. **Old time predicate elsewhere.** AC20 is a catalog closure over `prosrc` in `morrow_identity` and `morrow_work`.
7. **R1.** The checklist now says R1 widens, why, and that it feeds the production custody ADR. Rejected alternative: sending the presented secret instead of its digest would break the invariant that only digests leave the Worker.
8. **Presented-digest ambiguity.** §3 step 3 and AC18.
9. **Retention.** §10 gives classes, erasure hooks, growth and P09.T05 ownership.
10. **Logout clear.** Only dispatcher plans after the SQL call carry the clear; fallbacks never do (§4, AC26, AC29). The snapshot rule is limited to what it can see.
11. **Contracts.** Exact files in Exact outputs; the keeper validates with the generated validator.
12. **Keeper idle behaviour.** User input only; no abort of the rotate fetch; the shared lock ends at headers; streams never take it (§7, AC31).
13. **Dependencies and labs.** The harness and the `work_session_context` half are conditional; the new labs and pgwire use the full chain; the logout labs keep their slice; the oracle and its test are outputs; AC33 allows traffic to the oracle.
14. **Wording.** The step-9 reading cites ADR-0003 §1; IMP-11 cites the takeover brief; "record no session activity" replaces "READ ONLY".

**Optional improvements.** Accepted: (a) as a Coordination request with a stated fallback; (b) `lifetime_policy` dropped, legacy recognised by shape; (c) no rotation table and no command advisory lock; rotation is one generation audit through 0008's revocation branch, plus one family-advance branch; (e) `account_session_principal` is the eligibility source in steps 5 and 9; (f) `request-primitives.ts`; (g) a 5-minute schedule anchored on local monotonic time, with relative remaining times in the body; (h) `{"code":"authentication_required"}`; (i) `recorded_by name`; (j) the current executor set, with a `morrow_work_%` pattern; (k) the Max-Age regex and the 257-byte body; (l) lock timeouts and `keepalive`; (m) the SQL lab joins `pg-core`.
**Rejected: (d) rotation under `morrow_identity_sessions`.** P04.T02a D4 binds one lease purpose per role, and `morrow_identity_sessions` is a login-purpose role. Using it on the workspace route needs a two-purpose role-table change, broker allowlist edits (P04.T02a-AC11), and a new pool in the request-bound pool factory that ADR-0003 §6 freezes. The widening is stated instead and passed to the production custody ADR, which already decides between a permanent lease, a dedicated issuer Worker and a query proxy.

## Implementation notes
- **Per-definition validator export (routine follow-up, 2026-10-19).** The keeper validates a 200 rotate body with `validateSessionRotationResult` from `@morrow/contracts/validators/SessionRotationResult`. The packet first specified `validateCurrentDefinition("SessionRotationResult", body)` from `@morrow/contracts/validation`; Inputs and §7 now name the per-definition module, and `verify:boundaries` rejects the table in UI code (`UI_UNREVIEWED_DEPENDENCY` for the package specifiers, `UI_VALIDATOR_TABLE_IMPORT` for a local path to it, with any script extension, query or hash; the bundle checks in `verify:workspace-web` stay the backstop for transitive imports). It is the same compiled validator for the effective selector `core-v1.1:SessionRotationResult`, generated from the same Ajv instance without the 2.2 MB validator table. The generator emits one such module per name in the closed `browserValidatorDefinitions` list (`scripts/contract-sources.mjs`) and checks each against the table; the UI import allowlist and `verify:workspace-web` keep the table out of browser bundles. With the keeper imported by the production entry, the web entry chunk grows by about 6.8 KB (1.8 KB gzip) instead of 2.16 MB (138 KB gzip). Evidence: `docs/acceptance/P05.md`, AC31 and Notes (PR-2).
