# ADR-0037 Morrow as the main agent with scoped subagents: one agent kind, built by Morrow's team or created by Morrow with a person's approval

- Status: Accepted 2026-10-25 (the owner, OD-2026-10-25-3; see Approval)

- Amends: ADR-0023 decision 1 (the Coordinator line, the owner's addition and "Installable agents") and decision 11d (item 4); ADR-0024 items 1 and 2 (a created agent's mandate; who approves an agent's grants, item 5); ADR-0026 item 4's specialist caps, values unchanged (item 6); ADR-0027 items 1, 2, 3, 6, 9 and 12 where they name specialists, and item 8 (Morrow's tools and `agent.route`); ADR-0029 item 6's "never a specialist at launch"; ADR-0031 item 1's three specialist rows (item 8); ADR-0034 item 2 (`report_in_context` and the specialist step), item 6(a) ("Start check-up"), item 7 (the read-only answer in an Ask) and item 9 (`checkup_done`).

- Does not change: `agent-authority.ts` (`decideDelegation`, `decideAutomation`) and `workspace.task.delegate@1`; ADR-0005 (kill switches stay `human_only`; agents only propose them); ADR-0011's digest-bound approvals and ADR-0027 item 5's taint rule; ADR-0025 item 8, ADR-0030 item 3 and ADR-0031 item 2 (Level 2 customer data and `support.*` stay Support's); ADR-0026 item 4's US$7 and US$25 backstops; ADR-0034 item 8 (@Morrow in a project routes no agent); the Coordinator's exclusion from store reads, proposals, the computer, support tools and customer-tagged context (ADR-0027 item 8).
- Terms: **Morrow** is the Coordinator (`morrow.coordinator`). A **teammate** is any other agent, an installation of either origin (item 4). An **agent card** is an AgentProposal@1 shown in a conversation. **The Owner**, as in ADR-0024.
- Replaces: v1 build order PR 26 ("Specialists"); the follow-up PRs are in `docs/plan/adr-0037-implementation.md`.

## Context

Anthropic's article "Building agents: When to fold subagents into your main agent loop" (Diane Sarkis, 2026-10-22, https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) recommends one agent loop with skills and tools, and separate subagents only for context bloat, parallel fresh contexts, tool-choice or instruction conflicts, verification and modular permissions. A kept subagent should be called like a tool and return a compact result, so the main agent keeps the conversation; a full hand-off is for a subagent that must talk to the user. It starts evals with about 10 golden tasks and compares designs by "which tasks flipped", not only by score.

The agent harness review of 2026-10-25 (a working paper outside the repository) checked Morrow's design against that guidance. Each run is already one loop with tools checked in code (ADR-0027 items 1 to 3). It found three gaps: Morrow must pass even a read question to another agent by a one-way hand-off (`agent.route`, a 2,000-character brief, once per run), so nothing comes back to it; a specialist's report never reaches Morrow (ADR-0027 item 10, ADR-0023 decision 11 "Reports"), so it cannot build on findings; and no eval set exists. It recommended that installed agents stay separate for authority and product reasons (grants, scopes, customer-data level, mandates, caps, notebooks, the name on a proposal; Support never folded), that "ask an agent" return a closed, typed, bounded result as tainting data, and that folds or splits be decided by evals.

The owner chose real subagents (OD-2026-10-25-3) for scoped permissions per subagent, "so they don't accidently execute any things out of there work scope", and for an easy flow of one main agent with teammates. The same split gives least privilege and data isolation per context, and an accountable name on each agent's work. The owner also rejected the specialist as a separate, weaker kind: Morrow should be able to create teammates with the permissions their work needs, approved by the user, so that a built-in agent and one Morrow creates are the same kind. This keeps the owner's original idea of a main agent that creates "a proper subgent with relevenat skill for the task" (OD-2026-10-23-2).

## Decision

1. **Morrow is the main loop and keeps the conversation.** It answers from knowledge and work records, asks clarifying questions, drafts plan cards (ADR-0034) and agent cards (item 4), calls teammates and hands work off (item 3). It does not read store data or draft store changes: its fixed grant set keeps ADR-0027 item 8's exclusions, with `specialist.draft` replaced by `agent.propose` (on `agents.builder.describe`, granting nothing) and one teammate-call tool, `agent.ask` (on `workspace.task.delegate`, like `agent.route`), added. The names are working names; the contracts PR fixes them. Its check stays the asker's live grants ∩ the fixed set ∩ rules and stops.
2. **Every teammate is a scoped subagent.** It is an installation (`kind = 'installed'`) with its own principal, grants, Shopify scopes, caps, model profile, notebook and visible name, and it runs its own `AgentRunWorkflow` loop (ADR-0027 item 1) with its own tool subset and a fresh context per run. Inside a run it uses skills and tools. It never calls, routes to or creates an agent: it never holds `agent.ask`, `agent.route`, `agent.propose`, `workspace.task.delegate` or an `agents.*` capability, and package validation refuses a package that declares one (depth 1). Each of its tool calls runs `decideDelegation` (calls and hand-offs) or `decideAutomation` (mandate runs) over the full intersection: the requester's live grants, the installation's grants, the envelope, connector scopes, live policy and stops, and the installation owner's current authority. A called or handed-off run is a routed run for ADR-0027's purposes: its lease, wall time and turn limit are an installed agent's (items 1 and 6), never a specialist's deadline.
3. **How Morrow uses a teammate.** Wherever `agent.route` is allowed today (ADR-0027 item 8, ADR-0034 item 7), Morrow may do one of these per run at launch, the envelope's one child:
   - (a) **Call it as a tool** (`agent.ask`). Morrow names one active teammate from a code-built list in its opening context and passes a closed brief: an objective of at most 2,000 characters and record ids. Code admits the teammate's run on a child task under the same envelope as `agent.route` (the person who started Morrow's run as requester and authorizer, Morrow as dispatcher, depth 1, one child), without `inbox.ask` or posts to the person, so the teammate cannot talk to the person. The run reads, and outside an Ask creates, only what its grants allow; its proposals carry its name and still need a person's approval of the exact digest. It ends with **TeammateResult@1**: an outcome code, counts, ids of the records it created, closed next-step codes, its read tags and taint, and one summary of at most 2,000 characters, within ADR-0027 item 3's 8 KiB. Code validates it and gives it to Morrow's turn as wrapped data naming its source (ADR-0027 item 5). If the teammate's run consumed untrusted content, Morrow's run becomes tainted, and the taint and its sources carry into every card, task, call or hand-off the run makes afterwards (ADR-0034 item 3). A result with a customer read tag never enters Morrow's context (ADR-0031 items 2 and 6). The call is a durable wait outside Morrow's wall time, and the teammate's run holds its own credits.
   - (b) **Hand off** (`agent.route`), only when the teammate must own the conversation, for example Listings walking the person through product changes. The routed run starts from the person's own request plus Morrow's brief, carries the taint of Morrow's run, owns the child task's thread and may ask the person questions.
   - In a private Ask a call is read-only under the Ask-bound envelope (ADR-0034 item 7), with no hand-off and no agent card; before P05.T04b no agent runs in an Ask.
   - report@1's free text still never enters Morrow's context. TeammateResult@1 carries the typed counts and next-step codes of ADR-0034 item 9, from which code builds `checkup_done`. Morrow may draft a plan or agent card in a turn holding a TeammateResult@1; the card carries the result's taint (this replaces `report_in_context` for typed results).
4. **One agent kind, two origins.**
   - **First-party agents** are AgentPackage@1 releases that Morrow's team builds and publishes with recorded evals and a live-eval digest (ADR-0023 decisions 1 and 10). A person installs one in one click, approving its grants and scopes on the install document (ADR-0024 item 2); stage-and-activate stays (P16.T03).
   - **Workspace-created agents** are drafted by Morrow on the go with `agent.propose`, as an agent card: AgentProposal@1, closed and digested with RFC 8785. The model writes the name, purpose, instructions (role text) and any skill text for this agent, picks first-party skills by id (pinned by digest), and picks tools from the fixed tool catalogue. Code derives and writes the rest from those tools: the exact capability ids and verbs, the Shopify scopes they need, data classes, the store (server-derived), any trigger kinds from the closed list, credit caps and limits (item 6), and the model profile (the workspace's default for new teammates, Opus 5.5 at medium under ADR-0036; a holder of `governance.model_default.revise` may pick another offered entry, which changes the digest and nothing else, ADR-0027 item 12). The model never names a capability, scope, cap, store or model. A card holds no code, URL or credential, and its text never adds a tool or a capability. This amends ADR-0023 decision 11d for this origin only: there is still no skill registry, no skill tool and no skill shared between workspaces.
   - **Created only by a person's approval of the exact card.** "Add to team" opens a server-built document bound to the card's digest, the actor and a standalone-workspace session, valid for 5 minutes and consumed once. One idempotent transaction rebuilds the card from live grants, scopes and rules (`stale` on any change), checks the approver (item 5), and creates the workspace package, a fresh principal, the installation (owned by the approver), its grants and caps, its 90-day mandate when the card names triggers (ADR-0024 items 1 and 2), and an audit record. Approving the exact card replaces stage, sample and activate for this origin, as ADR-0028 item 5 did for specialists: a card holds no code, its tools are the reviewed catalogue's, and every external effect still needs a digest-bound approval at the gateway.
   - **Edits and later changes.** Before approval a person may change the name, purpose and instructions, remove tools, triggers or grants, or lower caps; each edit is a new revision with the editor and a new digest that keeps the card's taint (ADR-0024 item 8). Any later addition of grants, tools, scopes or triggers, any change to instructions or skills, and any raised cap is a new card and a new approval; runs in flight keep the revision their admission pinned. A person may remove a grant, pause the agent (`agents.installation.disable`, `human_only`) or remove it at any time.
   - **Plan steps.** A plan card's step names an active teammate or "a new teammate" with only a title and purpose, so `agent.propose` stays the only card drafter. Tapping a new-teammate step starts one Morrow run limited to `knowledge.search`, `work.read`, `message.post` and `agent.propose` for that step; the step becomes a ready agent step (ADR-0034 item 6(b)) once its card is approved. "Start check-up" becomes "Add to team".
   - **The same in every other way.** Both origins have the same runtime, tool catalogue, authority checks, stops, holds and caps, workspace rules (a Never on any agent for a class binds every agent), notebooks, retention, model and effort choice, and place on the Team page. The Team page shows one list of teammates under Morrow, each with its provenance: "Built by the Morrow team", or "Made by Morrow" with the date and the person who approved it.
5. **Guardrails.**
   - **Morrow proposes, people approve.** Only a person approves an agent card or a later change, holding `agents.installation.activate` (`human_only`). No agent, Morrow included, approves a card, a grant or a change.
   - **No grant beyond the approver's own.** The approver holds each capability on the card with its verbs and `delegate` under live grants (ADR-0024 item 2's `amplification_denied`; ADR-0025 item 7).
   - **The Owner, for four kinds of grant.** A card that holds a capability with a store effect (an `external_write` capability, even with the `propose` verb only), reads orders or customer data, is in the spend class (discounts, or caps above the rate card's defaults) or the communication class (messages to customers) needs the Owner, even when another member holds those grants. At launch the Owner is in practice the only approver, since store grants belong to the founding principal (ADR-0022 item 3).
   - **The fixed catalogue only.** Never on a card: `human_only` capabilities, `workspace.task.delegate`, `agents.*`, `agent.ask`, `agent.route` or `agent.propose`. At launch also never Level 2 customer data or `support.*`, which stay Support's (ADR-0025 item 8, ADR-0030 item 3); ADR-0023 decision 6's rule that a package may not declare both customer reads and the computer holds.
   - **Taint is shown and kept.** A card drafted in a run that consumed untrusted content says so above "Add to team" and lists its sources. The created agent's instructions keep that taint, so each of its runs starts tainted and every proposal from them needs a person's approval of its exact digest (ADR-0027 item 5). Approval never clears taint.
   - **Depth 1.** Only Morrow drafts agent cards; agents cannot create agents (item 2).
   - **Lifetime and number.** A workspace-created agent stays until a person removes it. Morrow may suggest removing one that has not run for 30 days, and never pauses or removes one itself. At most 10 active workspace-created agents per workspace at launch.
   - **Titles never confer authority.** A teammate's name, title, purpose or instructions, and Morrow's calls and hand-offs, confer nothing. Only a person's approval of exact grants does, and every tool call still checks the intersection in code.
6. **Money.** Every run reserves its hold at admission and settles at metered use (ADR-0026 item 4); a teammate's run holds its own credits and counts toward the US$25 daily backstop, and the US$7 per-run backstop binds every run. ADR-0026 item 4's specialist caps carry over to workspace-created agents with their values unchanged: at most 5% of the monthly grant per run, and 20% per workspace per day across them. Per-installation daily and monthly caps apply to both origins. Only the Owner raises a cap.
7. **What stays from ADR-0028.** The server-built, single-use document bound to actor, session and digest (item 3, now for "Add to team"); one idempotent transaction that rebuilds from live facts, checks the approver's grants with `delegate`, creates the principal, installation and grants, and writes the audit record (item 4 (a), (c), (e) and (i), with a general grant issuer in place of item 2's); a check before every tool call that the release or package is unrevoked and the switches are on (item 6, without its clock or deadline); workspace rules binding every agent (item 7); a workspace setting, "Let Morrow suggest new teammates", on by default once the platform switch is on, which the Owner may turn off (its owner question 1, answered (a)), and a platform switch committed off (item 8); deletion through ADR-0031's one registry (item 9). Retired: the `task_specialist` kind and the `morrow.specialist` release, the Specialist ceiling and `work_specialist_grants_issue`, the Start card, the 24-hour clock, the 1-hour and 8-hour deadlines, and the limits of 1 running per task and 2 per workspace.
8. **Data.** ADR-0031 item 1's specialist rows map to the new records on the same clocks: agent cards and their revisions, 90 days after approval, dismissal or expiry (for "Specialist specs"); "Add to team" documents, 24 hours after use or expiry (as "Start documents"); a removed agent's principal, installation, grants, envelopes and hops, kept content-free while a run, manifest or proposal references them and at the latest until `shop/redact`, uninstall or erasure, never deleted while a gateway operation that references them is unsettled (ADR-0031 owner question 1 (a)). A workspace-created agent's instructions and skill text are kept while it is on the team and deleted with its notebook and run turns when it is removed (ADR-0031 item 3). Each class gets its deletion handler in the PR that first writes it (G9).
9. **Switches and delivery.** Contracts with fakes come first. Agent cards, teammate calls and the Team change ship behind default-off switches, replacing `docs/decisions/specialists-staging.json`; none goes on before G9 and G10, the agent-loop switch (ADR-0027 item 11) and a passing eval round (item 10).
10. **Evals before folding or splitting.** A golden set of 10 to 16 tasks from the owner's store (the harness review's draft), each run at least twice, graded first by checks in code (tools called, forbidden tools absent, end code, cost, digest-bound proposals, no external effect), then by a rubric, with the owner's spot checks. Designs are compared task by task (which tasks flipped), not only by totals. The set settles a call against a hand-off, when Morrow should create an agent rather than call one, and any later fold or split of first-party agents (Analyst with Inventory first), each by its own ADR. Cases point at store objects by Morrow ids in the deployed environment; the repository holds case ids and rubrics only. Live rounds run under ADR-0035's standing approval and the caps; raising the daily backstop for eval days is the owner's decision.

## Security invariants touched

None is weakened. A workspace-created agent gains no authority that a person with those grants did not approve on its exact card.
- **Tenancy; no client-supplied ids:** cards, documents and packages are FORCE RLS tables; the store and every id come from server facts (`lab:tenant-conformance`, a new `lab:agent-cards`).
- **The intersection, in code at every tool call:** unchanged kernel; new `lab:agent-authority-workers` rows deny a teammate call or a created agent's run when any term fails, and refuse `agent.*` tools and `workspace.task.delegate` to every teammate (`agent-package.test.mjs`, `tool-catalogue.test.mjs`).
- **Digest-bound approvals:** an edited card, a stale card or a reused, expired or foreign document is refused; a tainted card stays tainted after approval (`lab:agent-cards`, `approval-records.test.mjs`).
- **Who approves:** an agent, a non-holder, a holder without `delegate` and a non-Owner for the four Owner-only kinds are refused (`lab:agent-cards`).
- **Untrusted content:** TeammateResult@1 is closed and wrapped, taints Morrow's run, and never carries customer-tagged data to Morrow (`lab:agent-runs`).
- **Budgets in code; `human_only` stops; default deny; immutable migrations:** `lab:run-credits`, `stops.test.mjs`, `edge:check`, `migration-history.test.mjs`.

## Consequences

- **Code.** Contracts: AgentProposal@1 and its "Add to team" document, TeammateResult@1, and AgentPackage@1 generalised for workspace-authored packages (an `origin`, instruction and skill text) or a successor version; `agent.ask` and `agent.propose` in a new tool catalogue version; SpecialistSpec@1, SpecialistStartDocument@1 and the Specialist ceiling retired. SQL: an origin on installations, workspace packages, card revisions and documents, and a general grant issuer with the exclusions of item 5 (an authority packet). The agent loop (PR #64): the teammate call as a durable step with a typed result. Morrow (v1 build order PR 12): the new tools and a code-built list of active teammates in its opening context. The Team page: one list with provenance, the card, change cards and removal. Data: the rows of item 8. Projects: a plan step names a teammate or a new one (ADR-0034 item 6(a)), and migration 0046's `specialist` assignee kind is mapped by a forward migration. Graph and plan docs follow (`AG-specialist`, `IK-task-specialist`, `F-specialists`, `F-agent-builder`, `mvp.md`, `v1-build-order.md`). The order and sizes are in `docs/plan/adr-0037-implementation.md`.
- **Scope.** A slice of P16.T02 (the agent builder) comes into launch: Morrow drafts an agent from the fixed catalogue; the full builder, merchant-written skills and a registry stay after launch.
- **Cost.** A teammate call adds a model run: about US$0.46 expected for Morrow's run (ADR-0027 item 12) plus about US$0.56 for an expected six-turn teammate run at Opus 5.5 medium (ADR-0036), against a hand-off's similar total with no answer back to Morrow. The controls are one call or hand-off per run at launch, the per-run and daily backstops, item 6's caps, caching of the conversation (an owner decision still open), and evals that show when a call pays.
- **Risks.** Model-written instructions are not evaluated before use; provenance, taint, the person's approval, the catalogue and the gateway contain them. A summary written by an injected teammate can mislead Morrow; Morrow has no effect tools and its cards and tasks carry the taint. Agent sprawl is limited by the cap of 10 and the idle suggestion.
- **Open items from the harness review** that this record does not decide: per-person memory (none at launch; knowledge pages instead), the notebook read-back path and taint on notebook entries (PR #68), a graceful final turn near the input cap and later compaction, caching the growing conversation, a skill size budget and an on-demand `skill.read`, who may hold `workspace.question.request` (PR #64), and whether `run_turns` becomes a customer-content class before Support.
- **Values written to carry out the decision,** which await the owner's confirmation with the contracts PR: one call or hand-off per Morrow run; the 2,000-character brief and summary; the 30-day idle suggestion; the limit of 10 created agents; item 6's carried-over caps.

## Alternatives considered

- **Keep specialists as a separate, run-scoped, weaker kind (ADR-0028).** The owner rejected two kinds and the weak ceiling.
- **One main agent with skills and tools only.** Loses per-agent scoped permissions, Support's data isolation and an accountable name on each proposal; evals may still fold particular pairs.
- **Let Morrow read store data itself.** Not taken: Morrow stays without store access, and teammates read under their own grants.
- **Agents that create or call agents.** Authority chains and sprawl; depth stays 1.
- **One standing specialist principal per workspace** (rejected by ADR-0023). Still rejected: each created agent has its own principal and grants.
- **Morrow approves low-risk grants.** No: people approve every grant.

## Approval

The owner's statements in chat, verbatim, on 2026-10-25 (OD-2026-10-25-3). During the lead's review of the agent harness against the article cited under Context:

> okay but i think our subagent approach is better even for speciality agents because we can have per subagent scoped persmissions so they don't accidently execute any things out of there work scope and why we separating specialists with the installed agents? like suppose morrow created a specialist agent it should be shown as new teammate just like other subagents this way we have a easy to understand flow a main agent and then subagents just like grok bot/dots/claude duet etc. but I am thinking that is scoped permission a valid reason for going with real subagents architecture instead of main agent with skills and tool calls acrchitecture(but in UI/UX it will be shown as subagent so its easier for user to understand the flow )

Then, after asking "so what do you suggest subagents or main agent with skills and tool calls?" and reading the lead's recommendation of a main agent with scoped subagents (Morrow keeps the conversation and does not touch store data or draft store changes; every teammate a real subagent with its own loop, tools, permissions and context, never spawning subagents; a teammate called like a tool with a short structured result, a full hand-off only when it must talk to the person; small evals on the owner's real tasks):

> okay your recommendation seems good now i don't like the specialist as seperate weak permissioned one, morrow should be able to deploy subagents with as much permission as required but that permission should be approved by the user, this way we don't have 2 seperate types of subagents (installed & speciality) both are same, its just one is already built by our team and can be one click installed by user in there sysytem other is created on the go by the main agent

What it approves: the recommendation (items 1 to 3 and 10) and the one agent kind with two origins in place of the specialist kind (item 4).

Written from it: item 5's guardrails, which the lead told the owner in reply would be written in; items 6 to 9, which carry the decision into the money, ADR-0028, data and switch records without changing a value or a clock; the amendments named in the header; and the values listed under Consequences, which await the owner's confirmation.
