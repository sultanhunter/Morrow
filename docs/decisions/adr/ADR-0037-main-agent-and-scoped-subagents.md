## Context

Anthropic's article "Building agents: When to fold subagents into your main agent loop" (Diane Sarkis, 2026-10-22, https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) recommends one agent loop with skills and tools. It keeps separate subagents for three cases (context bloat, parallel fresh contexts, tool-choice or instruction conflicts), lists verification and modular permissioning among subagents' strengths, and notes that per-user permissions can also be checked inside tools in one loop. A kept subagent should be called like a tool and return a compact result, so the main agent keeps the conversation; a full hand-off is for a subagent that must talk to the user. It starts evals with about 10 golden tasks and compares designs by "which tasks flipped", not only by score.

The agent harness review of 2026-10-25 (a working paper outside the repository) checked Morrow's design against that guidance. Each run is already one loop with tools checked in code (ADR-0027 items 1 to 3). It found three gaps: Morrow must pass even a read question to another agent by a one-way hand-off (`agent.route`, a 2,000-character brief, once per run), so nothing comes back to it; a specialist's report never reaches Morrow (ADR-0027 item 10, ADR-0023 decision 11 "Reports"), so it cannot build on findings; and no eval set exists. It recommended that installed agents stay separate for authority and product reasons (grants, scopes, customer-data level, mandates, caps, notebooks, the name on a proposal; Support never folded), that "ask an agent" return a closed, typed, bounded result as tainting data, and that folds or splits be decided by evals.

The owner chose real subagents (OD-2026-10-25-3) for scoped permissions per subagent, "so they don't accidently execute any things out of there work scope", and for an easy flow of one main agent with teammates. The same split gives least privilege and data isolation per context, and an accountable name on each agent's work. The owner also rejected the specialist as a separate, weaker kind: Morrow should be able to create teammates with the permissions their work needs, approved by the user, so that a built-in agent and one Morrow creates are the same kind. This keeps the owner's original idea of a main agent that creates "a proper subgent with relevenat skill for the task" (OD-2026-10-23-2).

The lead then put this record's listed values to the owner. The owner asked for a "truty multi agent system" in which Morrow orchestrates teammates in any way rather than one call per request, for structured results without a character cap that "might strip important information", and for credits as the only spend limit, with no hardcoded money caps; the other values as recommended (OD-2026-10-25-4).

## Decision

1. **Morrow is the main loop and keeps the conversation.** It answers from knowledge and work records, asks clarifying questions, drafts plan cards (ADR-0034) and agent cards (item 4), calls teammates and hands work off (item 3). It does not read store data or draft store changes: its fixed grant set keeps ADR-0027 item 8's exclusions, with `specialist.draft` replaced by `agent.propose` (on `agents.builder.describe`, granting nothing) and two tools added: the teammate call, `agent.ask` (on `workspace.task.delegate`, like `agent.route`), and `agent.result.read`, which opens an item that a teammate's result references (item 3(a)) and grants nothing else. The names are working names; the contracts PR fixes them. Its check stays the asker's live grants ∩ the fixed set ∩ rules and stops.
2. **Every teammate is a scoped subagent.** It is an installation (`kind = 'installed'`) with its own principal, grants, Shopify scopes, model profile, notebook and visible name, and it runs its own `AgentRunWorkflow` loop (ADR-0027 item 1) with its own tool subset and a fresh context per run. Inside a run it uses skills and tools. It never calls, routes to or creates an agent: it never holds an `agent.*` tool (`agent.ask`, `agent.result.read`, `agent.route`, `agent.propose`), `workspace.task.delegate` or an `agents.*` capability, and package validation refuses a package that declares one (depth 1). Each of its tool calls runs `decideDelegation` (calls and hand-offs) or `decideAutomation` (mandate runs) over the full intersection: the requester's live grants, the installation's grants, the envelope, connector scopes, live policy and stops, and the installation owner's current authority. A called or handed-off run is a routed run for ADR-0027's purposes: its lease, wall time and turn limit are an installed agent's (items 1 and 6), never a specialist's deadline.
3. **How Morrow uses teammates: orchestration in any way** (OD-2026-10-25-4). Wherever `agent.route` is allowed today (ADR-0027 item 8, ADR-0034 item 7), Morrow may use as many teammates as the work needs in one run. It may call teammates and hand work off, in sequence or in parallel (several calls in one turn, within ADR-0027 item 6's tool calls per turn), call the same teammate more than once (each call a fresh run, item 2), and pass the records one call returns to the next. There is no limit of one call or hand-off per run. A run's calls are bounded only as any run is: by its stop conditions (the turn and tool-call limits and the wall time of ADR-0027 item 6, as ADR-0039 amends it), the credits in the workspace's balance (item 6) and a person's stop, plus the delegation kernel's existing bound of 32 children per envelope, which is unchanged; a call past that bound is refused with a code, as one the balance cannot cover is. Each call or hand-off is one child under Morrow's envelope at depth 1, admitted and checked in code on its own, exactly as the first: the child run's tool calls run the full intersection (item 2), and a teammate never calls, hands off to or creates an agent.
   - (a) **Call it as a tool** (`agent.ask`). Morrow names one active teammate from a code-built list in its opening context and passes a structured brief: an objective, record ids (result items included) and typed fields, with no character cap; long material goes by record id. Code admits the teammate's run on a child task under the same envelope as `agent.route` (the person who started Morrow's run as requester and authorizer, Morrow as dispatcher, depth 1), without `inbox.ask` or posts to the person, so the teammate cannot talk to the person. The run reads, and outside an Ask creates, only what its grants allow. It opens a result item named in its brief only when code finds that the item belongs to a result the calling Morrow run received, the same check as `agent.result.read` (below), and then only under its own grants and the item's read tags; any other record named in its brief it opens only as its own grants, the record's read tags and the requester's visibility allow, so another member's private Ask stays closed to it (ADR-0016 item 5). A model-written id is never authority to read. An item's taint carries into its run. Its proposals carry its name and still need a person's approval of the exact digest. It ends with **TeammateResult@1**, structured, with no character cap: an outcome code, counts, ids of the records it created, closed next-step codes, its read tags and taint, a summary and typed findings.
     - **Nothing is cut.** A summary, finding or table too large for one tool result (ADR-0027 item 3's 8 KiB, unchanged), and every file, is stored as a **result item**: a FORCE RLS record that names the run that produced it and holds its read tags and taint, shown in the result by id, kind, size and title. Morrow opens an item in full with `agent.result.read`, page by page when it is larger than one tool result, so Morrow takes in what it needs and its context does not overflow. Code opens an item for Morrow only when it belongs to a result that Morrow's own run received, and for a called or handed-off teammate only when it belongs to a result that the calling Morrow run received and is named in the teammate's brief (new `lab:agent-runs` cases: Morrow and a teammate each refused an item from another run, and a teammate refused an item from another person's private Ask).
     - **Wrapped, tainting data.** Code validates the result and gives it to Morrow's turn as wrapped data naming its source (ADR-0027 item 5), and each opened item the same way. If the teammate's run consumed untrusted content, Morrow's run becomes tainted, and the taint and its sources carry into every card, task, call or hand-off the run makes afterwards (ADR-0034 item 3). A result or item with a customer read tag never enters Morrow's context (ADR-0031 items 2 and 6).
     - **Credits and time.** Each call is a durable wait outside Morrow's wall time, and the teammate's run holds its own credits from the workspace's balance. A call is admitted only if its hold fits at once: a call the balance cannot cover, or one that would wait for credits (ADR-0026 item 3 (e)), returns a refusal code to Morrow at once, and Morrow may go on with what it has. A called run cannot ask the person, so it has no waits of its own, and its 30-minute wall time bounds Morrow's wait for it.
     - **Morrow's lease while it waits.** Morrow's run records its wait as naming its open child runs (several, for parallel calls), and the stale-run sweep (ADR-0027 item 1) skips a run whose recorded wait names an open child run. In the same transaction as the terminal commit of the last open child run that the wait names, by any path (a stop or the sweep's close of the child included), and under a lock on the parent run so that exactly one of two commits that end together does it, an ids-only definer executable only by `morrow_runtime_executor` re-issues the parent run's 30-minute lease after re-running admission's checks: the requester's live grants, the Coordinator's fixed set, rules, stops and switches. If any fails, the parent run ends instead. It is the lease source for a resume after calls, as the answer command is after a question and `admit_mandate_run` for a mandate run (ADR-0027 item 1) (new `lab:agent-runs` cases: Morrow's lease lapsing mid-call, a grant revoked mid-call, a stop mid-call, the sweep running mid-call, two parallel calls ending in either order or together, and the same teammate called twice).
   - (b) **Hand off** (`agent.route`), only when the teammate must own the conversation, for example Listings walking the person through product changes. The routed run starts from the person's own request plus Morrow's brief, structured as in (a) and opened under (a)'s checks, carries the taint of Morrow's run, owns the child task's thread and may ask the person questions. A hand-off returns nothing to Morrow's run, which may go on calling teammates or hand other work to others, each hand-off on its own child task.
   - In a private Ask, calls are read-only under the Ask-bound envelope (ADR-0034 item 7), as many as the work needs, with no hand-off and no agent card; a new teammate comes only from a plan card's step (item 4, owner-confirmed in OD-2026-10-25-4). Before P05.T04b no agent runs in an Ask.
   - report@1's free text still never enters Morrow's context. TeammateResult@1 carries the typed counts and next-step codes of ADR-0034 item 9, from which code builds `checkup_done`. Morrow may draft a plan or agent card in a turn holding one or more TeammateResult@1; the card carries their taint (this replaces `report_in_context` for typed results).
4. **One agent kind, two origins.**
   - **First-party agents** are AgentPackage@1 releases that Morrow's team builds and publishes with recorded evals and a live-eval digest (ADR-0023 decisions 1 and 10). A person installs one in one click, approving its grants and scopes on the install document (ADR-0024 item 2); stage-and-activate stays (P16.T03). A first-party package keeps its release's reviewed grant set and its own issuer: item 5's card exclusions apply only to packages with `origin = workspace`, so Support keeps `support.*` and Level 2 customer data (ADR-0030 item 3), and the Listings issuer of migration 0031 is unchanged.
   - **Workspace-created agents** are drafted by Morrow on the go with `agent.propose`, as an agent card: AgentProposal@1, closed and digested with RFC 8785. The model writes the name, purpose, instructions (role text) and any skill text for this agent, picks first-party skills by id (pinned by digest), and picks tools from the fixed tool catalogue. Code derives and writes the rest from those tools: the exact capability ids and verbs, the Shopify scopes they need, data classes, the store (server-derived), any trigger kinds from the closed list, an installed agent's run limits (ADR-0027 item 6; no money cap, item 6), and the model profile (the workspace's default for new teammates, which is the former specialist profile, Opus 5.5 at medium by default under ADR-0027 item 12; a holder of `governance.model_default.revise` may pick another offered entry, which changes the digest and nothing else, ADR-0027 item 12). The model never names a capability, scope, limit, store or model. A card holds no code, URL or credential, and its text never adds a tool or a capability. This amends ADR-0023 decision 11d for this origin only: there is still no skill registry, no skill tool and no skill shared between workspaces.
   - **Created only by a person's approval of the exact card.** "Add to team" opens a server-built document bound to the card's digest, the actor and a standalone-workspace session, valid for 5 minutes and consumed once. Confirming it is the request: an access change bound to the card's digest, which then passes the review of item 5 (the solo Owner's phrase and cool-down, or a second member). When it passes, one idempotent transaction rebuilds the card from live grants, scopes and rules (`stale` on any change), re-checks the requester and the approver (item 5), and creates the workspace package, a fresh principal, the installation (owned by the requester), its grants, its 90-day mandate when the card names triggers (ADR-0024 items 1 and 2), and an audit record. For this origin the exact card replaces P16.T03's provisional revision and sample, because a card holds no code, its tools are the reviewed catalogue's and every external effect still needs a digest-bound approval at the gateway. Unlike ADR-0028 item 5, it does not replace the review gate: `agents.installation.activate` stays `review_required`, and nothing here removes a second reviewer.
   - **Edits and later changes.** Before approval a person may change the name, purpose and instructions, or remove tools, triggers or grants; each edit is a new revision with the editor and a new digest that keeps the card's taint (ADR-0024 item 8). Any later addition of grants, tools, scopes or triggers, and any change to instructions or skills, is a new card and a new approval under the same review; runs in flight keep the revision their admission pinned. A person may pause the agent at any time (`agents.installation.disable`, a `human_only` kill switch with no second approver, ADR-0005); removing a grant or the agent keeps its own review rule (ADR-0011 Q3 and Q4).
   - **Plan steps.** A plan card's step names an active teammate or "a new teammate" with only a title and purpose, so `agent.propose` stays the only card drafter. Tapping a new-teammate step starts one Morrow run limited to `knowledge.search`, `work.read`, `message.post` and `agent.propose` for that step; the step becomes a ready agent step (ADR-0034 item 6(b)) once its card is approved. "Start check-up" becomes "Add to team".
   - **The same in every other way.** Both origins have the same runtime, tool catalogue, authority checks, stops and run limits, credit holds, workspace rules (a Never on any agent for a class binds every agent), notebooks, retention, uploads (ADR-0029 item 6, as amended: in a sandbox, as the uploader's tags allow, and only with the computer tools; owner-confirmed in OD-2026-10-25-4), model and effort choice, and place on the Team page. The Team page shows one list of teammates under Morrow, each with its provenance: "Built by the Morrow team", or "Made by Morrow" with the date and the person who approved it.
5. **Guardrails.**
   - **Morrow proposes, people approve.** Only a person requests or approves an agent card or a later change, holding `agents.installation.activate` (`human_only`, `review_required`). No agent, Morrow included, approves a card, a grant or a change.
   - **The access-change gate stays** (owner-confirmed in OD-2026-10-25-4). Approving a card, or a later change that adds anything, issues grants and may issue a mandate, so it is a `control` effect reviewed as access_change (ADR-0011 Q7 and Q9). The person who confirms "Add to team" is its requester and will own the agent, so they are conflicted, as are the card's editors (ADR-0011 Q1). A solo Owner (ADR-0011 Q2) passes only with the exact confirmation phrase and the 300-second cool-down, which they may cancel (ADR-0011 Q3). In a team, a second member who is not conflicted approves; the Owner approves alone only on the terms ADR-0024 item 2 sets for an installed agent's mandate, while no other member holds the card's store grants (ADR-0024 owner question 1 (b)). A lighter gate, such as one tap for the Owner, would need its own ADR.
   - **No grant beyond one's own.** The requester and the approver each hold every capability on the card with its verbs and `delegate` under live grants (ADR-0024 item 2's `amplification_denied`; ADR-0025 item 7), and the approver also holds ADR-0011 Q5's reviewer verbs.
   - **The Owner, for four kinds of grant.** A card that holds a capability with a store effect (an `external_write` capability, even with the `propose` verb only), reads orders or customer data, is in the spend class (for example discounts) or the communication class (messages to customers) needs the Owner as its requester or its approver, even when another member holds those grants. At launch the Owner is in practice the only person who can request or approve such a card, since store grants belong to the founding principal (ADR-0022 item 3).
   - **The fixed catalogue only.** Never on a card: `human_only` capabilities, `workspace.task.delegate`, `agents.*` or any `agent.*` tool (`agent.ask`, `agent.result.read`, `agent.route`, `agent.propose`). At launch also never Level 2 customer data or `support.*`, which stay Support's (ADR-0025 item 8, ADR-0030 item 3; owner-confirmed in OD-2026-10-25-4); ADR-0023 decision 6's rule that a package may not declare both customer reads and the computer holds.
   - **Taint is shown and kept.** A card drafted in a run that consumed untrusted content says so above "Add to team" and lists its sources. The created agent's instructions keep that taint, so each of its runs starts tainted and every proposal from them needs a person's approval of its exact digest (ADR-0027 item 5). Approval never clears taint.
   - **Depth 1.** Only Morrow drafts agent cards; agents cannot create agents (item 2).
   - **Lifetime and number.** A workspace-created agent stays until a person removes it. Morrow may suggest removing one that has not run for 30 days, and never pauses or removes one itself. At most 10 active workspace-created agents per workspace at launch. Both values are owner-confirmed (OD-2026-10-25-4).
   - **Titles never confer authority.** A teammate's name, title, purpose or instructions, and Morrow's calls and hand-offs, confer nothing. Only a person's approval of exact grants does, and every tool call still checks the intersection in code. Morrow stays separate from the optional Chief of Staff and CMO installations (ADR-0023 decision 1).
6. **Money: credits only** (OD-2026-10-25-4; ADR-0039 records the rule for every run). Every run, a teammate's run of either origin and each of Morrow's calls included, reserves and draws credits from the workspace's balance as it works and settles at metered use (ADR-0026 items 4 and 5); when the balance cannot cover its next step, the work stops, and a call the balance cannot cover is refused at once (item 3(a)). This record sets no money cap: ADR-0026 item 4's specialist caps (5% of the monthly grant per run, 20% per workspace per day) retire with the specialist kind and do not carry over to workspace-created agents, and no per-agent, per-call or per-day money ceiling replaces them. The fixed money caps of ADR-0026 item 4 and ADR-0036 go by ADR-0039; the owner's Anthropic monthly limit stays outside Morrow as the backstop. The non-money stops stay: each run's turn and tool-call limits and wall time (ADR-0027 item 6), and a person may stop any run at once. Settings the Owner controls, such as a model ceiling, stay settings, not money caps.
7. **What stays from ADR-0028.** The server-built, single-use document bound to actor, session and digest (item 3, now for "Add to team"); one idempotent transaction that rebuilds from live facts, checks the requester's and the approver's grants with `delegate`, creates the principal, installation and grants, and writes the audit record (item 4 (a), (c), (e) and (i), with an issuer for workspace-created agents in place of item 2's, for `origin = workspace` only); a check before every tool call that the release or package is unrevoked and the switches are on (item 6, without its clock or deadline); workspace rules binding every agent (item 7); a workspace setting, "Let Morrow suggest new teammates", on by default once the platform switch is on, which the Owner may turn off (its owner question 1, answered (a)), and a platform switch committed off (item 8); deletion through ADR-0031's one registry (item 9). Retired: the `task_specialist` kind and the `morrow.specialist` release, the Specialist ceiling and `work_specialist_grants_issue`, the Start card, the 24-hour clock, the 1-hour and 8-hour deadlines, and the limits of 1 running per task and 2 per workspace.
8. **Data.** ADR-0031 item 1's specialist rows map to the new records on the same clocks: agent cards and their revisions, 90 days after approval, dismissal or expiry (for "Specialist specs"); "Add to team" documents, 24 hours after use or expiry (as "Start documents"); a removed agent's principal, installation, grants, envelopes and hops, kept content-free while a run, manifest or proposal references them and at the latest until `shop/redact`, uninstall or erasure, never deleted while a gateway operation that references them is unsettled (ADR-0031 owner question 1 (a)). A workspace-created agent's instructions and skill text are kept while it is on the team and deleted with its notebook and run turns when it is removed (ADR-0031 item 3). Result items (item 3(a)) are run content: they keep the read tags of the run that produced them and its `run_turns` clock, 90 days from that run's end, and are deleted with its turns. Each class gets its deletion handler in the PR that first writes it (G9).
9. **Switches and delivery.** Contracts with fakes come first. Agent cards, teammate calls and the Team change ship behind default-off switches, replacing `docs/decisions/specialists-staging.json`; none goes on before G9 and G10, the agent-loop switch (ADR-0027 item 11) and a passing eval round (item 10). **Slip rule** (in place of ADR-0023 decision 11's): if G11 is missed, or the agent-card authority packet is not merged by G18's date (2026-12-04), agent cards move to the first fast follow, and nothing for them starts in W7 to W10; teammate calls and hand-offs to first-party agents stay. G18 is retitled for the agent-card authority packet.
10. **Evals before folding or splitting.** A golden set of 10 to 16 tasks from the owner's store (the harness review's draft), each run at least twice, graded first by checks in code (tools called, forbidden tools absent, end code, cost, digest-bound proposals, no external effect), then by a rubric, with the owner's spot checks. Designs are compared task by task (which tasks flipped), not only by totals. The set settles a call against a hand-off, when parallel or repeated calls pay, when Morrow should create an agent rather than call one, and any later fold or split of first-party agents (Analyst with Inventory first), each by its own ADR. Cases point at store objects by Morrow ids in the deployed environment; the repository holds case ids and rubrics only. Live rounds run under ADR-0035's standing approval, on the workspace's credits and within the owner's Anthropic monthly limit.

## Security invariants touched

None is weakened. A workspace-created agent gains no authority that a person with those grants did not request and, under ADR-0011's access-change review, approve on its exact card. One accepted residual widens, as stated under Leases.
- **Tenancy; no client-supplied ids:** cards, documents, packages and result items are FORCE RLS tables; the store and every id come from server facts, and code opens a result item for Morrow only when it belongs to a result Morrow's own run received, and for a teammate only when it belongs to a result its calling Morrow run received, never by a model-written id alone (`lab:tenant-conformance`, a new `lab:agent-cards`, and `lab:agent-runs` rows refusing a teammate an item from another run or from another person's private Ask). The new issuer serves `origin = workspace` only; first-party grant sets and the Listings issuer are unchanged (`lab:agent-cards` refuses a first-party installation at the new issuer; `lab:group:pg-linking` stays green unchanged).
- **The intersection, in code at every tool call:** unchanged kernel; new `lab:agent-authority-workers` rows deny a teammate call or a created agent's run when any term fails, for every call of a run alike (a second call, parallel calls and a repeated call to the same teammate included), and refuse `agent.*` tools and `workspace.task.delegate` to every teammate (`agent-package.test.mjs`, `tool-catalogue.test.mjs`). Unrestricted orchestration widens how many children Morrow's envelope has, never what any child may do: depth stays 1.
- **Digest-bound approvals:** an edited card, a stale card or a reused, expired or foreign document is refused; a tainted card stays tainted after approval (`lab:agent-cards`, `approval-records.test.mjs`).
- **Who approves (ADR-0005 §3, ADR-0011 Q1 to Q3):** refused are an agent, a non-holder, a holder without `delegate`, a non-Owner for the four Owner-only kinds, an Admin approving alone in a team, a requester or editor approving their own card in a team, and a solo Owner without the exact phrase or before the cool-down ends (`lab:agent-cards`).
- **Untrusted content:** TeammateResult@1 is closed, structured and wrapped, as is each result item Morrow opens; both taint Morrow's run, and neither carries customer-tagged data to Morrow (`lab:agent-runs`).
- **Leases (ADR-0022 item 9):** the re-issue when the last of a run's open calls ends is one more lease source, ids-only and executable only by `morrow_runtime_executor`, and it re-runs every admission check (`lab:agent-runs`). It widens ADR-0022 item 9's residual by one case, as ADR-0024 item 6 did: a compromised orchestrator could resume a Morrow run that waits on a call once that call's run has ended, within the requester's live grants and Morrow's fixed set. It cannot start a run or a call.
- **Budgets in code; `human_only` stops; default deny; immutable migrations:** every run's credit hold and the balance check before each step stay in code, outside prompts (ADR-0039); `lab:run-credits`, `stops.test.mjs`, `edge:check`, `migration-history.test.mjs`.
